Continuous batching：每一轮重新组队

交互2026-10-20更新于 2026-10-22

一台推理服务器正在同时处理三个请求。A 只想生成一句话，B 要写一段代码，C 要总结一份长文。A 结束之后，GPU 可以立刻接纳 D；B 和 C 已经写入的历史仍留在各自的 KV cache 中。这样，每一轮前向都有自己的请求名单，短请求释放的位置能马上用于新工作。这就是 continuous batching。

实现这一点需要把生成循环拆开：保存每条请求的状态，只执行本轮选中的输入，提交新输出，再重新调度。KV cache 让请求可以暂停在两个 token 之间；分页缓存让不同长度的历史能够共同使用显存池。调度器决定下一轮给谁多少计算位置。

一轮里究竟调度什么

一个普通 decode 请求本轮带来一个新输入 token。一个尚未读完 prompt 的请求可以带来一段输入。记本轮 prefill token 数为 \(\htmlData{symbol=p}{P}\)，decode 请求数为 \(\htmlData{symbol=d}{D}\)，模型实际处理的 token 行数是 \(P+D\)。所有请求共享权重矩阵乘法，各自用请求 ID、位置和页表找到历史。

服务通常同时限制一轮的 token 数、活动请求数和 KV 占用。设 token 预算为 \(\htmlData{symbol=b}{B}\)，则 \(P+D\le B\)。若本轮已有 48 条 decode 请求、预算为 256，就还有 208 个位置可以用于 prefill。一个 2000-token prompt 可以先处理其中 208 个，剩下部分留到后续迭代。

输入行数相同，执行时间仍会随形状变化。decode 要读取已经积累的历史，prefill 的多个 query 则能复用权重与部分数据。调度时需要用 token 数约束工作量，再用实际测量建立 \(T(P,D,S)\)：这里 \(S\) 表示历史长度分布，\(T\) 表示这一轮的墙钟时间。

从三条请求手算一次调度

用一个确定的算例观察循环。A 在 0 ms 到达，prompt 长 6、输出长 3；B 在 2 ms 到达，prompt 长 2、输出长 2；C 在 6 ms 到达，prompt 长 3、输出长 2。每轮优先安排 decode，然后按到达顺序填入 prefill，token 预算为 4。轮内到达的请求在下一轮开始时加入。

为便于逐项核算，设执行时间为 \(T=2+0.5P+D\) ms：2 ms 是固定成本，每个 prefill 位置增加 0.5 ms，每个 decode 位置增加 1 ms。完成最后一段 prefill 后就能采样第一个输出；之后每个 decode 步再产生一个输出。

第一轮 0→4 ms 只处理 A 的前 4 个 prompt token；第二轮 4→8 ms 处理 A 的剩余 2 个与 B 的 2 个，两个请求都在 8 ms 产出首 token。第三轮 A、B 各带一个 decode 输入，占用 2 个位置，C 用剩下 2 个位置读取 prompt，耗时 \(2+0.5\times2+2=5\) ms。到 13 ms，B 已完成，可以释放缓存。

第四轮用 3.5 ms 完成 A 的最后一个输出和 C 的最后一段 prefill；第五轮只推进 C，耗时 3 ms。整段工作在 19.5 ms 完成，产出 7 个 token，总输出吞吐为 \(7/0.0195\approx358.97\) token/s。

把首字等待与逐字停顿分开算

对请求 \(r\)，记到达时刻为 \(a_r\)，第 \(i\) 个输出时刻为 \(t_{r,i}\)。首 token 延迟为 \(\mathrm{TTFT}_r=t_{r,1}-a_r\)，相邻输出间隔为 \(\mathrm{ITL}_{r,i}=t_{r,i}-t_{r,i-1}\)。一个请求的平均 ITL 给出其 decode 阶段的平均 TPOT。

上例中 A 的 TTFT 为 8 ms，后续 ITL 为 5、3.5 ms；B 在 2 ms 才到达，因此 TTFT 为 6 ms；C 的 TTFT 为 \(16.5-6=10.5\) ms。相同服务器吞吐可以对应完全不同的等待体验。长 prompt 夹进一轮时，会延长这一轮全部活动 decode 请求的输出间隔。

Chunked prefill 为什么能减少长停顿

如果一次送入几千个 prompt token，这次前向结束前，已经运行的 decode 请求都要等待。把 prompt 切成较短的 chunk，就能在两个 chunk 之间再次推进已有请求。每一段仍使用全局位置：已处理 512 个 token 后，新 chunk 的第一个位置为 512；它能读取前面已写入的 KV，随后按因果关系读取当前 chunk。

chunk 太短时，固定调度成本、kernel 启动和较小矩阵的执行效率会影响 prefill 吞吐。chunk 较长时，首 token 计算可能更快完成，已有请求的 ITL 却可能变长。因此应固定请求到达轨迹、输入输出长度与硬件，扫描预算，记录 p50/p95 TTFT、ITL 和满足延迟目标的吞吐。预算取值应由这些曲线决定。

在 vLLM 的 V1 调优接口中，max_num_batched_tokens 控制迭代 token 预算，max_num_seqs 控制请求数量，max_model_len 控制单请求的长度上限。把长 prompt 切成多轮后，它仍然占用原来的位置编号和上下文范围；排查超长输入时，应同时查看输入 token 数与输出预留量。

计算位置够用，缓存也要有地方写

一轮开始前，每条入选请求都要为新增 K/V 获得容量。设页大小为 \(b\)，请求已有 \(s_r\) 个位置，本轮追加 \(n_r\) 个，需要新增的页数为

$$\Delta p_r=\left\lceil\frac{s_r+n_r}{b}\right\rceil-\left\lceil\frac{s_r}{b}\right\rceil.$$

假设每页 16 token，四条请求当前长度都为 16，下一轮各推进一个 token，就需要同时取得 4 页。若空闲池只有 3 页，调度器必须缩小本轮集合或回收其他状态。已有长度为 15 的请求则可以写入自己的最后一个空槽。这个差异解释了为什么同样的 batch size 会突然触发抢占。

执行流程可以明确为四步：先计算候选集合和所需页数，再一次性预留资源；前向成功后提交长度与采样结果；请求完成、取消或超时后统一归还页面。预留失败时保持请求的原状态，避免某些请求已经加长、另一些还停在上一轮。

怎样定位真实服务中的长尾

首 token 很慢，已有请求却输出平稳。这常发生在 decode 优先而新请求积压时。先看等待队列长度、最老请求等待时间和 prefill 每轮实际获得的预算，再为 prefill 设定服务额度或等待时间上限。公平性目标可以用等待年龄表示，让持续到来的短 decode 工作无法无限推迟同一条长 prompt。

吞吐增大后出现周期性延迟尖峰。将尖峰与 KV 利用率、抢占次数和重算 token 数对齐。抢占释放显存，却会让被恢复的请求再次执行一部分 prefill。若反复到达容量边界，应降低活动序列数或增长承诺，检查页大小与长度分布，并把恢复计算计入实际服务成本。

一次请求结束后显存占用持续升高。沿正常结束、EOS、客户端取消、超时、异常五条路径检查同一释放入口，记录请求持有的物理页与引用计数。固定小负载反复运行，结束后空闲页数应返回基线。共享 prefix 块可以继续驻留，但活动引用数应正确减少。

线上调度还会与 CPU 提交和异步执行重叠。排查时给每轮分配单调递增的 ID，把“计划的请求”“实际执行的输入”“提交的输出”分别记录。这样可以定位批次重排、取消与结果回传之间的竞态，而不必从最终生成文本猜测是哪一轮出错。

容量实验最好使用开放到达过程：按固定时间戳向服务提交请求，使某轮变慢时，后面的请求仍然按计划到达。这样队列会显式积累，能够看清系统何时接近饱和。固定并发的闭环测试会在响应变慢时自动降低新请求到达速率，适合测执行效率，却可能掩盖等待时间的增长。两类实验分别记录到达率、完成率与队列长度，才能将调度收益解释到服务层。

练习：核对时间与容量

1. 首 token 到底在什么时候产生？

按上面的 4-token 预算，写出 A、B、C 的全部输出时刻，并计算 B 和 C 的 TTFT。

参考解答

A 为 [8, 13, 16.5] ms，B 为 [8, 13] ms，C 为 [16.5, 19.5] ms。B 的 TTFT 是 8−2=6 ms；C 是 16.5−6=10.5 ms。最后一段 prefill 完成时已经得到第一个输出分布。

2. 预算有空位，为什么仍要少选一条请求？

页大小 8，三条请求长度分别为 7、8、16，每条都要追加 1 个 token。空闲池只有 1 页。求总需求，并给出一个可执行集合。

参考解答

新增页数分别为 0、1、1，共需 2 页。可以选择长度 7 和 8 的两条请求；也可以选择长度 7 和 16 的两条。剩下一条在后续轮次获得页面后继续。调度选择还要考虑等待年龄和服务目标。

3. 增大 chunk 会怎样改变等待？

已有 8 条 decode 请求，一个 chunk 含 64 个 prefill token；按 \(T=2+0.5P+D\) ms 估计轮时。若 chunk 改为 16，轮时下降多少？处理全部 64 个 prompt token 时固定成本增加多少？

参考解答

单轮从 42 ms 降到 18 ms，下降 24 ms。64 个 prefill token 分成 4 轮，固定成本由 2 ms 变为 8 ms，增加 6 ms；期间 decode 也能推进更多轮。完整负载下还应把其输入和输出数一起统计。

运行确定性的调度实验

下载 lab.py，使用 Python 3 运行：

python3 lab.py --budget 4
python3 lab.py --budget 2

默认输出应包含 A=[8,13,16.5]、B=[8,13]、C=[16.5,19.5]，以及 output_throughput=358.97 token/s。脚本用独立手算的时间轴校验预算、token 总数和完成状态，时间来自上述成本公式。

先修改 C 的到达时间，预测它会在哪个轮次加入；再把 decode 优先改为 prefill 优先，比较三条请求的输出间隔。下一步可以加入固定大小的页池，让每轮同时满足计算预算和缓存准入，接到最小推理引擎中的真实前向。
