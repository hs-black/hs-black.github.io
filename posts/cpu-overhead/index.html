CPU overhead：GPU 为什么在等

交互2026-10-20更新于 2026-10-22

一次 decode 里，GPU 可能只花几微秒执行一个小 kernel，CPU 却要依次组织 tensor、选择执行路径、准备参数并提交工作。GPU 时间线出现空白时，优化那个已经很短的 kernel 往往收益有限。更有用的起点是把 CPU 提交和 GPU 执行放在同一条时间轴上，看下一份工作究竟什么时候到达。

用一个队列模型解释空白

设 CPU 为第 i 个 kernel 做准备和提交需要 \(\htmlData{symbol=h}{h_i}\)，GPU 执行需要 \(\htmlData{symbol=g}{g_i}\)。用 \(e_i\) 表示提交完成时刻，\(s_i\) 表示 GPU 开始时刻，\(f_i\) 表示 GPU 完成时刻。单 CPU 提交线程、单 GPU stream 的递推为

$$e_i=e_{i-1}+h_i,\qquad s_i=\max(e_i,f_{i-1}),\qquad f_i=s_i+g_i.$$

初始 \(e_0=f_0=0\)。CPU 可以在 GPU 执行时准备后续 kernel，因而一轮耗时由两条队列共同决定。GPU 排队等待为 \(s_i-e_i\)，GPU 在前一项结束后的空闲为 \(s_i-f_{i-1}\)。前者说明工作已到、资源还忙；后者说明设备完成上一项后还在等待下一项。

每次 CPU 花 3 μs、GPU 花 8 μs 时，四次提交在 3、6、9、12 μs 完成，设备完成时刻却是 11、19、27、35 μs。CPU 在 12 μs 已经返回，GPU 仍有 23 μs 工作。这段队列积压让后续 CPU 开销被设备执行覆盖。

把 CPU 改成 8 μs、GPU 改成 2 μs，完成时刻变成 10、18、26、34 μs。设备每执行 2 μs 就要等下一份工作。如果 GPU kernel 再缩短一半，最后完成时刻只有 1 μs 的改善，因为关键路径主要由 host 提交间隔控制。

一次取标量怎样打断流水

loss.item() 需要把设备上的标量变成 Python 数值。CPU 必须等产生这个数值的工作完成，然后才继续执行后面的代码。因此原来积累的领先量被消耗，之后若连续提交许多小 kernel，GPU 会再次暴露 Python 和 runtime 的间隙。

类似边界还包括某些 D2H 结果读取、依赖设备数值的 Python 分支，以及输出大小取决于数据的操作。排查时把日志、调度判断和输出整理也放进 trace。若业务只需要每几十轮记录一次统计量，可以在设备端累积，降低取回频率；若每轮都必须做决策，则考虑把决策表达为设备计算或与已有同步点合并。

需要同步的操作在 CPU profiler 中常显得非常慢，因为等待前面的 GPU 工作被记在这个调用上。把同步移动到前一行，时间可能随之转移。应结合 CPU API、GPU kernel 和依赖事件判断等待来源，再决定优化真正占据关键路径的工作。

每个计时范围回答什么问题

CPU wall clock 加首尾设备同步，测量一段计算从准备到完成的整体时间；无结束同步时，往往只测到提交返回。CUDA event 记录设备 stream 上的两个位置，能测这两个位置之间的时间，但这一段也可能包含 stream 等待或 CPU 未及时提交后续工作产生的空隙。

torch.cuda.synchronize(device)
t0 = time.perf_counter()
for _ in range(repeats):
    step()
torch.cuda.synchronize(device)
wall_ms = (time.perf_counter() - t0) * 1000 / repeats

a = torch.cuda.Event(enable_timing=True)
b = torch.cuda.Event(enable_timing=True)
a.record()
for _ in range(repeats):
    step()
b.record(); b.synchronize()
stream_ms = a.elapsed_time(b) / repeats

多 GPU 程序明确指定目标 device，多 stream 程序在末尾汇合需要计入的分支。先热身到编译、缓存和内存分配状态稳定，再开始重复测量。对很短的单次调用，计时与 profiler 本身的开销可能明显，重复批量测量和单次延迟分布应分别记录。

读懂一次 launch 的两段延迟

Nsight Systems 可以同时展示 host API 与 GPU kernel。一次 launch API 的 CPU 区段反映框架、驱动和调用成本；API 提交完成到 kernel 真正开始之间，则可能包含前序 GPU 工作、资源等待或依赖事件。两个区间的优化手段不同。

看到 40 μs 的“launch latency”时，先拆开这两个区间。若 API 本身很短而 GPU 队列前面有大 kernel，问题是排队或调度。如果 GPU lane 空闲、CPU 还在处理大量小算子或组装输入，则检查 Python 循环、对象分配、tensor 元数据操作、锁竞争和逐请求处理。把相关 host 区段加上 NVTX 标记，能让一次猜测变成可定位的时间范围。

连续 batching 把多条请求放入一次 forward，会摊薄每次固定调度成本。融合减少 kernel 数量并可能减少中间流量；CUDA Graph 将稳定的依赖图一次重放，降低重复提交工作。三者对应不同层级，选择应与 trace 中实际的空白位置相匹配。

把主机工作拆成可优化的部分

请求调度可能包含 token 分词、页表更新、采样准备、Python 容器遍历和 kernel 提交。按职责分别记录各个 CPU 区段的时间，就能确定开销来自哪一层。比如每个请求各建一份小 tensor，会同时产生对象管理、分配和复制；批量更新一块预分配元数据缓冲，可能把这些工作合成一次，代价则是更明确的缓冲所有权和有效长度管理。

在闭环基准里，发送端常等本轮完成才发送下一轮，系统不会积累真实的到达排队。开放负载按外部时间表发请求，更容易暴露 host 调度饱和：CPU 消费请求的速度低于到达速度时，GPU 甚至可能因准备不足而有空闲，用户端队列却持续增长。测吞吐拐点时，应同时观察接收队列、CPU 工作和设备利用率。

设每请求固定调度成本为 30 μs，一次统一处理 B 条请求另有 10 μs 的批级成本，则每请求平均 host 成本为 \(30+10/B\) μs。若把逐请求逻辑向量化，使固定工作降到每批 30 μs，模型会变为 \(40/B\) μs。两种成本随 batch 的变化规律不同，测几个 batch 点可以帮助判断优化应落在批级还是请求级。

优化上限先由关键路径决定

设当前端到端关键路径有比例 \(\htmlData{symbol=f}{f}\) 可以被加速，局部加速倍数为 s，其余部分保持原速。整体加速比为

$$S=\frac{1}{(1-f)+f/s}.$$

若可优化的 host 区段占 30%，将它加速 3 倍后，整体只快 \(1/(0.7+0.3/3)=1.25\) 倍。这里的 30% 应来自端到端关键路径：已经与 GPU 重叠的 CPU 工作，缩短后未必改变完成时刻。

平均速度与服务尾延迟

单步性能要放回请求流程。聚合更多请求可以减少每请求固定成本，也会改变排队等待和一次设备计算的长度。如果调度器每处理一大批才返回首个结果，平均吞吐提高时，单条请求的 TTFT 仍可能变差。比较方案时固定请求到达过程、输入输出长度分布和硬件预算。

尾延迟需要保留逐请求时间戳。100 次观测里，95 次为 10 ms、5 次为 100 ms，平均值为 14.5 ms，中位数为 10 ms，而 nearest-rank p99 为 100 ms。只有一个平均值，很容易把少量 CPU 抢占、内存分配或同步尖峰掩盖掉。

若 p50 正常而 p99 周期性变差，先把尖峰对应到 CPU 区段，检查日志刷新、垃圾回收、编译、分配和数据准备；若尖峰出现在 GPU 忙碌队列之后，则检查长 prefill 或大 batch 的占用。采集的数据应足以区分“请求还没被安排”和“请求已经提交但等设备”这两种等待。

为一次优化设计可证伪的实验

假设 GPU 空白来自每轮 Python 循环，可先保持模型与输入一致，只把逐元素 Python 路径改成批量张量操作。若 trace 中 CPU 提交区段缩短、GPU 空白减少且输出一致，这个假设得到支持；若 CPU 已提前提交而 GPU 仍等待，则继续追踪设备依赖和资源竞争。

比较 CUDA Graph 前后时，保留相同输入更新与输出消费方式，避免一条路径包含复制而另一条省掉了它。比较融合前后时，额外记录 kernel 数和张量流量，因为收益可能同时来自提交和访存。把每种变化对应到预期观测，可以避免把不同来源的加速都归为同一种原因。

真实应用还可能受 CPU 线程调度影响。为关键请求路径保留线程标记，查看发生长间隙时该线程是在运行、等待锁，还是未被调度；随后再决定减少共享锁、拆分后台工作或调整执行资源。设备时间线中的空白提供起点，主机线程状态提供更具体的解释。

练习与实验

1. 提交完成与设备完成

四个 kernel，CPU 各花 3 μs，GPU 各花 8 μs。CPU 返回和 GPU 完成相差多少？

展开解答

CPU 返回为 12 μs，GPU 完成为 35 μs，相差 23 μs。GPU 总执行 32 μs，首个 kernel 等待 CPU 提交的 3 μs 也在端到端范围内。

2. Amdahl 上限

关键路径中可优化部分占 30%，局部加速 3 倍。整体加速多少？若局部耗时趋近零，上限是多少？

展开解答

实际为 \(1/0.8=1.25\) 倍；理想上限为 \(1/0.7\approx1.43\) 倍。进一步收益需要处理其余 70% 的关键路径。

3. 同样的中位数

方案 A 的 100 次延迟为 99 次 20 ms、1 次 200 ms；方案 B 为 95 次 20 ms、5 次 45 ms。按 nearest-rank 定义，二者 p99 是多少？

展开解答

A 的第 99 个排序样本是 20 ms，B 是 45 ms。A 的最大值更高；要评价 50 ms 的 SLO，应同时统计实际超标比例，A 为 1%，B 为 0%。分位数与超标率各保留一部分信息。

下载 CPU 队列实验：

python3 lab.py --host 3 --gpu 8 --kernels 4
python3 lab.py --host 8 --gpu 2 --kernels 4

默认输出 finish=35 us、host_return=12 us；交换参数后完成时刻为 34 μs。脚本将逐项递推与闭式解交叉检查，最后打印 checks: PASS。添加一次中间同步，让后续 e 从上一次 f 继续，观察领先量怎样消失；再把一组小 kernel 合成一次提交，预测新的空闲区间。
