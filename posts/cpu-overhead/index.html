CPU overhead：GPU 为什么在等

沿着一条时间线，分清提交、排队、执行与同步

先找到 CPU 在哪里

GPU 计算之前，CPU 先把工作组织好

一个请求到达，CPU 处理输入、挑选这一轮的请求，并准备索引、张量和算子参数。

框架和 CUDA runtime 把 GPU 工作提交到 stream。提交与执行完是两个不同时间点。

CPU 还要处理采样、输出或下一轮调度。哪些步骤落在 CPU，取决于推理引擎的实现。

CPU overhead 指为完成 GPU 工作付出的主机端组织与提交成本；tokenization 等阶段应分开计时。

异步执行

CPU 不必等一个 kernel 跑完再提交下一个

CPU 提交 K₁ 后返回，GPU 稍后开始执行。下面两条线分别表示主机 API 和设备执行。

GPU 跑 K₁ 的同时，CPU 已经提交 K₂、K₃。它们进入队列，按照同一 stream 的顺序执行。

此时 CPU 提交得足够快，GPU 可以连续工作。提交到开跑的间隔变长，也可能只是队列更满。

条块长度为教学示意，不代表实测延迟。不同 stream 可以有并发，但仍受依赖和硬件资源限制。

提交跟不上计算

小 kernel 跑得很快，下一份工作却还没到

GPU 算一个短 kernel 很快，CPU 还在准备下一个。队列耗尽以后，设备只能等。

这些空白是真正的 GPU idle gaps：空白处既没在算，也不是在等同一 stream 中的前序 kernel。

低 batch decode 会反复经过很多小算子。减轻每轮 CPU 工作、合并提交，可能比单独加快某个 kernel 更有效。

这里只示意提交不足造成的空闲；通信依赖、同步和数据拷贝也可能制造空白，需要用 trace 区分。

会打断异步流水的操作

需要 GPU 的结果，CPU 才必须停下来等

CPU 如果马上要把 GPU 计算结果变成一个 Python 数字，例如对 CUDA tensor 调用 .item()，就要等这个结果准备好。

等待期间不能越过依赖继续做后续的主机工作；等数据回来后，还需要重新准备并提交 K₂。

能把读回移到迭代边界、合并读回，或把后续计算留在 GPU，就能减少这种停顿。

显式 synchronize 用于确实需要的边界和测量。不是每次 kernel launch 都会同步。

把固定成本分摊出去

一次调度，推进多个请求

每个请求分别做很多重复的 Python 和框架调用，固定成本会付很多遍。

把多个活跃请求组织到同一轮 batch，CPU 的部分固定开销由更多 token 分摊；GPU 也能得到更大的工作块。

Continuous batching 在每轮边界移走已完成请求、接入新请求。调度本身仍要时间，还要兼顾等待延迟和显存。

批量大小与收益取决于负载；更大 batch 不等于每条请求延迟一定更低。

减少重复提交

固定的一段执行，可以让 CUDA Graph 重放

每一轮重复同一组操作，CPU 仍逐个准备与提交，短 kernel 场景就容易受这些开销影响。

CUDA Graph 提前记录操作及依赖。以后用一次 replay 发起这一段工作。

GPU 仍运行这些 kernel。Graph 主要减少重复调度与提交；kernel fusion 则会把多个 kernel 合成更少的 kernel。

CUDA Graph 需要可捕获的计算与稳定的存储布局；动态请求通常通过 bucket、padding 或局部 graph 处理。

诊断

测量时，把三种时间分开

CPU wall time

只包住异步调用的 Python 计时，主要看到提交耗时；结尾同步后，才覆盖等待 GPU 完成的时间。

CUDA events

在 stream 上标记边界，测设备时间区间。读取耗时前，先确保结束 event 已完成。

系统 trace

Nsight Systems 或 PyTorch Profiler 同时显示 CPU API、GPU kernel、拷贝和同步。

把 GPU 空白对齐到 CPU：在调度、分配、读回，还是通信等待？

想清楚再优化

优化的下一步，由空白的位置决定

  • GPU 连续忙：分析算子、显存读取和通信，CPU 未必是瓶颈。
  • GPU 在等下一次提交：检查调度路径、Python 循环、batching 和 CUDA Graph。
  • CPU 在等 GPU 回传：找到 .item()、同步拷贝、synchronize 和控制流依赖。
  • 每轮都在分配：复用工作缓冲区，检查 allocator 与实际同步。

先 warm up，再用相同输入、并发和计时边界比较。既看吞吐，也看首 token 延迟与逐 token 延迟。
