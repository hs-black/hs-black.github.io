CUDA Graph：把一轮计算录下来

交互2026-10-20更新于 2026-10-22

一次 decode 的几十个 kernel 往往会以同样的依赖关系反复执行。CUDA Graph 把这段设备工作及其依赖记录下来，之后一次 replay 就能提交整段计算。要让新一轮数据进入这张图，需要稳定的存储地址、明确的输入更新顺序，以及一套管理不同形状的策略。

热身、捕获和重放

热身先触发初始化、算法选择和必要的运行时准备。捕获阶段记录设备操作及其依赖；重放阶段重新执行这些已记录操作。Python 代码在捕获时执行，其控制流由当时的路径决定，后续 replay 直接使用记录好的设备图。

对 PyTorch 常用的静态捕获路径，输入、输出和中间缓冲在 graph 生命周期内需要保持地址有效。每轮新输入通过 copy_ 写入固定输入存储；每轮输出从固定输出存储读取。稳定的地址为重放提供直接可用的参数，也使存储所有权成为正确性的一部分。

static_x = torch.zeros(4, device="cuda")
warm = torch.cuda.Stream()
warm.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(warm):
    for _ in range(3):
        f(static_x)
torch.cuda.current_stream().wait_stream(warm)
graph = torch.cuda.CUDAGraph()
with torch.cuda.graph(graph):
    static_y = f(static_x)

static_x.copy_(new_x)
graph.replay()
saved_y = static_y.clone()

这里 f 是待捕获的稳定张量计算；输入复制、replay 与输出复制排在同一 stream 上，形成明确的先后顺序。实际应用应保留 static_x、static_y 与 graph 对象，并把捕获范围控制在可重复执行的设备计算段。

地址、Python 引用与数值快照

假设捕获函数为 \(y=x^2+1\)。第一轮把 3 写进固定输入，输出为 10；第二轮把 4 写进去，输出为 17。若 a=static_y，a 持有同一块输出存储；若 b=static_y.clone()，b 保存独立副本。因此第二轮之后 a 读到 17，b 仍读到第一轮的 10。

detach() 断开 autograd 关系，同时保留存储别名；需要保留上一轮数值时，使用独立复制，并确保复制在下一轮覆盖之前完成。这个问题同样会出现在编译器管理的 CUDA Graph 输出中：保存 tensor 引用的生命周期，与保存某轮结果数值的生命周期要分别设计。

另一种常见错误是 static_x=new_x。这会重新绑定 Python 变量，原图记录的输入指针仍指向原来的存储。把 data_ptr() 放进最小正确性检查，确认 capture 与 replay 使用相同输入输出地址；把随机新值原地写入，再逐轮与 eager 输出比较。

把动态信息放进稳定接口

KV cache 可以在预先分配的块池里增长。固定的是大块存储和 kernel 接收的地址，当前长度、页表、slot mapping 等动态信息则通过固定元数据缓冲更新。这样每次 replay 仍执行同一类设备工作，而读取的有效位置由新元数据决定。

若 batch shape 或 kernel 拓扑改变，可以为若干形状准备不同 graph。服务循环先选择能覆盖当前工作量的桶，写入输入与元数据，设置有效长度或 mask，然后重放对应图。输出只返回真实请求的有效部分。对有副作用的缓存写入，padding 请求也必须有明确的屏蔽规则。

桶的收益、空算与持久容量

请求 batch 为 1、3、5、8 时，桶集合 [1,2,4,8] 分别选择 1、4、8、8，共执行 21 个槽，实际请求共 17 个，空算比例为 \(4/21\approx19.05\%\)。只保留桶 8，则执行 32 个槽，空算比例为 46.88%。较密的桶减少 padding，也增加捕获次数和持久存储。

捕获前先按真实分布统计每个桶会被调用多少次。低频大桶若长期占着 workspace，可能挤占 KV 池，让并发下降；它的局部延迟收益要与整个服务的容量一起比较。共享 graph 内存池需要遵守相应的执行顺序和生存期，交错重放不同图时要重新核对别名关系。

一轮服务怎样提交稳定图

以分页 KV 的 decode 为例，调度器先选出本轮请求，再为新增 token 预留槽位，将 token id、position、有效长度、页表和 slot mapping 写进相应固定缓冲。Graph 中的 kernel 按这些元数据读取历史、写入新 K/V 并产出 logits。重放完成后，采样与请求状态更新决定下一轮输入。

取消请求、回收物理页和下一轮覆盖元数据都要等待相关设备读取结束。可以把一轮执行关联到一个完成 event；页池和元数据缓冲的复用者在合适时刻等待它。若采用多份轮转元数据缓冲，每份都需要单独的在途状态，以便 CPU 提前准备下一轮而不覆盖当前轮。

图的形状桶与 KV 容量是不同维度。一个 batch=32 的图可以处理不同历史长度，前提是 kernel 的执行路径支持通过元数据表达这些长度，且缓存和工作区容量足够。若算法根据长度选择不同拓扑或 workspace，就应把相应条件纳入图的选择键。图缓存键应反映真正改变执行契约的条件。

计算净收益与回本点

设捕获与准备的额外成本为 \(\htmlData{symbol=c}{C}\)，eager 一轮为 \(t_e\)，使用 graph 后的一轮总成本为 \(t_g\)。这里 \(t_g\) 包含输入复制、padding、replay 和必要的输出保存。执行 n 轮之后，净收益条件为

$$C+nt_g\lt nt_e\quad\Longleftrightarrow\quad n>\frac{C}{t_e-t_g}.$$

C=600 μs、eager=12 μs、graph 路径=10 μs 时，300 轮恰好持平，第 301 轮才有净收益。若一轮主要由长 GEMM 占据，重复 launch 只占很小比例，graph 能省下的空间也小；若含许多微小 kernel，提交开销可能成为主导。

Kernel fusion 可以同时减少 launch 和中间张量流量，CUDA Graph 主要减少重复提交稳定图的工作。两者可以组合：先得到适合设备执行的融合 kernel，再降低整轮调度成本。评价时应比较完整路径，保留输入更新、输出消费和缓存管理的实际开销。

捕获边界与跨流依赖

捕获区内需要 CPU 立即获得结果的操作，例如 .item()，会要求同步，通常要移到图外。根据设备数值执行 Python 分支的逻辑，也应改成适合图表达的设备控制流，或作为选择 graph 的外部调度逻辑。首次初始化、动态分配与库内部行为应先通过热身和最小捕获用例确认。

如果输入更新在 stream A，replay 在 stream B，需要 B 等待 A 的复制完成；如果输出由另一个 stream 消费，下一次 replay 必须尊重该消费者的读取寿命。Pinned host 输入也需要等 DMA 读完后再覆写。统一的队列顺序可以满足这些条件，多流方案则用 event 显式连接。

重复重放中的三类问题

每轮输出都相同，先确认新值确实写入固定输入，并检查 graph 捕获时的指针。第一轮结果正确、保存到列表里的旧结果后来一起变化，检查列表元素是否共享固定输出；需要留存的结果在重放边界前复制。只有并发执行时随机出错，检查跨流生产、消费与覆盖之间的 event。

数值正确但吞吐下降时，分别测 eager、仅 replay、输入更新加 replay、完整服务路径。前两组定位提交收益，后两组显示复制、padding 与调度成本。再记录 graph 持久显存和可用 KV 块数，确认是否因容量下降抵消了单轮加速。

建立逐轮正确性证据

最小测试先使用固定 shape 和不断变化的数据，每轮将 graph 输出与 eager 参考对照。随后加入保存上一轮输出、跨流消费、不同 batch 桶和页表改变，分别检查数值、指针及生命周期。让不同请求使用可辨认的输入，可以发现某个槽沿用了上一轮元数据的错误。

测量准备成本时，把热身、捕获和实例化分别计时。稳态测量则用同一组已准备好的图，并按生产负载的频率调用各桶。最后统计整套图的持久显存和有效请求吞吐；一个桶在微基准中节省几微秒，还需要足够的使用次数和可接受的内存成本才能进入最终服务配置。

与 torch.compile 组合时，由编译器管理的 graph 可能有自己的 step 边界与输出生命周期规则。按所用框架版本核对这些边界，并保持需要长期保存的结果具有明确所有权。把数值留存的决定放在调用接口上，可以减少上层业务对内部重放细节的依赖。

练习与实验

1. 输出别名

第一轮输入 3，a=static_y，b=static_y.clone()；第二轮输入 4，函数 y=x²+1。a、b 分别为多少？

展开解答

a 引用重放覆盖的固定输出，值为 17；b 拥有第一轮复制，值为 10。若 b 使用 detach()，它仍共享原输出存储。

2. 桶集合的代价

batch 序列 [1,3,5,8]，把桶 [1,2,4,8] 改成 [4,8]，总执行槽数增加多少？

展开解答

细桶选择 [1,4,8,8]，总 21；粗桶选择 [4,4,8,8]，总 24，多 3 个槽。实际请求 17 个，粗桶空算比例为 7/24≈29.17%。

3. 低频桶要不要捕获

准备一个桶需 1200 μs，eager 每轮 30 μs，graph 完整路径每轮 24 μs。该桶预计只使用 100 次。

展开解答

净节省条件为 n>1200/6=200，至少 201 次。100 次时 eager 共 3000 μs，graph 共 3600 μs；该负载下保留 eager 路径更省时间。

CPU 存储与分桶实验可直接运行：

python3 lab.py --replays 300
python3 lab.py --replays 301

它验证别名为 17、副本为 10、细桶共 21 个槽，回本点为 301。把模拟器的原地输入更新改成重新绑定变量，观察图仍然读取哪块存储。

真实 CUDA Graph 示例在 CUDA PyTorch 环境运行 python3 gpu_example.py，逐轮验证随机输入、固定 data_ptr 和输出覆盖。成功后输出 CUDA graph correctness: PASS；在此基础上扩大张量和计算链，再设计性能测量。
