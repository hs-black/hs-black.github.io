CUDA streams、events 与异步流水

把“同时发出去”变成正确的数据依赖和真正的重叠。

2026-10-20 · → 推进 / ← 回放 / 拖动时间轴

工程原理

CPU 已经返回，GPU 可能还没开始

一次 kernel launch 把工作放进队列。Python 下一行开始执行，不代表 GPU 已经完成上一行。

提交时间

CPU 花时间准备参数、进入 runtime、把命令排队。

完成时间

GPU 等依赖、等资源，再执行。结果能被消费者安全读取才算完成。

先修：CPU overhead；把 timeline 上的 CPU 和 GPU 两条轨道分开读。

工程原理

一个 stream，是一条有序命令队列

stream A：H2D₀ → kernel₀ → D2H₀

同一 stream 内，后续工作遵守前序依赖。不同 stream 之间，程序员要显式表达数据关系。

顺序来自哪？

同流顺序、event 等待、显式同步，以及具体 API 的同步语义。

重叠来自哪？

工作没有依赖冲突，而且 GPU 的执行资源与带宽还有空间。

工程原理

画箭头前，先给缓冲区命名

阶段读取写入必须等什么
Hᵢ：上传host_in[i]device_in[slot]该槽上轮读完
Cᵢ：计算device_in[slot]device_out[slot]Hᵢ 完成
Dᵢ：下载device_out[slot]host_out[i]Cᵢ 完成

两槽循环使用：slot = i mod 2。Hᵢ₊₂ 复用同一槽，必须等 Dᵢ 完成。

逐步演算

让下一份上传，躲进这一份计算

每份输入：H2D 2 ms、计算 5 ms、D2H 1 ms；4 份输入，2 个缓冲槽。

拖动时间轴，观察复制引擎和计算单元各自的队列。

假设 H2D、D2H 各有独立可用引擎；计算队列串行。条带位置是 CPU 实验的精确调度结果。

工程原理

32 ms 变成 23 ms，节省来自重叠

串行：4 × (2 + 5 + 1) = 32 ms
流水：2 + 4 × 5 + 1 = 23 ms

开始先上传 2 ms；计算单元连续工作 20 ms；最后一份再下载 1 ms。加速比 32 / 23 ≈ 1.39。

这个例子 2 个槽已足够。一般的三阶段理想流水公式为 Σt + (N−1) max(t)，前提是依赖、缓冲与引擎都允许该排程。

工程原理

stream 数量，和硬件通道数量不同

复制与计算

异步复制能力取决于设备；页锁定 host 内存和合适的 stream 排程是重叠的基础。

两个 kernel

能否并发取决于资源：SM、寄存器、shared memory、带宽。一个大 GEMM 可能已占满它们。

把 8 条 stream 画出来，并不能推导出 8 倍并行度。先看设备能力，再看 profiler 中实际重叠。

工程原理

Pinned memory：让 DMA 的源地址保持稳定

页锁定内存不能被操作系统随意换出。异步 host↔device 传输通常需要这样的 host 缓冲区。

host = torch.empty(n, pin_memory=True)
device.copy_(host, non_blocking=True)

copy_ 返回后，host 仍可能在被 DMA 读取。此时填入下一批数据，会改变正在传输的内容。

提前建立有限的 pinned buffer 池；频繁 pin/unpin 自身有成本。non_blocking=True 不保证实际重叠。

工程原理

先算传多少字节，再猜能藏多少时间

X：[4096, 4096]，FP16 → 4096² × 2 = 32 MiB

教学条件：有效单向传输带宽 16 GiB/s，则 X 的纯传输下界为 32 MiB / 16 GiB/s = 1.953 ms。

若计算只有 0.5 ms，一份计算无法掩盖约 2 ms 的上传；继续增加计算 stream，不会增加链路带宽。

下界未含调用、排队与协议开销。GB/s 和 GiB/s 必须统一后再相除。

工程原理

Event 是队列里的一个完成标记

upload：copy → record(ready)
compute：wait(ready) → kernel

record 在指定 stream 中插入标记；它前面的工作完成，标记才完成。wait_event 把等待放在 GPU 队列里，CPU 可以继续提交其他工作。

event.synchronize() 会阻塞调用它的 CPU 线程；stream.wait_event() 主要表达设备端顺序。

逐步演算

少一条等待边，快出来的可能是错结果

C₀ 需要 H₀ 的结果。把“调用先后”与“设备真正开始执行”放在同一时间轴。

安全排程：计算等上传完成；错误排程：计算读到了仍在传输的缓冲区。

时间与容量为教学示例。

工程原理

把生产者和消费者连起来

uploaded = torch.cuda.Event()
with torch.cuda.stream(upload):
    device.copy_(host, non_blocking=True)
    uploaded.record(upload)
with torch.cuda.stream(compute):
    compute.wait_event(uploaded)
    result = model(device)

wait_event 后的工作等待 uploaded；等待之前已经提交的工作不会被追溯阻挡。

CPU 不能在 event 完成前修改 host；device 和 result 的存储也要活到使用结束。

工程原理

“数据已经写好”和“内存不会被复用”是两件事

就绪依赖

消费者何时允许读取？用 wait_event / wait_stream 等待生产者。

存储寿命

消费者何时读完？在此之前，分配器与业务代码都不能把这块地址交给下一份数据。

引用消失可能让缓存分配器复用地址；引用仍在，也挡不住业务代码主动 copy_ 覆写同一个 tensor。

工程原理

record_stream 保护分配器寿命，不替你等数据

consumer.wait_stream(producer)  # 数据就绪
with torch.cuda.stream(consumer):
    y = use(x)
x.record_stream(consumer)       # 告知分配器：consumer 仍会用 x

当 x 的最后一个 Python 引用释放，分配器要等登记的使用结束后再复用存储。

record_stream 不是读写锁，也不建立生产者→消费者依赖。手动管理池时，仍要用完成 event 控制覆写时机。

逐步演算

两个槽轮流用：复用必须经过“读完”

slot 0 先装 chunk 0，slot 1 装 chunk 1；chunk 2 想进 slot 0 时，先等 chunk 0 下载结束。

状态变化：上传 → 计算 → 下载 → 空闲。槽位不是任务身份。

图中 0–15 ms 取自 4 份任务的双缓冲排程；同一槽输入与输出按一个整体管理。

工程原理

复用前，等待这个槽上一位使用者

slot = i % 2
with torch.cuda.stream(upload):
    if i >= 2:
        upload.wait_event(downloaded[i - 2])
    d_in[slot].copy_(h_in[i], non_blocking=True)
    uploaded[i].record(upload)
# compute 等 uploaded[i]；download 等 computed[i]
# download 完成后 record(downloaded[i])

每份任务用独立 event，方便追踪依赖。若复用 event 对象，要保证等待对应的是预期那一次 record。

工程原理

第二个槽花了多少显存？

一个槽的常驻内容字节数两个槽
输入 [1024,4096] FP168 MiB16 MiB
输出 [1024,4096] FP168 MiB16 MiB
合计16 MiB32 MiB

从单槽到双槽，多付 16 MiB 设备缓冲。另算 pinned 输入/输出、模型权重、workspace 与 KV cache。

只有输入输出缓冲纳入本表；不能把 32 MiB 当作整个请求的显存。

工程原理

默认 stream 的规则，要随运行环境一起确认

Legacy NULL stream

可能与普通 blocking streams 产生隐式同步。cudaStreamNonBlocking 可避开这类 NULL stream 同步。

Per-thread default

每个 CPU 线程拥有自己的默认 stream，表现为普通 stream；不同线程并不自动互等。

库可能使用自己的 stream。跨库共享 tensor 时，确认当前 stream、就绪事件和内存寿命的约定。

工程原理

通信想重叠，也要有独立的计算可做

张量并行中的 all-reduce 若直接产生下一层输入，下一层就必须等它。可以重叠的是不依赖该结果的工作。

可尝试的机会

分块产出、分块通信；不同 micro-batch；下一块的准备工作。

共同争用

通信 kernel 也可能占用 SM 和 HBM。时间轴重叠后，两个操作各自可能变慢。

结合 分布式推理 的逐卡数据依赖检查；异步 API 返回的 work handle 也有各自完成语义。

工程原理

找到最慢阶段，再决定加什么资源

理想稳态周期 ≥ max(tH2D, tcompute, tD2H)
时间（ms / 份）主要限制值得先尝试
2 / 5 / 1计算优化 kernel、合适的批量
7 / 2 / 1上传链路少传数据、复用 GPU 常驻内容
1 / 2 / 8下载减少回传、GPU 上后处理

共享带宽、槽数量、CPU 提交与依赖可能把周期拉得更长。

逐步演算

计时器圈住哪一段，就只回答哪一个问题

CPU 在 0–1 ms 完成提交，GPU 在 1–9 ms 工作。没有同步的主机计时，只看到前一段。

先确定想测提交开销、设备区间，还是用户等待的总时间。

示意时间；GPU 事件在其 stream 中生效，不自动覆盖其他 stream。

工程原理

单流 kernel 时间，用前后 GPU event 圈住

start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record(stream)
with torch.cuda.stream(stream):
    y = model(x)
end.record(stream)
end.synchronize()
print(start.elapsed_time(end))  # 毫秒

多流端到端计时：先让起点支配各支流，再让终点等待所有支流完成；或者主机计时并同步到最终完成。

工程原理

工程原理

双缓冲没变快：先改一件事

教学 trace：H 2 ms、C 5 ms、D 1 ms；4 份仍耗时 32 ms。每次提交后立刻调用 synchronize()。

原因

CPU 等每份全部完成才提交下一份，流水从未被填满。

修改与验证

用槽完成 event 表达复用依赖，连续提交；最后再等全部结果。检查正确性和实际重叠。

移除等待前先补足真实依赖，不能把所有 synchronize 机械删除。

计算稳态吞吐与总耗时

N = 10；H/C/D 分别 2/5/1 ms；独立引擎且缓冲充足。求串行耗时、理想流水耗时、稳态每秒完成份数。
展开参考解答

串行：10 × 8 = 80 ms。流水：8 + 9 × 5 = 53 ms。

最慢阶段 5 ms / 份，稳态 1000 / 5 = 200 份/s。本批平均吞吐 10 / 0.053 ≈ 188.7 份/s，启动与排空让它低于稳态。

练习 2

这段程序缺的是哪一种保护？

A 流生成 x；B 流读 x。程序只有 x.record_stream(B)，没有 B.wait_stream(A)。结果偶尔错误。
展开参考解答

record_stream 只告诉分配器 B 还在使用 x，不建立 A→B 的就绪依赖。

在 B 的消费操作之前等待 A 的生产完成事件，或在合适位置调用 B.wait_stream(A)。仍保留寿命管理；手动覆写还要等消费完成。

练习 3

第三份上传为什么不能从 4 ms 开始？

双槽示例中，H₀=[0,2]、C₀=[2,7]、D₀=[7,8]。H₁ 在 4 ms 结束；H₂ 想覆写 slot 0。求最早开始时间。
展开参考解答

复制引擎 4 ms 空闲，但 slot 0 的计算仍在读输入，下载尚未读完输出。按整槽复用策略，要等 D₀ 在 8 ms 完成。

H₂ 最早 [8,10]。只等 H₁，违反的是存储复用依赖；不能靠增加 stream 修复。

练习 4

0.2 ms 和 4.2 ms，谁测错了？

主机计时：kernel 调用前后相差 0.2 ms；最后同步后总计 4.2 ms。GPU event 区间为 4.0 ms。如何解释？
展开参考解答

三者测量边界不同：0.2 ms 是提交路径；4.0 ms 是设备事件之间的区间；4.2 ms 是主机提交到完成的端到端等待。

要比较用户延迟，用相同同步边界的端到端耗时；优化 launch 开销时才单独观察提交路径。数值相加是本题的示例排程，不是通用恒等式。
