CUDA streams、events 与异步流水

交互2026-10-20更新于 2026-10-22

读入一批数据、算一次前向、把结果拷回 CPU，三个步骤连起来才是一次完整处理。GPU 计算期间，复制引擎可能有能力上传下一批数据。CUDA stream 把命令排成有序队列，event 则把不同队列间的数据依赖接起来；缓冲区的生命周期决定这种重叠能否一直安全地持续。

提交、执行与完成是三个时刻

CPU 调用异步 CUDA API 后，通常很快就能继续执行 Python。命令随后进入设备队列，等依赖和执行资源就绪才开始工作。同一 stream 内的命令按序执行，因此先上传 X、再计算 f(X)，会自然形成先写后读的关系。不同 stream 之间通过 event 建立这种先后关系。

例如 H2D 上传需要 2 ms，计算需要 5 ms，D2H 回传需要 1 ms，串行处理四批共花 \(4(2+5+1)=32\) ms。若上传、计算、回传各有可独立工作的资源，下一批上传可以嵌入当前批计算，稳态中每 5 ms 完成一批。这里的 2、5、1 ms 是用于排程的输入。

用时间线推导重叠

设每批三个阶段分别耗时 \(\htmlData{symbol=h}{h}\)、\(\htmlData{symbol=c}{c}\)、\(\htmlData{symbol=d}{d}\)，共有 n 批。在缓冲充分、每阶段有独立资源且每批时长固定时，第一批需要 \(h+c+d\) 才能流完；后面每批按最慢阶段的节奏完成：

$$T_n=h+c+d+(n-1)\max(h,c,d).$$

代入四批与 2、5、1 ms，得到 \(8+3\times5=23\) ms。收益来自三个阶段在不同批之间重叠。增加 stream 后，实际并发仍受复制引擎、SM 资源、内存带宽和依赖边约束；这些硬件约束会体现在时间线上的阶段间空白或竞争中。

双缓冲默认排程中，第 0 批占槽 0，第 1 批占槽 1。第 2 批再次使用槽 0，要等第 0 批回传在 8 ms 结束，因此其上传从 8 ms 开始。计算阶段仍从 12 ms 接上，最终耗时保持 23 ms。把计算改为 2 ms、上传改为 7 ms 后，上传成为决定节奏的资源；增加计算 stream 很难缩短这条关键路径。

Event 把生产者接到消费者

一个 event 记录在某条 stream 中，表示该位置之前的工作已经完成。消费者调用 wait_event，把“等这个 event 完成”插入自己的队列；CPU 可以继续提交其他工作。两条基本依赖是上传完成后才能计算，以及计算完成后才能回传。

ready = torch.cuda.Event()
done = torch.cuda.Event()
with torch.cuda.stream(upload):
    device_slot.copy_(host_batch, non_blocking=True)
    ready.record()
with torch.cuda.stream(compute):
    compute.wait_event(ready)
    result = model(device_slot)
    done.record()
with torch.cuda.stream(download):
    download.wait_event(done)
    host_result.copy_(result, non_blocking=True)

这段代码的 host_batch 和 host_result 使用 pinned memory，stream 与缓冲对象都保持存活。CPU 真正读取 host_result 前还需要等待回传完成；同样，复用 host_batch 前需要确保 DMA 已经读完。把这些对象的所有者和释放时刻写清楚，比依赖某次运行恰好较慢更可靠。

数据依赖与分配器寿命

一个 tensor 在 stream A 上分配，随后被 stream B 使用。B 要等待 A 的生产工作，分配器也要知道 B 尚未使用完这块存储。前者用 wait/event 建立顺序，后者可以用 tensor.record_stream(B) 登记跨流使用；当 Python 引用释放时，分配器会据此推迟存储复用。

若明确管理所有使用者，也可以在回收前让原分配 stream 等待消费者完成。高层库内部采用哪条路径，会影响回收时机、额外 event 与内存峰值。调试随机数值错误时，保留 tensor 引用或临时同步能帮助判断是否存在生命周期竞态；找到原因后，应把精确依赖落实到生产者、消费者和回收边界。

手工创建的外部 CUDA stream 还多一层生命周期：包装对象可能只持有一个外部句柄，而分配器直到 tensor 释放时才会向登记的 stream 记录 event。因此外部 stream 的销毁必须晚于所有相关 tensor 的跨流使用和回收操作。C++ 扩展与 Python 共用内存时，建议把 stream 所有者和 tensor 使用范围一起封装。

Pinned memory、槽复用与容量

稳定的 pinned host memory 允许 DMA 在 CPU 继续运行时读取或写入数据。把普通内存临时 pin 住本身有成本，因此输入管线常预先建立一组 pinned 缓冲，并循环使用。non_blocking=True 应配合源、目标内存类型与使用时机一起检查，才能判断是否形成了实际重叠。

设每槽需要输入缓冲 \(M_x\)、输出缓冲 \(M_y\) 和 workspace \(M_w\)，使用 b 个完全独立槽时，容量约为 \(b(M_x+M_y+M_w)\)。如果 workspace 可通过 event 安全串行复用，可以单独计算它的数量。增加第三个槽只在已有排程因槽复用而停顿时才有机会改善吞吐。

传统 legacy default stream 与 per-thread default stream 的同步规则不同，第三方库也可能在内部使用自己的 stream。出现意外串行时，查看 Nsight Systems 中实际 stream id 与等待事件，再检查库调用的 stream 绑定方式。通信与计算重叠也遵循同一原则：两者需要可独立推进的工作，还会竞争设备资源。

把一份输入从生产追到回收

把每个缓冲槽表示为状态机，会让依赖更直观：空闲→host 已写好→H2D 已提交→计算可用→D2H 已完成→空闲。CPU 可以提前准备另一个空闲槽，但只能在自己的写入阶段修改该槽。每次循环带上批次编号，检查输出是否对应预期批次，能发现因过早复用造成的数据串批。

一份输入占 64 MiB、有效上传带宽为 16 GiB/s 时，纯传输时间约为 3.906 ms。若计算只有 2 ms，单个上传通道限制稳态间隔；若计算为 8 ms，上传有机会被覆盖。选择 chunk 大小时，既要考虑每次传输的固定成本，也要保留足够多独立 chunk 建立流水，过大的 chunk 会减少可重叠机会。

完成 event 可以用 query() 非阻塞查询，也可以让下一阶段的 stream 等待。轮询频率太高会增加 CPU 工作；每轮直接同步整个设备则会让无关 stream 也停在同一个 host 边界。可以把等待放到真正要读取结果或复用槽的地方，使其他请求继续推进。

测出端到端收益

CUDA event 适合圈定同一 stream 上的一段工作。测量整个多流流水线时，可以在末端加入 join event，等待全部分支完成，再记录结束；或者用 CPU wall clock 加首尾同步测整个批处理。只在一个 stream 上记录结束，会漏掉尚未完成的其他分支。

当双缓冲没有变快时，先看上传与计算是否真的重叠。如果两条 lane 完全串行，检查 pinned memory、默认 stream 和等待位置；如果重叠明显但计算变慢，检查带宽竞争；如果批间出现周期性空白，标记每个槽的释放点，判断缓冲数是否不足。Profiler 开启 stack 和 shape 采集会增加开销，精确计时应使用较轻的独立运行。

让时间线解释吞吐变化

多流实验固定总输入字节数和计算量，分别改变槽数、chunk 大小和 stream 数。每轮只改变一个因素，记录总完成时间、各资源忙碌区间和峰值缓冲容量。如果槽数从 1 到 2 改善明显、从 2 到 4 几乎不变，可以从图上确认已有双缓冲是否覆盖了所有可隐藏的传输。

异步提交也会把失败的报告位置向后推移。定位非法访问时，可先缩小到一份输入与一条 stream，再在关键阶段后同步以确定失败区间。修复之后恢复原来的精确 event 依赖，并重新验证所有批次输出。这样定位手段与最终调度策略各自承担明确职责。

当多个 kernel 并发争用 SM 时，同一份计算的持续时间可能随调度变化。记录各 kernel 的开始、结束和重叠区段，可以判断并发带来的吞吐收益是否伴随单请求变慢。带延迟目标的服务需要把这种变化放进请求级时间戳里评估。

练习与实验

1. 四批数据的完成时间

h=2 ms、c=5 ms、d=1 ms，缓冲充足。计算 4 批和 10 批的完成时间。

展开解答

第一批为 8 ms，稳态间隔 5 ms。四批 \(8+3\times5=23\) ms，十批 \(8+9\times5=53\) ms。串行十批为 80 ms。

2. 缺少哪条边

一个 tensor 已调用 record_stream(B)，但 B 偶尔读取到旧值。生产者在 A 上运行。应该先检查什么？

展开解答

检查 B 是否等待 A 上的数据生产完成。record_stream 登记的是分配器使用寿命；数据就绪需要 A 记录完成 event，再让 B 等待该 event。

3. 第三次上传的起点

默认双缓冲排程里，为什么 H2 需要从 8 ms 开始？

展开解答

H2 复用槽 0，而 D0 在 7–8 ms 读取该槽。H2 的写入必须等 D0 结束，因此即使 H2D 引擎在 4 ms 后空闲，也要等到 8 ms。

4. 两个计时器

CPU 从调用到返回测得 0.2 ms，完成全部设备工作需 4.2 ms。分别对应什么？

展开解答

前者衡量 host 提交耗时，后者衡量包含完成等待的请求耗时。若请求必须取得 GPU 输出，端到端延迟采用后者；CPU 是否能提前提交下一批则由前者和队列状态共同决定。

CPU 排程实验把依赖和资源占用写成可检查的图：

python3 lab.py --chunks 4 --buffers 2 --h2d 2 --compute 5 --d2h 1

默认流水线为 23 ms，单槽串行为 32 ms；实验会主动移除上传等待和槽复用等待，并检测相应 hazard。把 buffers 改为 1、4，再把 H2D 改为 7，核对瓶颈与缓冲依赖如何变化。

真实 CUDA 示例保留 stream、event、pinned buffers 和逐批正确性验证。下载后运行 python3 gpu_example.py；观察 trace 时重点对照 H2D、计算、D2H 与复用事件。
