DeepSeek-V4-Pro 推理：一枚 token，8 张卡

交互2026-10-20更新于 2026-10-22

把 DeepSeek-V4-Pro 放到 8 张卡上，首先要确定每张卡保存什么、计算什么、何时需要等其他卡。这里沿参考推理实现的分工展开：query 与输出投影按头切分，路由专家按 ID 分配；每个 rank 保存完整 shared KV、mHC 状态与共享专家。8 路划分的路由专家权重本身就需要约 95.7 GiB/卡；使用 80 GiB 设备时，需要进一步选择满足容量与整除约束的划分。

一个 decode step 消费每条请求的一枚输入 token，逐层更新状态，最后产生下一枚输出 token。权重持续驻留 HBM，kernel 将本轮需要的权重和 KV 分块搬到片上计算，再把激活和新缓存写回。理解容量与时间，分别需要一份常驻张量账本和一条计算依赖时间线。

1. 先分清分片与副本

Pro 有 61 个主干层，隐藏宽度为 7168。设 \(\htmlData{symbol=tp}{G}=8\) 是共同执行一个副本的卡数。每张卡都执行所有层，Q 的后一段投影切分输出头，O 的后一段投影切分输入通道。每卡产生 O 的一份部分和，再通过 all-reduce 汇成完整结果。

对象全局大小每 rank 的分工
Query 头12816 个
输出投影组162 组
Indexer 头648 个
每层路由专家38448 个
shared KV / mHC 残差每条目 512 维 / 每输入 [4, 7168]完整副本
每层共享专家1 个完整副本

增加并行卡数会缩小路由权重和头分片，却保留每卡复制项。这里“共享 KV”指同卡上的多个 query 头共同读取一份向量；在这套分工中，各张卡有自己的相同 KV 副本。四路残差则是模型内部的激活轴，随每张卡上的输入共同流动。

并行度还受可整除约束。头数、输出组数、Indexer 头数和专家数，都要能被 \(G\) 整除。Pro 的输出投影有 16 组，满足这些维度的均匀切分可选 G=1、2、4、8、16。 算出容量所需卡数后，还应与合法分片集合、设备拓扑和通信成本一起选择。

2. 权重与量化 scale 的容量

路由专家占据大部分权重。一个专家由三块矩阵组成，每层专家数为 \(E=384\)，隐藏宽度 \(d=7168\)，中间宽度 \(m=3072\)，层数 \(L=61\)，所以主干路由专家参数量为

$$P_{\mathrm{route}}=L E\,3dm=1,547,396,186,112.$$

这份原生 FP4 布局沿矩阵的输入维度，每 32 个元素保存一个 8-bit scale。元素本体每个占半字节，scale 摊销每个占 1/32 字节，合计

$$b_{\mathrm{FP4}}=\frac{4}{8}+\frac{1}{32}=0.53125\ \mathrm{B/参数}.$$

于是主干路由权重共 765.5977 GiB，均分 8 卡后为 95.6997 GiB/卡。GiB 为 \(2^{30}\) 字节。每层共享专家使用 FP8，本体每元素 1 字节、每个 128×128 权重块配 1 字节 scale，所有层合计约 3.753159 GiB，并在各卡复制。

把其余权重继续列成独立行：Q/KV/O 投影、embedding 与词表头、mHC、router、MTP。加载器和 kernel 使用的量化布局也要对应 checkpoint：packed 元素、scale 轴、块大小和转置顺序共同确定矩阵语义。将 checkpoint 转为另一种 FP4 格式时，需要重新计算这些元数据和对齐开销。

FP4 的容量收益还要连接到实际 GEMM 路径。一个 Pro 专家有 63 Mi 个参数，原生 packed 权重和 scale 占 33.46875 MiB，完整展开成 BF16 会占 126 MiB。高效路径将解包、scale 应用与矩阵乘分块衔接，让当前 tile 在片上消费；若先在 HBM 写出整个 BF16 权重矩阵，再启动 GEMM，就会增加临时容量以及一遍写入、读取流量。检查 trace 中反量化 kernel 的输出形状和生命周期，才能判断 checkpoint 的压缩是否延伸到了执行阶段。

在 8 卡、8 请求、32K 上限时，三项合计 102.056 GiB/卡，已经超过 80 GiB。将 TP 调到 16 后，路由权重变成 47.850 GiB/卡，三项降至约 54.206 GiB/卡。完整容量还需把剩余权重与执行峰值填入账本；实际部署也可以结合 PP 或其他并行组组织专家。 这也说明，部署的第一道判断是完整常驻量能否进入每张卡；每 token 激活约 49B 描述的是计算涉及的参数规模。

3. 逐层计算历史状态

主 attention 每条 shared KV 为 512 个 BF16 元素，即 1024 字节。所有 61 层各有 128 条局部环形缓存；此外 30 个 CSA 层各保存约 \(N/4\) 条压缩记忆，31 个 HCA 层各保存约 \(N/128\) 条。设 \(\htmlData{symbol=context}{N}\) 是分配的上下文长度，单请求、单卡主 KV 为

$$M_{\mathrm{main}}=1024\left[61\times128+30\left\lfloor\frac{N}{4}\right\rfloor+31\left\lfloor\frac{N}{128}\right\rfloor\right]\ \mathrm B.$$

CSA 的 Indexer 还保存 128 维 BF16 索引向量，因此单请求索引缓存为 \(30\lfloor N/4\rfloor\times128\times2\) 字节。压缩器有未完成组的 value 与 gate 状态，两份都用 FP32。每个 CSA 层主压缩器和索引压缩器共 80 KiB，每个 HCA 层 512 KiB。

N=32,768，单请求/单卡容量增长因素
全部主 KV255.375 MiB局部固定，压缩条目随 N 增长
Indexer cache60 MiB随 N/4 增长
未完成压缩组状态17.843750 MiB固定长度状态
合计333.218750 MiB各 rank 保存完整副本

这里区分“已使用的长度”和“预先分配的长度”尤其重要。参考实现创建缓存时按 max_batch_size 与 max_seq_len 分配。即使实际只来了一条短请求，分配上限也已经决定张量容量：

slots = window + (max_seq_len // ratio if ratio else 0)
kv_cache = zeros(max_batch_size, slots, 512)
index_cache = zeros(max_batch_size, max_seq_len // 4, 128)

Pro 设 8 请求、32K 上限时，上述缓存约 2.603 GiB/卡；改为 1,048,576 长度上限后约 77.136 GiB/卡。调大上下文上限会在请求到来前改变显存占用。服务框架的分页管理可以按需分配实际页面，但容量估算应使用它实际实现的压缩状态布局和量化格式。

更新缓存时，当前位置写入局部槽 \(t\bmod128\)；CSA 在 \((t+1)\bmod4=0\) 追加一条压缩记忆，HCA 在 \((t+1)\bmod128=0\) 追加一条。压缩组完成后才对当前及后续 query 可见。跨 chunk 保存的 remainder 决定下一组能否继续正确池化。

4. 长 prefill 的峰值从哪里来

常驻缓存能放下，prefill 仍可能在构造中间张量时触及容量上限。以一条 32K prompt 为例，CSA 候选数为 8192。参考 Indexer 先为每个本地索引头计算 query×候选分数，张量形状为

$$[B,S,H_{\mathrm{index}}/G,C]=[1,32768,8,8192].$$

这里 \(B\) 为请求数，\(S\) 为这次 prefill 的 query 数，\(H_{\mathrm{index}}=64\)，\(C\) 为压缩候选数。按 BF16，这个中间张量单层就达到 4 GiB；按头求和后的 \([1,32768,8192]\) 仍有 512 MiB。最终留下 1024 条 top-k 结果，只描述结果大小；执行峰值取决于它之前产生了什么。

如果报错出现在 Indexer 的 score 分配，先保留同一批输入，记录每层峰值与分配形状，再尝试缩短本轮 prefill chunk 或启用分块、融合的 score/top-k 路径。分块把中间态限制在较小的 query/candidate 范围，逐步合并选择结果。验证时同时检查 chunk 边界：局部窗口顺序、CSA 重叠组、未完成 remainder 和 query 的因果可见范围。

参考 forward 的 start_pos>0 路径使用逐 token 的状态更新。为它添加多 token chunk 时，需要让状态机显式覆盖整个 chunk 内的多个组完成点。测试长度选 3/4/5、7/8/9、127/128/129，再分别用整段、单 token、不同 chunk 切分读取同一输入，比较每个位置的输出。

5. 一个 Block 怎样经过各张卡

同一层开始时，每卡都有相同的四路残差。mHC 汇合后得到 \([B,S,7168]\)，各卡用自己的 query 头读取本地 KV。输出投影把本地头的结果映射为 \([B,S,7168]\) 的部分和，归约后各卡得到完整 attention 输出。接着 MoE 执行分到本卡的路由专家，再归约各卡的加权部分和，最后加上本地共享专家结果。

图中的归约将 [2, 3, -1, 4, 5, -2, 1, 4] 相加得到 16，并把结果交给所有 rank。GPU 实际执行时，每个 rank 处理的是整批向量和多个通道。只要某个 rank 的局部计算尚未完成，依赖它的 collective 就要等待；所以时间线中一张卡上的“通信耗时”也可能含有等待其他卡到达的时间。

层与层之间还有严格依赖：当前层的 mHC 输出决定下一层输入。一次 decode 依次经过全部 61 层，再经输出头和采样器生成下一枚 token。下一枚 token 在下一次模型调用中被消费并写入各层缓存，这正是缓存生命周期与输出计数需要分开跟踪的原因。

6. 从张量形状推导通信量

参考 O 投影在 all-reduce 前将输出转为 FP32，MoE 部分和也用 FP32。设 \(\htmlData{symbol=batch}{B}\) 为请求数，\(\htmlData{symbol=query}{S}\) 为本轮每请求输入数，\(d=7168\)，一次归约的完整消息大小为

$$\htmlData{symbol=payload}{M}=BSd\times4\ \mathrm B.$$

Ring 的 reduce-scatter 与 all-gather 各运行 \(G-1\) 轮，每轮发送 \(M/G\) 字节。因此每卡发送总量为 \(2(G-1)M/G\)。若每轮启动时间为 \(\htmlData{symbol=alpha}{\alpha}\)，有效链路带宽为 \(\htmlData{symbol=beta}{\beta}\)，粗略时间模型为

$$T_{\mathrm{ring}}\approx2(G-1)\alpha+\frac{2(G-1)M}{G\beta}.$$

B=32、S=1、G=8 时，完整输出张量为 896 KiB，一次 ring 每卡发送 1568 KiB。一层至少包含 O 与 MoE 两次合并，CSA 还包含 Indexer 分数归约。实际 collective 可以采用不同算法；trace 中的张量形状、dtype、参与 rank 与拓扑，决定该用哪一份时间账本。

用一组假设链路参数估算：每轮启动 1 μs、有效带宽 100 GB/s，上述归约的固定项为 14 μs，字节项约 16.056 μs，合计约 30.056 μs。扩展到更多卡时，权重分片继续缩小，而 ring 的轮数增加；跨节点链路还会改变启动时间与有效带宽。选择 TP 时，可以将每层计算节省量与新增通信时间放在同一张表中。

如果将通信 dtype 改成 BF16，payload 减半，固定启动成本仍然存在。小 batch 下，大量小 collective 的启动延迟可能占主要部分；大 batch 下，字节与链路带宽的比值更重要。改归约精度后，应重新比较 logits、top-k 专家和长生成结果。

7. 专家负载与通信重叠

一个 token 选择 6 个路由专家。合批之后，不同 token 可能选择不同专家，因此本轮读取的专家集合也会变大。令 \(E=384\) 是一层路由专家数，假设每个 token 均匀独立选择 6 个专家，一个专家未被 B 条请求选中的概率为 \((1-6/E)^B\)，于是

$$\mathbb E[\text{本轮不同专家数}]=E\left[1-\left(1-\frac6E\right)^B\right].$$

B=32 时，预计访问约 152.0 个专家。这个基线帮助解释合批的双重效果：每个专家可以处理更多 token 行，同时更多专家的权重被读取。实际分布需要记录每专家 token 数、每 rank 的不同专家数和耗时，才能区分大量小 GEMM 与少数热点。

另一种服务组织方式是先把 token 分给不同 rank，再将激活 dispatch 到专家所在卡，计算完成后 combine 回 token 所属卡。全局 32 个 token、每个选 6 个专家、BF16 输入时，朴素输入 payload 为 \(32\times6\times7168\times2=2688\) KiB。按目标 rank 合并同一 token 的发送、扣除本地专家后，网络字节数会变化；IDs、路由权重与对齐还形成元数据。

Dispatch、expert GEMM、combine 可以分波次流水。以下时间线为四个波次设定 dispatch=2 ms、计算=3 ms、combine=2 ms，并让三种资源分别处理各自队列。第一个波次在 7 ms 结束，后续每 3 ms 完成一个，总长 16 ms；全部串行则为 28 ms。

重叠收益来自独立资源并行工作，关键路径仍受最长服务阶段控制。若 dispatch 与 combine 争用同一链路，或某个专家波次变成热点，应把共享资源约束加入调度。优化评估沿依赖关系找出实际空档，并计算每阶段对端到端耗时的贡献。

8. 容量、并行与数值的工程取舍

模型刚加载就 OOM

先分开记录权重加载完成、cache 创建完成、第一次 prefill 三个时刻的 allocated 与 reserved 显存。权重阶段超限，核对 packed dtype、scale、每 rank 的专家范围和复制权重；cache 阶段跃升，核对 batch/sequence 上限；第一次 prefill 跃升，再定位 score、临时激活或 workspace 的分配。这三个时刻对应三种不同调整对象。

同一个求和，为什么改变并行组织后数值会变

浮点加法的舍入与求和顺序有关。改变 batch、分块大小或归约树，会改变部分和在哪一级相加；低精度输入与 FP32 累积又形成另一组数值边界。如果两个 Indexer 候选分数十分接近，小差异就可能改变 top-k 集合，随后放大为 attention 输出差异。应先测固定输入下的分数误差与第 k、第 k+1 名的间隔，再判断这次选择变化来自正常舍入还是状态更新错误。

对吞吐优化采用固定的硬件、软件和输入集合建立基线，分别记录最大误差、logprob 与选择结果。在确定性配置下做回归，可以压缩运行间波动；在高吞吐配置下改变 batch 和并行度，则检验系统对实际调度的数值稳定性。

同一输入在换 batch 或换 TP 后生成不同

先用固定 token 做 teacher forcing，逐位置比较 logprob 与关键中间张量，定位第一次分歧。若压缩 KV 相同而 top-k 不同，检查分数归约和并列项的选择规则；若专家 ID 相同而输出不同，继续比较局部 GEMM、共享专家激活裁剪和归约精度。生成过程会将一个早期 token 差异放大为完全不同的后续序列，因此逐位置证据比末尾文本更有效。

GPU 时间变短，用户仍觉得慢

将请求拆成排队、prefill 与逐步 decode，分别记录 TTFT、ITL、吞吐和尾分位数。设一次 decode 的暴露开销为 attention 3 ms、专家 5 ms、通信 2 ms、CPU/调度 6 ms，总计 16 ms。专家加速两倍得到 13.5 ms，即 1.19×；CPU 降至 1 ms 则得到 11 ms，即 1.45×。优化顺序由实际关键路径决定。

# 已加载模型上的设备计时；warm-up 后测量
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
torch.cuda.synchronize()
start.record()
logits = model(tokens, start_pos=position)
end.record()
end.synchronize()
print(start.elapsed_time(end), "ms")

CUDA event 记录所在设备和 stream 的时间线。多卡为每个 rank 保存事件与通信 trace，再用 wall clock 记录完整请求；最慢 rank 与请求排队会共同影响服务延迟。改变 batch 时，也要同时记录缓存容量、专家负载与 SLO 达标吞吐。

9. 练习与实验

练习 1：容量与合法并行度

主干路由专家含 scale 共 765.597656 GiB。先求 80 GiB 卡的字节下界，再要求 TP 整除输出组 16、Q 头 128、Indexer 头 64、专家 384，求最小合法 TP。

展开解答

仅按路由权重，ceil(765.597656/80)=10 张。合法均匀 TP 是 1、2、4、8、16，其中满足该容量下界的最小值为 16，路由权重变为 47.849854 GiB/卡。共享权重、缓存和运行时峰值继续加在这项之上。

练习 2：上下文扩大四倍

单请求上下文上限由 32,768 改为 131,072，仍使用 BF16 缓存与 FP32 压缩状态。计算主 KV、Indexer、状态与合计容量。

展开解答

主 KV 为 998.625 MiB，Indexer 为 240 MiB，压缩状态保持 17.843750 MiB，总计 1256.468750 MiB。固定的局部窗口和未完成组状态使总量小于原来的四倍。每 rank 保存这些副本，所以增加 TP 不改变本题的每卡缓存数。

练习 3：小消息归约

G=8、B=32、S=1，输出为 FP32。计算一次 O all-reduce 的消息大小、ring 每卡发送量，并说明改为 BF16 后哪个时间项会缩小。

展开解答

M=32×7168×4=917504 B，即 896 KiB；每卡发送 2(G−1)M/G=1568 KiB。BF16 将字节项减半，固定启动项 2(G−1)α 保持不变；实际还需要重新测量并验证数值。

练习 4：手推一个流水时间线

四波任务，各需 dispatch 2 ms、计算 3 ms、combine 2 ms，三阶段独立且各阶段按波次顺序处理。写出四波 combine 完成时刻。

展开解答

Dispatch 完成于 2、4、6、8 ms；计算完成于 5、8、11、14 ms；combine 完成于 7、10、13、16 ms。相邻波次的节拍由 3 ms 计算阶段决定，串行总时间为 4×7=28 ms。
