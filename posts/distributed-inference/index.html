分布式推理：数据怎样走过每张卡

交互2026-10-20更新于 2026-10-22

把一个模型从两张 GPU 扩到四张，单轮解码可能从 8.5 ms 变成 9 ms。计算确实分得更细了，通信却开始跨越更慢的链路。要解释这半毫秒，得追踪每张卡保存什么、计算什么，以及下一步究竟在等谁。

一次推理有三类数据：权重是模型参数，通常常驻显存；KV cache 保存各层已处理位置的 key/value，随请求增长；激活是当前这批 token 的中间结果，沿计算图向前传递。并行方式决定这三类数据在设备之间的归属。一个参与通信的进程叫 rank，下面每个 rank 使用一张 GPU。

1. 从一层矩阵乘开始分工

考虑线性层 \(Y=XW\)：\(X\) 的形状是 \([T,H]\)，权重 \(W\) 是 \([H,F]\)，输出是 \([T,F]\)。这里 \(\htmlData{symbol=tokens}{T}\) 是本轮总 token 行数，\(H\) 是输入宽度，\(F\) 是输出宽度。单 token decode 中，一条请求贡献一行；prefill 可以让一条请求贡献许多行。一次乘加记作 2 FLOPs，计算量约为 \(2THF\)。

沿权重的输出维度切分，令 \(W=[W_0,W_1]\)。两张卡读取相同的 \(X\)，各自得到 \(Y_0=XW_0\) 和 \(Y_1=XW_1\)。这两份结果拥有不同的输出通道。如果下一层需要完整的 \(Y\)，就按通道拼接；如果下一层能消费对应通道分片，就可以直接继续计算。

沿输入维度切分则得到另一种关系：\(X=[X_0,X_1]\)，权重上下分成 \(W_0,W_1\)，于是 \(Y=X_0W_0+X_1W_1\)。每张卡产出的是同一组输出位置的部分和。All-reduce SUM 把这些部分和相加，再让参与的每张卡得到完整结果。

2. 两层 MLP 怎样只做一次归约

Transformer 的 MLP 可以把两种切法配对。第一层按输出通道切，逐元素激活函数 \(\phi\) 在本地执行；第二层沿相同的中间通道切，最后归约输出：

$$Z_r=\phi(XW_{1,r}),\qquad Y_r=Z_rW_{2,r},\qquad Y=\sum_{r=0}^{p-1}Y_r.$$

这里 \(r\) 是 rank 编号，\(\htmlData{symbol=ranks}{p}\) 是 TP rank 数。若完整 MLP 宽度为 \(H\to F\to H\)，每卡保存 \([H,F/p]\) 的第一层权重和 \([F/p,H]\) 的第二层权重。中间激活 \(Z_r\) 始终是 \([T,F/p]\)。门控 MLP 的 gate 与 up 投影要使用同一组通道分片，使逐元素乘法能够本地完成。

取 \(X=[1,2]\)、\(W_1=\begin{bmatrix}3&5\\4&6\end{bmatrix}\)、\(W_2=\begin{bmatrix}1&2\\3&4\end{bmatrix}\)，激活为 ReLU。第一张卡得到中间值 11，第二张卡得到 17；第二层的部分和分别是 \([11,22]\) 和 \([51,68]\)。相加得到 \([62,90]\)，与完整矩阵计算一致。

共享 bias 应在归约后加一次。若每卡都先加相同的 bias 再 SUM，两个 rank 会把 bias 加两遍。用小矩阵与单卡参考逐层比较，通常能很快区分这种代数错误和正常的浮点归约误差。

# 每个 rank 的 y_partial 形状均为 [T, H]
y_partial = activation(x @ w1_local) @ w2_local
dist.all_reduce(y_partial, op=dist.ReduceOp.SUM)
y = y_partial + bias

3. 把消息大小变成每轮耗时

对 \(p\) 个 rank，ring all-reduce 把每卡的 \(\htmlData{symbol=message}{M}\) 字节张量划成 \(p\) 块。Reduce-scatter 走 \(p-1\) 轮，每轮发送 \(M/p\) 字节；all-gather 再走同样多的轮次。因而每卡总发送量是 \(2(p-1)M/p\)。

$$t_{AR}\approx 2(p-1)\htmlData{symbol=latency}{\alpha}+\frac{2(p-1)}p\frac{M}{\htmlData{symbol=bandwidth}{\beta}}.$$

\(\alpha\) 是每轮通信启动延迟，单位为秒；\(\beta\) 是该路径上的有效单向带宽，单位为 B/s。它们要按目标拓扑和消息规模测量。取 \(p=4\)、\(\alpha=3\,\mu s\)、\(\beta=100\) GB/s，一条 BF16 激活的消息大小为 \(M=T\times4096\times2\)。当 \(T=1\)，消息仅 8 KiB，估计耗时约 18.1 μs；当 \(T=1024\)，消息为 8 MiB，估计耗时约 143.8 μs。

小 batch decode 的消息越小，固定延迟越显眼。评估 TP 扩展时，把每层暴露出来的通信时间加入关键路径。若 TP=2 的计算、暴露通信和其他开销分别为 7、1、0.5 ms，而 TP=4 是 4、4.5、0.5 ms，最终就是 8.5 对 9 ms。重叠区段只计一次；profiler 上所有 kernel 持续时间之和通常大于端到端时间。

4. 按层切分，靠独立请求填满流水线

Pipeline parallel 把连续的层放到不同设备或设备组。每段保存自己的权重，以及这些层对应的 KV；边界传递当前 token 的激活。单条请求的一枚 token 必须依次经过所有段，随后才产生下一枚 token 的输入。

不同请求或独立 micro-batch 可以在各段同时计算。设有 \(p\) 个等时 stage，单段耗时 \(t_s\)，共有 \(m\) 个独立 micro-batch；忽略边界传输时，前向流水总时间和设备平均利用率为

$$T_{pipe}=(m+p-1)t_s,\qquad U=\frac{m}{m+p-1}.$$

第一批用 \(p\) 拍穿过流水线，之后每拍完成一批。4 个 stage、8 个 micro-batch 需要 11 拍，利用率为 72.7%。若只有一个 micro-batch，利用率为 25%。这解释了 PP 更容易服务高并发吞吐；低并发时，逐 token 延迟仍包含串行经过各段的时间。

层数平均分配只是起点。Embedding、输出词表投影、不同 attention 层与 MoE 层的耗时和显存不同。先在目标输入长度和 batch 下测每段用时，再调整层边界。一个长期繁忙的 stage 会让上游积压、下游空闲。

5. 专家并行要同时算网络和最忙的 rank

MoE 的专家权重分布在各卡。Router 为每个 token 选出 \(k\) 个专家，dispatch 把激活发到专家所在卡，combine 把结果带回原卡并按路由权重相加。若本层共有 \(T\) 个 token、hidden width 为 \(H\)、每元素占 \(b_e\) 字节，且远端分配比例为 \(\rho\)，整组设备 dispatch 的有效 payload 约为

$$V_{dispatch}\approx T k H b_e\rho.$$

例如 1024 token、top-2、\(H=4096\)、BF16、远端比例 0.75，发送量为 12 MiB，返回同宽结果又约 12 MiB。实际传输还包括索引、路由权重和对齐；把同一 token 发往同一目标 rank 的多次分配合并，可以减少重复激活传输。

通信完成后，各卡专家的工作量仍可能很不均匀。四卡负载从 \([256,256,256,256]\) 变成 \([640,128,128,128]\)，总分配数相同；若每份分配计算成本近似相等，利用率变成 \(1024/(4\times640)=40\%\)。记录每个 expert 的 token 数、各 rank 的 dispatch/计算/combine 时间，才能判断需要路由均衡、热点专家复制、专家放置调整，还是改善互联。

6. 先筛容量，再比较部署方案

每卡峰值显存由实际权重分片、KV、激活与通信工作区、运行时和 graph pool 共同组成。MoE 的常驻权重按总参数量计算。一个总参数 64B、每 token 激活 8B 的 BF16 模型，理想均分到四卡时，每卡仍需 \(64\times10^9\times2/4=32\) GB，即约 29.8 GiB 的权重。

若目标并发每卡还要 6 GiB KV 和 5 GiB 其他空间，总计 40.8 GiB，40 GiB 卡就需要改变配置。用八卡可以把理想权重降到 14.9 GiB；接下来比较跨节点 TP=8 与节点内 TP=4、节点间 PP=2 的通信关键路径。KV 的切分要查具体实现：KV heads 少于 TP ranks 时可能复制，PP 则按层归属存储。

Data parallel 把一组能独立执行模型的副本复制多份，各自服务请求。如果一个 TP=4 副本已经满足显存与延迟，八卡还应比较两个 TP=4 副本的总吞吐。选择依据是固定资源、固定请求分布下的 goodput，并同时看长上下文的显存峰值。

7. 常见设计问题：更多卡能换来什么

GQA 模型的 KV heads 可能少于 TP ranks。例如一层只有 8 个 KV heads，TP=4 时可给每卡分 2 个；TP=8 时每卡 1 个；TP=16 时，按完整 head 分配的实现会复制 KV heads。权重仍可能继续切分，但 KV 显存收益开始受复制限制。估算时从实际每卡 head 数出发，将层数、序列长度、head dimension 和 KV dtype 逐项相乘。

在 PCIe 多卡上，增加 TP 让矩阵乘变小，也让每层的归约经过更多参与者。按模型的真实消息范围做通信扫描：

./build/all_reduce_perf -b 8K -e 8M -f 2 -g 4

保存小消息延迟、大消息带宽和 rank 到 GPU/NIC 的映射，再与模型每层的激活尺寸对应。若低并发 decode 受启动延迟限制，可以比较更小 TP 加 PP、量化后更少卡的副本，或相同资源上的多个独立副本。若长 prefill 由大矩阵乘主导，更高 TP 则可能有效缩短首 token 延迟。

执行计划还须保持 collective 契约：同一 group 的各 rank 按相同顺序调用匹配的操作、元素数和 dtype。条件分支和变长专家交换都要保持这个约定。逐序号对齐调用轨迹，可以发现一边进入 broadcast、另一边进入 all-reduce 的控制流分歧；对 EP，再检查每对发送与接收的 split size。

8. 练习与实验

练习 1：八卡 ring 要发送多少

每卡消息 16 MiB，8 个 rank，启动延迟 2 μs/轮，有效单向带宽 50 GB/s。求每卡发送量与总耗时估计。

展开解答

发送量为 \(2\times7/8\times16=28\) MiB。启动耗时 28 μs，字节耗时 \(28\times2^{20}/(50\times10^9)=587.2\) μs，总计约 615.2 μs。

练习 2：填满前向流水线

4 个等时 stage，每段 2 ms。利用率达到 80% 至少需要多少独立 micro-batch？此时总时间与单批无等待延迟各是多少？

展开解答

\(m/(m+3)\ge0.8\) 得 \(m\ge12\)。总时间 \((12+3)\times2=30\) ms，平均完成间隔 2.5 ms；一批依次经过四段的无等待延迟为 8 ms。

练习 3：输出总多一份 bias

两卡各计算 z_local @ w_local + bias，然后 all-reduce SUM。请写出当前输出与正确输出，并修正。

展开解答

当前输出是 \(\sum_rZ_rW_r+2b\)，正确输出是 \(\sum_rZ_rW_r+b\)。将共享 bias 移到归约后添加，或让一个明确的 rank 在归约前添加一次。

练习 4：在显存和时延之间选方案

每卡 40 GiB。A 方案占 40.8 GiB；B 占 22.9 GiB、每轮 12 ms；C 占 22.9 GiB、每轮 10 ms，采用 TP=4、PP=2。目标为每轮 ≤11 ms，应先测哪一个？C 有 8 个独立 micro-batch 时的理想流水利用率是多少？

展开解答

C 满足当前容量与延迟约束，理想利用率为 \(8/(8+2-1)=88.9\%\)。继续用目标到达率和上下文分布测试队列、尾延迟以及 KV 增长。A 需要先降低显存占用，B 需要削减关键路径至少 1 ms。

下载 Python 实验，用 Python 3 标准库运行：

python3 lab.py
# TP result = [62, 90]; ring = 12.00 MiB; PP = 72.73%

先修改第一层权重的一列并手算输出，再检查 TP 与完整矩阵结果。随后把 ring 的 rank 数从 4 改为 8，将前向流水的 micro-batch 数改为 1，观察通信启动成本和空泡的变化。
