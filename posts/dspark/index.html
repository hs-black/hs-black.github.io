DSpark

投机解码要先产生几枚草稿，再让目标模型一起验证。若草稿模型仍然逐 token 跑完整前向，这段串行计算会吃掉一部分收益。DSpark 把工作拆成两个层次：较重的 backbone 并行产生整段特征，较轻的 Markov head 顺着已经抽出的 token 补上局部依赖；置信度再帮助引擎选择值得送去验证的前缀。

这三个部件分别回答三个问题：未来位置大致应该是什么、相邻候选怎样协调、有限验证容量应该分给谁。理解它们之间的数据依赖，比记住一张架构图更有用。

一次并行计算准备整段特征

设活动请求数为 \(R\)，每条请求最多提出 \(\htmlData{symbol=g}{\gamma}\) 个候选，隐藏宽度为 \(d\)，词表大小为 \(V\)。target 的已确认上下文特征、当前 anchor 和 mask 位置送入 draft backbone，得到隐藏状态 \(H\in\mathbb R^{R\times\gamma\times d}\) 与基础 logits \(U\in\mathbb R^{R\times\gamma\times V}\)。

并行算出 U 后，候选还需要彼此协调。例如两个位置各自认为 A、B 都合理，独立采样会产生 AA、AB、BA、BB 四种组合；若上下文实际更偏好 AA 或 BB，相邻位置就需要知道前一个究竟抽中了什么。Markov head 用前一个真实 token 生成一份转移偏置，再加到当前基础 logits。

低秩转移怎样改变下一行分布

记上一枚 token 为 \(x_{k-1}\)，当前基础 logits 为 \(U_k\)。使用参数 \(W_1\in\mathbb R^{V\times r}\)、\(W_2\in\mathbb R^{r\times V}\)，先查出前词的 r 维向量，再投影回词表：

$$b_k=W_1[x_{k-1}]W_2,\qquad q_k=\operatorname{softmax}(U_k+b_k).$$

这里的 \(\htmlData{symbol=r}{r}\) 是低秩维度，\(q_k\) 是当前候选的实际采样分布。第一个位置读取 anchor，后面依次读取刚抽出的候选。重的上下文计算已经并行完成，剩下的串行链是查表、低秩投影、归一化和采样。

强度为 1、前词为 A 时，两个 logits 相差 \(\ln3\)，所以概率比为 3:1，得到 [0.75,0.25]；前词为 B 时则反过来。若第一词均匀取 A、B，产生 AB 或 BA 的概率为 \(0.5\times0.25+0.5\times0.25=0.25\)。没有转移偏置时这个概率为 0.5。

低秩结构也有可计算的成本。取 \(V=128000,r=256\)，两个矩阵共 \(2Vr=65.536\)M 参数，FP16 占 125 MiB。一次投影约有 \(2rV=65.536\)M FLOP，8 个位置共约 524.288M FLOP。完整 \(V\times V\) 转移矩阵则有 16.384B 参数，FP16 约 30.52 GiB。低秩显著缩小存储，词表投影和 softmax 仍然会出现在服务时间线上。

置信度预测哪一种事件

target 验证当前候选时，使用相同前缀下的目标分布 \(p_k\) 和实际草稿分布 \(q_k\)。这一位置的总接受概率为

$$c_k^*=\sum_v\min(p_k(v),q_k(v))=1-\frac12\lVert p_k-q_k\rVert_1.$$

confidence head 用当前隐藏状态和前一 token 的信息预测这个条件接受概率，记为 \(\htmlData{symbol=c}{c_k}\)。它衡量 draft 与 target 的分布重合程度。训练时可以把上面的重合质量作为软标签，用二元交叉熵拟合 sigmoid 输出；backbone 与 Markov head 则学习接近 target 的候选分布。

第 k 个候选最终能被保留下来，需要前面的候选先通过。调度以预测的累计存活概率估计边际收益：

$$\htmlData{symbol=a}{a_k}=\prod_{i=1}^{k}c_i.$$

预测条件率 [0.9,0.8,0.7,0.5] 对应预测存活率 [0.9,0.72,0.504,0.252]。最后一个位置的条件接受率预测为 50%，按这组估计，它为本轮增加输出的概率为 25.2%。遇到前面被拒绝的训练样本时，后缀属于未进入当前验证路径的部分，应按训练目标处理这种条件与删失关系。

为什么正确排序还需要绝对概率校准

假设四个位置都预测为 0.9，而实际条件接受率为 0.8。模型预测的第四位存活概率是 0.6561，实际为 0.4096；预计每轮输出数从真实的 3.3616 被高估成 4.0951，约高出 21.82%。调度器用这些数值估计 token/s，持续高估会把容量分给收益较低的长后缀。

温度校准可以把置信 logits 缩放后再 sigmoid：\(c'_k=\sigma(\operatorname{logit}(c_k)/T_k)\)。例如 \(T=\ln9/\ln4\approx1.585\) 时，0.9 会映到 0.8。逐位置的校准要同时观察累计存活概率，因为前面的小误差会沿乘积放大。

验证时把预测落在相近区间的前缀分桶，统计实际存活比例。若两个桶分别有 200、300 个样本，预测均值为 0.75、0.85，实际为 0.60、0.80，加权绝对校准差为 \(0.4\times0.15+0.6\times0.05=0.09\)。还应按代码、对话、长上下文等任务切片，并保留每桶样本数。训练集、校准集与最终评测集分别承担拟合、纠偏与检验的角色。

把有限验证位置分给高收益前缀

设 R 条请求各占一个 anchor，分给第 r 条请求的候选长度为 \(\ell_r\)，target 总输入位置预算为 \(\htmlData{symbol=b}{B}\)。预算与期望输出分别为

$$B=R+\sum_r\ell_r,\qquad E=R+\sum_r\sum_{j=1}^{\ell_r}a_{r,j}.$$

对固定、在相关候选抽样前已确定的概率曲线，每增加一个位置，就增加对应的累计存活概率。由于同一请求的累计率沿位置递减，按边际收益排序可以得到合法前缀；相同分值时先选同一请求的更早位置。

预算为 5 时，两个 anchor 之外还有三个名额。最高收益是 A₁=0.9、A₂=0.72、B₁=0.6，长度分配为 (2,1)，预计输出 \(E=2+0.9+0.72+0.6=4.22\)。若轮时为 5.4 ms，吞吐估计为 781.48 token/s。

容量也需要结合硬件决定。增加一个位置带来收益 a、增加耗时 \(\Delta T\)，当前输出期望为 E、轮时为 T，那么值得增加的条件是

$$\frac{E+a}{T+\Delta T}>\frac ET\quad\Longleftrightarrow\quad a>\frac{E\Delta T}{T}.$$

从 E=4.22、T=5.4 ms 出发，若下个位置收益为 0.36、耗时增加 1 ms，收益门槛约为 0.7815，应该停下。若只增加 0.1 ms，门槛约为 0.07815，则值得继续。实际轮时可能在 kernel、图捕获形状桶或并行配置边界处跳变，因此需要测量整条服务曲线。

调度决定需要遵守采样因果关系

是否让候选 \(x_k\) 进入验证，应由抽取它之前可用的信息决定。当前隐藏状态、前一 token 和历史容量预算都可以参与决定；这样候选仍然来自原来的 \(q_k\)，后续 p/q 校正才能保持目标分布。

看一个两词表例子：p=q=[0.5,0.5]。若先抽候选，抽到 A 就保留，抽到 B 就放弃并重新从 p 抽一次，最终 A 的概率变成 \(0.5+0.5\times0.5=0.75\)。这个偏差发生在“是否使用这次抽样”的选择上。

异步引擎可以用较早轮次的历史信号决定当前容量，再用满足因果条件的当前置信度分配前缀。这样 CPU 可以提前准备 batch 形状，GPU 同时执行前一轮。实现时将轮次、请求 ID、概率版本和容量版本一起保存，清楚区分“决定入选”与“抽取候选”的依赖。

capacity = choose_from_history(history)
previous, survival = anchor, 1.0
for k in range(max_candidates):
    qk, ck = head(H[k], previous)
    if not admit(survival * ck, capacity):
        break
    candidate[k] = sample(qk)
    saved_q[k] = qk
    previous = candidate[k]
    survival *= ck
    capacity -= 1

从训练质量走到服务吞吐

部署时首先对齐 target 权重、模板、thinking 模式和训练任务分布。draft 在某类 target 输出上学到的候选习惯，会影响换任务后的接受长度；置信度校准也会随着任务分布变化。分别记录逐位置接受率、预测存活率和实际产出，再决定需要重新校准还是重新训练 draft。

其次测量 Markov head 与采样阶段的串行成本。候选长度增长时，低秩投影、词表 softmax、CPU/GPU 同步都可能沿位置累积。将 backbone、head、target 验证和调度分别标记到时间线上，再在相同并发下扫描 rank、候选长度和预算。若 head 已成为瓶颈，可以考虑更小 rank、数据驻留或融合；若 target 已饱和，应优先缩短低收益后缀。

最后审计一轮的状态交接：保留实际 q、候选 token、条件置信度、入选前缀和 target 接受数。target 仍按投机采样规则接受或纠正；提交后回滚分叉 KV，新的纠正或 bonus token 留作下一轮 anchor。训练质量、调度收益与概率正确性在这些明确的接口上连接起来。

词表张量还会影响峰值内存。若 R=32、γ=8、V=128000，一份 [R,γ,V] 的 FP32 logits 有 32768000 个元素，占 125 MiB。基础 logits、Markov 修正和概率若分别物化，峰值会继续增长。结合接受算法需要保留的 q，设计张量复用和释放时机；同时测显存与轮时，才能评估融合和重算的实际取舍。

练习：Markov、预算与选择偏差

1. 求实际用于接受检验的 q

基础 logits 为 [0,0]，前词对应的 W₁ 行为 [2]，W₂=[ln2/2,−ln2/2]。目标 p=[0.5,0.5]。求 q 与总接受率。

参考解答

偏置为 [ln2,−ln2]，概率比 4:1，q=[0.8,0.2]。接受率为 min(0.5,0.8)+min(0.5,0.2)=0.7。

2. 分配三个草稿位置

A 条件率 [0.9,0.8,0.5]，B 为 [0.6,0.6,0.6]，总预算 5。求长度、期望产出及 5.4 ms 轮时下的吞吐。

参考解答

累计率分别为 [0.9,0.72,0.36] 和 [0.6,0.36,0.216]。选择 A₁、A₂、B₁，长度 (2,1)，E=4.22，吞吐约 781.48 token/s。

3. 后一个置信度可以决定首词是否入选吗？

抽出 x₁ 后才得到依赖 x₁ 的 c₂。若 c₂ 高才保留 x₁，否则重新抽 target。描述偏差来自哪里，并给出因果顺序。

参考解答

入选事件依赖 x₁ 的取值，改变了送验候选的分布。应先用抽样前的信息决定 x₁ 是否入选，再抽 x₁；后续位置按相同顺序决定。p=q 的 A/B 算例已经能把最终 A 概率从 0.5 推到 0.75。

枚举前缀，检查分配是否最优

下载 lab.py，运行：

python3 lab.py
python3 lab.py --budget 6

默认输出混搭概率 0.25、prefixes=[2,1]、E[output]=4.2200，给定 profile 的最优预算是 5。脚本枚举全部合法短前缀，独立验证排序分配，并覆盖全 0、全 1、相同收益和选择偏差。

先调整一段轮时曲线，预测最优预算怎样改变；再模拟置信度统一高估 0.1，比较预测与实际产出。下一步接入真实 profile 时，应固定硬件、上下文和并发，并同时观察单请求延迟目标。
