Engram：条件记忆怎样与 MoE 分工

交互2026-10-22

像 “Diana, Princess of Wales” 这样的高频固定搭配，在语料里会出现无数次。标准 Transformer 每次遇到它，都要老老实实从前几层的注意力和 FFN 一路算上来，重新把这几个 token 拼成一个实体表示，再结合上下文决定它在这句话里起什么作用。如果我们干脆把常见局部组合存进一张可训练的查表里，遇到时直接读出来，只让隐藏状态判断“这份记忆此刻该用多少”，前面好几层重复拼接的活就省下来了。

这就是 Engram 做的条件记忆模块：用输入 token 做确定性寻址，拿当前层的隐藏状态做门控，再把结果写回残差流。一旦引入这条路径，一个很实际的问题马上就跟着来了——在总参数和每 token 激活计算预算都固定的前提下，稀疏参数到底该分多少给 MoE 专家做动态计算，分多少给查表存静态局部模式？

先确定地址，再解释内容

常见 tokenizer 会给大小写、前导空格不同但词义相同的写法分配不同 ID（比如 Apple、apple 和 ␣apple）。如果直接拿原始 ID 做 n-gram 查表，同一个短语会被拆成好几份独立条目，白白浪费容量。Engram 的第一步是先把 token 文本做规范化，用一张固定的映射表 \(\mathcal P\) 把等价写法归并到同一个 canonical ID：

$$x'_t = \mathcal P(x_t).$$

注意这张映射只用于查表寻址，主干网络和最后的输出预测仍然吃原始的 token 序列 \(x_t\)，不会丢掉大小写或格式信息。

接下来，在位置 \(t\) 取出以当前 token 结尾的各阶后缀 n-gram，\(g_{t,n}=(x'_{t-n+1},\ldots,x'_t)\)。为了压低哈希冲突，每一阶都配 \(K\) 个独立的哈希头，每个头维护各自的可训练表 \(E_{n,k}\) 和哈希函数 \(\varphi_{n,k}\)。查出来的向量全部拼在一起，就得到当前位置的检索记忆：

$$r_{t,n,k}=\varphi_{n,k}(g_{t,n}),\qquad e_{t,n,k}=E_{n,k}[r_{t,n,k}],\qquad \htmlData{symbol=memory}{e_t}=\operatorname{concat}_{n=2\ldots N,\,k=1\ldots K}e_{t,n,k}.$$

这里 \(N\) 是最大 n-gram 阶数，每行宽度记为 \(q\)，拼出来的总维度就是 \(d_{mem}=(N-1)Kq\)。举个具体的数：取 bigram 和 trigram（\(N=3\)），每阶 4 个头、每行 128 维，读出来的记忆向量 \(e_t\) 就是 \(2\times 4\times 128=1024\) 维。

查表本身是“瞎”的——规范化会合并不同写法，有限的哈希桶也免不了让毫无关系的短语撞到同一行。Engram 靠两层机制兜底：多头哈希让冲突尽量分散在不同头的组合里，后面的上下文门控再决定读出来的东西和当前语境合不合拍。关于哈希表容量、碰撞时的梯度干扰以及按行分片，可以顺着看 Over-Encoding。

顺手记下一个在后面系统部分非常关键的性质：只要输入 token 序列定了，整张网络里所有 Engram 层的查表地址就全知道了。MoE 的路由必须等当前层的隐藏状态算出来才能决定去哪几个专家，而 Engram 的地址只依赖已知的离散 token ID，这意味着它可以提前把数据从主机内存预取到卡上，和前面几层的 GPU 计算重叠。

上下文怎样决定记忆的作用

同一个局部短语放到不同语境里，意思可能完全不同，更何况哈希表里还掺着碰撞噪声。这时候，已经聚合了前面若干层信息的主干隐藏状态 \(h_t\in\mathbb R^d\) 就派上用场了：用它来给读出的记忆打分，决定这次该放行多少。具体做法是把检索向量 \(e_t\) 分别投影成用于匹配的 key 和用于写入的 value：

$$k_t=W_Ke_t,\qquad v_t=W_Ve_t,\qquad W_K,W_V\in\mathbb R^{d\times d_{mem}}.$$

记 \(R(\cdot)\) 为 RMSNorm，论文给出的标量门控就是把 \(h_t\) 和 \(k_t\) 各自归一化后再做缩放点积，过一个 sigmoid：

$$s_t=\frac{R(h_t)^\top R(k_t)}{\sqrt d},\qquad \htmlData{symbol=gate}{a_t}=\sigma(s_t),\qquad \tilde v_t=a_t v_t.$$

这里 \(\sigma(s)=1/(1+e^{-s})\in(0,1)\)，用一个标量同时缩放整条 value 向量。和注意力不同，这里不需要对着整张大表做 softmax——要读哪几行早就由哈希锁死了，门控只负责“按上下文拧阀门”。先做 RMSNorm 再点积，则是把 \(h_t\) 和 \(k_t\) 的模长对齐，避免某个分支幅值变大直接把 sigmoid 顶饱和。

拿一个二维例子算一下就直观了：取单位向量 \(h=[\cos\theta,\sin\theta]\)、\(k=[1,0]\)，\(v=[1,2]\)，设 RMSNorm 的 gain 为 1、\(\epsilon=0\)。二维单位向量的均方根是 \(1/\sqrt2\)，除以它之后长度变成 \(\sqrt2\)，所以归一化点积 \(s=\sqrt2\cos\theta\)。方向一致（\(\theta=0^\circ\)）时门值约 0.804，正交（\(90^\circ\)）时正好是 0.5，完全反向（\(180^\circ\)）时压到 0.196，最终写入残差的增量就是这三个系数去乘 \([1,2]\)。

复现时有个容易踩的细节：官方演示代码在送进 sigmoid 之前，对归一化点积多做了一步 \(\operatorname{sign}(s)\sqrt{\max(|s|,10^{-6})}\) 变换——它会把接近 0 的小 logit 拉开、把绝对值大的 logit 压平（同向二维算例里门值会从 0.80443 降到 0.76660）。对齐代码或做算子移植时，别忘了连同这步变换、RMSNorm 的归约精度以及 \(\epsilon\) 和 gain 一起对清楚。

如果主干用了多路残差（比如 mHC），Engram 也能自然接进去：所有分支共享查表向量 \(e_t\) 和 value 投影 \(W_V\)，只为每条分支保留独立的 key 投影 \(W_K^{(b)}\) 和标量门。这样查一次表、算一次 value，每条残差流却能按各自的上下文独立决定吃多少记忆。实现上可以把共享的 \(W_V\) 和各分支的 \(W_K^{(b)}\) 拼成一次大矩阵乘，免得一堆小 GEMM 吃不满 GPU 算力。

短卷积与流式状态

门控算完 \(\tilde v_t\) 后，Engram 并没有立刻加回残差流，而是再接了一层轻量的 depthwise causal convolution，沿时间维把附近位置的记忆再揉一次，进一步扩大局部感受野。每个通道 \(c\) 各自做独立卷积：

$$z_{t,c}=\sum_{j=0}^{w-1}A_{j,c}\,R(\tilde v_{t-j\delta})_c, \qquad y_t=\tilde v_t+\operatorname{SiLU}(z_t),\qquad h_t\leftarrow h_t+y_t.$$

其中 \(w\) 是卷积核宽度，\(\delta\) 是空洞步长（dilation），\(j=0\) 对应当前位置，序列开头之前补零。原论文取 \(w=4\)，并把空洞步长设成最大 n-gram 阶数 \(\delta=N\)。拿 \(N=3\) 来说，算位置 \(t\) 时卷积要回头读 \(t,\ t-3,\ t-6,\ t-9\) 四个点——换句话说，单步解码必须把最近 \((w-1)\delta = 9\) 步的卷积输入留着。

这就给推理引擎添了两份必须跨步维护的局部状态：哈希寻址要留最近 \(N-1\) 个 canonical ID，短卷积要留最近 \((w-1)\delta\) 个归一化后的门控 value。从 chunked prefill 切到 decode、或者长 prompt 分块进卡时，这两份状态必须严丝合缝地接上；只要偷懒在每个 chunk 开头重新零填充，块首的 n-gram 哈希和卷积输出就会同时算歪。

写推理实现时，最省心的验收办法就是拿同一段序列跑三遍——整段一次算、逐 token 算、按不等长 chunk 切开算——逐位置核对哈希行号、门值和最终输出是否完全一致；再把两个请求交错着跑，确认状态按请求严格隔离、请求结束能干净释放，切块越界和卷积方向写反这类 bug 基本一次就能抓出来。

条件计算与条件记忆怎样分预算

MoE 和 Engram 走的都是“大总参、小激活”的稀疏路子，但激活后干的活完全不同：MoE 挑少数专家做上下文相关的非线性变换，花的是条件计算；Engram 挑少数表行直接读出可复用的局部模式，花的是条件记忆。

既然两者都在吃稀疏参数预算，问题就变成了一笔分配账。记 \(P_{tot}\) 为不含词表 embedding 和输出头的总参数，\(P_{act}\) 为每 token 的激活参数，剩下的稀疏参数池就是 \(P_{sparse}=P_{tot}-P_{act}\)。Engram 论文用一个比例 \(\rho\in[0,1]\) 来切这块蛋糕：

$$P_{\mathrm{MoE,inactive}}=\rho P_{sparse},\qquad P_{\mathrm{memory}}=(1-\rho)P_{sparse}.$$

\(\rho=1\) 就是纯 MoE；往回调低 \(\rho\)，相当于削掉一部分路由专家，把省出来的参数全部换成查表行数，同时尽量锁死激活 FLOPs。拿 \(P_{tot}=10\text{B}\)、\(P_{act}=1\text{B}\) 打个比方，\(\rho=0.8\) 时，9B 稀疏预算里分出 7.2B 给未激活专家，剩下 1.8B 建成记忆表。

论文在 5.7B 和 9.9B 两个总参数规模、各自固定训练 FLOPs 的条件下扫了一遍 \(\rho\)，验证损失走出了一条很明显的 U 形曲线：全给 MoE 或过度给查表都不是最优，谷底落在把约 20%–25% 的稀疏参数分给记忆的区间（\(\rho\approx 0.75\text{–}0.80\)）。背后逻辑很好理解——纯靠专家去硬记高频短语太浪费动态算力，而把专家砍得太狠又会伤到复杂推理，两类稀疏度互补而不是互相替代。

放回整个“外部局部记忆”谱系里看，最近三条路线各有取舍：OE（Over-Encoding）直接学 token 组合表，在输入端融合；SCONE 先单独训一个编码模型学高频 n-gram 表示，训练完离线算好整张表、推理时挂在卡外；Engram 则直接端到端训练多头哈希表，插在中间层用上下文门控按需吸收。三者表面上都在加参数，但账面成本落的地方不一样——SCONE 把开销前移到了离线编码和建表，OE 和 Engram 把记忆和主干一起训，而 Engram 又多花了一小笔中间层投影与门控计算来换取按语境过滤冲突的能力。

为什么插入位置会影响有效深度

Engram 该插在第几层，背后是一对很直接的权衡：插得太靠前，隐藏状态刚过一两层、还没攒够上下文，门控分辨多义词和哈希碰撞的能力会偏弱；可插得太靠后，前面十几层早就自己把局部短语拼完了，记忆表再送进去就成了马后炮。最划算的位置，往往落在“上下文刚好够做门控、又还来得及替后续层省力”的偏早中段。

省下来的前几层究竟算不算变相增加了有效深度，论文用了两个量来验证：一是直接把中间层隐藏状态接上最终 LM head，看它和最后一层输出分布的 KL 散度沿深度怎么下降（也就是著名的 logit lens 思路，看模型多早就进入“准备好预测”的状态）；二是在同一批样本上算不同模型各层表示的 CKA 相似度，看 Engram 的第 \(l\) 层对应基线模型的第几层。

结果在实体末尾 token 上非常直观：Engram 第 5 层的表示就已经和纯 MoE 基线的第 12 层差不多对齐。换句话说，原本要花前十几层注意力加 FFN 才能拼出来的静态实体特征，靠查表一步到位之后，后面十几层就可以腾出手去做真正的长程推理和组合。

顺着“深度如何被利用”这条线，还可以对照着看 Attention Residuals：残差连接改的是中间层的表示怎样被后层读取，条件记忆改的是一部分局部表示最初从哪儿来，两者改的是深度方向上的两个正交环节。

预取窗口怎样变成吞吐

查表有个非常讨喜的硬件特性：表总容量和单步流量彻底解耦。一张 100B 参数的 BF16 记忆表足有 200 GB，单卡 HBM 根本塞不下；但每个 token 真正要读的行数是固定的。沿用前面的配置——bigram 和 trigram 各 4 个头、每行 128 个 BF16 元素——每个 token 只读 \(8\times 128\times 2 = 2048\text{ B}\)。哪怕一个 batch 进来 512 个新 token，总共也就搬 1 MiB 数据，表再扩十倍这个数也不变。

这就让把整张大表直接卸到主机内存（host DRAM）变得很划算：推理开始、拿到 token ID 的瞬间，CPU 就立刻算哈希、把这一步需要的行 gather 出来走 PCIe 发给 GPU；与此同时，GPU 照常跑 Engram 之前的那些 Transformer block。真正拖慢整条流水线的，只有传输盖不住的那一小截：

$$t_{fetch}=t_0+\frac{B_{fetch}}{\beta},\qquad \htmlData{symbol=stall}{t_{stall}}=\max(0,t_{fetch}-t_{before}).$$

这里 \(t_0\) 是调度、主机侧 gather 和 DMA 启动的固定开销，\(B_{fetch}\) 是本步要搬的字节数，\(\beta\) 是有效 PCIe 带宽，\(t_{before}\) 则是前面所有前置 block 拼出来的计算掩护窗口。

按默认参数算一遍：512 个 token、插在第 4 个 block，取数耗时 \(8 + 1{,}048{,}576 / (25\times 10^9)\times 10^6 \approx 49.94\ \mu\text{s}\)，前面 3 个 block 给出的掩护窗口是 \(45\ \mu\text{s}\)，所以 GPU 只需要干等约 \(4.94\ \mu\text{s}\)。只要往后挪一层插到第 5 个 block，前置窗口涨到 \(60\ \mu\text{s}\)，传输延迟就被彻底藏掉了。

落到真实系统里还有两件事会改写这个账本：一是 batch 变大时，传输字节和前置层的计算时间都在涨，谁涨得更快取决于当时卡在算力还是带宽；二是热点行留在 HBM 缓存里之后，实际走 PCIe 的字节会少一大块。调预取节奏本身也是个平衡——发得太晚会直接暴露 GPU 空等，一股脑把后面所有 Engram 层的向量提前拉进显存又会吃掉大量临时缓冲，所以通常按插层距离限死在途的预取深度，并用 timeline 盯住 gather、DMA 和 GPU wait 到底重叠了多少。

论文里给了个实测锚点：在 H800 上跑 512 条序列（长度在 100–1024 token 间均匀分布），把一张 100B 参数、完全放在 host DRAM 里的大表插进 4B 和 8B 稠密主干的第 2 个 block，实测最大吞吐损失也只有约 2.8%。插到这么靠前的位置都能把大部分传输藏掉，靠的就是前面说的确定性寻址。

从模块正确到系统有效

训练和推理对待这张大表的方式完全相反。训练时表行要持续收梯度、做更新，通常按行切到多张卡上，靠 all-to-all 把激活行拉过来、反向再把梯度送回去；到了推理阶段，表权重彻底冻结，自然语言的 Zipf 分布马上就派上用场了——把高频短语对应的热点行留在 HBM 缓存里，长尾行扔进 host DRAM，大表负责撑容量，缓存负责挡掉重复的 PCIe 流量。评估这套缓存时记得按实际省下来的读出字节算命中率，而不是按行计数，因为冷热行在不同请求间的复用率差得很远。

如果要把 Engram 真正接进自己的模型栈，拆成三关来过最不容易踩坑：第一关锁死数值与状态契约——确认 canonical 映射表固定、门控公式（到底带不带 signed-sqrt）与归约精度对齐、整段和分块流式输出逐位一致；第二关在相同主干与 FLOPs 预算下做受控消融，先把表长、阶数、插层位置和 \(\rho\) 扫出收益曲线；最后一关才接上真实服务负载压测吞吐、P99 延迟和峰值显存，看 PCIe 预取窗口在自己的机器拓扑上能不能真把表藏住。

计算与诊断

1. 手算门值与写入量

二维场景下取 \(h=[0,1]\)、\(k=[1,0]\)、\(v=[1,2]\)，RMSNorm 的 gain 为 1、\(\epsilon=0\)。按论文公式算门值 \(a\) 和短卷积前的残差输出 \(h+av\)；再把 \(h\) 换成 \([1,0]\) 重算一遍。

展开解答

正交时 \(h^\top k=0\)，归一化点积 \(s=0\)，门值 \(a=\sigma(0)=0.5\)，写入增量为 \([0.5,\ 1]\)，残差输出为 \([0.5,\ 2]\)。换成同向 \([1,0]\) 后，两个向量归一化后长度均为 \(\sqrt2\)，所以 \(s=\sqrt2\)、\(a\approx 0.80443\)，写入增量为 \([0.80443,\ 1.60886]\)，残差输出约 \([1.80443,\ 1.60886]\)。

2. 表容量与每步流量

一张 100B 参数的 BF16 记忆表，最大阶数 3、每阶 4 个头、每行 128 维。整张表占多少 GB？如果忽略缓存和重复行去重，512 个 token 这一步要搬多少 MiB？

展开解答

总容量是 \(100\times 10^9\times 2 = 200\text{ GB}\)。每个 token 跨 bigram 和 trigram 一共读 \(2\times 4 = 8\) 行，即 \(8\times 128\times 2 = 2048\text{ B}\)；512 个 token 合计 \(1{,}048{,}576\text{ B}\)，正好 \(1\text{ MiB}\)。前者决定表放不下 HBM、得去 host DRAM，后者决定 PCIe 搬运只要几十微秒。

3. 最早能藏住传输的插入层

单步要搬 2 MiB，有效带宽 25 GB/s，固定开销 8 μs，每个前置 block 计算耗时 15 μs。假设输入确定就立刻发起预取，最早插在第几个 block 才能把取数完全藏住？

展开解答

总取数时间约 \(8 + 2{,}097{,}152/(25\times 10^9)\times 10^6 \approx 91.89\ \mu\text{s}\)。要盖住它至少需要 \(\lceil 91.89 / 15 \rceil = 7\) 个前置 block，所以最早插在第 8 个 block。如果为了效果想往更早的层挪，办法只有三条：压低单步读出字节、靠热点缓存挡掉一部分流量，或者把 PCIe 有效带宽拉上去。

4. 切块后块首输出对不上

配置为最大阶数 \(N=3\)，短卷积 \(w=4\)、\(\delta=3\)。整段算出来没问题，切成两个 chunk 后第二块开头几个位置偏了。跨块到底要留哪些状态？怎么快速定位是哈希坏了还是卷积坏了？

展开解答

跨块要留两样东西：上一块最后 2 个 canonical ID（供 n-gram 拼接），以及最后 9 个归一化后的门控 value（供空洞卷积回头读）。排查时按数据流切一刀最快：先核对第二块开头每个位置的哈希行号，行号就对不上，直接查 ID 缓存和左侧 padding；行号、\(k\)、\(v\)、门值全一致再往下看卷积输入，以及 \(t-3\)、\(t-6\)、\(t-9\) 三个偏移有没有越界或方向写反。多请求并发时，还要顺手确认两份状态是不是按请求 ID 独立存的。

核对门控、流式更新和预取

想把上面的公式和边界条件亲手跑一遍，可以下载配套的 NumPy 脚本，直接执行 python3 lab.py --seed 7。脚本只依赖 NumPy，一口气把四件事全验了：用有限差分校对带 RMSNorm 门控的解析梯度、对比论文门与官方 demo 的 signed-sqrt 变换、检验整段与分块流式下的后缀哈希和空洞因果卷积是否逐位对齐，以及复算一遍前面的容量和预取等待算例。

默认参数跑通后，能看到同向二维门值约 0.80443、官方 demo 变换后约 0.76660；分块与整段卷积的最大误差在浮点精度内（\(\lt 10^{-14}\)），而脚本里故意清零块间历史的反例会立刻触发边界偏差；预取算例则会复现第 4 个 block 的 4.94 μs 等待，以及 2 MiB 读出最早在第 8 个 block 被藏住。也可以把 --chunk 7 换成任意正整数再跑，流式结果都应该和整段完全一致。
