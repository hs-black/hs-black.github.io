GEMM：从三重循环到 Tensor Core

一个乘加很简单；难的是让同一份数据被反复使用。

先固定三个轴：M、N、K

A[M,K] × B[K,N] → C[M,N]

M 是输出行数，N 是输出列数，K 是求和长度。一个 C[i,j] 由 A 的第 i 行与 B 的第 j 列点积得到。

LLM 线性层常把本次 token 数放在 M，输入 hidden size 放在 K，输出 hidden size 放在 N。

先修：张量布局与 stride、Roofline。以下先算 C=AB，不读取旧 C。

GPU 工程 · 从地址到计算

三重循环已经给出了正确答案

for i in range(M):
    for j in range(N):
        acc = 0.0
        for k in range(K):
            acc += A[i, k] * B[k, j]
        C[i, j] = acc

i、j 之间可以并行；同一个输出的 K 项必须正确累加。实际 kernel 会把多个输出组成 tile，并让线程协作搬运输入。

沿 K 前进，每一步增加一张外积

A=[[1,2],[3,4]]，B=[[5,6],[7,8]]。先取 k=0，再取 k=1；C 的四项一起增长。

数值为教学示例；拖动时间轴观察变化。

一次 FMA 按 2 FLOPs 计

FLOPs ≈ 2 × M × N × K

每个输出做 K 次乘法和 K 次累计。数学上从首项直接初始化可写成 K 次乘法、K−1 次加法；性能账本通常按每次 FMA=2 统一计数。

M=N=K=4096 → 137,438,953,472 FLOPs ≈ 137.439 GFLOP

这里 1 GFLOP = 10⁹ 次浮点运算；不要与 GiB 的二进制单位混用。

朴素实现浪费在哪里？

若每个 C[i,j] 都独自读取一行 A 与一列 B，且忽略 cache 复用：

输入读取元素 = 2MNK；输出写入元素 = MN
FP32 算术强度 ≈ 2MNK / (8MNK+4MN) → 0.25 FLOP/byte

A[i,k] 本可给 N 个输出复用，B[k,j] 本可给 M 个输出复用。分块就是让这些复用在片上发生。

这是无 cache 复用的教学流量模型；真实 naive kernel 可能已经受益于 cache 与广播。

把每个输入只读一次，会是什么上界？

最少逻辑字节 = s(MK + KN + MN)

s 是输入、输出相同 dtype 的 byte 数；假设 β=0，不读取旧 C。BF16 的 s=2。

4096³：字节 = 96 MiB；AI = 1365.33 FLOP/byte

这个 AI 是理想数据复用的整矩阵账本。矩阵超过片上容量、不同 block 重读输入时，实际 HBM 字节会增加。

同一权重，M 改变了复用机会

BF16，N=K=4096M=1（单 token）M=2048
计算量33.55 MFLOP68.72 GFLOP
理想读写量约 32.02 MiB64 MiB
理想 AI约 1 FLOP/byte1024 FLOP/byte

M=1 时读来一大块权重，只服务一行输出。M 增大后，同一权重能服务更多 token。

这解释了 batch 对线性层的意义；整模型的 attention、KV cache 与调度还要另外记账。

GPU 工程 · 从地址到计算

tile 的宽高决定复用，BK 决定分段

一段计算：2 BM·BN·BK FLOPs
一段输入：s(BM·BK + BK·BN) byte
AI输入 = 2 BM·BN / [s(BM+BN)]

BF16，BM=BN=64：32 FLOP/byte。BK 在这个比值里消掉了；增大 BK 仍会影响流水、循环开销和片上容量。

此处只计一段 A/B 输入。完整 tile 还需写 C；跨 block 的 L2 复用也不包含在内。

双缓冲先算 shared memory 容量

读下一段时计算当前段，需要同时存两份 A/B tile；以下仅算 operand 缓冲。

SMEM = stages × (BM·BK + BK·BN) × s
BF16，stages=264×64×32128×128×64
单段 A+B8 KiB32 KiB
双缓冲16 KiB64 KiB

还需给 padding、barrier、epilogue 等留空间。真正占用以编译器报告和目标 GPU 限额为准。

GPU 工程 · 从地址到计算

输出累加器也要住在片上

FP32 accumulator 容量 = BM × BN × 4 byte

64×64 输出 tile 需要 16 KiB。若平均分给 128 个线程，光 accumulator 就是每线程 32 个 32-bit 寄存器。

128×128 输出 tile 需要 64 KiB；同样 128 线程时变成每线程 128 个寄存器，还没算地址、临时值与输入 fragments。

这是均匀分配的容量估计。实际 register fragment 布局与寄存器数由编译结果决定。

GPU 工程 · 从地址到计算

tile 越大，为什么可能越慢？

教学硬件预算：每个 SM 可分配 96 KiB shared memory。若一个 block 使用 64 KiB，仅按此资源就最多驻留一个 block。

block 上限 ≤ floor(96 / 64) = 1

换成 16 KiB 并不保证能驻留 6 个：寄存器、线程数、block 数限制也可能先到。

大 tile 提高复用；小 tile 提供更多并行任务。选择取决于形状、资源和流水，不能只优化一个 AI 数值。

HBM/L2 → shared memory → register / MMA operand → 计算。下一段输入到达时，C accumulator 继续累加。

Tensor Core 执行小矩阵乘加

D = A_fragment × B_fragment + C_fragment

把标量 FMA 换成矩阵指令后，线程协作提交一组 fragments；仍需 kernel 负责搬运、布局、同步和输出。

warp 级指令

如 mma.sync / WMMA：参与线程必须按指令要求共同执行，不能让任意一个 lane 单独算完整 tile。

更大协作组

某些架构有 warp-group MMA 与异步机制。协作范围和合法布局取决于具体指令。

合法 tile 与数据格式是接口的一部分

指令支持的 M/N/K 片段大小、dtype、地址对齐与 register 排列都有约束。应用矩阵不必是这些大小的整数倍，尾部可以补零并屏蔽写回。

Triton 的 tl.dot 描述矩阵乘加，编译器根据后端、形状和 dtype 选择实现。要确认是否用了 Tensor Core，查看编译代码与 profiler。

本实验用 FP16 输入、FP32 accumulator；不把“调用 tl.dot”直接等同于“达到峰值吞吐”。

GPU 工程 · 从地址到计算

累加用 FP32，也不能恢复输入已经丢失的位

FP16 / BF16 输入在进入乘法前已被舍入。FP32 accumulator 减少长 K 累计误差，但不会恢复原输入精度。

reference = FP32(A) @ FP32(B)

先固定已经量化到输入 dtype 的 A、B，再用较高精度参考检查 kernel。比较绝对误差与相对误差，特别观察接近 0 的输出。

若使用 FP32 输入的 Tensor Core 路径，还需要显式了解 TF32 等精度模式；不把不同精度模式当作同一实验。

一个 program 负责一个输出 tile

pid_m = program_id(0)；pid_n = program_id(1)
rows = pid_m * BM + arange(BM)
cols = pid_n * BN + arange(BN)
grid = (ceil(M/BM), ceil(N/BN))

所有 program 覆盖不同的 C tile；每个 program 沿 K 扫完整个求和维度，避免多个 program 写同一个输出。

GPU 工程 · 从地址到计算

地址计算继承真实 stride

A_ptrs = A + rows[:, None]*stride_am + ks[None, :]*stride_ak
B_ptrs = B + ks[:, None]*stride_bk + cols[None, :]*stride_bn

A tile 是 [BM,BK]，B tile 是 [BK,BN]。广播仅构造地址网格，不是复制原矩阵。

使用真实 stride，才能接收转置 view；更多细节见 张量布局。

逐步算一遍

7×9×5 的矩阵，4×4×4 tile 如何收尾？

最后一个 program 覆盖 rows 4…7、cols 8…11；第二个 K 段覆盖 k 4…7。有效范围之外加载 0，输出只写合法位置。

数值为教学示例；拖动时间轴观察变化。

GPU 工程 · 从地址到计算

输入 mask 与输出 mask 各管一件事

a = load(A_ptrs, mask=(rows < M) & (ks < K), other=0)
b = load(B_ptrs, mask=(ks < K) & (cols < N), other=0)
acc += dot(a, b)
store(C_ptrs, acc, mask=(rows < M) & (cols < N))

输入补零防止越界并保持数学结果；输出 mask 防止把 padding 部分写进其他内存。

只 mask store 不够：错误的 load 仍可能越界或把垃圾值带进有效输出。

program 顺序还能改变 L2 复用

相邻输出 tile 若共享 A 的行块或 B 的列块，后执行的 block 可能从 L2 命中刚刚用过的输入。

按行连续遍历

一行内反复使用同一 A 行块；B 列块的复用距离可能较长。

按小组遍历

在若干 M tile 与 N tile 间交错推进，缩短部分 operand 的复用距离。

这是地址到 program ID 的映射选择；block 实际调度不保证严格顺序，收益依赖 cache 与任务形状。

GPU 工程 · 从地址到计算

M、N 太小，K 很大时怎么办？

只有少数 C tile 时，很多 SM 无事可做。Split-K 把 K 拆给多个 program，各自算部分和，再归约。

C = Σₛ C_partial,s

并行度提高，却新增 partial 输出、归约和调度成本；归约顺序也会改变浮点舍入。

先确认瓶颈是任务数量不足，再考虑 Split-K。大矩阵本来已有足够 C tile 时，额外归约可能得不偿失。

GPU 工程 · 从地址到计算

把 bias 和激活留在写回之前

若先写 C，再启动 kernel 读取 C、加 bias、做激活，就多出一次完整 C 的读和写。

可避免的中间流量 ≈ 2 × M × N × s

M=2048、N=4096、BF16：中间 C 是 16 MiB，融合可避免约 32 MiB 逻辑读写。最终输出仍需写回。

融合也会增加寄存器与代码复杂度。必须比较融合后的整体时间，而不是只数少了几个 kernel。

把 FLOPs 和 byte 换成时间下界

教学设备预算：可用计算吞吐 100 TFLOP/s，带宽 1 TB/s。计算 4096³ 的 BF16 GEMM，采用理想 96 MiB 流量。

T计算 ≥ 137.439 GFLOP / 100 TFLOP/s = 1.374 ms
T搬运 ≥ 100.663 MB / 1 TB/s = 0.101 ms

理想重叠下，下界是 max(两者)=1.374 ms；不是二者相加，也不是实际 kernel 必然达到的时间。

若真实流量更多、并行不足或利用率低，下界需要重新估计。

练习 1

算术强度会随 BK 无限增长吗？

BF16 tile 为 BM=64、BN=64、BK=32。求单段 FLOPs、A+B 输入 byte 数与 AI。BK 改成 64 后，这三个值如何变化？
展开参考解答

原始 FLOPs=2×64×64×32=262144；输入=(64×32+32×64)×2=8192 byte；AI=32 FLOP/byte。

BK 翻倍，FLOPs 与输入 byte 同时翻倍，AI 仍为 32。片上容量和流水开销却会变化；此处不含 C 写回。

练习 2

这块输出会吃掉多少片上空间？

BF16 tile 128×128×64，operand 双缓冲，FP32 accumulator。求 SMEM 和 accumulator 容量；若 128 个线程均分 accumulator，每线程至少多少个 32-bit 寄存器？
展开参考解答

SMEM=2×(128×64+64×128)×2=65536 byte=64 KiB；accumulator=128×128×4=64 KiB。

平均每线程 16384/128=128 个 32-bit accumulator 寄存器。地址、输入 fragments 等还会额外占用，实际以编译报告为准。

练习 3

尾块有哪些位置必须屏蔽？

M=7、N=9、K=5；BM=BN=BK=4。最后一个输出 program、最后一个 K 段中，A、B 各有多少有效元素？输出能写几个元素？
展开参考解答

rows=4,5,6,7，仅前 3 行有效；cols=8,9,10,11，仅第 1 列有效；ks=4,5,6,7，仅 k=4 有效。

A 有 3×1=3 项，B 有 1×1=1 项，其他输入补 0；输出可写 3×1=3 项。最后写出的值包含之前所有 K 段的累计。

练习 4

少读一次中间结果，能省多少？

C=[2048,4096]，BF16。分离的 bias+激活 kernel 读取并覆盖整个 C；融合到 GEMM epilogue 可以避免多少逻辑字节？能因此断言快一倍吗？
展开参考解答

C 大小=2048×4096×2=16777216 byte=16 MiB。避免一次读和一次写，共 32 MiB；最终输出写回仍存在。

不能断言倍速。还需考虑 GEMM 主计算、bias 读取、融合资源开销、cache 与 launch 时间；用完整路径计时验证。
