GEMM：从三重循环到 Tensor Core

交互2026-10-20更新于 2026-10-22

一个线性层 \(C=AB\) 的数学表达式只有三个字母，GPU 却要决定几千个线程怎样分工、每块输入从哪里读、累加结果放在哪。理解 GEMM 优化，可以从一张输出小块出发：它需要哪些 A、B 元素，这些元素能在片上用几次，又需要多少存储来保留正在计算的结果。

三重循环给出计算与复用关系

设 \(A\in\mathbb R^{\htmlData{symbol=m}{M}\times\htmlData{symbol=k}{K}}\)，\(B\in\mathbb R^{\htmlData{symbol=k}{K}\times\htmlData{symbol=n}{N}}\)，输出 \(C\) 为 \(M\times N\)。M 是输出行数，N 是输出列数，K 是累加维度。每个元素按同一条规则计算：

$$C_{ij}=\sum_{q=0}^{K-1}A_{iq}B_{qj}.$$

固定 q 时，A 的一列乘 B 的一行，得到一张 \(M\times N\) 的外积。沿 K 累加这些外积，就形成最终输出。每个乘加按 2 FLOPs 计，总工作量约为 \(2MNK\)。这也解释了复用：一个 \(A_{iq}\) 可以服务 N 个输出，一个 \(B_{qj}\) 可以服务 M 个输出。

先建立字节账本

朴素实现为每个输出加载 K 对输入。若输入元素占 b 字节，逻辑加载量约为 \(2MNKb\) 字节，按此计算的算术强度接近 \(1/b\) FLOP/B；BF16 输入时是 0.5 FLOP/B。实际 HBM 流量还由 L1/L2 命中率决定。显式分块则把多个输出需要的同一份输入放进片上存储，主动控制复用。

理想情况下，每个输入只读一次、输出只写一次，总流量为 \(b(MK+KN+MN)\)，对应强度

$$I_{\rm ideal}=\frac{2MNK}{b(MK+KN+MN)}.$$

BF16 的 4096 立方矩阵乘约有 137.44 GFLOP，最低流量为 96 MiB，理想强度约 1365 FLOP/B。将 M 减到 1，权重矩阵几乎只服务一条输入，强度就大幅下降。Prefill 与 decode 使用同一权重，却可能处于不同的性能区域。

Tile 把复用放进片上存储

一个 thread block 或 Triton program 负责 \(B_M\times B_N\) 个输出，沿 K 每次推进 \(B_K\)。一个 stage 读入 \(B_M B_K+B_K B_N\) 个元素，完成 \(2B_MB_NB_K\) FLOPs。忽略输出写回时，它的输入强度为

$$I_{\rm tile}=\frac{2B_MB_N}{b(B_M+B_N)}.$$

这里 K 的分块长度约掉了。增加 \(B_M,B_N\) 会增加输入在 tile 内被使用的次数；增加 \(B_K\) 主要改变每轮搬运大小、循环次数和流水线资源。BF16 的 64×64×32 tile，每 stage 读 8 KiB，做 262144 FLOPs，强度为 32 FLOP/B。

双缓冲让下一轮输入加载与当前计算重叠。64×64×32 的两份 BF16 输入缓冲共 16 KiB，FP32 输出累加器另需 16 KiB。扩大到 128×128 会让累加器变成 64 KiB，这些寄存器分散在参与计算的线程中。资源用量决定一个 SM 能同时驻留多少 block；tile 较大时，复用增加与并行度下降需要一起权衡。

把资源预算换成驻留数量

假设一个 SM 可用于该 kernel 的 shared memory 预算为 96 KiB，每个 block 的输入缓冲为 32 KiB，那么仅这一项最多允许三个 block 同时驻留。若累加器和临时变量让每个 block 消耗过多寄存器，实际驻留数量还会更低。占用率由 shared memory、寄存器、线程和 block 数限制共同决定，可以逐项取上限的最小值。

继续看 128×64 的输出 tile：8192 个 FP32 累加值至少需要 32 KiB 寄存器容量。假设均分给 256 线程，每线程仅累加值就需 32 个 32-bit 寄存器；加入输入片段、地址和循环临时值后，总需求可能明显更高。把 tile 某一边翻倍时，要同时预测这部分资源与 program 数的变化，再从编译结果核对。

多 stage 流水线通常让一组线程提前搬入后续输入，计算线程消费当前 stage。每个缓冲 stage 都有“加载完成”和“消费完成”两个边界：前者允许计算开始，后者允许覆盖旧数据。增加 stage 可以覆盖更长的搬运延迟，但缓冲占用线性增加；当现有 stage 已足以覆盖延迟，再增加深度可能只减少驻留 block。

Tensor Core 怎样参与

Thread block 的输出 tile 会继续拆给 warp 或 warp group，再拆成硬件支持的矩阵乘加形状。Tensor Core 指令对输入类型、布局、对齐和 tile 形状有明确要求。编译器或库把逻辑矩阵整理成这些指令可接收的片段，执行小矩阵乘加，并把部分和保留在寄存器累加器中。

FP16/BF16 输入配 FP32 累加能降低长归约中的累积误差，输入在量化时丢失的精度仍会影响乘积。验证 kernel 时应固定输入、累加和输出的精度约定，分别观察绝对误差与相对误差。对接近零的参考值，相对误差会放大，用混合容差判断更合适。

尾块、stride 与写回

输入 shape 很少恰好被 tile 整除。以 M=7、N=9、K=5，tile=4×4×4 为例，输出方向需要 \(2\times3=6\) 个 program，K 方向需要两轮。最后一轮 K 只有一个有效位置，多出的输入位置填零；输出最后一个 tile 只有 3 行、1 列有效。加载 mask 保护输入并提供正确的乘法零元，写回 mask 保护输出边界。

rows = pid_m * BM + tl.arange(0, BM)
cols = pid_n * BN + tl.arange(0, BN)
ks = block_k * BK + tl.arange(0, BK)
a = tl.load(A + rows[:, None]*sa0 + ks[None, :]*sa1,
            (rows[:, None] < M) & (ks[None, :] < K), other=0.)
b = tl.load(B + ks[:, None]*sb0 + cols[None, :]*sb1,
            (ks[:, None] < K) & (cols[None, :] < N), other=0.)
acc += tl.dot(a, b)

地址里的 sa0,sa1,sb0,sb1 来自真实 stride。只验证连续输入，很容易漏掉转置权重或切片激活的寻址错误。把 7×9×5、1×13×7 等形状加入测试，可以同时检查三条轴的尾部。

从 program 编号定位输出

最简单的二维 grid 大小为 \((\lceil M/B_M\rceil,\lceil N/B_N\rceil)\)。编号 \((p_m,p_n)\) 对应输出左上角 \((p_mB_M,p_nB_N)\)，每个 program 的 acc 从零开始，循环遍历所有 K 块。循环结束后，把 acc[r,c] 写到 C+(p_m*BM+r)*sc0+(p_n*BN+c)*sc1，并按真实 M、N 屏蔽尾部。

一个常见地址错误是把 A、B 的 stride 与逻辑轴位置混淆。A 的第二轴对应 K，B 的第一轴对应 K；若 B 来自转置权重，其 K stride 与 N stride 可能与连续矩阵相反。先用很小的整数矩阵验证每个 tile 的输入，再对照外积累加结果，能把寻址错误和归约错误分开。

FP32 累加器的初始值、输出转换和 epilogue 顺序也属于接口。若实现 \(C=\alpha AB+\beta C_{old}\)，还必须读取旧 C，原来的单次写回字节账本需要增加这次读取。将 bias、激活融合进去时，确认其广播轴与 dtype，并用具有不同列偏置的输入测试，避免所有常数恰好相同而掩盖轴错误。

复用之外，还要让 GPU 有活可做

输出 program 数约为 \(\lceil M/B_M\rceil\lceil N/B_N\rceil\)。M、N 很小而 K 很大时，少数 program 可能无法填满所有 SM。Split-K 把 K 分给更多 program，产生多个部分输出，再归约合并；它换来并行度，也增加临时存储、写读和归约开销。应在输出并行度不足的形状上比较这笔交换。

Program 的访问顺序也会影响 L2。沿 M 方向分组访问，可以让相邻 program 在 B tile 仍留在缓存时重复使用它。另一方面，bias、激活等逐元素运算适合接在累加器写回之前，减少 C 的中间写读。例如 BF16 的 4096×4096 输出，每消除一次完整读写就减少 64 MiB 流量。

大 tile 反而慢，怎样查

先把形状、dtype、stride、输出精度和 epilogue 固定，再对照吞吐变化。如果大 tile 仅在小矩阵上慢，计算输出 program 数，查看是否缺少并行任务；如果大矩阵也慢，检查 registers/thread、shared memory、occupancy 和 local-memory 流量。出现 spill 时，把累加器或流水线深度缩小，观察时间是否恢复。

若只有非整除形状变慢，计算有效工作占填充工作的比例。上述 7×9×5 例子有效 FMA 为 315，六个输出 tile、两轮 K 共执行 \(6\times2\times4^3=768\) 个 tile FMA，利用率约 41%。这个比例解释了小形状的填充成本，也提示 autotune 需要覆盖实际服务的形状分布。

性能实验先热身，再使用 CUDA event 包围重复调用，并与同样精度的库实现比较。报告应同时记录设备、软件版本、M/N/K、stride、是否包含转换和输出分配。这样一次更快的 kernel 才能转化成可复现的线性层收益。

误差与性能的交叉检查

Split-K 改变求和分组，浮点结果会受加法顺序影响。可以先用 FP64 的小规模参考确认索引与数学正确，再在目标输入 dtype 下设定基于误差分布的容差。把 K 逐步增大，观察绝对误差是否平滑增长；若误差只在某个 tile 边界突然出现，优先检查 mask 和部分和归约。

针对真实模型建立形状集合时，应同时收集 M、N、K 和 stride。大量 token 的 prefill、小 batch decode、不同 expert 的小 GEMM，可能各自偏好不同配置。一个 autotune winner 应在代表性形状分布上评估总成本，必要时保留按形状选择的多个实现。

练习与实验

1. BK 翻倍

BF16，BM=BN=64，把 BK 从 32 改为 64。单 stage 输入强度与输入容量分别怎样变化？

展开解答

强度都为 \(2\times64^2/[2(64+64)]=32\) FLOP/B。单 stage 输入从 8 KiB 变为 16 KiB；双缓冲从 16 KiB 变为 32 KiB。

2. 累加器账本

输出 tile=128×64，用 FP32 累加。累加器总容量是多少？若平均分到 256 线程，每线程至少保存多少个累加值？

展开解答

共有 8192 个 FP32，容量 32 KiB；每线程平均 32 个 FP32 值。寄存器还要容纳输入片段、指针和循环状态。

3. 尾部 mask

M=7、N=9、K=5，tile=4×4×4。最后一个输出 tile 和最后一个 K tile 各有多少有效元素？

展开解答

最后输出 tile 位于行 4–7、列 8–11，有效输出为 3×1。最后 K tile 为 4–7，只有 K=4 有效；这一轮 A 有 3×1 个有效输入，B 有 1×1 个。

4. 融合省多少字节

BF16 的 4096×4096 输出先写回，再由独立 bias kernel 读写。融合 bias 可减少多少流量？

展开解答

中间输出为 32 MiB；融合消除其中一次写回及下一次读取，共减少 64 MiB。最终输出写回仍然需要保留。
