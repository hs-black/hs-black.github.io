推理压测与 SLO：测出真正可用的容量

交互2026-10-20更新于 2026-10-22

一个服务每秒生成 1000 个 token，用户仍可能等上几秒才看到第一句话。另一个服务吞吐稍低，却能让绝大多数请求及时开始、平稳输出。决定交互体验的是请求经历的时间线；决定能接多少用户的是在这些时限内完成的工作量。

压测需要同时控制输入和观察结果：谁在什么时候发来多长的 prompt，期望生成多少 token；服务何时接收、何时产生第一个输出、后续输出怎样到达。把这些时刻保存下来，batch、缓存和并行配置的变化才有可解释的含义。

1. 先给时间戳一个明确的起点

用 \(a\) 表示客户端实际提交请求的时刻，\(t_1\) 表示第一个输出 token 到达客户端，\(t_O\) 表示最后一个输出 token 到达；\(\htmlData{symbol=output}{O}\) 是实际输出 token 数。于是首 token 延迟为 \(TTFT=t_1-a\)，完整请求延迟为 \(E2E=t_O-a\)。后续每个相邻输出间隔是 \(ITL_i=t_i-t_{i-1}\)。

$$TPOT=\frac{t_O-t_1}{O-1}=\frac{1}{O-1}\sum_{i=2}^{O}ITL_i\qquad(O\ge2).$$

TPOT 是一条请求内的平均输出间隔。当请求只输出一个 token，TPOT 没有定义，应单独标记。ITL 则能呈现中途的停顿。例如输出在 180、210、240、420 ms 到达，ITL 为 30、30、180 ms，TPOT 为 80 ms；最后的 180 ms 停顿会被平均值压低。

流式 HTTP 的一次回调可能携带多个 token，也可能是空的协议事件。需要按所用接口的 token 计数规则处理内容，明确记录的是 token 到达还是文本 chunk 到达。代理缓冲、网络合并和客户端事件循环阻塞都可能让输出集中抵达；服务端每步平稳，并不自动保证客户端看到同样的节奏。

2. 请求率和并发数控制的是不同的负载

开放负载按预定时刻产生请求，即使前面的请求尚未完成也继续到达。可以使用固定间隔、泊松到达，或生产 trace。它适合测给定需求下是否发生积压。封闭负载维持固定数量的客户端：一条请求结束后，客户端才发下一条。它适合观察一定并发量下能完成多少工作。

封闭负载自带反馈。服务变慢时，每个客户端更晚发送下一条，总到达率随之下降。一个 500 ms 的停顿，会让开放负载继续积累请求，封闭负载却会暂时减少新工作。如果只把封闭负载的延迟当作固定请求率下的表现，就会漏掉本该排在后面的用户。

稳定系统满足 Little 定律：

$$\htmlData{symbol=inflight}{L}=\htmlData{symbol=rate}{\lambda}\,\htmlData{symbol=duration}{W}.$$

这里 \(L\) 是平均在途请求数，\(\lambda\) 是长期完成速率（请求/s），\(W\) 是平均 E2E（秒）。目标 15 req/s、平均请求耗时 2 s，就需要平均 30 个在途请求。若客户端只允许 20 个，固定这个平均耗时下能提供的速率约为 10 req/s。容量规划还要为长尾和突发留出余量。

当服务需求稳定在每请求 100 ms，单 worker 上限为 10 req/s。把开放到达率调到 12 req/s，吞吐逐渐靠近 10，而队列持续增长。真实 LLM 的服务时间随 batch、上下文和调度而变；可以用同样的时间戳方法测出它的服务曲线。

3. 客户端也有队列

给请求再记录两个时刻：计划到达 \(a_{plan}\) 与实际发出 \(a_{send}\)。若并发 semaphore、连接池或客户端 CPU 使发送延后，这段延迟是 \(d_{client}=a_{send}-a_{plan}\)。用户需求视角的首字等待为

$$TTFT_{plan}=(t_1-a_{send})+(a_{send}-a_{plan}).$$

实践中可以同时保存“从发送开始”的网络/服务延迟，以及“从计划开始”的整体延迟。针对带并发上限的 benchmark，检查版本中的计时器在哪里启动：若启动点位于 semaphore 之后，报告就会省略此前等待。vLLM 的公开问题记录提供了固定服务时间 mock server 的复现方式；这种小服务很适合验证压测器本身的时间戳语义。

观察到“输出更长，TTFT 反而下降”时，也要先固定到达过程。固定并发下，输出变长会让旧请求更晚离开，新增 prefill 的到达节奏一起改变。再检查 prefix cache 命中、warmup 与输入分布，才能把负载变化和引擎性能变化分开。

4. 将时限写成逐请求的通过条件

设观测窗口长度为 \(\Delta\) 秒。成功吞吐是成功完成数除以 \(\Delta\)；输出吞吐是这些请求实际产生的 token 总数除以 \(\Delta\)。如果服务要求 TTFT ≤1 s、TPOT ≤50 ms，那么请求同时成功且满足这两个条件，才计入 goodput：

$$G=\frac{1}{\Delta}\sum_j \mathbf1[\mathrm{success}_j\land TTFT_j\le1\mathrm{s}\land TPOT_j\le50\mathrm{ms}].$$

这里 \(j\) 是请求编号，\(G\) 单位为合格请求/s。若业务还约束最大 ITL 或完整请求截止时间，就把对应条件加入同一个指示函数。单 token 输出只检查适用的时限。

在 60 s 窗口里，配置 A 成功 900 条、达标 810 条，吞吐为 15 req/s、goodput 为 13.5 req/s；配置 B 成功 1080 条、达标 648 条，吞吐为 18 req/s、goodput 为 10.8 req/s。对于这个交互目标，A 提供了更多可用服务。

分母也要固定。有限 trace 的“最后完成减首次到达”包含启动和排空；稳态吞吐通常在稳定时间窗内统计完成数。请求跨越边界时，要明确延迟统计按到达队列还是完成队列收集。失败、超时、主动取消及尚未完成的请求应保留计数，避免最慢的请求从结果里消失。

5. 尾延迟的样本单位决定结论

每条请求贡献一个 TTFT 和至多一个 TPOT；长请求会贡献许多 ITL。因此，对全部 ITL 求 p99，会让长请求按间隔数量获得更大权重；对每条请求的 TPOT 求 p99，则让每条请求各占一个样本。两者回答的体验问题不同，报告需要写明采样单位。

分位数要由合并后的原始样本或兼容的 histogram 计算。98 个 10 ms 与 2 个 100 ms 合并后，nearest-rank p99 取排序第 99 项，是 100 ms。分别计算两组的 p99 再平均，会得到 55 ms，失去原来分布的意义。

样本量也影响稳定性。只有 100 条请求时，p99 接近最慢几条；重复相同 trace 或增加独立样本，可以观察结果是否由一次初始化或罕见长请求主导。比较版本时保留分布、样本数和失败率，最好保存逐请求明细供复算。

6. 一次可复现的容量扫描

首先固定模型 revision、tokenizer/chat template、输入输出长度分布、采样参数和请求 trace。Cache 冷热决定 prefill 工作量：冷缓存测试每次保持不同前缀，热缓存测试记录可复用前缀及命中率。输出长度应以实际生成数计量；EOS 与输出上限共同决定请求何时结束。

然后在低负载验证输出正确、流式时间戳与错误统计。单独运行 warmup，让编译、权重加载、graph capture 和连接建立完成。冷启动本身若属于服务目标，就单列冷启动场景。压测客户端与服务器分开记录 CPU、网络和发送延迟，确认客户端能够持续产生所要求的负载。

最后逐步提高请求率，固定同一组 SLO，画出成功吞吐、goodput、p99 TTFT、p99 ITL 与 KV 峰值。队列增长时，继续增加并发通常会增大等待。先识别限制来自计算、KV 容量、调度预算还是输入端，再改变一个参数比较结果。

观测组合优先检查的证据可比较的调整
TTFT 上升，ITL 稳定prefill 排队、长 prompt 比例、cache missprefill token 预算、路由、chunk 大小
TTFT 与 ITL 同时恶化总体过载、长 prefill 干扰、KV 抢占与重算降低准入、调整 chunked prefill、扩副本
服务器 token 规律，客户端成批到达代理缓冲、连接池、事件循环与反序列化耗时直连与代理对照、客户端分片
仅首轮慢或重复请求越来越快编译/graph、冷热连接、prefix 命中分别报告冷、热状态，统一 warmup

实验记录应包含 GPU 型号与数量、互联、软件版本、TP/PP/DP、batch token budget、max sequences、prefix cache、编译和 graph 配置。预测“减小 chunk 会改善 ITL，但可能推迟长 prompt 的 TTFT”，再检查曲线，这样一次没有加速的实验也能解释系统。

7. 计算、排错与 CPU 实验

练习 1：输出流中的尖峰

请求 0 ms 提交，四个 token 在 [180,210,240,420] ms 到达。求 TTFT、TPOT、最大 ITL。TTFT ≤200 ms、TPOT ≤60 ms 时是否计入 goodput？

展开解答

TTFT 为 180 ms；三个 ITL 为 30、30、180 ms；TPOT 为 \((420-180)/3=80\) ms，最大 ITL 为 180 ms。TPOT 超过门槛，该请求未同时达标。

练习 2：平均并发需求

目标吞吐 15 req/s，平均 E2E 为 2 s，客户端最多 20 个在途请求。求所需平均并发及当前并发限制下的吞吐估计。

展开解答

平均在途数 \(L=15\times2=30\)。若平均耗时保持 2 s，20 个在途请求支持约 10 req/s。提高并发后要重新测量 W，因为新增排队可能继续增加平均耗时。

练习 3：吞吐和 goodput 分开算

同样 60 s，A 成功 900 条且 810 条达标；B 成功 1080 条且 648 条达标。求成功吞吐、goodput 与成功请求中的达标率。

展开解答

A 为 15 req/s、13.5 合格 req/s、90%；B 为 18 req/s、10.8 合格 req/s、60%。如果另有失败，还应使用总提交数计算整体成功率和整体达标率。

练习 4：合并 p99

A 组有 98 个 10 ms 间隔，B 组有 2 个 100 ms 间隔。按 nearest-rank 计算各组 p99、平均后的 p99 与全部样本的 p99。

展开解答

两组分别为 10 和 100 ms，平均得到 55 ms。全部 100 个样本中，第 99 个是 100 ms，所以合并 p99 为 100 ms。合并 histogram 时还要保持同一桶边界与采样单位。

下载 lab.py，Python 3 标准库即可运行。实验使用 60 个请求、100 ms 固定服务时间与 FCFS 队列：

python3 lab.py
# throughput=8.027 req/s; goodput=8.027 req/s
# p99_TTFT=40.000 ms
python3 lab.py --rate 12
# throughput=10.000 req/s; goodput=1.667 req/s
# p99_TTFT=1023.333 ms
python3 lab.py --arrival open --stall-ms 500 --json
python3 lab.py --arrival closed --stall-ms 500

先预测一次 500 ms 停顿会影响哪些后续请求，再比较开放和封闭负载的输出。实验带有手算时间戳、失败计数和分位数检查。扩展时可以加入客户端 semaphore，分别记录计划与发送时间，复现客户端排队导致的统计差异。
