KV cache 压缩：把历史装得更小

同样一段历史，能不能用更少的字节记住？

先数清楚，缓存里有什么

一个标准 KV cache：层 × token × KV head × head dimension × 数值字节数。

每个小格代表一份 KV。长上下文、更多并发、更多层，都会让这些格子继续堆起来。

沿 head 轴做共享：GQA / MQA 减少每个 token 的 KV 头数。

沿表示或 token 轴做压缩，再降低每个数的精度。不同方法省的是不同的一维。

动画图解 LLM 系统

GQA：几个 Q，共用一组 K、V

Q 的头数保持不变，K、V 的头数减少。

左侧 8 个 query heads 原本各有一组 K、V，缓存需要保存 8 份。

把 query heads 分成两组，每组 4 个 Q 共用一组 K、V。KV 头数从 8 变成 2。

MQA 再走一步：所有 Q 共用一组 KV。不同 Q 仍会产生不同 attention 权重与输出。

8 / 2 / 1 为结构示意；GQA / MQA 是模型结构选择，通常需要训练或 uptraining。

MLA：把多头 KV 存成低维 latent

多个头的内容可以先压进一小条联合表示 c，再用于 attention。

标准多头缓存直接存展开的 K、V。MLA 为每个 token 缓存低维 latent c。

内容路径由 c 提供多个头需要的 K、V 信息；推理中可通过矩阵乘法结合律，把部分上投影吸收到其他权重中。

位置路径单独保存用于 RoPE 的 key。缓存由“内容 latent + 位置 key”组成；长度仍然随 token 数增长。

示意结构来自 DeepSeek-V2 的 MLA；实际尺寸与权重吸收方式由架构决定。

少存 token：合并，或淘汰

头数和维度都不变时，还能减少历史位置的数量。

一开始保存每个位置。越靠右越新，旧位置仍占着完整的 KV 空间。

合并：把一组 token 表示汇成一个摘要。位置变少，但摘要要承载这组内容。

淘汰：只保留被选中的 KV，例如重要历史加最近窗口；未来若要用到被丢弃的细节，就无法直接读取它。

动画只展示两种操作；实际策略可能按层、头、query 或累积 attention 得分选择。

量化：位置都留着，每个数更短

用低位整数和少量 scale 元数据近似原来的 K、V。

BF16 的每个数占 16 bit。降低位宽，就能让同一段历史少搬一些字节。

按组量化：x 大致表示为 s × (q − z)。把浮点数映射到有限整数等级，并保存 scale 等元数据。

attention kernel 读取后反量化，或使用支持低位数据的计算路径。压缩比例还要扣除元数据、残差区和对齐开销。

4 bit 为示意；KIVI 对 K 按通道、对 V 按 token 分组，以适应不同的离群值分布。

把节省落实到字节数

以一个假想模型为例：32 层、8192 token、32 个 KV 头、head dim 128。

BF16 缓存：2 × 32 × 8192 × 32 × 128 × 2 = 4 GiB，每条序列一份。

换成 8 个 KV 头的 GQA，其他维度不变：4 GiB ÷ 4 = 1 GiB。

再把数值编码从 16 bit 降到 4 bit：纯载荷降至 0.25 GiB。实际占用还要加量化元数据等开销。

算术示例；模型需匹配相应的 GQA 结构与量化方案。

怎么判断压得是否值得？

先量准确性

在自己的长上下文、代码、检索任务上比较输出。尤其检查远距离细节、多轮对话和罕见实体。

再量系统收益

看峰值 KV 占用、可用并发、prefill 延迟和 decode 延迟。压得更小不自动等于端到端更快。

定位误差来源

头共享改变模型容量；位置压缩改变可见细节；低位量化改变数值。分别做消融，才知道瓶颈在哪。

让 kernel 接住收益

紧凑布局、融合反量化、合适的 block 大小，才能把字节减少兑现成带宽节省。
