KV cache 压缩：把历史装得更小

交互2026-10-20更新于 2026-10-22

一条长请求占用的显存，常常逐渐从模型权重转向 KV cache。32 层、8 个 KV 头、每头 128 维、BF16 的模型，每保存一个位置就增加 128 KiB；8192 个位置是一条请求 1 GiB，32 条这样的请求就是 32 GiB。

缓存压缩可以从几个不同维度入手：让多个 query 共享 KV 头，把多头表示写入低维 latent，合并或淘汰位置，以及降低每个元素的存储位宽。先把这些维度写进同一份容量公式，再判断每种方法需要模型训练、缓存管理和 kernel 分别做哪些工作。

一份历史的四个容量因素

普通 GQA 的缓存容量为：

$$M_{KV}=2\,L\,H_{kv}\,S\,\htmlData{symbol=head-dim}{d}\,\htmlData{symbol=bytes}{b_e}.$$

其中 \(L\) 是层数，\(H_{kv}\) 是每层 KV 头数，\(S\) 是已保存位置数，\(d\) 是每头维度，\(b_e\) 是每元素字节数。系数 2 对应 key 和 value 两份。同长度的 \(B\) 条请求再乘以 \(B\)；长度不同时，对各请求的 \(S\) 求和。

GQA 减少 \(H_{kv}\)，位置淘汰减少 \(S\)，数值量化减少 \(b_e\)。MLA 则用另一种状态形状替代两份多头张量。模型架构决定可以采用哪些表示；缓存实现决定这些表示是否按紧凑布局实际保存。

GQA 与 MLA 怎样减少状态

GQA 让 \(H_q\) 个 query 头共享 \(H_{kv}\) 个 KV 头，每组大小 \(G=H_q/H_{kv}\)。例如 32 个 query 头共享 8 个 KV 头，KV 元素数降为 MHA 的 1/4。计算输出时，各 query 仍有自己的分数和加权和。Kernel 若在一组 query 之间复用同一份 K/V，还能把容量收益转成更少的读取。

MLA 把每个位置的 K/V 内容共同压入 \(d_c\) 维 latent：\(c_j=W^{DKV}h_j\)，再由各头的矩阵恢复内容 key/value。内容点积可以调整结合顺序：

$$q_i^\top W_i^{UK}c_j=\big((W_i^{UK})^\top q_i\big)^\top c_j.$$

先把 query 投影到 latent 空间，就能直接读取缓存里的 \(c_j\)。Value 的上投影也可与输出投影结合。带位置的部分单独保存为 \(d_R\) 维 key，因而每层每位置缓存元素数是 \(d_c+d_R\)。具体执行路径还要匹配 prefill、decode、分片和 kernel 的成本。

以 \(d_c=512,d_R=64\) 为例，每位置每层保存 576 个元素。对照 8 个 KV 头、每头 128 维的 GQA，元素数是 \(2\times8\times128=2048\)，比例为 \(2048/576\approx3.56\)。若使用 BF16、32 层和 8192 个位置，GQA 是 1 GiB，latent 缓存为 288 MiB。

把一组数映射到整数码

对称 INT4 量化的一种常见窄范围约定是使用整数码 −7 到 7。给一组实数选择 scale \(s=\max|x|/7\)，然后存储 \(q=\operatorname{clip}(\operatorname{round}(x/s),-7,7)\)，读取时重构 \(\hat x=sq\)。这里 round 取最近整数，恰好处在中点时取偶数。在没有裁剪的范围内，每个元素的舍入误差最多约为 \(s/2\)。

取精确 scale \(1/7\)，整数码为 [−7,−1,2,7]，重构为 [−1,−1/7,2/7,1]，最大误差为 \(2/35\approx0.05714\)。K 和 V 的误差进入不同路径：K 误差先改变 logits，V 误差直接改变加权内容。

$$\Delta s_j=\frac{q^\top\Delta k_j}{\sqrt d},\qquad \Delta a\approx\big(\operatorname{diag}(a)-aa^\top\big)\Delta s,\qquad \Delta y_V=\sum_j a_j\Delta v_j.$$

这里 \(a\) 是原始 attention 权重，\(\Delta y_V\) 固定这些权重，仅观察 V 误差。对 K-only、V-only 和联合量化分别测试，能看清当前任务主要受哪条误差路径影响。

实际位宽还包括 scale 和残差区

若每 \(g\) 个元素共享一个 2 B scale 和一个 2 B zero-point，INT4 的平均存储为 \(0.5+4/g\) B/元素。\(g=64\) 时是 0.5625 B，较 BF16 的压缩倍数约为 3.56。最后一组不足 \(g\) 个元素时仍要保存一组元数据；底层布局还可能加入对齐填充。

近期 token 常保留为高精度 residual 区，积累到合适粒度后再量化。设总长度 \(S\)，近期高精度长度 \(R\)，普通 GQA 维度仍为 \(L,H_{kv},d\)，预算可写为：

$$M=2LH_{kv}d\left[(S-R)\left(0.5+\frac4g\right)+2R\right].$$

上图默认 \(g=64,R=128\)，旧缓存约 283.5 MiB，近期缓存 16 MiB，总计 299.5 MiB，较原来的 1024 MiB 压缩约 3.42 倍。减小分组能更细地适应局部数值范围，但元数据和反量化工作会随之增加。

为什么 K 和 V 适合不同分组

若某个 K 通道持续出现大值，把同一 token 的全部通道放进一组，会让这个大通道拉大整个组的 scale，小通道只能使用很粗的刻度。按通道沿历史位置分组，可以把不同通道的范围分开。V 的分布与使用方式不同，按 token 分组往往更方便保留当前位置的内容结构；最终选择应结合模型的离群分布和 kernel 布局。

可以构造一个具有固定离群通道的 K 张量，分别进行按 token 与按通道分组。先比较 K 重构误差，再用相同 query 检查 logits 和最终输出。误差较小的存储布局还需要匹配批量读取、scale 寻址和解码路径，才能同时得到数值与性能收益。

量化组的轴还决定增量写入方式。按时间轴组成一个 K 组时，新 token 到来可能让最后一个组继续增长；组的最大值变化后，scale 和已有整数码需要一起更新。近期高精度区域可以把这类频繁重写推迟到组满时完成。按 token 的 V 组通常在写入时就拥有该位置的全部通道，比较容易一次确定 scale。

对分页缓存，量化组、物理页和 kernel tile 是三个粒度。若组跨越物理页，scale 的归属和尾部回收会更复杂；若每页独立量化，最后一组可能有填充。选择粒度时可以先列出一页的整数码字节、scale 数量、尾组元素数，再检查一次 attention tile 会读取多少页和多少份元数据。这样的布局预算能把“数学压缩率”接到真实显存访问上。

合并和淘汰位置需要未来查询的假设

窗口模型可以在规定的可见范围之外释放 K/V。内容选择模型则需要评估未来 query 是否仍会需要那些位置。一次查询读取得少，说明的是这次读取集合；决定永久删除时，需要额外的保留或恢复策略。

位置合并还会改变 attention 的位置语义。两个 key 分别经过不同 RoPE 角度旋转，合并后的向量对应怎样的逻辑位置、代表怎样的概率质量，都需要在算法中定义。评估时可以先做远距离数字检索、多轮指代和顺序任务，再看整体语言指标。这样能区分量化造成的小数值偏差与历史信息真正丢失的影响。

容量收益怎样转成推理收益

长上下文 decode 常受 KV 读取带宽限制，压缩后少搬的数据可能覆盖解码成本。短上下文时，量化、元数据寻址和反量化的固定开销占比更高。沿上下文长度和 batch 大小扫描，在相同权重、请求集合与输出长度下比较峰值显存、step 时间和输出误差，能找到压缩开始划算的区间。

高效路径在消费每个 tile 时读取整数码与 scale，反量化后直接参与 attention。若先把全部历史展开成完整 BF16 临时张量，峰值内存和额外带宽会吞掉部分收益。Profiler 中要观察反量化输出的生命周期，以及量化后的缓存是否仍被另一份高精度副本长期持有。

Residual 管理也需要按实际新增长度做预算。单 token decode 每次增加 1，chunked prefill 一次可能增加几百个位置；量化触发条件应计算“原 residual 长度 + 本次输入长度”。构造跨阈值的 chunk，逐次记录量化区与高精度区的长度及峰值内存，可以验证 flush 粒度和显存上界。

还可以估算压缩的带宽回本点。设原始 KV 读取量为 1 GiB，压缩后为 0.3 GiB，有效带宽为 1 TB/s，理想节省约 0.75 ms。若新增解码与管理开销为 0.2 ms，这部分 attention 有机会净省约 0.55 ms；同样开销放到仅 64 MiB 的短历史上，节省量可能不足以抵偿。把同一路径实测的有效带宽和新增耗时代入，就能得到对应负载下的回本判断。

质量实验也应覆盖缓存的生命周期。先量化一个固定前缀，然后让后续 query 逐步变化，观察早期 key 的小误差会不会在新的查询方向上被放大。多轮聊天、长文引用和精确数字提取适合暴露这种差异。再固定请求与随机种子，逐项比较 K-only、V-only、组大小和 residual 长度，让一次变化对应一个可解释的原因。

预算与质量练习

1. 4 bit 实际压缩多少

1,048,576 个元素，BF16；INT4 每 64 个元素存 4 B 元数据。量化后多少 KiB，压缩几倍？

展开解答

整数码占 512 KiB，元数据占 64 KiB，总计 576 KiB。原来是 2048 KiB，比例为 2048/576≈3.56。

2. Latent 状态容量

32 层、8192 个位置、BF16，latent 512 维加位置 key 64 维。缓存多少 MiB？

展开解答

每层每位置保存 512+64=576 个 BF16 元素，占 1152 B。32 层、8192 个位置共有 262,144 份状态，乘以每份的字节数，合计 301,989,888 B，即 288 MiB。

3. 当前读取与长期保存

一个动态选择器每步只读取 10% 的历史。需要什么额外条件，才可以释放另外 90% 的缓存？

展开解答

需要证明未来查询的可见性规则会永久排除这些位置，或提供恢复、重算、压缩替代等机制。固定滑动窗口有明确的淘汰边界；内容相关选择需要进一步的保留策略与质量评估。

同时检查误差与字节

下载 NumPy 实验并运行 python3 lab.py --seed 7 --group 32。它检查 INT4 舍入界，分别测量 K-only、V-only 输出误差，并核对 576 KiB 元数据算例与 299.5 MiB residual 算例。将 group 改为 16、64，比较误差；实验中的整数码使用 int8 保存以便观察，容量计算按两个 INT4 打包进一个字节的布局进行。
