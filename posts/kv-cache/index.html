KV cache：记住已经算过的历史

交互2026-10-20更新于 2026-10-22

模型已经读完一段 8000 token 的提示词，生成了第一个新 token。为了生成第二个，它需要再把前面 8000 个位置都跑一遍吗？如果每次都这样做，越长的对话就会积累越多重复工作。KV cache 的出发点很直接：找出下一步仍然需要、而且数值不会变化的结果，把它留下来。

这个想法同时带来两个后果。旧 token 的投影和前向计算可以省掉，生成会快很多；留下来的结果却要占用显存，而且新 query 仍需读取它们。因此，“有缓存”并不意味着不再处理历史。理解缓存的关键，是分清不必再算什么、仍然要读什么、什么时候又要多存一份。

1. 先算清楚一行 attention

假设我们只看一个 attention 层、一个头。位置 \(t\) 的 hidden state 经过三组投影，得到 query \(q_t\)、key \(k_t\) 和 value \(v_t\)。Query 用来询问“哪些历史位置与现在有关”；key 提供匹配用的向量；value 提供被加权汇总的内容。三者都是有 \(d\) 个分量的向量。

当前 query 与允许读取的每个 key 做点积。因果模型在位置 \(t\) 只能读取编号 \(0\) 到 \(t\) 的位置，所以包含自己。先把点积除以头维度的平方根，得到分数，再用 softmax 归一化：

$$z_{t,j}=\frac{\htmlData{symbol=q}{q_t}^{\mathsf T}\htmlData{symbol=k}{k_j}}{\sqrt{\htmlData{symbol=d}{d}}},\qquad a_{t,j}=\frac{e^{z_{t,j}}}{\sum_{r=0}^{t}e^{z_{t,r}}},\qquad 0\le j\le t.$$

\(q_t\) 是当前位置的 query，\(k_j\) 是历史位置 \(j\) 的 key；\(d\) 是每个头的向量维度。\(a_{t,j}\) 是位置 \(j\) 的注意力权重，同一行权重的和为 1。

随后用这一行权重混合 value。输出仍然是一个 \(d\) 维向量：

$$o_t=\sum_{j=0}^{t}a_{t,j}\htmlData{symbol=v}{v_j}.$$

为方便手算，把 value 暂时看成标量。三个位置的已缩放分数为 \([0,\ln2,\ln3]\)，value 为 \([2,4,8]\)。取指数得到 \([1,2,3]\)，总和为 6，所以权重是 \([1/6,2/6,3/6]\)。最后输出 \(2/6+8/6+24/6=17/3\approx5.667\)。向量 value 的计算完全一样，只是对每个分量都做这次加权求和。

注意这次计算读取了什么：一个当前 query、一排历史 key、一排历史 value。历史位置当时发出的 query 并没有出现在公式里。它已经完成了自己的任务，后来的 token 不需要再用它来提问。这就是缓存 K、V 而通常不缓存 Q 的直接原因。

2. 旧 K/V 为什么不会变

“后面还要用”只说明值得缓存，还不足以说明缓存正确。另一个必要条件是：追加新 token 后，已有 K/V 必须与重新计算的结果相同。因果 attention 给了我们这个条件。

先看第一层。位置 2 的输入来自它自己的 token embedding 和位置编码；attention 只能读位置 0、1、2。后来追加位置 3，不会进入位置 2 的可见范围，因此位置 2 的输出不变。第二层收到的旧位置输入也就不变，它产生的旧 K/V 同样不变。沿着层数继续推，所有层的旧位置都成立。逐 token 的 RMSNorm、MLP 和残差相加也不会让未来 token 反过来修改历史。

因此，已有前缀的每层 K/V 可以原样复用。新的 token 只需要计算自己的 hidden state、Q/K/V 和每层输出；它的 query 去读已保存的历史，然后把自己的 K/V 留给下一步。只要权重、输入前缀、位置编码和可见性规则一致，缓存路径应当与完整前向得到相同的结果，允许浮点运算顺序造成的小误差。

这也告诉我们什么时候要使缓存失效。修改第 100 个 token，不仅改变这一位置的 K/V，还会影响其后所有能看见它的位置；不能只替换一个槽位。切换 adapter、改变 RoPE 的频率配置，或换一套 attention mask，也可能改变缓存的含义。服务端的 prefix cache 因而需要识别“同一段计算”，不能只比较一串表面相同的文本。

一个可执行的判断：固定一段输入，将最后一个 token 改掉。正确的因果前向中，之前所有位置的输出都应该不变。如果这个检查失败，先检查未来位置是否被 mask，缓存优化还不应该开始。

3. Prefill、decode 与待消费的 token

缓存保存模型已经处理过的输入位置所对应的 K/V。刚采样出的 token 会成为下一轮的输入，经过前向后才写入缓存。因此，输出长度和缓存长度之间有一个需要显式记录的时间差。

例如提示词有三个 token，编号为 0、1、2。Prefill 把它们一起送入模型：第一层并行计算三个位置，在因果 mask 下做 attention，并保存第一层的 K/V；第二层再处理第一层输出，保存第二层的 K/V。层与层仍然有依赖，不能因为位置并行就认为所有层同时执行。

全部层完成后，最后一个 prompt 位置产生 logits。采样器从 logits 选出第一个新 token，记为 \(y_0\)。这时缓存仍然只有 prompt 的三个位置。下一次前向才把 \(y_0\) 作为输入，使用绝对位置 3，算出并追加它的 K/V；随后得到预测 \(y_1\) 的 logits。

Prefill 一次处理很多已知 token，线性层能在矩阵乘中复用权重；decode 每条请求通常只带来一个新输入。新的输出又决定下一轮输入，所以单条请求的这些 decode 步骤串行发生。增加 batch 可以让不同请求在同一轮并行推进。

如果 prompt 长度为 \(P_0\)，最终生成 \(O\ge1\) 个输出，而且最后一个输出产生后立刻结束，那么最多有 \(P_0+O-1\) 个位置参与前向、写入 KV。最后采样出的那个 token 不必再被消费。容量准入也可以保守地按 \(P_0+O\) 预留，但统计“已用缓存长度”时应数已经处理的输入，不能直接拿已生成 token 数代替。

4. 从一条序列到 GQA batch

单头的公式很清楚，真正实现时却必须知道每条轴代表什么。设本轮有 \(B\) 条请求，每条输入 \(C\) 个新 token，模型 hidden size 为 \(D\)。输入张量便是 \(X\in\mathbb R^{B\times C\times D}\)。这里 \(C\) 是本次输入的长度；普通 decode 中 \(C=1\)。

Query 有 \(H_q\) 个头，缓存的 key/value 各有 \(H_{kv}\) 个头，每头维度为 \(d\)。先做投影，再拆出头这一维：

$$W_Q\in\mathbb R^{D\times H_qd},\qquad W_K,W_V\in\mathbb R^{D\times H_{kv}d}.$$
张量按 batch、位置、头、分量排列含义
输入 \(X\)\([B,C,D]\)本轮新输入
\(Q\)\([B,C,H_q,d]\)本轮的 query
新 \(K,V\)各 \([B,C,H_{kv},d]\)本轮要追加的 K/V
追加后的 cache各 \([B,P+C,H_{kv},d]\)\(P\) 个旧位置加 \(C\) 个新位置

\(B\)：请求数；\(C\)：本次新输入长度；\(P\)：调用前已有缓存长度；\(D\)：模型宽度；\(H_q,H_{kv}\)：query 与 KV 头数；\(d\)：每头维度。不同实现会交换轴顺序，元素总数不变。

这里假设 query、key 和 value 的每头维度相同。模型常取 \(D=H_qd\)，但投影的输入维度和输出维度在数学上可以不同；小实验采用不同的输入、输出宽度，reshape 由投影后的元素数决定。真正的模型配置还可能采用不同的 K/V 维度，应按各自形状计数。

在普通 MHA 中，query 和 KV 头一一对应，\(H_q=H_{kv}\)。GQA 让多个 query 头共享一组 K/V。例如 \(H_q=4,H_{kv}=2\)，query 头 0、1 读取 KV 头 0，query 头 2、3 读取 KV 头 1。共享的是 K/V 向量；每个 query 仍然计算自己的分数和权重。

$$\htmlData{symbol=g}{G}=\frac{\htmlData{symbol=hq}{H_q}}{\htmlData{symbol=hkv}{H_{kv}}},\qquad \operatorname{kvhead}(h)=\left\lfloor\frac{h}{G}\right\rfloor.$$

上式中 \(G\) 是每组 query 头的数量，\(h\) 是从 0 开始的 query 头编号，假设头按组连续排列且 \(H_q\) 能被 \(H_{kv}\) 整除。GQA 缓存保存 \(H_{kv}\) 份。参考代码用 repeat 展开头对应关系；高效 kernel 通过头索引直接复用底层 K/V。

把请求组成 batch 后，还有一个独立问题：各请求的历史长度往往不同。短请求为了矩阵布局而补出的槽位必须被 mask。零 key 与 query 的点积是 0，softmax 仍可能给它分配概率；对应的零 value 会稀释真实输出。将补齐位置的分数置为负无穷，才能使它的 softmax 权重归零。

5. 追加多个 token 时，位置与 mask 怎样对齐

缓存把一次完整前向拆成了多次调用，但没有重置序列的位置。已有 \(P=3\) 个位置时，新送入的两个 token 应使用位置 3、4。RoPE 要用正确的位置旋转 query 和 key；缓存里的 key 也必须与当前 query 使用同一套位置编码约定。

位置编码之外，还要构造正确的 causal mask。记本次 chunk 长度为 \(C\)，本次 query 的局部编号为 \(i\)，则它的绝对位置是 \(P+i\)。追加后共有 \(P+C\) 个 key，key 的全局编号为 \(j\)。允许读取的条件是：

$$\operatorname{allowed}[i,j]=\bigl(j\le \htmlData{symbol=p}{P}+i\bigr),\qquad 0\le i<\htmlData{symbol=c}{C},\quad 0\le j<P+C.$$

\(P\) 是调用前已经缓存的 token 数；\(C\) 是本次新增输入数；\(i\) 从本次 chunk 的 0 开始，\(j\) 从整段历史的 0 开始。比较之前必须把它们放到同一个坐标系。

取 \(P=3,C=2\)，query 长度为 2，key 长度为 5，所以 mask 是 \(2\times5\)。Query 3 可以看 key 0、1、2、3，不能看 key 4；query 4 则能看全部五个。两份新 K/V 可以一起算出、一起写入；causal mask 根据各 query 的绝对位置决定本行的可见范围。

物理地址还会带来第三套编号。例如滑动窗口只分配 4 个槽位，位置 5 可以写入槽位 \(5\bmod4=1\)，但它的 RoPE 位置仍然是 5。窗口里当前保存了哪些绝对位置，必须由缓存管理器记录。使用 PagedAttention 后，页表负责定位物理地址，RoPE 继续使用序列的绝对位置。

对不同长度的 batch，请求 A 可能已有 3 个位置，请求 B 只有 1 个。它们本轮新输入的位置、有效 key 长度和 mask 都要按请求计算。框架中用于表示当前位置的参数也不一定等于张量的物理长度，尤其在 padding、预分配或滑动窗口存在时，先检查 API 的具体语义。

6. 显存账本：一份历史有多大

容量可以直接从张量形状推出来。只看一条请求、一个已编码 token：每层存 \(H_{kv}\) 个 key 向量和 \(H_{kv}\) 个 value 向量，各有 \(d\) 个元素。若模型有 \(L\) 层，每个缓存元素占 \(b_e\) 字节，那么每个 token 的 KV 大小是：

$$m_{\mathrm{token}}=2\,\htmlData{symbol=l}{L}\,\htmlData{symbol=hkv}{H_{kv}}\,\htmlData{symbol=d}{d}\,\htmlData{symbol=bytes}{b_e}\quad\text{字节/token}.$$

这里 \(L\) 是层数，\(H_{kv}\) 是每层 KV 头数，\(d\) 是每头维度，\(b_e\) 是每个元素的字节数。前面的 2 表示 key、value 两份，已经计入公式，不应再次乘 2。

若有 \(B\) 条请求，每条已缓存 \(S\) 个位置，所需有效数据容量为：

$$M_{\mathrm{KV}}=\htmlData{symbol=b}{B}\,\htmlData{symbol=s}{S}\,m_{\mathrm{token}}=2BLSH_{kv}db_e.$$

这一处 \(B\) 是并发请求数，\(S\) 是每条请求的历史长度，单位是 token；它们分别沿请求轴和时间轴放大容量。不同请求长度为 \(S_r\) 时，用 \(\sum_r S_r\) 代替 \(BS\)。预分配空槽、分页尾部碎片和分配器开销还要另算。

取一个具体配置：32 层，8 个 KV 头，每头 128 维，缓存用 BF16，每元素 2 字节。计算得到

$$m_{\mathrm{token}}=2\times32\times8\times128\times2 =131072\ \mathrm{B}=128\ \mathrm{KiB}.$$

这里使用二进制单位：1 KiB = 1024 B，1 GiB = 2³⁰ B。一条 8192 token 的历史占 \(8192\times128\,\mathrm{KiB}=1\,\mathrm{GiB}\)。32 条同长度请求就是 32 GiB。若只把 query 头数从 32 增到 64，同时保持 8 个 KV 头，缓存大小不变；query 的计算量可能增加，但它不在这个存储公式里。若把 KV 头从 8 改为 32，其余不变，缓存才会扩大到四倍。

请求的上下文越长，KV cache 占用越大。可用于 KV 的预算应先从设备总容量中扣除权重、临时工作区、通信缓冲区和其他常驻内存。假设扣除后确实剩下 16 GiB，而每条请求都要保证可存 10240 个已编码位置，每条需要 1.25 GiB，按这一项预算最多容纳 \(\lfloor16/1.25\rfloor=12\) 条。

多卡也不能简单把整个缓存公式除以 GPU 数。若 KV 头被分片，每张卡保存较少的头；若某些 KV 头被复制，每张卡仍要为副本付出容量。先写出每张卡实际持有的 \(H_{kv}\) 和请求集合，再算本地缓存。这和 分布式推理 中“权重分片、激活复制、缓存复制”是同一个问题。

7. 缓存省计算，为什么还会越来越慢

缓存省掉了旧 token 的重新投影和整层前向，却没有从 attention 公式里删除旧位置。标准 dense attention 的一个新 query 仍需要与所有可见 key 做匹配，再按权重读取 value。所以缓存越长，一步 decode 要扫描的数据通常越多。

先估计计算量。对单层、单个 decode 输入，一条请求有 \(H_q\) 个 query 头，每个头读取 \(S\) 个历史位置，每个向量有 \(d\) 维。QK 点积约做 \(2H_qSd\) FLOPs，加权求和 V 再做约 \(2H_qSd\) FLOPs。每个乘加按 2 FLOPs 计，忽略 softmax 等较小项：

$$F_{\mathrm{attn}}\approx4\,\htmlData{symbol=b}{B}\,\htmlData{symbol=l}{L}\,\htmlData{symbol=hq}{H_q}\,\htmlData{symbol=s}{S}\,\htmlData{symbol=d}{d}.$$

\(B\) 是本轮解码请求数，\(L\) 是层数，\(H_q\) 是 query 头数，\(S\) 是每条历史长度，\(d\) 是头维度。这是计算量；刚才的显存公式则使用 KV 头数 \(H_{kv}\)。

再估计内存读取。若每份历史 K/V 从 HBM 读取一次，GQA 组内充分复用，忽略当前 Q 和少量输出，读字节数就接近 \(M_{\mathrm{KV}}\)。一轮的理想读取时间为：

$$T_{\mathrm{KV}}\gtrsim \frac{2BLS\,\htmlData{symbol=hkv}{H_{kv}}d\,\htmlData{symbol=bytes}{b_e}}{\htmlData{symbol=beta}{\beta}}.$$

分子里的 \(H_{kv}\) 是每层 KV 头数，\(b_e\) 是每个缓存元素的字节数；\(B,L,S,d\) 仍分别表示请求数、层数、历史长度和头维度。\(\beta\) 是用于这次读取的有效带宽，单位字节/秒。分子是这一轮要读的历史字节数，因此相除得到秒。缓存命中、kernel 的读取次数、访存布局和通信都会影响实际时间；这个估算首先帮助我们判断数量级。

沿用 128 KiB/token 的配置。8 条请求、每条 4096 token，共有 4 GiB 历史。把有效带宽设为 1 TiB/s 作为教学输入，则读一遍约需 \(4/1024\,\mathrm{s}=3.90625\,\mathrm{ms}\)。历史加倍而请求数不变，读取量也加倍。这个数还没有包括读模型权重、MLP、采样和调度的时间。

这说明了 batch 的一个不对称。线性层的权重可以被同轮多条请求复用；每条请求的 KV 历史却通常不同，batch 增加一条，就多一份要读的缓存。因此扩大 batch 能摊薄读权重的成本，却不会把每条请求的历史自动变成共享数据。GQA 通过减少 KV 头节省存储和读取；稀疏 attention 改变读哪些历史；KV 压缩 改变历史怎样表示。它们优化的是不同环节。

如果测到短上下文时很快，长上下文时每 token 延迟逐渐上升，可以先画出延迟与历史长度的关系，再对照缓存字节增长。如果连很短的上下文都出现大片 GPU 空隙，则应检查 CPU 提交、同步和调度。缓存账本给出一个可验证的解释，不应该代替时间线和实际测量。

8. 实现与排错：先比较数值，再讨论速度

一个容易检查的参考实现可以先用连续数组。每层接收本轮 hidden state 和旧缓存，计算本轮 Q/K/V，用绝对位置处理 RoPE，再追加 K/V，最后构造带历史偏移的 mask：

# x_new: [B, C, D]；旧缓存已有 P 个位置
q, k_new, v_new = project(x_new)
positions = P + arange(C)
q, k_new = rope(q, k_new, positions)
k = concatenate([k_cache, k_new], axis="time")
v = concatenate([v_cache, v_new], axis="time")
allowed = key_positions[None, :] <= positions[:, None]
y = attention(q, k, v, allowed)
return y, (k, v)

当前 token 的 K/V 必须在 attention 的可读集合里，因为因果注意力允许关注自己。处理完这一层后，输出再进入下一层；不能拿第一层的 K/V 供所有层共用。生产实现通常通过预分配或页表写入，避免每一步 concatenate 都复制整段历史，但地址优化不应该改变上述可见性和数值关系。

验证时保留一个独立的完整前向路径。对同一段随机输入，分别一次算完、逐 token 计算、按不同 chunk 长度计算，比较每个位置的 attention 输出或最终 logits。逐元素的数值误差可以暴露概率分布的变化；argmax 只能检查选中的 token 是否一致。

现象优先检查能区分问题的输入

接入 PyTorch SDPA 时，先检查 mask 的坐标

一种典型故障是：完整 prompt 的输出正常，接上 KV cache 后，后续位置开始重复或偏离。此时可以先用三个历史位置、两个新 query 做最小复现，直接打印 2×5 的布尔 mask。PyTorch 2.14 的 SDPA 在非方形矩阵上将 is_causal=True 对齐到左上角；缓存追加需要用 query 的绝对位置判断可见范围。

以单头张量为例，Q 的形状为 [1, 1, C, d]，K/V 为 [1, 1, P+C, d]。P 是旧缓存长度，C 是新输入长度。显式构造 mask 后，把它作为这次调用的完整可见性规则：

q_pos = P + torch.arange(C, device=q.device)
k_pos = torch.arange(P + C, device=q.device)
allowed = k_pos[None, :] <= q_pos[:, None]
y = torch.nn.functional.scaled_dot_product_attention(
    q, k, v, attn_mask=allowed,
    is_causal=False, dropout_p=0.0,
)

当 P=3、C=2，第一行允许位置 0～3，第二行允许位置 0～4。对于单 token decode，若 K/V 恰好包含全部有效历史和当前输入，整行都可见。不等长 batch 还需把每条请求的有效长度或 padding mask 与这条因果规则取交集。用相同输入对比显式 mask 路径和完整前向，可以把索引问题与 kernel 数值误差分开定位。

浮点精度也属于接口。先用 FP64 的小输入建立参考，再检查 FP32/BF16 的合理误差范围。训练时的 dropout 应关闭，参考与增量路径应使用相同权重和位置配置。如果一个实现路径把中间结果舍入得更频繁，微小差异可能正常；明显的、随位置规律增长的差异则常常是索引或 mask 错误。

9. 计算与排错练习

先写出判断，再展开解答。公式中使用的量会在每道题重新给出。

练习 1：容量够不够

模型有 32 层，每层 8 个 KV 头，每头 128 维，K/V 都用 BF16（2 B/元素）。已扣除权重和临时内存后，KV 预算为 16 GiB。若每条请求需要保证存下 10240 个已编码 token，最多能容纳几条？如果只把 query 头数从 32 改为 64，答案变吗？

展开参考解答

每 token 为 \(2\times32\times8\times128\times2=131072\) B，即 128 KiB。每条需要 \(10240\times128\,\mathrm{KiB}=1.25\,\mathrm{GiB}\)，所以最多 \(\lfloor16/1.25\rfloor=12\) 条。

只改变 query 头数不会改变这份 KV 账本，因为缓存仍然只有 8 个 KV 头。query 计算量和其他临时内存可能变化，但题目已把 KV 预算固定为 16 GiB。

练习 2：没有 shape 错误的错误 mask

已经缓存位置 0、1、2，本轮输入位置 3、4。写出正确的 2×5 布尔 mask。若所有有效分数相等，五个 value 为 [1,2,3,4,5]，两个 query 的输出各是多少？若误用局部下三角，又会是多少？

展开参考解答
正确：Q3 → [1, 1, 1, 1, 0]
      Q4 → [1, 1, 1, 1, 1]
错误：Q3 → [1, 0, 0, 0, 0]
      Q4 → [1, 1, 0, 0, 0]

等分数对应均匀权重。正确输出是 \((1+2+3+4)/4=2.5\) 和 \((1+2+3+4+5)/5=3\)。错误输出是 1 和 1.5。区别来自是否比较 \(j\le P+i\)，这里旧缓存长度 \(P=3\)。

练习 3：输出与缓存的交接时刻

prompt 长 5，要求生成 3 个输出 token。第一个输出由 prefill 末尾的 logits 采样产生；第三个输出产生后立即结束。总共执行几次 decode 前向？结束前缓存对应多少个已编码位置？

展开参考解答

第一个输出还没有自己的 KV。需要两次 decode 前向：消费第一个输出以预测第二个，再消费第二个输出以预测第三个。

写入缓存的位置数是 \(5+2=7\)，也就是 prompt 长度 + 输出数 − 1。第三个输出已交给用户，但不再送回模型。如果之后继续生成，才需要把它消费并追加到缓存。

练习 4：缓存读一次要多久

沿用每 token 128 KiB 的缓存配置。本轮有 8 条请求，每条已有 4096 个可见位置。假设历史 K/V 从 HBM 各读一次，有效带宽为 1 TiB/s。读取这些历史约需多久？历史变为 8192 时呢？

展开参考解答

总字节数是 \(8\times4096\times128\,\mathrm{KiB}=4\,\mathrm{GiB}\)。1 TiB/s = 1024 GiB/s，所以 \(4/1024\,\mathrm{s}=3.90625\,\mathrm{ms}\)。

历史加倍后，读取量为 8 GiB，对应 7.8125 ms。端到端耗时还包括权重读取、其他算子和调度。128 KiB/token 已包含 K、V 两份数据。

10. 运行 NumPy 实验

下载 lab.py。它实现单层 GQA 与 RoPE，保留完整前向、逐 token 和 chunk 三条执行路径。输入和权重用固定种子产生，不需要模型下载，也不需要 GPU。

python3 -m pip install "numpy>=1.24,<3"
python3 lab.py --seed 7 --chunk 3

正常输出应包含：

full vs token: PASS
full vs chunks: PASS
wrong mask detected: PASS
128 KiB/token; 8192 tokens = 1.000 GiB

最后一项容量计算使用 32 层、8 个 KV 头和 BF16；前面的正确性实验则使用更小的单层 FP64 张量。两者服务不同目的：小张量让每个索引都能检查，容量算例让显存量级接近实际模型。

先把 --chunk 改成 1、2、5、11，预测为什么结果应该不变，再运行验证。接着打开 incremental()，找到 positions = np.arange(start, end)，思考将它改为每块都从 0 开始会影响哪里。实验已主动构造一条错误 mask 路径并确认它与参考不同；你可以同样给错误 RoPE 位置增加一个检查。

最后把 qh 从 4 改为 8、保持 kh=2。query 头数会增加，K/V 缓存的元素数应保持不变。这一修改同时检验了 GQA 分组、投影形状和容量公式。完成这些数值检查后，再尝试预分配缓存，或进入 PagedAttention，把同一段逻辑历史放进不连续的物理页中。
