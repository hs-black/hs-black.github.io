综合实战

每层计算都能标出形状

张量单轮批处理形状
输入 X[B, 32]
Q / K / V[B, 4, 8] / 各 [B, 2, 8]
拼接后的历史 K/V各 [B, Tmax, 2, 8]
Attention 分数[B, 4, Tmax]
输出 logits[B, 64]

B 是本轮请求数；Tmax 是这轮最长历史。短请求的 padding 必须被 mask。

综合实战

一个 decoder block 的顺序

z = RMSNorm(x)
q, k, v = project(z)
q, k = RoPE(q, k, absolute_position)
y = Attention(q, append(cache, k, v))
x = x + y @ Wo
z = RMSNorm(x)
x = x + (SiLU(z @ Wgate) * (z @ Wup)) @ Wdown

每层维护自己的 KV。上一层的输出成为下一层输入；完成所有层后才得到 logits。

综合实战

独立参考：每次重算完整前缀

score[h, t, s] = Q[t,h] · K[s,h] / √8

只保留 s ≤ t 的分数，对最后一维做 softmax，再加权求和 V。这个路径不经过页表。

history = prompt + generated
logits = model.dense(history)[-1]
next_token = argmax(logits)

参考实现慢，但逻辑直接。它提供独立于分页和调度的正确性基线。

综合实战

因果性有一个很强的检查

两段输入 [1,3,5,7] 与 [1,3,5,31] 只改变最后一个 token。前三个位置的 logits 应保持一致。

dense([1,3,5,7])[:3] = dense([1,3,5,31])[:3]

这个检查直接约束未来信息不能泄漏。随后再比较每个增量位置与完整前向的 logits。

只比较 argmax 容易漏错：两个错误分布仍可能选中同一个 token。

综合实战

Batch 里没有共同的历史长度

A 已有 3 个有效位置，B 只有 1 个。QK 计算为了成批使用长度 3，但 B 的后两项必须清除。

综合实战

绝对位置不等于物理槽位

缓存写到位置编号 5 时，RoPE 仍然使用位置 5。它可以落在物理页 4 的槽位 1。

position = cache.length logical_page, slot = divmod(position, page_size)

将 RoPE 位置改成 slot，会让每个页边界都重新从零开始。shape 完全合法，数值却已经不一致。

综合实战

页池把容量与地址分开

pool[physical_page, layer, K_or_V, slot, kv_head, d]
page_table[logical_page] = physical_page
physical_page = page_table[position // page_size]
slot = position % page_size

同一物理页存放固定数量的 token；每个 token 都有两层的 K/V。请求持有页表和有效长度。

本实验不共享页面，因此一个物理页只属于一个请求。Prefix sharing 是后续扩展。

综合实战

沿着页表找到位置编号 5

页大小 4，页表为 [2,4]。逻辑位置从 3 增长到 5，读取顺序不随物理布局改变。

页内偏移不变；页表改变逻辑页与物理页的对应关系。

2 × L × Hkv × d × bytes = 2 × 2 × 2 × 8 × 8 = 512 B/token

综合实战

预留额度与真正分配的页不同

准入时预留请求可能使用的最大页数；实际跨页时才从 free list 取页。

credit = ceil((prompt_length + max_new − 1) / page_size)

A 的 prompt 长 3，生成 4 个 token：最多计算 6 个输入位置，预留 2 页。开始处理时只需要实际分配 1 页。

这个保守策略避免所有活动请求增长后一起耗尽页面，但可能降低利用率。

综合实战

最后采样出的 token，还没有 KV

prompt 长 3，目标生成 4 个 token。每轮先消费一个输入，再从 logits 采样。

综合实战

调度循环的状态转换

到达队列 → 等待准入 → 活动队列
选取至多 batch 个请求，各取 1 个输入 token
一次 step_batch 完成全部选中请求的矩阵计算
prompt 已消费完 → 采样并记录输出时刻
达到 max_new → 释放页与预留额度
否则 → 放回活动队列末尾

每个请求只在同一轮出现一次。Round-robin 避免活动请求长期得不到推进。

综合实战

为什么 C 等待时还有一页空闲？

请求到达额度
A：prompt 3 / output 402 页
B：prompt 1 / output 301 页
C：prompt 5 / output 222 页
D：prompt 2 / output 331 页

B 在第三轮结束（完成时刻为 3），释放 1 份额度。A 仍预留 2 页，C 需要 2 页，暂时不能准入；FIFO 后面的 D 一起等待。

允许 D 越过 C 会改变公平性。要比较等待分布，而不只看平均 batch 大小。

综合实战

这个 prefill 也按 token 推进

已经实现

同轮不同请求共享 QKV / MLP 矩阵运算；KV 按页保存，gather 后做带 padding mask 的 attention。

下一步优化

把同一 prompt 的多个 token 合为 chunk，构造全局 causal mask；随后实现直接读页的 GPU kernel。

先保留一个统一的正确路径，再替换耗时最大的部件。

综合实战

采样策略也需要明确顺序

temperature → top-k → top-p → 重新归一化 → 抽样

temperature = 0 在代码里走 argmax。正温度时先稳定排序；top-p 保留首次达到阈值的那个 token。

每个请求使用独立 RNG。调度顺序改变时，不会因为共享随机数流而直接改变它获得的随机数。

真实低精度批处理仍可能产生数值差异；此实验验证的是 float64 小模型。

综合实战

用已知概率检查采样器

p = [0.6, 0.3, 0.1]，top_p = 0.8 保留前两项 → [2/3, 1/3, 0]

运行 12000 次抽样，检查频率接近这个解析结果；第三项应始终为零。

测试输入直接使用 log(p)，避开模型计算，这样失败就能定位到采样器本身。

综合实战

给每个状态一个不变量

每个 physical_page 只有一个 owner
同轮每个请求只能出现一次
已分配页数 ≤ 活动请求预留额度
cache.length = 已消费的输入 token 数
全部请求完成后，所有页回到 free_list

有效长度控制读取范围；页所有权控制写入对象；额度控制准入。三个条件解决不同的问题。

综合实战

故障一：所有 RoPE 位置都改成零

第一位置可能完全正常，第二个位置开始就会与 dense 参考不同。

python3 lab.py --fault position
# EXPECTED DETECTION [position]:
# Not equal to tolerance ...

先固定输入，比较每层 Q/K 的旋转前后结果，再确认位置来自 cache.length。页号、槽位和 batch 下标都不能替代它。

综合实战

故障二：短请求读到了 padding

单请求和等长 batch 都能通过；同 batch 的历史长度不同时才失败。

python3 lab.py --fault mask
# EXPECTED DETECTION [mask]:
# Not equal to tolerance ...

Padding 的 K/V 即使为零，未屏蔽的 score=0 仍会分走 softmax 概率。把补零当作 mask 是两个不同操作。

综合实战

故障三：请求完成，页面没有归还

输出 token 全部正确，也仍然可能泄漏内存。连续运行后，池会提前耗尽。

python3 lab.py --fault leak
# EXPECTED DETECTION [leak]:
# live KV pages exceed active reservation credits

请求完成时，实际页面和预留额度都要释放。正常结束、取消、异常退出都应该经过同一个清理入口。

综合实战

一次只改变一个变量

先固定权重、prompt、输出长度和到达序列，再改变 batch、页大小或池容量。每次先跑正确性检查。

预测

页越大，页表更短，但尾部空槽可能增加；batch 越大，每轮可能处理更多请求。

核对

请求等待、分配页数和运行时间分别怎样变？短小 CPU 矩阵不一定因 batch 增大就更快。

计时排除预热，报告多次运行分布；不要把一次较小的数字直接解释为算法改进。

练习 1

容量与最后一个 token

仍用默认模型和 float64，页大小改为 3。prompt 长 5，生成 5 个 token，最多需要几页？KV 占多少字节？
展开参考解答

会参与前向的输入数为 5+5−1=9。最后采样出的 token 不再执行前向。

ceil(9/3)=3 页；每页 3×512=1536 B，共 4608 B。这里只算已分配 KV 页。

练习 2

补零为什么还会影响输出？

短请求只有一个有效 key，score=0，value=6。拼 batch 后补两个零 key/value。没有 mask 时输出多少？正确输出多少？
展开参考解答

三个 score 都是 0，softmax 为 [1/3,1/3,1/3]。错误输出为 6/3=2。

将无效项设为 −∞ 后，概率为 [1,0,0]，正确输出为 6。补零不等于从归一化分母中删除。

练习 3

用额度解释队头阻塞

池有 3 页。A 预留 2 页，实际只分配 1 页；C 是等待队头，需要 2 页，D 在后面，需要 1 页。哪些请求可以准入？
展开参考解答

剩余额度只有 1 页，C 不能准入。当前 FIFO 规则也不让 D 越过 C，所以两者都等待。

放行 D 能利用空闲容量，但可能延长 C 的等待。比较策略时记录每请求等待和尾延迟。

练习 4

检查 top-k 与 top-p 的组合

原分布 [0.5,0.3,0.2]。温度 1，先 top-k=2，再 top-p=0.7。最终保留哪些 token，各自概率多少？
展开参考解答

top-k 后重归一化为 [0.625,0.375]。第一项累计 0.625<0.7，必须包含第二项。

因此最终保留前两项，概率仍为 [0.625,0.375]。若先做 top-p，会采用不同的截断基准；必须明确策略顺序。
