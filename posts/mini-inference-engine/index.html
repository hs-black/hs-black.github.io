从零写一个最小推理引擎

交互2026-10-20更新于 2026-10-22

一个模型的前向函数接收 token，返回 logits。一个推理引擎则需要长期管理很多条生成过程：哪些输入已经计算，哪些输出刚刚采样，哪一页显存属于谁，下一轮推进哪些请求，以及请求结束后怎样释放资源。

这些状态可以在一个小型 NumPy 模型里完整实现。固定随机初始化的权重与短 token ID 序列，让每次前向都有可重复的数值结果；独立的完整序列实现负责提供参考；分页和调度逐层接入。这样，优化前后出现差异时，可以沿具体的张量与状态定位。

先写一条完整的模型计算路径

实验模型有 2 层，隐藏宽度 \(D=32\)，query 头数 \(H_q=4\)，KV 头数 \(H_{kv}=2\)，每头维度 \(d=8\)，FFN 中间宽度 64，词表大小 64。一个 token 的 hidden state 是 32 维向量；投影后的 Q 有 4 个头，K/V 各有 2 个头。

每层先做 RMSNorm，再计算 Q、K、V，对 Q/K 应用 RoPE，随后执行因果 attention、输出投影和残差。第二个 RMSNorm 后接 SwiGLU 与另一次残差：

$$\operatorname{MLP}(x)=x+\left[\operatorname{SiLU}(\operatorname{RMS}(x)W_g)\odot(\operatorname{RMS}(x)W_u)\right]W_d.$$

完整路径 dense(tokens) 一次处理 T 个位置。attention 分数形状为 [Hq,T,T]，query 位置 i 只允许读取 key 位置 j≤i。GQA 将每个 KV 头提供给两个 query 头，在这个小实现中用显式 repeat 展开，便于检查头映射。

这条 dense 路径独立构造下三角 mask，直接使用连续张量。它与分页实现共享模型权重，但分别执行索引和历史读取。两条路径在这些最容易出错的地方拥有独立实现，比较结果才有诊断价值。

把同一前向改成一次追加一个位置

增量路径 step_batch(tokens,caches) 每条请求处理一个新输入。请求 r 的当前缓存长度为 \(s_r\)，那么新输入的绝对位置就是 \(s_r\)。这一位置计算出的 K/V 写入当前层的槽位，query 再读取该请求从 0 到 \(s_r\) 的全部有效历史。

批内请求长短不同，临时 gather 张量可以补齐到最长长度 \(S_{\max}\)。请求 r 的合法范围由 \(j\le s_r\) 决定；其余补齐槽位在 softmax 前设为 \(-\infty\)。即便补齐的 K/V 全为零，这个 mask 仍然必需，因为分数 0 会在 softmax 分母中贡献 \(e^0=1\)。

图中 A 有三个有效值 [1,2,3]，正确输出为 2。若为了与长度 6 的 B 对齐而补上三个零，却把它们一起归一化，A 的输出就变成 \(6/6=1\)。这个算例解释了为何单请求测试全部通过，混合长度 batch 才暴露错误。

RoPE 的位置也来自每条请求自己的已计算长度。请求在队列中暂停几个 tick 后继续，其语义位置保持连续；batch 行号、页号和调度时间各自承担不同职责。将这些变量分别命名，可以减少实现中误用同一整数的机会。

从逻辑位置找到缓存中的元素

页大小为 \(\htmlData{symbol=b}{b}\) 时，逻辑位置 j 对应逻辑页 \(\lfloor j/b\rfloor\) 和页内偏移 \(j\bmod b\)。每条请求持有页表，页表将逻辑页映射到物理页。物理池中的每页储存所有层在这几个 token 位置上的 K/V。

默认缓存使用 float64，每元素 8 字节。设层数 L=2、KV 头数 Hkv=2、每头 d=8，那么每个位置占

$$m_{\mathrm{token}}=2LH_{kv}d\times8=512\ \mathrm B.$$

页大小 4 时，每页 2048 B；3 页池为 6144 B。这个字节数描述物理 KV 数组；模型权重、Python 对象和临时 gather 张量各自有独立的存储成本。页面总量可以一次分配好，请求占用的页数再随着长度增长。

实现的一个关键顺序是“为整个 batch 检查新增页需求，然后统一预留，再执行各层写入”。如果第二条请求分配失败时第一条已经改写缓存，回退就会困难。预留阶段只要不足，就返回失败；提交阶段在整轮成功后统一增加各请求的逻辑长度。

一个请求的三份进度

请求对象保存 prompt、已经采样的 generated token、每个输出的 emitted tick、缓存对象与容量承诺 credit。prompt 处理进度由缓存长度推进；读完 prompt 的最后一个位置时，输出 logits 已经可以采样首 token。随后每轮取 generated 的最后一个 token 作为新输入。

刚采样的 token 已经属于输出文本，进入下一轮前向后才拥有 K/V。因此 prompt 长为 P、最多生成 O 个输出，而且最后一个输出产生后立即结束时，最多缓存

$$P+O-1$$

个位置。这个边界直接影响准入额度。若每页 b 个位置，每条请求的保守承诺为 \(\lceil(P+O-1)/b\rceil\) 页；已经占用的物理页可以更少。承诺确保请求继续生成到长度上限时仍有空间，物理页则按实际增长领取。

把请求放进同一个循环

调度器维护尚未到达、等待准入和活动请求三个队列。每个 tick 先接收新请求，再按 FIFO 检查容量承诺；然后从活动队列取至多 batch 条请求执行一次 step_batch。未完成请求放回队尾，完成请求释放缓存并归还承诺。

这个实现将 prompt 也逐 token 推进，prefill 和 decode 共用同一条 batched 路径。一次前向使逻辑 tick 加 1，输出在该轮结束时记录。真实服务可以在保持同样状态不变量的基础上加入 chunked prefill，把一条请求的多个新位置拼进同一轮。

前两条请求执行时，物理上只使用 2 页，却已经承诺了全部 3 页。B 完成后归还 1 页承诺；队头 C 需要 2 页，仍要等待 A 释放额度。这里能看到 FIFO 与保守准入的取舍：容量容易证明，短请求可能受到队头等待影响。

下一步可以实验不同准入策略：在保证活动请求的增长预算后，允许能放下的短请求先进入；同时记录被跳过请求的等待年龄。这样，吞吐、公平性与容量承诺会成为可比较的设计选择。

让随机流跟着请求走

模型输出矩阵的第 i 行属于本轮 selected[i]。采样后要按这个映射写回请求；单独的每请求随机数生成器让调度顺序改变时，随机流仍然跟随同一请求。temperature=0 走确定性的 argmax，便于先核对 dense 与 cached 的完整生成序列。

对随机采样，应分别测试给定 logits 的概率变换和抽样频率，再测试引擎中的请求归属。把所有请求混在一个全局 RNG 中，会让先运行的请求消费后续随机数，改变别的请求得到的样本。保存 request ID、随机种子和采样步号，有助于重复播放同一条生成轨迹。

建立能够定位问题的正确性证据

先逐位置比较 dense 与 cached logits，记录最大绝对误差和容差；再比较 greedy 输出。仅比较 argmax 容易漏掉问题，因为错误 logits 仍可能把同一个词排在第一名。实验中的 verify() 覆盖不同页大小、batch 大小、长度不齐和跨页增长，并在请求结束后检查所有页面归还。

失败测试同样重要。position 把位置清零，应由数值对照发现；mask 去掉补齐 mask，需要混合长度 batch 触发；leak 保留结束请求的页面，由生命周期不变量发现。故障与检查一一对应，使每个断言都有明确用途。

复杂引擎里的许多工程问题都能回到这些不变量：batch 压紧后请求身份仍一致，缓存键对应实际输入，异步写入完成后才能发布可读状态，取消请求后仍在运行的 kernel 需要保留其数据寿命。性能优化可以改变布局、调度和执行顺序，测试应持续检查计算结果与资源所有权。

练习：把实现写成可验证的账本

1. 一条请求需要承诺几页？

prompt 长 7，最多输出 6，页大小 4。求最大缓存位置、承诺页数及末页空位。

参考解答

最多缓存 7+6−1=12 个位置，承诺 3 页，末页恰好填满。最后一个输出尚未经过前向，请求已经结束。

2. 两条请求如何写入同一轮？

A、B 缓存长度为 3、4，页大小 4，各追加一个输入。求各自绝对位置和新增页需求。

参考解答

绝对位置为 3、4。A 写入已有页的偏移 3，新增 0 页；B 写入下一逻辑页的偏移 0，新增 1 页。分配检查在该轮各层写入之前完成。

3. 同 token 输出是否足以证明正确？

参考 logits=[10,9,0]，错误实现为 [10,1,0]，greedy 都返回第一项。怎样发现这类错误？

参考解答

逐项比较 logits，第二项误差为 8；再比较 softmax，第二项的抽样概率有明显变化。独立数值参考能发现 argmax 检查遗漏的分布错误。

4. 小模型缓存占多少字节？

L=2、Hkv=2、d=8，float64，页大小 4、池 3 页。计算每 token、每页、整池大小；若改为 float32 呢？

参考解答

float64 为 512 B/token、2048 B/page、6144 B/pool；float32 每元素字节数减半，对应 256、1024、3072 B。修改 dtype 后还需重新选择数值比较容差。

运行引擎、故障注入与测量

下载 lab.py 和 实验记录模板，运行：

python3 -m pip install numpy
python3 lab.py
python3 lab.py --demo
python3 lab.py --fault position
python3 lab.py --fault mask
python3 lab.py --fault leak
python3 lab.py --benchmark

默认检查应全部通过；三次故障运行应报告对应错误被检测到。demo 中 A 的首输出 tick 为 3，B 为 1；C、D 等待容量后再准入，最后页池回到全空闲。benchmark 报告当前 CPU 上 NumPy float64 小模型的多次运行统计。

每次扩展只改变一个层面：先加跨页且长度不齐的新请求，再实现 chunk prefill，再增加 prefix sharing 或 grammar matcher。将新路径与独立 dense 参考对齐，记录请求轨迹、容量和数值误差，随后用固定负载比较执行时间。这样的实验记录可以直接指导后续 GPU 后端的实现。
