已有模型怎样长成 MoE：从权重复用到专家分化

交互2026-10-22

手里已经有一个花大价钱训好的 dense checkpoint，现在又批了一笔算力，怎么花更划算？沿着原结构继续训当然是一条路，也可以走另一条：把 FFN 扩成多个专家，让每个 token 只激活其中几个，把新增参数留给更细的分工。这就是 sparse upcycling（稀疏升级）——拿现成的 dense 权重初始化更大的 MoE，再接着训。

把权重拷几份不难，真正麻烦的是「转换这一刀」切下去之后前后怎么衔接。刚复制完时所有专家长得一模一样，router 往哪送答案都相同；门控如果没归一化，这一层的输出幅度会突然掉一截；要是把大 FFN 切成细粒度小专家，不仅不能切错通道，还得保证初始路由把原 FFN 的各个分片都拼全。任何一个环节没接好，后面烧掉的算力就不是在长新能力，而是在帮模型重新学回刚刚丢掉的东西。

从一个 FFN 到多个专家

把一层 FFN 写成函数 \(f(x)\)，输入是当前 token 的隐藏向量 \(x\in\mathbb R^d\)，输出同样是 \(d\) 维向量。最直接的转换做法是建 \(\htmlData{symbol=experts}{E}\) 个专家，全部载入同一份 FFN 权重，于是初始时 \(f_1=\cdots=f_E=f\)，而 attention、归一化和其余层原封不动地继承下来。Router 为每个 token 给这 \(E\) 个专家打分，挑出 \(\htmlData{symbol=topk}{K}\) 个，输出加权求和：

\[y(x)=\sum_{i\in\htmlData{symbol=selected}{S(x)}}\htmlData{symbol=gate}{g_i(x)}f_i(x).\]

这里 \(S(x)\) 是被选中的专家集合，\(g_i(x)\) 是实际参与加权的门控系数。刚复制完时所有专家完全一样，可以直接把 \(f(x)\) 提出来：

\[y(x)=\left(\sum_{i\in S(x)}g_i(x)\right)f(x).\]

结论很直接：只要 token 没有因为容量上限被丢弃，且选中专家的门控之和等于 1，转换后的这一层就精确保持原来的输出；每层都如此，整条网络的前向也就无缝接上了。这一步在跑第一次参数更新之前就能验完——固定一批 token、关掉 dropout，逐层对比 dense 与 MoE 的隐状态误差，再核对最终 logits 即可。

Sparse Upcycling 论文最早在 T5 和 ViT 上系统试了这类权重复用，讨论过该转换哪些层、专家容量怎么设、优化器状态要不要继承。具体超参往往取决于模型和任务，但评测口径是固定的：从同一个 dense checkpoint 分叉，在同等算力下直接对比「继续训 dense」和「转成 MoE 再训」的质量—成本曲线。关于 MoE 的 token dispatch、容量与专家并行细节，前面 MoE 的路由与系统实现 已经拆过，这里不再重复。

门控既控制输出，也控制梯度

记 router 打出的 logits 为 \(z_i\)，在全体专家上做 softmax 得到概率 \(p_i=e^{z_i}/\sum_j e^{z_j}\)。常见的门控写法有两种：

\[g_i=\begin{cases}p_i,&i\in S,\\0,&i\notin S, \end{cases}\qquad\text{或}\qquad g_i=\begin{cases}\dfrac{p_i}{\sum_{j\in S}p_j},&i\in S,\\0,&i\notin S. \end{cases}\]

左边是先对全体专家做 softmax，再截出 top-k；右边则把选中的几项重新归一，等价于只在选中集合内部做 softmax。从前向看，右边的门控和恒为 1，转换瞬间输出严丝合缝；左边呢？初始化时 router 分数大致均匀，选出来的门控之和约等于 \(K/E\)——比如 8 个完整复制的专家里选 2 个，这一层的输出当场缩水成原来的四分之一。

问题在于，前向好衔接的写法，反向梯度反而不一定好传。我们只盯专家输出里的一个标量分量 \(v_i\)，加权结果是 \(y=\sum_i g_i v_i\)。在 top-k 名次不变的局部邻域里，先看右边这种选中集合内归一化：

\[\frac{\partial y}{\partial z_j}=g_j(v_j-y)\quad(j\in S),\]

未选中专家的局部导数则是 0。对照公式一眼就能看出问题：刚复制完时，所有选中专家给出的 \(v_j\) 完全相同，加权平均 \(y\) 也等于这个值，括号里的 \(v_j-y\) 直接归零——主任务损失顺着输出权重传回 router 的梯度暂时断了。换成 top-1 更极端：选中的唯一专家门控恒为 1，哪怕后面专家分化了，这条梯度也永远是 0。此时 router 只能靠负载均衡之类的辅助损失推动，主任务本身没法直接教它该选谁。

再看左边这种全体 softmax 后取 top-k。记 \(a_j=v_j\mathbf1[j\in S]\)，求导可得：

\[\frac{\partial y}{\partial z_j}=p_j(a_j-y).\]

这里选中专家的概率总量 \(\sum_{i\in S}p_i\) 直接留在输出里，它会跟着 \(z_j\) 一起变。所以哪怕所有专家输出一模一样（只要不为 0 且 \(K\lt E\)），加权后的 \(y\) 仍不等于 \(v_j\)，\(a_j-y\) 就不会归零——router 从第一步起就能收到主任务梯度。代价正是前面看到的：转换瞬间输出尺度会掉一截。这也是为什么 NVIDIA 的大规模 upcycling 研究专门把「门控归一化顺序」和「权重缩放」绑在一起做消融：初始化对得齐，不代表后面一定收敛得快。

SwiGLU 怎样切成细粒度专家

如果把整个 FFN 完整复制，每个 token 选 2 个专家就得算两份完整 FFN，激活计算量直接翻倍。另一种思路是把每个专家切小，用大致相同的激活计算量去组合更多个细粒度专家。记模型隐藏宽度为 \(d\)、原 FFN 中间宽度为 \(m\)，无 bias 的 SwiGLU 可以写成：

\[h=\operatorname{SiLU}(W_gx)\odot(W_ux),\qquad f(x)=W_dh.\]

其中 \(W_g,W_u\in\mathbb R^{m\times d}\) 分别是 gate 和 up 投影，\(W_d\in\mathbb R^{d\times m}\) 是 down 投影，中间向量 \(h\) 共有 \(m\) 个通道。把这 \(m\) 个通道均匀分成 \(\htmlData{symbol=granularity}{G}\) 组 \(J_1,\ldots,J_G\)，每组宽 \(m/G\)。因为逐元素乘法各通道互不干扰，整个 FFN 恰好拆成 \(G\) 个独立小专家之和：

\[f(x)=\sum_{g=1}^{G}W_d[:,J_g]\left[\operatorname{SiLU}(W_g[J_g,:]x)\odot W_u[J_g,:]x\right]=\sum_{g=1}^{G}f^{(g)}(x).\]

写 checkpoint 转换脚本时有个容易踩的坑：同一个索引集合 \(J_g\) 必须同时切在 \(W_g, W_u\) 的行和 \(W_d\) 的列上。很多训练框架为了吞吐，会把 gate 和 up 融成一个大张量来存；切之前必须先按框架的内存排布拆开，再配对切片。行号一旦配错，矩阵形状依然合法，程序照跑不误，但中间通道早就张冠李戴了。Megatron-LM 官方转换器专门显式处理了这组对应关系。

切完之后，把每个分片各自复制几份，就凑出了更大的专家池。要让初始输出精确还原原来的 FFN，得同时过两道关：第一，router 必须从每个分片里恰好挑出一份副本，把 \(f^{(1)}\) 到 \(f^{(G)}\) 收全；第二，如果选中的 \(G\) 个门控都是 \(1/G\)，加权求和只得到 \(f(x)/G\)，还得把各副本的 down 投影乘上 \(G\) 才能把幅度拉回来。分片漏选靠调倍数救不回来，分片选齐了幅度不对也会偏移，下面可以亲自试一下。

Virtual grouping 就是把这套思路落到了初始化里：先把各个分片和它们的副本编好组，配上对应的 router 初值，保证转换瞬间每个 token 刚好凑齐一整套分片，再把门控压低的幅度补回来。等训练跑起来，专家权重和路由都会放开更新，不再受初始分组限制。

补幅度时，选缩放哪一层权重也有讲究。如果是 \(f(x)=W_2\operatorname{ReLU}^2(W_1x)\) 这种齐次结构，把 \(W_1\) 和 \(W_2\) 同时乘上正数 \(s\)，输出会精确放大 \(s^3\) 倍，所以开个立方根就能把缩放均匀摊给两层权重。SwiGLU 却不行：\(\operatorname{SiLU}(u)=u\sigma(u)\)，一旦缩放 \(W_g\)，里面的 sigmoid 门值跟着变，输出不再按简单的幂次放大（后文 lab.py 验了这一点）。如果把倍数全压在最后的 \(W_d\) 上，前向可以做到机器精度级还原，但代价是 \(W_d\) 的权重范数和后续梯度尺度会被单独放大；反过来把缩放分摊到多层权重，前向虽会带一点初始误差，优化轨迹却可能更稳。

从复制到分工

一模一样的专家，是怎么走出不同方向的？记损失对 MoE 层输出的梯度为 \(u\)，专家 \(i\) 的输出对其参数的雅可比矩阵为 \(J_{f_i}\)，只要它被选中，参数梯度里就有一项 \(g_i J_{f_i}^\top u\)。虽然初始化时所有专家权重完全一致，但 router 分给每个专家的 token 集合、门控权重 \(g_i\) 和上游误差 \(u\) 并不相同，所以第一步更新就会把它们推向不同方向。只要专家输出拉开一点差距，前面归零的 \(v_j-y\) 就不再是 0，router 随之重新收到「选哪个专家更降 loss」的主任务信号。

拿个极简算例就能把这条因果链看清楚：复制三个相同的线性专家，对四个样本做 top-2 归一化路由。第一次反向时，三个专家拿到的梯度各不相同，而 router 的梯度严格为零；只要让专家先更新一步，再算一次反向，router 梯度立刻变成非零。后面的 NumPy 实验把这两步完整算了出来。

不过在真实训练里，有梯度不等于分化得动。线上盯训练时，通常要按层看四样指标：各专家分到的 token 负载、参数更新范数、门控熵，以及同一分片不同副本之间的输出相关性。如果少数专家长期饿死、拿不到 token，先查路由初始化和容量设置；如果负载很均匀，但副本之间输出依然高度相关，说明大家还在干一样的活，新增容量还没真正分化开。

分化得快不快，还和学习率与优化器状态密切相关。很多 dense checkpoint 是从余弦退火尾巴上拿出来的，学习率已经压得很低，直接接着这个末值往下训，新复制出来的专家半天拉不开差距；这时往往需要重新做一次 warmup，或者从同一个转换点分叉，对比「延续末值」和「重新升温」两种计划下，共享层、专家和 router 各自的实际更新比例。优化器状态也是同样的道理：继承旧的 Adam 一、二阶矩会直接改变更新步长，而新加的 router 压根没有历史状态，两边步调不一致很容易出问题（这些更新量的监控方式见 训练稳定性）。

如果不想靠「完全相同的副本慢慢熬出差异」，Branch-Train-MiX 走了另一条顺序：先从同一个基座分叉，在不同领域上各自独立训出一批 dense 模型，再把它们的 FFN 直接留作专家、其余共享层做权重平均，最后接上 token 级 router 一起继续训。这样专家进门时就自带分工，但代价是前期多了各领域的独立训练开销；而且把不同分支的 attention 等共享层直接平均，本质上就是 模型合并——参数能不能对齐、合并后会不会掉点，同样得过一遍账。

已有投入与下一笔预算

先算参数账。记不动的共享部分（嵌入、attention、归一化等）有 \(N_s\) 个参数，待转换的 dense FFN 合计有 \(P_f\) 个参数。把 FFN 切成 \(G\) 份细粒度专家、扩到总数 \(E\) 个、每个 token 激活 \(K\) 个，再算上新增的 router 参数 \(N_r\)，总参数与每 token 激活参数分别是：

\[\htmlData{symbol=total}{N_{\rm total}}=N_s+\frac{E}{G}P_f+N_r,\qquad \htmlData{symbol=active}{N_{\rm active}}\approx N_s+\frac{K}{G}P_f.\]

总参数决定权重显存的大头，激活参数决定主要矩阵乘 FLOPs 的量级（\(N_r\) 占比很小，估算激活参数时通常略去）。拿一个 7B dense 模型代进去：\(N_s=1\mathrm B\)、\(P_f=6\mathrm B\)，取 \(E=64,G=8,K=8\)，转完之后总参数涨到约 49B，每 token 激活参数仍停在 7B——差不多用同样的单 token 计算量，换了七倍大的参数池。

再算训练账，这里要分清你站在哪个时间点做决策。如果手里已经有一个现成的 dense checkpoint，前期算力属于沉没成本，你只关心下一笔新增预算花在「继续训 dense」「upcycling 成 MoE」还是「从零训 MoE」上更划算；但如果是在从头规划整条训练流水线，就必须把转换前后的算力合起来记：

\[C_{\rm total}\approx6N_{\rm dense}\htmlData{symbol=dense-tokens}{D_d}+6N_{\rm active}\htmlData{symbol=moe-tokens}{D_m}.\]

其中 \(D_d\) 和 \(D_m\) 分别是转换前后的累计 token 数。不同配置的激活参数与系统开销不同，同样训 100B token 花的算力和卡时可能差很远，所以做对比时别只画 loss—token 曲线，一定要把 FLOPs 和实际 GPU 时间也拉到一起看。

顺着这本账往前推，马上会遇到一个关键问题：dense 模型训到什么时候转 MoE 最划算？《Scaling Laws for Upcycling》发现了一个很直观的权衡：dense 训得越久，转换时的起点越低，但复制出来的专家在后续阶段收敛得反而越慢（可以理解成旧权重「定型」了）。论文用一个带交互项的经验幂律来刻画这种折中：

\[\widehat L(d_d,d_m)=A d_d^{-a}d_m^{-b+c\log d_d}+L_\infty,\qquad d_d,d_m>0.\]

这里的 \(d_d=D_d/D_0\)、\(d_m=D_m/D_0\) 是按固定单位 \(D_0\) 归一化后的阶段长度（转换瞬间的损失跳变另记，幂律只拟合 \(d_m>0\) 的后续区间）。盯住 \(d_m\) 的指数就能看懂它的意思：后续训练的有效衰减率是 \(b-c\log d_d\)。只要交互项系数 \(c>0\)，前期 dense 训得越长，\(d_d^{-a}\) 把起点压得越低，同时 \(b-c\log d_d\) 却把后面的下降斜率拉平了。

工程上想摸清自己模型家族的这条曲线，做法很直接：选三个不同训练进度的 dense checkpoint，用同一套配方转成 MoE，各跑几档新增预算，留出最长那档做留出验证（这类拟合、留出验证和外推误差的坑，我们在 训练预算与 Scaling Laws 里专门拆过）。

相同 FLOPs，为什么速度不同

细粒度切分能在激活参数不变的情况下把专家数量翻好几倍，但问题马上就来了：账面 FLOPs 一样，跑在 GPU 上速度真的一样吗？拿两组总参数和激活参数完全相同的配置比一下——粗粒度 \((E,G,K)=(8,1,1)\) 对细粒度 \((64,8,8)\)。假设一层处理 \(T=1024\) 个 token 且路由均匀，每个专家平均分到的 token 数居然一模一样：

\[n_e=\frac{TK}{E}=128.\]

可落到 8 张专家并行（EP）卡上，矩阵乘法的形状已经彻底变了。粗粒度每张卡只有 1 个大专家，算一次宽 GEMM；细粒度每张卡塞着 8 个小专家，每个的中间宽度缩成原来的八分之一，得算 8 次窄 GEMM。总 FLOPs 没变，但窄矩阵的 Tensor Core tile 利用率更容易掉，内核启动和 grouped GEMM 调度开销也会抬头。所以光看「每专家平均 token 数相同」，根本判断不了算得快不快。

更刺眼的变化在通信。每个 token 调 \(K\) 个专家，来回就要发 \(K\) 份输入、收 \(K\) 份输出。记隐藏宽度为 \(d\)、每元素占 \(b\) 字节，一次前向里 dispatch 加 combine 的逻辑通信量是：

\[\htmlData{symbol=payload}{V_{\rm logical}}=2TKdb.\]

把 \(T=1024,d=4096,b=2\)（BF16）代进去：粗粒度 top-1 只要传 16 MiB，细粒度 top-8 直接涨到 128 MiB，整整 8 倍。实际跨卡流量还会受本地命中率、专家放置策略和同目的地 token 复用的影响，未必真的满打满算翻 8 倍，但 \(K\) 增大带来的通信压力是实打实的。

真要选粒度，别在纸上拍脑袋，直接固定总专家参数和激活 FLOPs，在目标硬件上扫一遍实际训练会用到的 microbatch：用 profiler 把路由、permute、dispatch、专家 GEMM 和 combine 拆开计时，再挂上完整前反向与优化器步，盯最忙那张 rank 的耗时和各专家的 token 分布。这样瓶颈在哪一目了然——专家计算的有效吞吐掉下去，是小 GEMM 太碎；卡间耗时差拉大、大家都在等最慢那张卡，是负载偏斜；dispatch 和 combine 的等待时间占了大头，就是通信撞墙了。

实验与练习

下载 NumPy CPU 实验 lab.py，安装 NumPy 后运行：

python3 -m pip install numpy
python3 lab.py

脚本用纯 NumPy 跑了四组小验证：拿有限差分核对两种门控的 router 导数、在三个相同的线性专家上更新一步看分化怎么启动、对随机输入检验 SwiGLU 切分能否精确还原，以及验算前面的参数和逻辑通信账本。默认输出包括：

Cloned experts, selected-softmax top-2: y=2.000000
One expert update: toy loss 2.117188 -> 2.034577
router gradient norm now 0.026028

跑通之后最后一行会打印 PASS。想顺手多试两个边界情况的话，可以把 toy_loss 里的 top-2 改成 top-1，亲眼看看归一化门控的 router 梯度怎么一直死在 0；或者故意把某个分片的 down 投影列索引切歪，体验一下重建断言怎么第一时间把映射 bug 抓出来。

练习 1：复制以后，输出和梯度是多少

8 个专家的标量输出都是 2，router 给出的全体 softmax 概率均为 \(1/8\)，固定选中其中 2 个。分别算出「全体 softmax 后选取」和「选中集合内归一化」两种写法下的输出 \(y\)，以及 \(y\) 对单个选中 logit 和未选中 logit 的局部导数。

展开解答

先看全体 softmax 后选取：输出为 \(y=2\times(1/8)\times2=0.5\)。套用 \(\partial y/\partial z_j = p_j(a_j-y)\)，选中位置的导数是 \((1/8)(2-0.5)=0.1875\)，未选中位置是 \((1/8)(0-0.5)=-0.0625\)。8 项相加得 \(2\times0.1875+6\times(-0.0625)=0\)，正好对应「所有 logits 同时平移一个常数不改变 softmax 输出」的性质。

再看选中集合内归一化：两个门控各为 \(1/2\)，输出直接还原成 2，所有 router 局部导数全为 0。（注：logits 完全相等时正好落在 top-k 的并列边界上，以上导数针对固定选中分支后的局部区间，写有限差分测试时给选中项加一点极小扰动固定名次即可。）

练习 2：缩放正确，为什么还原失败

两片 FFN 的输出分别是 \(a=[1,2]\)、\(b=[3,-1]\)，原 dense 输出为两者之和。每片各复制两份，固定选 2 个专家，归一化门控都是 \(1/2\)，down 权重也都乘 2。分别算选 A₀+B₀ 和选 A₀+A₁ 的输出；后者能不能靠一个整体标量救回来？

展开解答

原 dense 输出是 \(a+b=[4,1]\)。选到 A₀+B₀ 时，\((1/2)(2a)+(1/2)(2b)=a+b=[4,1]\)，分毫不差；但选成 A₀+A₁ 时，结果是 \((1/2)(2a)+(1/2)(2a)=2a=[2,4]\)。想靠一个整体标量 \(s\) 把 \([2,4]\) 缩回 \([4,1]\) 是不可能的——第一维要求 \(s=2\)，第二维要求 \(s=1/4\)，根本无解。少了分片 B 的方向贡献，调多大的缩放倍数都补不回来。

练习 3：两阶段预算怎样记

一个 dense 模型有 1B 共享参数和 6B 待转换 FFN 参数，已经训了 300B token。转成 \(E=64,G=8,K=8\) 的 MoE 后再训 90B token。按主要权重矩阵估算，总参数、激活参数、新增计算量和两阶段总计算量分别是多少？

展开解答

略去很小的 router 参数，总参数为 \(1+(64/8)\times6=49\mathrm B\)，激活参数为 \(1+(8/8)\times6=7\mathrm B\)。转换后的新增计算量是：

\[C_m=6\times7\times10^9\times90\times10^9=3.78\times10^{21}\text{ FLOPs}.\]

前期 dense 阶段已经花掉 \(6\times7\times300\times10^{18}=1.26\times10^{22}\text{ FLOPs}\)，两阶段合计 \(1.638\times10^{22}\text{ FLOPs}\)。如果手头已有这个 300B 的 checkpoint，评估要不要做 upcycling 只看新增的 \(3.78\times10^{21}\) FLOPs 值不值；如果是从零规划整个训练项目，则要拿两阶段总账去和从头训 MoE 对比。

练习 4：同样的计算量，为何通信增大

比较 \((E,G,K)=(8,1,1)\) 和 \((64,8,8)\)，每层有 1024 个 token，隐藏宽度 4096，BF16 每元素占 2 字节。算出平均每专家 token 数和 dispatch/combine 逻辑总量，并说明上真机用 profiler 测时还必须补看哪些指标。

展开解答

两种配置下，每个专家平均都分到 128 个 token（\(1024/8=128\) 与 \(1024\times8/64=128\)）。按每次专家调用来回各传一份向量算，粗粒度的逻辑通信量是 \(2\times1024\times1\times4096\times2=16{,}777{,}216\) 字节（16 MiB），细粒度因为 \(K\) 翻了 8 倍，直接涨到 128 MiB。

总参数和激活 FLOPs 没变，是因为专家数量乘 8 的同时每个专家的中间宽度除了 8；但上真机跑时，profiler 还得补齐四类实测数据：窄 GEMM 的实际算力吞吐、各专家与各 rank 的负载分布、考虑本地命中和同目的地复用后的真实跨卡字节数，以及 dispatch/combine 的通信等待时间。
