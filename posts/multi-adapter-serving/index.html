多 Adapter 推理服务

交互2026-10-20更新于 2026-10-22

同一轮推理里，四条请求分别使用 B、A、C、A 三个 adapter。它们共享底座模型，却要求不同的任务行为。给每个 adapter 单独启动一个模型副本会重复保存底座，也会把本来可以合并的矩阵乘法拆小。多 Adapter 服务把公共计算合起来，再按请求身份补上各自的低秩增量。

服务端需要同时管理两种共享：所有请求共享底座权重，同一 adapter 的请求共享增量权重。每条请求的缓存、行位置和版本则要跟随自身生命周期。算子速度、显存准入与缓存身份因此连成了同一个问题。

1. 共享底座，分组计算增量

第 i 个输入行使用 adapter a，前向为

$$Y_i=X_iW^\top+s_a(X_iA_a^\top)B_a^\top.$$

这里 \(X\in\mathbb R^{N\times d_i}\)，N 是本轮 token 行数；W 的形状为 \([d_o,d_i]\)。adapter a 的 \(A_a,B_a\) 分别是 \([r_a,d_i]\)、\([d_o,r_a]\)，\(s_a\) 是缩放系数。decode 通常每请求贡献一行，prefill 则可贡献许多行。

先对整批 X 计算一次 \(XW^\top\)，再把属于同一 adapter 的行取出来，完成两次低秩乘法。分组时保存原 row_id，最后把增量散回同一行。底座输出与 adapter 输出只有在行身份对齐后才能相加。

y = x @ W.T
for identity in unique(adapter_ids):
    rows = where(adapter_ids == identity)
    A, B, scale = adapters[identity]
    z = x[rows] @ A.T
    y[rows] += scale * z @ B.T

这条 CPU 参考路径很适合检验 grouped kernel。把 batch 倒序，输出应按相同方式倒序；把同一请求单独运行，结果应与混合 batch 中的对应行一致。若各组的矩阵乘数值都正确，但请求得到别人的答案，首先检查 gather/scatter 的排列与逆排列。

2. 异构 rank 付出了什么代价

令 \(n_a\) 为 adapter a 本轮负责的行数，\(r_a\) 为它的 rank。增量分支的有效运算量约为

$$\mathrm{FLOPs}_{adapter}=2(d_i+d_o)\sum_a n_ar_a.$$

四行 rank=[16,4,8,4]，输入输出宽度均为 4096，rank 总和是 32，因而需要 524,288 FLOPs。若所有行都补齐到 rank 16，rank 槽总数变成 64，运算量翻倍。低 rank 请求占比高时，这个 padding 开销会明显影响算子选择。

rank 分桶减少无效工作，却会增加组数和调用次数。Prefill 中每个 adapter 常有较多行，适合 grouped GEMM；decode 中每组可能只有一两行，启动、索引和访存成本更突出。应该同时记录每轮不同 adapter 数、每组行数和 rank 分布，按真实形状比较 kernel。

在相同底座下，单个热 adapter 的吞吐提供计算基线；多个热 adapter 混合可以隔离分组开销；超过驻留容量的交替流量则会触发换入。把三者混在一次平均值里，很难判断新增时延来自哪里。

分组还有一个排队维度。某个热 adapter 每毫秒收到数十条请求，很容易凑到高效的 GEMM；冷 adapter 的一条请求可能一直等不到同伴。调度时可以同时设置最大组大小与等待截止时间，组内优先级再考虑请求年龄。实验中保持总 token 量相同，改变 adapter 的流量倾斜度，分别记录组大小分布、GPU 时间与各组的 P99 TTFT。这样可以找到增加 batch 复用与等待延迟之间的可接受范围。

3. 准入时预留整笔资源

显存预算由底座、驻留 adapter、活动请求 KV、workspace 和预留空间组成。沿用 32 层、每层两个 \(4096\times4096\) 投影、rank 16 的例子，单个 BF16 adapter 占

$$32\times2\times16\times(4096+4096)\times2\ \mathrm B=16\ \mathrm{MiB}.$$

一百份就是 1.5625 GiB。更多 adapter 常驻会提高权重命中率，同时减少 KV 可用空间。因此，准入条件要把新权重与当前轮所需 KV 一起计算，后续生成每轮继续做增长检查。

当前使用 44 MiB，剩余 20 MiB，新需求为 36 MiB。计划阶段选择可淘汰的 B 后，总量恰好回到 64 MiB。若 B 也有活动引用，C 就要排队或进入明确的抢占流程。准入失败应保留旧请求的映射与资源，不能留下只加载了一半的新状态。

LRU 给可淘汰对象排序；引用计数与 GPU 事件决定对象何时具备淘汰资格。异步执行中，CPU 已经返回并不等于 GPU 完成了读取。权重槽位的最终引用要延续到相应 kernel 的完成事件：

slot = reserve(adapter_revision)
copy_async(host_weights, slot, copy_stream)
ready.record(copy_stream)
compute_stream.wait_event(ready)
launch_adapter_kernel(slot, compute_stream)
finished.record(compute_stream)
retire_after(finished, slot)

请求取消同样经过这条回收路径。复制流完成 ready 后计算才能读取；计算完成 finished 后槽位才可复用。异步拷贝的 host 源也保留到 ready 完成；共享槽位在最后一个活动引用解除、所有在途 GPU 读者完成后才能复用。两个事件分别保护“数据已经就绪”和“旧读者已经离开”。

换入 16 MiB，在有效链路带宽 16 GiB/s 下，纯传输下界约 0.977 ms。若下一轮需要的 adapter 可提前预测，可以在当前计算期间预取；收益取决于链路与显存带宽是否允许重叠。trace 中应同时观察拷贝、kernel 和等待事件。

4. 缓存键需要描述实际计算

相同文字经过不同 adapter，hidden state 可能不同，后续层的 K、V 也随之改变。即便 adapter 只作用在 Q 或 MLP 上，它仍可能影响更深层的缓存。一个简单例子是 h 从 1 变成 2、K 投影系数为 3，得到的 key 就从 3 变成 6。

因此，普通 LoRA 服务的前缀身份应包含底座 revision、adapter revision、缩放与组合、token IDs、位置、可见性和其他输入条件。多模态特征、RoPE 配置与隔离范围也会影响可复用边界。将一份 cache 交给另一条请求前，应能重建这份 cache 对应的前向条件。

有些架构专门设计了更大的复用范围。例如 aLoRA 从指定 invocation 位置开始启用增量，较早的因果前缀仍按底座计算，因此那一段可以复用底座缓存。到达启用位置后，缓存带上 adapter 的计算身份。服务实现可以按这样的明确边界共享状态。

热更新也依赖不可变版本。逻辑名字 support 从 v3 指向 v4，只改变新请求的解析结果；已运行请求继续绑定 v3。v3 权重保留到最后一个 GPU 引用完成，缓存键继续携带 v3。这样可以在服务中同时观察新旧版本、回滚新请求路由，并保证一个请求的生成过程一致。

5. 多卡布局和服务配置

用列向量记 \(y=Wx+sBAx\)。若 W 按输出维切片，每卡 j 保存 \(W_j,B_j\)，A 与 x 可以复制，本卡得到 \(y_j=W_jx+sB_j(Ax)\)。若 W 按输入维切片，每卡先算 \(u_j=A_jx_j\)，把 r 维中间量归约后再用 B 展开。归约位置必须与底座的输出布局配合，保证增量只加一次。

Punica 将异构 LoRA 的增量组织成分段计算；S-LoRA 进一步结合 adapter 驻留、统一分页和异构 rank 调度。它们体现了同一个工程原则：高效 kernel 需要可用的权重、足够的 KV 预算和合适的组形状。

在支持相应底座与 rank 的 vLLM 环境中，可以注册两份已准备好的 adapter：

vllm serve /models/base --enable-lora \
  --lora-modules task-a=/adapters/a task-b=/adapters/b \
  --max-loras 2 --max-lora-rank 16

max_loras 描述单个 batch 中不同 LoRA 的数量，max_lora_rank 描述支持的 rank 上限。32 条使用 A 的请求只涉及一份 adapter；8 条各不相同的请求则涉及八份。启动后先查看 /v1/models 注册名称，再以该名称作为请求的 model 字段，对照单 adapter 的输出。

6. 把工程故障拆到可观测的边界

只在混合 batch 中出现错误。固定输入，分别运行单 adapter、同 adapter 多请求、不同 adapter 混合和倒序混合。逐层比较首次差异，重点核对 row_id、rank padding、scale 和 scatter。这个最小矩阵能把输入排列问题与权重加载问题分开。

开启 prefix cache 后跨任务串答案。先检查 adapter identity 是否进入缓存键，再比较同一前缀在不同 adapter 下的逐层 KV。对 aLoRA 这样的分段复用方案，验证 invocation 前后的边界。可以用“同 tokens，不同 revision/scale/位置”的测试组逐项确认隔离。

平均吞吐稳定，冷 adapter 的 TTFT 很高。记录到达、准入、换入开始、换入完成和首 token 时间，并按 adapter、冷热状态及长度分桶。若时间主要消耗在凑组，给冷组增加等待上限；若主要在加载队列，检查驻留抖动与预取。尾延迟问题需要保留每个租户的分布。

7. 练习与实验

练习 1：异构 rank 的有效工作

四行 rank=[16,4,8,4]，输入输出宽度都是 4096。计算有效 FLOPs、全补到 16 的 FLOPs 和无效占比。

展开参考解答

有效量 \(2\times8192\times32=524288\) FLOPs；补齐后 1048576 FLOPs。无效工作占补齐总量的 50%，相对有效工作多出 100%。

练习 2：请求 C 能否准入

沿用图中的 64 MiB 预算。如果 A、B 都有活动引用，如何处理 C？如果 B 已空闲呢？

展开参考解答

两者都活动时，可用20 MiB小于36 MiB需求，C进入等待或明确的抢占流程。B空闲时，计划回收16 MiB，提交C权重与4 MiB KV后总量恰好64 MiB。

练习 3：版本切换的正确边界

support 从 v3 更新到 v4，仍有 v3 请求运行。给权重、路由与 prefix cache 各写一条不变量。

展开参考解答

运行请求绑定不可变v3；新请求解析到v4；cache键包含实际revision和缩放等条件。v3权重槽位在最后一次GPU使用结束后回收。这样同一请求的前后步骤具有同一计算身份。

练习 4：LRU 的循环抖动

A、B、C 等大，依次访问 A→B→C→A→B→C，初始为空，访问结束即释放活动引用。容量为2份与3份时，各有多少次miss？

展开参考解答

容量2时六次都miss，每次驱逐下一轮将需要的对象。容量3时前三次miss、后三次hit。第三份驻留权重占用的显存还要与KV并发收益比较。

下载 lab.py，运行分组正确性、原子准入和缓存身份实验：

python3 -m pip install numpy
python3 lab.py
python3 lab.py --budget-mib 112

输出包含 grouped / merged-row reference: PASS、活动权重保护与原子准入检查，以及八类 prefix 身份隔离。将教学预算从 64 改为 112 MiB，queued 从 2 变为 0。再删去缓存键里的 adapter revision，观察哪一项隔离检查首先失败。
