多 Adapter 推理服务

一份底座，怎样同时服务不同任务？

2026-10-20 · → 逐步推进 · ← 回看 · 拖动时间轴

工程细节

相同底座，可以一起做大矩阵乘法

四个请求分别使用 adapter B、A、C、A。它们的底座权重 W 一样；每一行的增量权重不同。

Yᵢ = XᵢWᵀ + sₐ(XᵢAₐᵀ)Bₐᵀ；a = adapter(i)

共享的工作

把所有输入行放到一起，计算一次 XWᵀ。

分别的工作

按 adapter 身份分组计算增量，再写回原请求的行。

先修：LoRA / QLoRA、continuous batching、prefix caching。

工程细节

请求数、token 行数、adapter 数是三条轴

符号意义例子
N本轮计算的 token 行数decode 常是每请求一行
U本轮不同 adapter 的数量4 行可能只涉及 3 个 adapter
nₐ / rₐadapter a 的行数 / rankA 可有 2 行、rank 4
dᵢ / dₒ底座投影的输入 / 输出维度4096 / 4096

prefill 一个请求可以贡献很多行；因此 nₐ 是分到该 adapter 的 token 数，不一定等于请求数。

逐步算一遍

分组计算以后，必须恢复行顺序

输入行是 [B, A, C, A]；A 的两行可以共用同一套 Aₐ、Bₐ 矩阵。

首先记录每一行的原始 row_id。

动画只展示 adapter 分支；底座输出 XWᵀ 已按原行顺序保存。

工程细节

一个正确的 CPU 参考实现

y = x @ W.T
for adapter_id in unique(ids):
    rows = where(ids == adapter_id)
    A, B, scale = adapters[adapter_id]
    z = x[rows] @ A.T
    delta = scale * z @ B.T
    y[rows] += delta       # scatter 到原行，不是分组后的顺序

先用这条简单路径作正确性基线。优化后的 grouped kernel 可以减少调用和中间拷贝，但必须给每个原请求同样的输出。

工程细节

一个很隐蔽的错误：结果对了，请求错了

原顺序 [B₀, A₁, C₂, A₃]，排序后 [A₁, A₃, B₀, C₂]；分组结果不能直接与原顺序的 base 输出相加。

perm = [1, 3, 0, 2]；Y[perm] += grouped_delta

回归检查：把 batch 顺序倒过来，输出也应只倒序；同一请求单独运行与混在 batch 中运行，logits 应在数值容差内一致。

显式保存 request_id → row_id → adapter_id 映射，不能用“第 k 个分组”代替“第 k 个请求”。

工程细节

把 rank 不同的请求放在一起，会多算多少？

adapter FLOPs ≈ 2(dᵢ+dₒ) Σₐ nₐrₐ

四行的 rank 为 [16,4,8,4]，Σr=32；dᵢ=dₒ=4096，所以约 524,288 FLOPs。

若统一 padding 到最大 rank 16，四行共用 64 个 rank 槽，约 1,048,576 FLOPs；多出一倍乘加。

实际 kernel 还受到最小 tile、对齐和启动开销影响。数学上的有效 FLOPs 是比较实现时的基准。

蓝色格子做有效计算，空格子也可能占用工作量

每格代表一个 rank 方向。固定最大 rank 容易组 batch，也会给低 rank 请求补空槽。

先画出每行真正需要的 rank。

格子表示逻辑乘加槽；并非 CUDA 线程或 Tensor Core 的真实布局。

工程细节

prefill 与 decode，需要的 kernel 形状不同

Prefill：nₐ 较大

每个 adapter 对应一块矩阵，适合 grouped GEMM；tile 复用权重可以减少重复读取。

Decode：nₐ 较小

常常只有几行，矩阵很瘦。分段、融合、专用 GEMV 路径可减少大量小调用。

同样的 rank，prefill 与 decode 的最优实现未必相同。先记录每个 adapter 的行数直方图，再选择 kernel 和分组策略。

关联：GEMM 的 tiling 与算术强度。

共享底座以后，显存还被谁使用？

M = Mbase + Σ Mresident_adapter
+ MKV(active requests) + Mworkspace + Mreserve

base通常随模型进程常驻

KV cache随请求增长，结束后释放或转成可复用前缀

工程细节

一个 adapter 16 MiB，一百个就是 1.5625 GiB

沿用 32 层、每层两个 4096 × 4096 投影、rank 16、BF16 的例子：

32 × 2 × 16 × (4096+4096) × 2 B = 16 MiB

100 个 adapter：1600 MiB=1.5625 GiB。rank 64 的同配置 adapter 是 64 MiB；不同目标层也会改变大小。

模型文件很小不意味着可以全部常驻。每多留一份冷 adapter，都可能挤掉一批正在增长的 KV cache。

逐步算一遍

先预留整笔资源，再开始换入

总预算 64 MiB，每格 4 MiB。A=16、B=16、已有 KV=12；新 C 需要 32 MiB，首轮 KV 还要 4 MiB。

当前用了 44 MiB，剩余 20 MiB；新请求总共需要 36 MiB。

B 没有活跃引用，可以淘汰；A 正被请求使用。准入先原子预留，图中再展开物理换入过程。

工程细节

CPU 说“用完了”，GPU 可能还没有读完

slot = reserve(adapter_revision)
copy_async(host_weights, slot, copy_stream)
ready.record(copy_stream)
compute_stream.wait_event(ready)
launch_adapter_kernel(slot, compute_stream)
finished.record(compute_stream)
# finished 完成后，最后一个引用才能归零并允许复用 slot

请求取消也要等待已提交 kernel 的使用结束。若先复用 slot，新 adapter 可能覆盖旧请求正在读取的矩阵。

关联：streams、events 与缓冲区生命周期。

工程细节

准入是一笔“adapter + KV + 余量”的交易

只检查 adapter 是否装得下，会在下一步分配 KV 时突然失败。请求进入运行集合之前，应预留当前调度策略所需的总资源。

步骤要保持的条件
计划淘汰只选无活跃引用、无未完成访问的对象
预留新权重 + 本轮 KV + 临时空间不超过预算
提交失败不改变已运行请求的资源映射
增长后续 KV 超出预算时，按策略等待、抢占或重算

未知输出长度不可能无限预留；每轮继续做容量检查，拒绝、排队和抢占都应单独记录。

工程细节

LRU 解决“留下谁”，不解决“能否淘汰”

先筛资格

活跃权重、正在传输的权重、被已提交 kernel 引用的 slot 都不能直接复用。

再排优先级

在可淘汰集合里，可以按 LRU、热度、大小或未来需求选择；策略影响命中率和尾延迟。

某个 adapter 大且低频，仍可能有严格的首 token SLO。只追求命中次数，会让冷门任务长期等待。

逐步算一遍

让下一轮的 adapter 提前到达

教学输入：当前计算 6 ms，换入 4 ms。预取在第 1 ms 开始，且内存、链路和执行资源允许重叠。

串行路径要等计算结束，再花 4 ms 换入。

真实传输可能与计算竞争带宽；是否缩短关键路径，需要 trace 验证。

工程细节

16 MiB 的 adapter，传输下界是多少？

Tpayload = bytes / bandwidth
= 16 MiB ÷ 16 GiB/s = 0.9765625 ms

这是有效带宽的教学输入。请求还可能等待磁盘读取、CPU 准备、传输排队与事件同步。

若一次 decode 只需 2 ms，却每轮都换一个 adapter，约 1 ms 的传输已经很显眼。提高驻留命中率与重叠程度，比只减少 adapter FLOPs 更直接。

工程细节

按 adapter 聚类，可能让少数请求一直等

A 请求源源不断，B 每秒只来一个。总是先凑满 A 的大组，能减少切换，却可能让 B 的排队时延持续增长。

增加等待上限

记录最老请求年龄；达到阈值后给冷组服务机会，避免无限延期。

设置资源份额

限制单 adapter 的连续 token 预算或活跃请求数；同时观察每租户 goodput。

对所有请求混在一起算一个 p99，会掩盖冷 adapter 的体验。需要按 adapter、冷热状态和 prompt 长度分组。

工程细节

max_loras 限制的是一轮中的不同 adapter

一个 batch 有 32 行，如果都来自 A，U=1；8 行分别来自 8 个 adapter，U=8。两个工作负载的分组与权重驻留开销很不同。

配置维度影响
最大并发 adapter 数一轮允许的不同 adapter 身份
最大 rank支持的 rank 上限与可能的预分配
CPU adapter cache主机端可缓存的 adapter 集合
token / request 预算prefill 与 decode 的批量规模

具体可支持的 rank 与组合依版本、后端而变；部署前用真实 adapter 的配置做启动检查。

工程细节

相同文字，不保证相同 KV cache

hiddenₗ = fₗ(prefix, W, adapter)
Kₗ = hiddenₗ WK,ₗᵀ；Vₗ = hiddenₗ WV,ₗᵀ

即便 adapter 不直接修改 K、V 投影，它也可能改变更早层的 hidden state，从而改变后续层的 KV。

简单标量例子：同一 token 在 A 下 h=1，在 B 下 h=2；WK=3，则 K 分别是 3 和 6。只按 token IDs 复用缓存，会给 B 读到 A 的结果。

工程细节

缓存键要描述“同一次计算”

身份信息例子
底座与 adapter 的不可变 revisionbase-v1 + adapter-A-v3
增量组合与缩放A@0.7 + B@0.3；顺序敏感操作也要记录
完整前缀、位置、可见性token IDs、绝对位置、mask / window
其他影响输入或状态的配置RoPE、视觉输入摘要、隔离范围

部署时采用保守的完整身份键。只有证明某层 KV 完全不受差异影响，才可以进一步扩大共享范围。

工程细节

热更新时，让旧请求继续使用旧版本

把逻辑名字 “support” 从 v3 指向 v4，只改变新请求的解析。已运行请求绑定的 v3 权重和缓存身份保持不变。

request.adapter = resolve("support")  # 得到不可变 v3
... 请求运行中 ...
registry["support"] = v4              # 新请求开始用 v4
# v3 的最后一个 GPU 引用完成后，才允许淘汰旧权重

不能在原地覆盖 v3 的矩阵，却继续把它叫作 v3。权重身份、prefix cache key 和存储 slot 的代次要一起管理。

工程细节

张量并行时，低秩中间量可以更便宜

用列向量写 y=Wx+sBAx。若 W 按输出维切分，每卡拥有 Wⱼ、Bⱼ，A 和输入 x 可以复制，得到各自输出切片。

yⱼ = Wⱼx + sBⱼ(Ax)

若 W 按输入维切分，每卡先算 uⱼ=Aⱼxⱼ，再对 r 维 u 做求和。随后用 B 展开；把通信放在 r 维中间量上，可以避免某些 d 维传输。

需要与底座的分片、归约和输出布局一起设计；不能重复添加复制的增量。实验用逐卡结果求和后，与单卡参考核对。

工程细节

Punica 与 S-LoRA，把哪些部分做进系统？

Punica

共享底座 batch，把不同 LoRA 的增量组合成分段计算，减少一个 adapter 一串小 kernel 的开销。

S-LoRA

按需把 adapter 从主存搬到 GPU，统一管理 adapter 与 KV 的分页空间，配合异构 rank 的计算与调度。

这些设计说明：算子、内存布局和调度需要配合。单独换成 grouped GEMM，不会自动解决 adapter 换入和 KV 容量问题。

工程细节

压测要同时覆盖热、冷和交替请求

工作负载主要观察
单个热 adapter分支计算和 batch 基线
多个热 adapter 混合分组、rank padding、调度开销
冷 adapter 首次到达加载队列、换入与首 token 时延

固定总 GPU、输入/输出长度、到达率和质量设置；记录每 adapter 的 TTFT、ITL、goodput、换入字节与峰值 KV。

关联：推理压测与 SLO。

工程细节

吞吐只掉 5%，冷任务却慢了 10 倍

教学观测：热 A 占 95% 请求，冷 B 占 5%；整体吞吐接近基线，但 B 的 TTFT 由 20 ms 变成 200 ms。

先拆时延

从到达、准入、换入开始/结束到首 token，找出 180 ms 增量落在哪段。

再改一个因素

若主要在等待组批，限制聚类等待；若主要在换入队列，检查驻留策略与带宽。

只看平均 adapter FLOPs 或总吞吐，无法解释一个租户的排队体验。

练习 1

三种 rank 的混合 batch，要做多少乘加？

4 行的 rank=[16,4,8,4]；dᵢ=dₒ=4096。计算有效 adapter FLOPs、统一补到 rank 16 的 FLOPs 和浪费比例。
展开参考解答

Σr=32。有效：2×8192×32=524,288 FLOPs。padding 后：2×8192×64=1,048,576 FLOPs。

无效工作占 padding 总量的 50%；相对有效工作多算 100%。这两个比例的分母不同。

练习 2

C 能换入，但它的请求能运行吗？

预算 64 MiB；A=16、B=16、已有 KV=12，A 活跃、B 空闲。C=32，首轮还需 KV=4。该淘汰谁？若 B 也活跃呢？
展开参考解答

当前 44 MiB，空闲 20 MiB；新需求 36 MiB，缺 16。淘汰空闲 B 后恰好总计 64 MiB。

若 A、B 都活跃，不能覆盖任一权重。请求 C 等待或按明确策略抢占已有请求；不能只分配 C，再等 KV 分配失败。

练习 3

只换 adapter 的名字，缓存为什么污染了？

缓存键只有 token IDs；“support” 名称先指向 v3，再原地覆盖为 v4。旧请求仍在 decode。指出两处错误并设计修复。
展开参考解答

缓存身份遗漏底座/adapter revision 等计算条件，可能复用错误 KV；原地覆写让旧请求后半程读到另一套权重。

新请求解析到不可变 v4；旧请求固定 v3，权重带活跃引用。缓存键包含版本与缩放等身份；最后一次 GPU 使用结束后再回收 v3。

练习 4

容量从两份变成三份，命中率会怎样？

有 A、B、C 三份等大的 adapter，按 A→B→C→A→B→C 循环，每次请求结束即无活跃引用；只用 LRU，初始为空。算容量 2 与 3 时前六次 miss 数。
展开参考解答

容量 2：A、B、C、A、B、C 每次都淘汰下次需要的对象，六次都是 miss。

容量 3：前 A、B、C 三次 miss，之后三次 hit。但多留一份 adapter 会挤占 KV；最终选择还需比较并发容量与尾延迟。
