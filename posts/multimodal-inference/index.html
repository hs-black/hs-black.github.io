图像与视频推理：token、计算与显存账本

图片和视频如何变成真正的推理成本？

2026-10-20 · → 逐步推进 · ← 回看 · 拖动时间轴

问题从哪里来

同样一句话，带图后为什么慢了？

“这张图里写了什么？”只有十几个文字 token，图像却可能展开成几百到几千个视觉 token。

新增的工作

CPU 解码与缩放、图像传输、vision encoder、特征合并，再进入语言模型。

新增的历史

视觉特征进入语言序列后，也占上下文位置和 KV cache；生成每个新 token 时仍会读取。

先修：KV cache、张量布局。

逐步演算

一帧图像要穿过四份不同的数据

数据在变形：像素 → patch 特征 → 视觉 token → 文本模型里的 KV。

图中形状采用教学示例；真实 batch 常把不同请求的 patch 打包。

工程细节

先分清三种长度

符号形状或含义影响什么
F、H、W帧数、高、宽解码、缩放、输入体积
Npatch进入 vision encoder 的 patch 数视觉编码的计算与临时激活
Nvis合并后进入语言模型的向量数语言 prefill 与长期 KV
S = T + Nvis + M文字 T；媒体边界等附加 token M总上下文长度与调度预算

Npatch 与 Nvis 可以差 4 倍；把两者当成同一个 token 数，会把两个阶段的成本混在一起。

工程细节

448 × 672 的图片，先切成 1,536 块

取已经缩放好的 RGB 图像，patch 边长 p = 14。高度与宽度都能被 p 整除。

Hg = 448 / 14 = 32；Wg = 672 / 14 = 48
Npatch = Hg × Wg = 1,536

每个 patch 收集局部像素，经过投影得到 Dv 维向量。Npatch 个向量携带各自的二维位置。

这里使用 Qwen2.5-VL 的 p = 14、空间合并因子 m = 2；单张图在时间维扩成一个 temporal patch。

逐步演算

四个邻居合成一个视觉 token

每个 2 × 2 patch 组拼接特征，再经 learned merger 投影到语言模型的宽度。

动画画 16 → 4；448 × 672 的实例是 1,536 → 384。合并发生在视觉编码之后。

工程细节

预算从预处理之后的尺寸开始算

Nvis = (H′ / p) × (W′ / p) / m²

H′、W′ 是实际送入 encoder 的尺寸。缩放通常保留长宽比，并对齐到 p × m 的倍数。

同一张原图，配置会改变成本

max_pixels、裁剪策略、图片方向与采样实现都可能改变 H′、W′。

把账本贴在 processor 输出上

记录实际 grid_thw 和模型输入长度；用原始文件的分辨率估算后再核对。

Qwen2.5-VL 的空间倍数 28 来自 14 × 2 的空间合并，不是因为视频时间 patch 为 2。

工程细节

多 crop 让细字可见，也让 token 变多

另一类预处理会切多个高分辨率 crop，再加一张全局缩略图。每块都经过视觉编码。

Nvis,total = Σ Nvis,crop + Nvis,global + 额外边界 token

教学例：4 个局部 crop，各 256 token；全局图再占 256。仅视觉位置就是 1,280，不是 256。

收益

小字、细小物体与高分辨率局部信息更容易保留。

代价

编码次数、上下文长度与跨 crop 定位都增加；先看任务是否需要细节。

crop 数量与特殊 token 依模型和 processor 而定；这不是 Qwen2.5-VL 的固定切图规则。

工程细节

视频还多一个时间网格

取采样后的 F 帧；temporal patch 大小 τ = 2，相邻两帧共同形成一个时间块。

Tg = ceil(F / τ)
Nvis = Tg × (H′ / p) × (W′ / p) / m²

8 帧、448 × 448、p = 14、m = 2：Tg = 4，每个时间块 256 token，总计 1,024。

这里只给定已采样的帧；不足 τ 的尾部在实验里重复最后一帧。实际采样与补齐以 processor 输出为准。

逐步演算

8 帧如何变成 1,024 个位置

帧对沿时间轴组成 4 个时间块，每块再沿空间切 patch、合并。

本例采样时刻为 0、0.5、…、3.5 秒；图中的时间顺序保留在位置元数据中。

工程细节

帧数、覆盖时长和时间戳是三件事

改动视觉 token 的趋势可能失去什么
固定 8 帧，视频变长形状可以不变短暂动作容易落在采样间隙
同样时长，采样率翻倍帧数近似翻倍成本增加，时间分辨率提高
宽高都翻倍视觉 token 约变为 4 倍细节增加，时间密度没变

同样 8 帧既可能覆盖 4 秒，也可能覆盖 4 分钟。时间戳或时间位置不能只靠帧序号猜。

工程细节

语言模型读取的是向量，不是 JPEG

pixels = processor(media)
features = vision_encoder(pixels, grid_thw)
visual = merger(features)        # [Nvis, Dlm]
embeds = text_embedding(token_ids)
embeds[image_positions] = visual
logits, kv = language_model(embeds, positions, mask)

视觉位置与占位 token 数要对上。占位符少一个或特征顺序错一组，都可能把图像和文本错误配对。

这是视觉特征插入语言序列的一类实现；下面再单独算 cross-attention。

工程细节

每个视觉 token，也有每层的 K 和 V

标准保留 K、V 的 decoder：L 层、Hkv 个 KV 头、每头 d 维、每元素 b 字节。

每 token KV 字节 = 2 × L × Hkv × d × b

取 Qwen2.5-VL-7B 的文本配置：L = 28，Hkv = 4，d = 128；以 BF16 存储 b = 2。

2 × 28 × 4 × 128 × 2 = 57,344 B = 56 KiB

只计 KV 数组，不含权重、视觉激活、分配器浪费、临时 workspace 与其他缓存。

逐步演算

384 个视觉位置，留下 21 MiB KV

文字 256 + 教学约定的边界 4 + 视觉 384 + 预留输出 128 = 772 个位置。

全请求预留 KV 为 42.21875 MiB；视觉部分是 384 × 56 KiB = 21 MiB。

工程细节

能接纳多少请求，要给输出留位置

请求预留 = (T + M + Nvis + Omax) × 每 token KV 字节

例：772 × 56 KiB = 42.21875 MiB。若实际可用于 KV 的池只有 1 GiB，同型请求完整预留最多 floor(1024 / 42.21875) = 24。

分页调度器可以按需分配并控制接纳；按需增长不等于忽略输出上限，池耗尽时仍要暂停、抢占或拒绝。

这里的 1 GiB 已扣除其他占用；24 是容量算术，不是吞吐预测。见 PagedAttention。

工程细节

视觉位置把 prefill 的哪部分放大？

令总长度为 S、hidden width 为 D。投影与 MLP 主要随 S 线性增长；全序列 attention 的点积规模随 S² 增长。

QKᵀ + PV 的稠密算术量 ≈ 4 × S² × D FLOPs / 层

文字长度 260，加 384 视觉位置变为 644。S 比例 644 / 260 ≈ 2.48；S² 比例约 6.14。

这是稠密矩阵乘法工作量；因果三角、FlashAttention 的跳块与实现常数会改变实际执行量和时间。

工程细节

视觉 encoder 自己也有一本账

全局视觉 attention

若 Npatch 翻 4 倍，纯全局 attention 的 pair 数变 16 倍；线性层仍约 4 倍。

窗口视觉 attention

固定每窗 w 个 patch，局部 pair 数约 Npatch × w；某些层仍会做全局 attention。

Qwen2.5-VL 视觉 encoder 采用窗口 attention，并保留若干全局层。成本应按层的实际 mask 拆开算。

先算 Npatch 的视觉成本，再算 Nvis 的语言成本。只盯着语言模型 token，会漏掉高分辨率图像前面的峰值。

工程细节

Cross-attention 不把所有图像位置拼进文本

视觉前缀

语言 self-attention 长度包含 Nvis；视觉位置在多个语言层保留 KV。

独立视觉 memory

文本 query 在指定 cross-attention 层读取视觉 K、V；文本 self-attention 仍按文本长度计算。

cross-attention 点积量 ≈ 4 × T × Nvis × Dcross / cross 层

视觉 memory 仍占空间，但层数、头数、投影是否缓存均由架构决定，不能直接套“所有语言层 × 总序列长”。

例如 Mllama 使用视觉 encoder 与 cross-attention 适配模块。

工程细节

同一个 batch，图片大小可能完全不同

请求视觉长度文字 + 边界总输入
A256260516
B1,0242601,284
C256260516

稠密 padding 到 1,284：3 × 1,284 = 3,852 个槽位；真实位置只有 2,316。槽位利用率约 60.1%。

packed sequence 与变长 kernel 能减少 padding；视觉 encoder、语言 prefill 的打包边界和 mask 需要分别正确。

工程细节

调度时同时看视觉预算与语言预算

两个请求各有 1,000 个语言输入 token，视觉编码工作却可能不同：一个有很多 raw patch，另一个主要是文字。

视觉队列

限制每批 raw patch、解码像素与临时激活；把超大图片和短请求混排时看尾延迟。

语言队列

限制 prefill token、decode batch 与 KV 池；chunked prefill 把长输入拆入多轮。

给每个请求保留 request_id、media_id 和 feature offset；跨阶段重排之后仍要按原请求归还特征。

逐步演算

首 token 的时间，从排队前开始记

教学耗时：排队 30、解码 18、传输 6、视觉 24、语言 prefill 40、采样 2 ms。

这条串行关键路径共 120 ms；不同请求之间可能形成流水，不能把跨请求重叠当作单请求成本消失。

工程细节

同一张图，可以复用哪一份结果？

视觉 embedding 缓存的对象是“确定预处理与视觉权重下的确定媒体输入”。

key = hash(media_bytes, frame_timestamps,
           resize_crop_normalize_config, grid_layout,
           vision_weights_revision, vision_adapter_revision)
visual = cache.get(key)
if visual is None:
    visual = vision_forward(process(media))

只用 URL 做 key 会把内容更新误当命中。改裁剪、采样时刻或视觉 adapter 后，原 embedding 也不能继续复用。

工程细节

图片相同，不代表语言 KV 前缀相同

可以独立复用的部分

同一视觉模型、同一 processor 下，同样媒体可能复用视觉 embedding，即使提问不同。

KV 还依赖上下文

语言权重、adapter、前缀文字、媒体顺序、位置编码与可见性都影响每层 KV。

“先描述图 A，再读图 B”和“先读图 B，再描述图 A”拥有相同媒体集合，却不是相同 token 前缀。

把完整前缀身份加入 cache key。连接 Prefix caching 与 多 Adapter 服务。

工程细节

压测里留下能解释问题的字段

请求级阶段级质量与容量
原始/处理后尺寸、帧数解码、H2D、视觉耗时细字或短事件的正确率
Npatch、Nvis、总输入prefill、TTFT、TPOTKV 峰值与视觉激活峰值
输出长度、缓存命中队列等待、batch 组成失败率、达到 SLO 的请求数

固定媒体分布再比较两次配置；“平均请求长度”会掩盖少量超大视频。用分位数和长度分桶定位尾部。

工程细节

文字一样长，图片请求却突然 OOM

教学日志：旧配置 448 × 672；新配置 896 × 1,344。文字仍为 256 token，输出上限仍为 128。

项目旧新

先查 processor 的尺寸上限，再分开观察视觉编码峰值和 KV 常驻量。仅缩短输出，无法解释视觉 KV 已经增加的 63 MiB。

工程细节

把形状检查写在模型边界

assert visual.shape[0] == image_positions.sum()
assert visual.shape[-1] == text_embeds.shape[-1]
assert all(req.feature_count == expected_from_grid(req.grid)
           for req in batch)
log(request_id, actual_grid_thw, visual.shape,
    input_length, output_limit, cache_key)

比较单请求与 packed batch 的同一请求输出；再比较缓存命中与冷计算。这样能抓住错位、漏 mask 和错误复用。

expected_from_grid 必须按所用模型的合并规则实现；图像和视频的 delimiter 另计。

工程细节

分辨率与帧率，分别花在需要的信息上

OCR / 图表

优先保留字符与坐标轴的可辨认尺寸；确认缩图没有抹掉小字。

动作 / 短事件

优先覆盖事件时刻与前后变化；提高分辨率不能补回没采到的帧。

在固定成本预算下画质量曲线：横轴 Nvis 或实际时延，纵轴任务正确率。选择满足质量目标的成本点。

同一任务也要覆盖极端长宽比、旋转图、短暂事件、多图顺序和损坏媒体。

练习 · 先算，再展开

8 帧视频，需要多少视觉 token？

F = 8，H′ = 448，W′ = 672；p = 14，m = 2，τ = 2。求 raw patch 与视觉 token 数。若采样帧变为 16，其他不变呢？
展开参考解答

Tg = 8 / 2 = 4，空间网格 32 × 48。raw patch = 4 × 32 × 48 = 6,144；Nvis = 6,144 / 4 = 1,536。16 帧时 Tg = 8，分别变为 12,288 与 3,072，都是 2 倍。

练习 · 先算，再展开

一段视频的预留 KV 是多少？

上题 Nvis = 1,536；文字与附加 token 合计 260，输出预留 128。每 token KV 为 56 KiB。求总预留 MiB；1 GiB 的纯 KV 池最多完整预留几条？
展开参考解答

总位置 1,536 + 260 + 128 = 1,924。KV = 1,924 × 56 / 1,024 = 105.21875 MiB。floor(1,024 / 105.21875) = 9 条；10 条需要 1,052.1875 MiB。这里还没有其他内存占用。

练习 · 先算，再展开

宽高都翻倍，为什么不能直接说慢 4 倍？

视觉位置从 384 变为 1,536；文字与附加 token 固定为 260。算总输入长度比与稠密 attention 的 S² 比，并解释它们与时延的关系。
展开参考解答

S 从 644 变为 1,796，长度比约 2.79；S² 比为 1,796² / 644² ≈ 7.78。线性层与 attention 的增长不同，还叠加视觉 encoder、访存和队列；实际时延要分阶段测，不能直接用 4 倍或 7.78 倍替代。

练习 · 先算，再展开

缓存命中了，答案却读错了图

服务以图片 URL 为唯一 key。用户替换该 URL 的内容，同时把 resize 上限调大；另一个请求只改了语言 adapter。哪些缓存必须失效？
展开参考解答

媒体字节或预处理变化：视觉 embedding 必须重新计算，依赖它的语言 KV 也失效。只改语言 adapter、视觉部分完全没变：视觉 embedding 可复用，但语言 KV 必须区分 adapter 版本。URL 相同不能证明输入相同。
