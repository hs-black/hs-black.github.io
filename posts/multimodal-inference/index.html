图像与视频推理：token、计算与显存账本

交互2026-10-20更新于 2026-10-22

“这张图里写了什么？”只有十几个文字 token，图片却可能展开成几百到几千个视觉位置。一次带图请求要经过媒体解码、缩放、视觉编码、特征合并和语言模型；视频还增加采样与时间位置。输入文件很小，模型中的计算与缓存仍可能很大。

工程上的第一份账，应从 processor 的实际输出开始：多少 patch 进入视觉模型，多少向量进入语言模型，每个阶段保存多久。把这些长度与时延分开，才能解释分辨率、帧率和 batch 改变之后的表现。

1. 从像素网格到语言模型的输入

设处理后的图像尺寸为 \(H'\times W'\)，patch 边长为 p。尺寸已对齐时，视觉 encoder 接收的 patch 数为 \(N_{patch}=(H'/p)(W'/p)\)。每个 patch 经过投影变成一个向量，保留自身的二维位置。

以 Qwen2.5-VL 的 p=14、空间合并因子 m=2 为例，448×672 图像对应32×48网格，即1536个patch。视觉encoder先处理这些位置，随后每2×2邻居经 learned merger 合并成一个语言侧向量，因此

$$\htmlData{symbol=visual}{N_{vis}}=\frac{(H'/p)(W'/p)}{m^2}=384.$$

这里 \(N_{vis}\) 是送入语言模型的视觉向量数，决定语言 prefill 长度与长期 KV；\(N_{patch}\) 则决定视觉阶段的输入规模。合并发生在视觉编码之后，所以语言序列缩短的倍数不能直接套到前面的 encoder 工作量。

尺寸来自缩放、裁剪和对齐规则。修改 max_pixels 或切图策略后，应记录新的 grid_thw 和特征形状，再重算预算。另一类模型会产生多个局部 crop 加全局缩略图，语言侧长度则是各 crop 特征与边界 token 之和。预算函数应与所用 processor 的实际展开规则对应。

2. 帧数和时间位置共同描述视频

对采样后的 F 帧，设 temporal patch 大小为 \(\tau\)。时间网格长度是 \(T_g=\lceil F/\tau\rceil\)，每个时间块再进行空间 patching 与合并。保持同一空间尺寸时，

$$N_{patch}=T_g\frac{H'}p\frac{W'}p,\qquad N_{vis}=\frac{N_{patch}}{m^2}.$$

取 F=8、\(\tau=2\)、448×448、p=14、m=2，得到4个时间块，每块256个语言侧视觉向量，共1024个位置。F翻倍会使视觉长度翻倍；宽高同时翻倍会使空间位置约增至4倍。

帧数相同也可以覆盖很不一样的时间。8帧可能来自4秒或4分钟，时间戳承载了动作速度与事件间隔的信息。对短暂动作，采样是否覆盖关键时刻尤其重要。更高分辨率改善细节保留，更密采样改善时间覆盖；可以在固定视觉token预算下比较两者带来的任务质量。

3. 视觉位置进入语言 KV 账本

对把视觉向量插入 decoder 输入序列的模型，语言侧总长度为 \(S=T+N_{vis}+M\)：T 是文字token数，M 是媒体边界等附加位置。若预留O个输出位置，一条请求的容量预算按 \(S+O\) 计算。

标准GQA decoder的每token缓存字节数为 \(k_{KV}=2LH_{kv}db\)，L是层数，\(H_{kv}\) 是KV头数，d是每头维度，b是一个元素的字节数。以28层、4个KV头、128维、BF16为例：

$$k_{KV}=2\times28\times4\times128\times2=57344\ \mathrm B=56\ \mathrm{KiB/token}.$$

384个视觉位置占21 MiB。若文字与附加位置共260、输出预留128，总预留为772个位置，KV为42.21875 MiB。视觉encoder的临时激活另有峰值；调度时两者可能重叠，需要分别计量。

使用视觉cross-attention的架构需要另一套账本：视觉encoder输出作为独立条件序列，被指定的语言层读取，相应KV可能按cross-attention层数保存。先确定模型的数据路径，再选择容量公式，才能把架构差异变成可比较的资源量。

4. 长度增长怎样影响计算

语言线性层的主要工作随S增长，稠密attention的成对计算随 \(S^2\) 增长。将448×672改为896×1344，视觉token从384变1536；若文字与附加位置固定260，总输入从644变1796。长度约为2.79倍，平方项约为7.78倍。实际时延还由视觉encoder、kernel利用率与排队组成，分阶段时间才能说明是哪项主导。

动态形状给batch带来额外成本。若四张图的视觉长度分别为256、256、512、2048，把它们补齐到同一长度会分配8192个位置，其中有效位置为3072。按尺寸或长度分桶能减少padding，但等待凑桶又会增加排队。Packed表示可以保留真实长度，并通过offset、位置与mask描述各请求的边界。

图像解码和缩放通常在CPU一侧，像素与特征随后经过H2D或设备间传输。一个大视频请求可以同时占住解码线程、encoder预算与大量KV。仅按请求条数限制并发会掩盖这种差异；更合适的是分别设置媒体字节/像素、encoder patch、语言token和KV容量预算。

当视觉encoder与decoder使用不同资源池时，特征可提前计算并排队等待语言prefill。队列应保留request_id、媒体顺序与实际特征长度，并给已完成encoder但尚未进入decoder的特征设置容量预算。这样可以避免把语言侧排队转化为无限增长的中间特征驻留。

5. 视觉 embedding 与语言 KV 的复用边界

同一视觉模型、预处理和媒体内容会产生同一份视觉embedding。它的缓存键应包含媒体内容摘要、processor配置与版本、视觉权重或adapter版本、裁剪以及视频采样时刻。URL只是媒体定位方式，实际参与计算的是取得的内容及其处理结果。

语言KV还依赖完整前缀、媒体排列、位置、mask、语言权重和adapter。“先读图A再读图B”与相反顺序拥有不同的因果前缀。服务可以复用独立视觉特征，再为新的语言上下文重新prefill。这样缓存按计算依赖分层，命中率与正确性都容易检验。

这也给压测提供了四种有价值的工作负载：全冷媒体、视觉命中而语言前缀变化、完整前缀命中、媒体或processor变化后的重新计算。分别记录encoder时间、prefill时间和KV占用，可以量出每层复用节省了哪一步。

6. 在模块边界检查通用不变量

视觉向量插入语言序列时，特征数必须与对应的视觉占位数一致，特征宽度必须与语言embedding宽度一致，多个媒体的排列必须与文本占位次序一致。截断文本、改变crop数量、动态padding和batch打包都可能触碰这些边界。

assert visual.shape[0] == image_positions.sum()
assert visual.shape[-1] == text_embeds.shape[-1]
assert feature_count == expected_from_grid(actual_grid)
log(request_id, actual_grid, visual.shape,
    input_length, output_limit, media_order)

先用单图、双图、不同尺寸混合batch核对每个请求，再比较独立运行与packed运行的对应logits。这样可以同时验证processor展开规则、特征重排与attention边界。一个形状能相加的张量仍可能属于错误的图片，request_id与媒体序号需要贯穿传输和分组过程。

分析显存上升时，观察两个时刻：encoder工作期间的临时峰值，以及语言prefill后的KV驻留。若仅把宽高翻倍，384个视觉位置变1536，在上述56 KiB/token的配置中，视觉KV就从21 MiB变成84 MiB。将峰值按阶段拆开后，才能选择缩小分辨率、降低encoder并发、分块prefill或减少活动请求。

质量验收也应与成本曲线对应。OCR保留可辨认字符，视频任务保留关键时刻；记录真实处理尺寸、帧时间、Npatch、Nvis及任务指标。在相同媒体分布上比较达到SLO的请求数，少量超大输入对尾延迟的影响也能被看见。

7. 练习与实验

练习 1：8 帧视频的展开

F=8，H′=448，W′=672，p=14，m=2，τ=2。求视觉encoder patch数与语言侧token数；帧数改16会怎样？

展开参考解答

时间网格4，空间网格32×48。Npatch=6144，Nvis=1536。16帧时分别为12288、3072。

练习 2：完整请求容量

视觉1536，文字和附加位置260，输出预留128；每位置KV=56 KiB。1 GiB纯KV池可完整预留几条？

展开参考解答

每条1924个位置，容量 \(1924\times56/1024=105.21875\) MiB。1 GiB可预留9条，10条需要1052.1875 MiB。

练习 3：padding 的成本

四个请求视觉长度为256、256、512、2048。统一padding到最大长度时，有效位置占比是多少？拆成前三条和最后一条两个batch呢？

展开参考解答

有效位置3072，统一分配8192，占比37.5%。拆分后分配 \(3\times512+2048=3584\)，占比85.7%。执行时还需比较多一次batch调用和分桶等待。

练习 4：决定缓存失效的依赖

图片URL保持不变，但内容被替换；另一次只改语言adapter，视觉部分保持不变。分别说明两级缓存的复用范围。

展开参考解答

内容变化需要重算视觉embedding及依赖它的语言KV。仅改语言adapter时，视觉embedding可以复用，语言KV按新的计算身份重新生成。缓存键跟随对应阶段的全部输入依赖。

下载 lab.py。实验用逐块切片核对patch排列，以均值merger检查布局，随后验证时间补齐、缓存身份和KV账本。

python3 -m pip install numpy
python3 lab.py
python3 lab.py --height 896 --width 1344
python3 lab.py --frames 8 --height 448 --width 448

默认输出1536个raw patch、384个视觉token、21 MiB视觉KV和42.21875 MiB请求预留。两个变体的视觉KV分别为84 MiB和56 MiB。进一步实现一个预算器，按实际grid与输出上限为每轮选择可接纳请求集合。
