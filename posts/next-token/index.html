一次只猜一个 token

交互2026-10-19更新于 2026-10-22

给模型输入“今天的天气”，屏幕上的下一段文字怎样出现？一次前向计算会为整个词表产生一组分数，采样器从这些分数中选出一个 token。这个 token 随后成为新的输入，模型再计算下一轮。长答案就是这个循环累积的结果。

要实现一个能正确生成文本的小程序，需要把三种对象接起来：tokenizer 负责文本与编号的转换，模型把编号序列变成分数，采样器把分数变成下一次选择。它们共同决定输出的内容、长度和停止时机。

文本怎样变成模型的输入

Tokenizer 把文本分成词表中的片段，再把每个片段映射到整数编号。一个片段可能是完整单词、词的一部分、标点或若干字节。中文字符和 token 的数量关系由具体词表决定；统计上下文长度时，直接使用编码得到的编号数。

例如，某个教学词表把三个候选片段记为“晴”“雨”“雪”。模型接收的是它们对应的编号，embedding 表再把每个编号映射成一个向量。实际模型必须使用训练时配套的 tokenizer 和特殊 token 约定，这样编号才能找到正确的 embedding 行。

对聊天模型，输入还包含角色分隔符、轮次边界和 assistant 开始标记。应用通常先用模型提供的 chat template 组织消息，再编码成 token。手工拼接“用户：”可能改变模型实际看到的格式；把相同消息分别经过模板和手工路径编码，打印两组编号与解码结果，能直接定位这类差异。

从 logits 算出下一步概率

设词表大小为 \(V\)，最后一个有效输入位置输出向量 \(z\in\mathbb R^V\)。其中 \(z_j\) 叫第 \(j\) 个 token 的 logit。Softmax 用指数把分数转成非负数，再除以总和：

$$p_j=\frac{e^{z_j/\htmlData{symbol=temperature}{\tau}}}{\sum_{k=1}^{V}e^{z_k/\tau}}.$$

这里 \(\tau>0\) 是采样温度。温度越小，分数差异越突出；温度越大，分布越平。数值实现先减去最大的 logit，利用 \(e^{(z_j-m)/\tau}\) 计算，避免很大的指数溢出。减去相同常数会同时改变分子和分母，最终概率保持一致。

当 logits 是 \([2,1,0]\)、温度为 1 时，概率约为 \([0.665,0.245,0.090]\)。贪心解码每次选择分数最大的候选；随机采样按照概率抽取，因而相同输入可能产生不同结果。Top-k 保留分数最高的 k 项，top-p 保留累积概率达到阈值的最小候选集合，保留后再重新归一化。

一枚输出怎样进入下一轮

第一次前向读入完整 prompt，这一步叫 prefill。最后一个有效位置的 logits 用来选择第一个输出。后续 decode 每轮输入刚刚选出的 token，并读取之前保存的 KV cache。它为这个输入计算各层的 K/V，追加到历史，再产生下一枚输出的 logits。

假设 prompt 含 3 个 token，最终生成 2 个 token，并在选出第二个输出后立即停止。真正进入模型的输入共有 \(3+2-1=4\) 个位置：三个 prompt，加第一个输出。最后一个输出已经交给用户，下一轮前向尚未开始，因此它还没有对应的 K/V。这个边界关系会影响缓存复用、计时和流式服务的状态提交。

cache = empty_cache()
logits, cache = forward(prompt_ids, cache)
for step in range(max_new_tokens):
    next_id = sample(logits[-1])
    yield next_id
    if next_id == eos_id or step + 1 == max_new_tokens:
        break
    logits, cache = forward([next_id], cache)

EOS 是模型词表中的结束标记。应用还可以设置最大新增 token 数和字符串停止条件。流式输出通常逐步把 token 解码成文本；字节级 tokenizer 的一个字符可能跨多个 token，因此解码器应维护未完成的字节序列，等片段完整后再显示。

单条生成正常，组 batch 后为什么变了

一个常见入口是 padding。很多 decoder-only 生成循环直接取 logits[:, -1, :]。两条 prompt 长度不同时，右填充会让短请求的最后一列落在 padding 上。Attention mask 控制可读取的 key，却不会替应用把最后一列换成“最后一个有效 query”。这种循环适合左填充；自己实现批处理时，也可以按各请求的有效长度显式 gather logits。

排查时先固定采样策略，用贪心解码比较“单独运行”和“与长请求组成 batch”的第一步 logits。再核对有效 token 的 position ids、attention mask 和最后有效位置。只比较最终字符串容易被一次早期采样差异掩盖；逐步比较 logits 能找到最早发生分歧的位置。

遇到乱码、空输出或 token 数异常少，先独立检查 tokenizer 的 encode/decode 往返。记录模型 revision、tokenizer revision、chat template，以及特殊 token 的编号。这样能把输入组织问题和模型前向问题分开复现。生成速度则分别记录 prefill、每次 decode 和文本解码的用时，服务端还需要加上排队和网络时间。

练习

1. 手算一次采样

概率为 [0.665, 0.245, 0.090]，按顺序对应晴、雨、雪。均匀随机数为 0.80，选哪一个？

展开解答

累计区间为 [0,0.665)、[0.665,0.910)、[0.910,1)。0.80 落在第二段，因此选雨。重复大量独立采样后，各候选频率会接近给定概率。

2. 缓存里有几个位置？

Prompt 长度为 8，生成 5 枚 token 后立即结束。每层已有多少个缓存位置？

展开解答

共有 8+5−1=12 个位置完成前向。最后一枚输出留在采样结果中；若下一轮聊天要继续复用缓存，需要把它作为尚未消费的输入接上。

3. 找出 batch 的错误位置

短请求有效长度为 3，右填充到 5，代码读取第 4 列 logits。怎样构造最小修复和验证？

展开解答

读取零基索引 2 对应的 logits；或者为采用末列读取的生成循环使用左填充。固定位置与 mask 后，比较该行与单条无 padding 运行的末行 logits，再比较第一个贪心 token。
