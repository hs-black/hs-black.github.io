Over-Encoding：用查表扩展语言模型容量

交互2026-10-22

拿一个隐藏维度 4096、词表 131,072 的模型算一笔账：输入端按 token ID 查表，读一行 BF16 词向量只要搬 8 KiB；可到了输出端预测下一个 token，同样尺寸的投影矩阵要把整个词表全算一遍——131,072 个 logit，大约 10.7 亿次浮点运算。输入和输出虽然经常共享权重，用起这块矩阵来却完全是两回事。

这种不对称为扩容留出了一条便宜的口子：只把输入侧的查表做大。主干还是在原来的 token 序列上算，每个位置只多读几行向量，几乎不涨 FLOPs。Over-Encoding（OE）走的就是这条路——它把相邻 token 拼成局部 n-gram，单独建几张大表来查。听起来很直白，真要落地却得先答好四个问题：海量组合怎么寻址，哈希撞车时梯度会怎样，几十亿参数的表怎么跨卡存才不拖垮通信，以及多花出来的参数到底值不值。

输入和输出为何值得分别扩展

标准的输入 embedding 是一张 \(E\in\mathbb R^{V\times d}\) 的大表，\(V\) 是基础词表大小，\(d\) 是隐藏维度。拿到 token ID \(x_t\)，直接取出第 \(x_t\) 行 \(E[x_t]\) 就完事了——整张表虽然存着 \(Vd\) 个参数，每个位置实际只读 \(d\) 个数。换句话说，把表的行数拉大只会增加存储，单次查表要搬的数据量纹丝不动。

输出头刚好相反：它要把隐藏状态 \(h_t\in\mathbb R^d\) 乘上整个词表矩阵，算出 \(V\) 个 logits。两边的账写在一起，差距一目了然：

$$B_{\mathrm{lookup}}=d\,b_e\quad\text{B/token},\qquad F_{\mathrm{head}}\approx2dV\quad\text{FLOPs/token}.$$

这里 \(b_e\) 是单个元素的字节数（BF16 下为 2），乘加按 2 FLOPs 算。把 \(d=4096\)、\(V=131{,}072\) 代进去，输入侧每 token 只读 8192 B，输出头却要干掉约 1.074 GFLOPs——而且一扩词表，后者就跟着线性暴涨。

所以 OE 干脆把输入和输出拆开处理：基础 tokenizer、序列长度和输出词表一律不动，每个位置照旧预测下一个基础 token，只在输入侧给相邻 token 的局部组合加上查表。要是输出侧也想扩监督信号，可以另行搭配多 token 预测，不过那是另一本训练目标和计算账，和这里讨论的输入侧扩容互不干扰。

从一个 token 到一个局部上下文

拿一个 5 词的玩具词表上手试一下：padding=0、we=1、read=2、write=3、code=4（\(V=5\)）。句子 “we read we write read code” 就是序列 \([1, 2, 1, 3, 2, 4]\)。走到位置 \(t\) 时，我们手里不光有当前词 \(x_t\)，还顺带知道它前面那几个词。把这长度为 \(n\) 的后缀（suffix n-gram）看成一个 \(V\) 进制数，就能压成一个整数编号，再对第 \(n\) 阶表的行数 \(M_n\) 取模落到具体行号：

$$u_{t,n}=\sum_{j=0}^{n-1}x_{t-j}V^j,\qquad \htmlData{symbol=hash-row}{r_{t,n}}=u_{t,n}\bmod M_n.$$

序列开头越界的位置补 0。按这套编码，当前 token 在最低位，bigram “we read” 的完整编号是 \(2+5\times 1=7\)。为什么非得取模？因为直接按组合建表要开 \(V^n\) 行——十万词表光 trigram 就有 \(10^{15}\) 种可能，显存根本装不下。取模就是拿可控的表长 \(M_n\) 把地址空间硬压下来。

代价是不同短语可能会撞进同一行。比如 bigram 表只给 7 行时，“we read”（编号 7）和 “read code”（编号 14）取模后都掉在第 0 行，只能共用同一条向量；一旦把表扩到 11 行，它们就各自去第 7 行和第 3 行，互不打架了。扩容表长买回来的，正是这份把挤在一起的局部模式拆开的空间。

真写代码时，不用先把巨大的 \(u_{t,n}\) 拼出来再取模：从最左边的 token 开始，每步乘以 \(V\)、加上下一个 ID、顺手对 \(M_n\) 取一次模，递推算完的结果和最后统一取模完全等价，还不会爆整数。不过别忘了，哈希规则、词表版本、序列边界和 padding ID 全都绑死在模型权重上——训练和推理只要有一处对不上，查出来的就全是错行。

哈希碰撞怎样进入梯度

表开多大才算够用？先按最理想的均匀独立哈希估算一下。如果语料里有 \(U\) 种不同的 n-gram 要塞进 \(M\) 行，某一行全程没被命中的概率是 \((1-1/M)^U\)，反过来，期望被用上的行数就是：

$$\mathbb E[\text{使用行数}]=M\left[1-\left(1-\frac1M\right)^U\right].$$

拿两组数字感受一下：当 \(U=1000\)、表长也正好给 \(M=1000\) 时，期望只用掉约 632.3 行，意味着大概有 367.7 个模式被迫和别人挤在一起；把表拉大到 \(M=10000\)，用到约 951.7 行，冲突才明显稀下来。当然，这只是均匀分布下的基准——真实文本是重度长尾的，确定性取模偶尔还会撞出周期规律，真排表大小时，得按训练 token 的出现频次加权再算一遍碰撞率。

撞进同一行之后，反向传播会发生什么？记位置 \(t\) 的损失对查出向量的梯度为 \(g_t\)，那么第 \(r\) 行收到的总梯度就是所有命中它的位置之和：

$$\nabla_{E[r]}L=\sum_{t:\,r_t=r}g_t.$$

这就导致碰撞本身分好坏：如果撞到一块的两个模式本来就想把向量往同一个方向推，共享参数反而能多攒点更新样本；反过来，要是它们对下游任务的要求南辕北辙，梯度就会互相抵消，谁也学不好。所以排查碰撞问题，光盯着“有多少个短语落到同一行”不够，还得顺手看高冲突行里的梯度方向是不是在打架，再决定是该扩表、加哈希头，还是干脆把 n-gram 阶数降一档。

还有一个特别阴险的取模陷阱。看 bigram 编号 \(u_{t,2}=x_t+Vx_{t-1}\)：要是图省事把表长取成 \(M=V\)，那么 \(Vx_{t-1}\) 这项取模后直接归零，行号恒等于 \(x_t\)——前一个 token 被彻底抹掉，整张 bigram 表退化成了一张平平无奇的词表！所以表长 \(M\) 必须避开与词表进制 \(V\) 的公因子（通常取质数或与 \(V\) 互质的数），多头之间也要换不同的映射参数。顺带注意整数位宽：做大词表滚动乘加时，CPU 和 GPU 上关于中间溢出和取模的语义必须完全一致，否则线上线下查出的行号对不上。

层次组合、低维切片与表示

如果只靠一张高阶 n-gram 表，问题很快就会暴露：绝大多数长组合在语料里根本见不到几次，对应的行几乎得不到充分更新。OE 的做法是把多阶查表叠在一起——基础词向量 \(E_1[x_t]\) 兜住通用语义，bigram、trigram 再逐层补上更精细的局部语境。更进一步，没必要让每张大表都存完整的 \(d\) 维向量：把第 \(n\) 阶拆成 \(K_n\) 个窄表（行宽 \(q_{n,k}\ll d\)），查出来之后再各自过一个小投影矩阵 \(W_{n,k}\in\mathbb R^{d\times q_{n,k}}\) 升回 \(d\) 维相加即可：

$$h_t=E_1[x_t]+\sum_{n=2}^{N}\sum_{k=1}^{K_n} W_{n,k}E_{n,k}[r_{t,n,k}],$$

其中 \(N\) 是最高阶数，第 \((n,k)\) 个表 \(E_{n,k}\in\mathbb R^{M_{n,k}\times q_{n,k}}\) 拥有各自的行数 \(M_{n,k}\) 和哈希映射。主干网络拿到的依然是普通的 \(d\) 维输入，唯一多出来的计算只是这几个小投影。

把多出来的参数和每 token 投影计算量列成账：

$$P_{\mathrm{extra}}=\sum_{n,k}\big(M_{n,k}q_{n,k}+d\,q_{n,k}\big),\qquad F_{\mathrm{proj/token}}\approx2d\sum_{n,k}q_{n,k}.$$

代一组典型配置感受一下量级：两张表，各 10M 行、行宽 \(q=128\)，主干宽度 \(d=4096\)。两张表一共塞进了 2.56B 参数（BF16 占 5.12 GB），而投影矩阵总共才 1.05M；落到每个 token 头上，只需读两行共 512 B，投影计算约 2.10 MFLOPs，和动辄上 GFLOPs 的输出头完全不在一个量级。而且两个旋钮的代价是分开的：拉大表长 \(M\) 只涨第一项的存储，不加每步计算；加头数或拉宽 \(q\) 才会同时推高单 token 的访存和投影开销。

拆成多头还有一个关键前提：各个头必须用不同的哈希映射。要是几个窄头共享同一套地址，那任意两个短语只要撞车，就会在所有头上同时撞车，分头就白分了——本质上只是把一整块大向量切成了几段。反过来，只要映射互相独立，两个短语在第一个头撞上，在别的头大概率会被分到不同行里；在均匀独立哈希下，它们在 \(K\) 张 \(M\) 行的表里同时撞上的概率会骤降到 \(M^{-K}\)。

查词、查潜在类别与查上下文

用大表给语言模型补局部记忆，OE 不是第一个吃螃蟹的。往前翻这条技术路线，能看到三种风格迥异的取舍：

  • LookupLM 最早把前序 token 的哈希向量拼进 RNN 输入，专门用来记固定短语、罕见拼写和人名这类长尾组合——它证明了“存更多模式”不必靠把循环网络加宽来实现。
  • N-Grammer 不直接拿原始 token ID 拼地址，而是先把中间表示按头做离散聚类，再拿相邻位置的聚类 ID 拼成潜在 bigram 去查表，查出来的向量和原表示各自过 LayerNorm 后再拼接。好处是语义相近的输入能自动共享同一条组合表项，泛化更自然；代价是地址得等前面算完聚类才能确定。
  • OE 退回到最直接的原始 token ID 多阶后缀，在模型最入口把投影后的查表向量直接加进主干。因为只依赖输入序列，所有行号在主干开算之前就能一次性算齐，工程上极其好做预取和并行。

说到底，这一脉的设计就差在三个开关上：地址从哪来（原始 ID 还是潜在聚类）、窗口看多长、查出来的向量插在哪一层融合。沿着这条线再往前走一步，就是后面要讲的Engram：它保留了 OE 这种开算前就能定死地址的便宜做法，但不再在入口一把全加进去，而是让主干中间层的隐藏状态来门控——决定此刻到底要不要放行查出来的记忆。

大表怎样分片才保留稀疏性

算力上省下来的便宜，很容易在分布式通信里全吐回去。如果直接把几张大表扔进普通 FSDP，每次前向之前都要把整组权重 all-gather 一遍，每张卡就会被迫收下海量当前 batch 根本用不到的行。表越扩越大，查表计算量纹丝不动，通信量却直线往上飙，训练吞吐跟着一路往下掉。

要保住稀疏访问的好处，就得改成按行分片。假设有 \(p\) 张卡（rank），第 \(r\) 行固定归属于 \(\operatorname{owner}(r)=r\bmod p\) 号卡，在片内的偏移是 \(\lfloor r/p\rfloor\)。前向时，每张卡只把自己手头需要的行号发给对应的 owner，由 owner 查出向量再发回来；反向时反着走一遍，把梯度送回 owner，按行号原地累加。OE 的分布式实现跑的就是这套“发 ID → 取向量 → 回传梯度”的 all-to-all 路径。

两种方案的通信差了几个数量级？假设请求均匀落到各卡、每张卡分到 \(T_{\mathrm{local}}\) 个 token、暂不做请求去重，我们来比一下单次前向里平均每张卡要发出去多少字节：

$$B_{\mathrm{gather}}\approx\frac{p-1}{p}\,P_{\mathrm{table}}b_e, \qquad B_{\mathrm{rows}}\approx\frac{p-1}{p}\,T_{\mathrm{local}}H\,(b_{id}+q b_e).$$

这里 \(P_{\mathrm{table}}\) 是所有表的总参数量，\(H\) 是每个 token 要查的行数，\(q\) 是行宽，\(b_{id}\) 是单个行号的字节数。看清这两条式子的依赖项就行：左边跟着总表大小走，右边只跟着当前 batch 激活了多少行走（反向还会多一趟向量梯度回传，但量级同样只看激活行数）。

拿默认配置一看就明白了：两张表权重共 5.12 GB，做一次全表 gather，每张卡平均要发出 4.48 GB；换成按行分片，一次前向只发约 3.61 MiB，差了上千倍。不过省下带宽是有工程代价的：通信层得自己管好请求重排和回包还原，确保每个 token 拿回的正是自己要的那一行；同一个 batch 里有多个位置撞到同一行时，反向也必须把所有梯度严丝合缝地累加起来，绝不能互相覆盖。

跑在真实语料上，还会立刻碰到热点行问题——高频短语会反复砸向某几张卡，把 all-to-all 拖成木桶效应。真遇到掉速，先统计各 owner 收到的请求数和最慢那张卡的排队时间，再去上请求去重、热门行缓存或局部副本。只是训练时权重步步都在变，缓存热门行得操心更新同步；等到推理时表冻住了，直接缓存复用就省心得多。

另外别只盯着 BF16 权重的显存账：训练时每张表后面还拖着 FP32 master 权重和 Adam 的两份矩状态，实际显存通常是裸权重的几倍。更微妙的是未命中行到底更不更新。标准 dense Adam 下，哪怕某一行这一步梯度是 0，之前攒下的动量依然会衰减并推动权重，AdamW 的 weight decay 也会扫过整张表；要是照这个语义跑，每步优化器都得把几十亿参数的整张表从显存搬一遍，带宽立刻成了新瓶颈。反过来，如果改成只更新本步命中的稀疏优化器，就必须明确约定好“空闲几步再被唤醒时，动量和衰减怎么补算”。动代码前不妨先写个玩具序列——“访问一次、歇十步、再访问一次”——核对参数和一二阶矩是不是严格符合预期，别一不小心把优化器语义改歪了，还以为是分片带来的效果差异。

把视角拉回表本身，按行统计整个训练期的命中次数也很有用：你能一眼看出多少行从头到尾没人访问、多少行只蹭过寥寥几次更新、哪些行热得发烫。如果总表参数预算卡死了，这就对应着“少量宽行”和“大量窄行”的权衡——宽行给每个模式留出更大的表达空间，窄行则能多开行数把冲突压下去，只是两者牵动的投影成本和访问覆盖不同，得结合真实命中分布来挑。

动手搭完这套分片层，先跑两步最小验证最省心：第一步核对正确性，拿单机单表、按行分片以及打乱请求顺序后的结果逐项比对，前向向量必须比特级一致，反向每行梯度也要和集中式 scatter-add 对上；第二步做消融压测，固定同一份请求，分别拉大表长和拉大 batch size，看通信量和 step 时间怎么动，就能干净地分清瓶颈究竟卡在全表扫描、激活流量还是热点调度。

怎样判断新增容量花得值

加上输入大表之后，模型的“总参数量”和“每 token 激活计算量”脱钩了，光看 loss 降了多少很容易产生错觉。要做靠谱的消融，先把主干结构、tokenizer、训练 token 数和学习率曲线钉死，再去扫表长、阶数、头数和行宽；跑完不仅看验证集 loss，更要回头核对表的实际命中分布——要是扩了十倍表长，八成行根本没怎么被更新，那多出来的显存就是白花的。

高阶 n-gram 最常见的陷阱是背得太熟、泛化不动：训练集 loss 一路往下走，换到新来源的验证集上却原地踏步。想确认是不是踩进了这个坑，最直接的办法是按 n-gram 在训练集里的出现频次分桶评测，把高频短语、低频短语和从未见过的组合拆开看——如果收益全堆在高频桶里、未见桶纹丝不动，就在主干不变的前提下把阶数往回缩一档，或者加强数据去重。

最后，别忘了把这笔参数预算放进横向对比里：同样多花几十亿参数，拿去扩 OE 查表、多加几个 MoE 专家，还是直接加宽 dense 主干？三者要在相同的训练算力和推理延迟上限下同台打擂。大表最拿手的是把高频局部模式“提前缓存”成现成表示，但它替不了主干去整合长距离上下文和做动态推理；花多少钱买表、花多少钱买算力，归根结底看的是这笔参数能不能在同等算力账下换来更低的验证 loss，而不是单纯把参数量做大。

计算与诊断

1. 查表容量和输出计算

假设有两张 BF16 大表，各 16M 行、行宽 128，主干维度 4096。算一下表权重总容量、每 token 查表读取的字节数，以及投影的 FLOPs。再顺手算一笔对比账：如果把输出词表从 64k 扩到 128k（k 按 1000 计），完整输出头每 token 会多出多少 FLOPs？

展开解答

表权重一共 \(2\times16\times10^6\times128\times2=8.192\) GB（外加两块投影矩阵约 1.05M 参数）；每个 token 只读两行，共 \(2\times128\times2=512\) B，投影计算量约 \(2\times4096\times256=2{,}097{,}152\) FLOPs（约 2.10 MFLOPs）。相比之下，输出词表涨 64k，输出头每 token 就要多做 \(2\times4096\times64{,}000=524{,}288{,}000\) FLOPs，约 0.524 GFLOPs——足足是查表投影的 250 倍。

2. 哈希为什么会丢掉上下文

沿用 \(V=5\) 的小词表，bigram 编号按 \(x_t+5x_{t-1}\) 计算。分别取表长 \(M=5\) 和 \(M=7\)，看看 “we read” \([1,2]\) 和 “write read” \([3,2]\) 会落到哪一行，哪种选法能把它们分开？

展开解答

两者的完整编号分别是 7 和 17。对 5 取模全都得到 2，只剩下当前 token 的 ID；对 7 取模则分别落到第 0 行和第 3 行。一般地，只要取 \(M=V\)，就有 \((x_t+Vx_{t-1})\bmod V=x_t\)，前文完全失效。写单测时，固定结尾 token、换不同前缀看行号变不变，一眼就能抓出这种退化。

3. 同一行收到两份梯度

同一个 batch 里有两个位置都查到了第 3 行，传回来的梯度分别是 \([1,-2]\) 和 \([-0.5,1]\)。假设学习率 0.1、这一行原来的值是 \([0.2,0.3]\)，用最简单的 SGD（无动量、无衰减），更新后应该是多少？如果分布式回传写岔了，后到的梯度直接覆盖了先到的，结果又会错成什么样？

展开解答

正确的做法是先求和：总梯度 \([0.5,-1]\)，更新后变成 \([0.15,0.4]\)。如果发生覆盖、只保留了后一份梯度 \([-0.5,1]\)，结果就会跑偏成 \([0.25,0.2]\)。更糟的是，覆盖更新的结果还会随请求到达顺序变化；求和更新则对顺序完全不敏感，正好用来当分布式反向回传的自动化单测。

4. 表扩了 4 倍、吞吐掉下来，怎么定位

把表长拉大到原来的 4 倍，batch、头数和行宽全都不变。测下来 GPU 计算时间几乎没涨，单步耗时却明显变长了。选三个最直接的观测指标，把“全表 gather”“稀疏热点”和“优化器扫整表”这三种嫌疑分开。

展开解答

按一步训练的时间线逐段排查就行：第一，看前向之前的通信字节数有没有跟着暴涨 4 倍——涨了，多半是某处还在偷偷做全参数 all-gather，赶紧切回行分片；第二，拉出各 owner 收到的请求数和最慢那张卡的 all-to-all 耗时，要是分布严重偏斜，瓶颈就在热点行等待，换一批均匀随机 ID 压测一下立刻能坐实；第三，单独给 optimizer.step() 计时，如果只有这一段涨了近 4 倍，说明优化器在按 dense 语义扫整张表及其状态，得切到明确的稀疏更新实现。

一个可复现的稀疏查表实验

下载实验脚本，直接跑 python3 lab.py --seed 7（纯 NumPy，不需要 GPU）。脚本把前面聊过的核心机制全部过了一遍：滚动取模和 Python 任意精度大整数算出的行号是否严丝合缝、\(M=V\) 时的前缀退化、均匀哈希的期望占用率、按行分片的前向等价性与碰撞梯度累加（还顺带做了有限差分验导），以及文中的容量和通信算例。

跑通后你会看到：\(M=5\) 时结尾相同的 bigram 全挤在同一行，换到 \(M=7\) 就彻底散开；1000 个模式塞进 1000 行的模拟均值紧贴理论值 632.3；集中式和按行分片的前向、梯度最大误差都是 0。你也可以把 --ranks 4 换成 2 或 8——每行归属的卡变了，但算出来的向量和梯度纹丝不动；或者干脆进脚本把模拟表行数调小，亲眼看看冲突是怎么迅速堆起来的。
