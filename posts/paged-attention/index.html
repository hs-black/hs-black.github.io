PagedAttention：让 KV cache 按需生长

交互2026-10-20更新于 2026-10-22

一条请求刚读完 100 个 token，接下来可能只生成 20 个，也可能生成 2000 个。服务端必须保存它的 KV cache，却不知道这段缓存最终会长到哪里。给它预留一个足够大的连续数组，短请求会占着不用的空间；等数组满了再扩容，又可能要搬动已经写好的历史。

PagedAttention 把这个问题拆成两件事：请求认为历史是一条连续序列，显存只负责提供固定大小的块。一张很小的页表把两者接起来。请求增加一个 token 时，通常只写下一个槽位；跨过块边界时，再申请一块空闲显存。Attention 仍然按原来的逻辑位置计算，只是读取 K、V 前多了一次地址转换。

这改变的是缓存的组织方式。分页保持每个 token 的 K/V 元素数和完整 attention 的历史读取范围。容量收益来自更少的预留浪费、更容易复用的空闲块，以及多个请求对相同历史的共享；这些收益再转化成可以容纳的并发和调度空间。

1. 连续缓存在哪里浪费

假设每条请求最多允许 4096 个 token。若一开始就给每条请求分配能装下 4096 个 token 的连续 KV 空间，当前只有 128 个 token 的请求也会占据整份配额。它尚未使用的 3968 个位置不能再分给别人。这是预留空间与实际长度之间的浪费，与 attention 的数学计算无关。

另一种办法是按当前长度分配，再随着生成扩容。问题在于，请求结束的时间并不一致。显存里会留下大小不同的空洞：总空闲量可能够用，却没有一段足够大的连续空间。重新分配并复制缓存能解决一部分问题，但复制需要时间，也可能产生新旧两份缓存同时存在的峰值。

分页把缓存划成等大的物理块，每块容纳固定数量的 token。这里用小写 \(\htmlData{symbol=page-size}{b}\) 表示每块的 token 数，例如 \(b=16\)。一个请求的第 0 个逻辑块、第 1 个逻辑块，可以分别位于物理块 5 和物理块 1；它们不需要在显存中相邻。

只要空闲池还有一块，任意请求就能拿来扩展。已经写好的块保持原位，页表末尾多一个物理块编号即可。整块之间的分配空洞因而不再要求整理成一段连续区域；但最后一块仍可能装不满，这部分叫块内碎片，后面会单独计算。

“按需申请”指从预先建立的 KV 块池中取一块。显存池的物理容量可以早已分配好，请求占用的块数仍然按需增长。

2. 从逻辑位置找到物理地址

先看最小的地址转换。位置编号从 0 开始，\(\htmlData{symbol=position}{t}\) 是请求内部的逻辑 token 位置，\(\htmlData{symbol=page-size}{b}\) 是每块的 token 数。把 \(t\) 除以 \(b\)，商告诉我们去查页表的哪一项，余数告诉我们在块里的哪个槽位：

$$\htmlData{symbol=logical-page}{j}=\left\lfloor\frac{\htmlData{symbol=position}{t}}{\htmlData{symbol=page-size}{b}}\right\rfloor,\qquad \htmlData{symbol=offset}{r}=t\bmod b,\qquad \htmlData{symbol=physical-page}{p}=\operatorname{page\_table}[j].$$

本式中，\(j\) 是逻辑块编号，\(r\) 是块内偏移，\(p\) 是物理块编号；三者都从 0 开始计数。页表把逻辑块编号映射到物理块编号，块内偏移不变。

例如块大小为 4，页表是 [5, 1]。逻辑位置 0～3 在物理块 5，位置 4～7 在物理块 1。读取位置 6 时，先算出 \(j=1\)、\(r=2\)，再查到 page_table[1]=1，最终读取物理块 1 的槽位 2。历史顺序由页表项的排列决定。

再往下一层：算出字节偏移

页表只帮我们找到物理块。块中还有 KV 头与向量维度，因此 kernel 还要继续计算元素偏移。假设某一层的 K 数组采用连续布局 [物理块数, b, Hkv, d]，V 放在另一个同形状数组中。这里 \(\htmlData{symbol=kv-heads}{H_{kv}}\) 是 KV 头数，\(\htmlData{symbol=head-dim}{d}\) 是每个头的维度，\(h\) 和 \(c\) 分别是要读取的头编号与通道编号。

$$\operatorname{element\_offset}=((\htmlData{symbol=physical-page}{p}\,\htmlData{symbol=page-size}{b}+\htmlData{symbol=offset}{r})\,\htmlData{symbol=kv-heads}{H_{kv}}+h)\,\htmlData{symbol=head-dim}{d}+c.$$

仍然读取逻辑位置 6，但这次取 KV 头 1、通道 3。令每块 4 token、KV 头数为 2、头维度为 4，则元素偏移是 \(((1\times4+2)\times2+1)\times4+3=55\)。BF16 每元素 2 字节，所以地址是 K 数组首地址 + 110 B。这是这个教学布局的结果；真实 kernel 可以改变轴顺序或向量化布局，但必须保留同一个逻辑映射。

因此，“页表看起来正确”还不够。把 KV 头数与 query 头数混用、把字节 stride 当成元素 stride，都会读到错误数据。这也是地址公式要把每个轴写清楚的原因。

3. 散落的 KV 怎样计算同一个 attention

缓存放散了，最直接的做法是每轮先把它们重新拼成一个连续数组，再运行原来的 attention。这个办法适合写正确性参考，却又引入了一遍历史数据复制。PagedAttention 的关键是让 kernel 沿页表直接读取各个物理块，边读边算，避免为了调用 attention 而先拼回完整历史。

数学上，当前 query 看到的仍是同一组 key 和 value。对一个 query 头，用 \(\htmlData{symbol=score}{z_i}\) 表示它与第 \(i\) 个 key 点积、缩放并加上 mask 后的分数，\(\htmlData{symbol=value}{v_i}\) 表示对应的 value 向量。Attention 输出是：

$$\htmlData{symbol=output}{y}=\frac{\sum_i e^{\htmlData{symbol=score}{z_i}}\,\htmlData{symbol=value}{v_i}}{\sum_i e^{z_i}}.$$

本式的求和覆盖当前 query 能看到的所有有效逻辑位置。\(z_i\) 是一个标量分数，\(v_i\) 和输出 \(y\) 是向量；图 2 会先用只有一个通道的 value，把每一步算成普通数字。

页表只改变这些 \((z_i,v_i)\) 在内存中的取出位置，不改变求和对象。只要 mask 与数值归一化正确，分页结果就应与连续布局一致。但“每个块分别做 softmax，再把输出平均”并不正确：各块贡献的概率总量通常不同，不能给它们相同的权重。

用一个反例看清归一化在哪里

假设两个块分别含两个位置，四个分数为 \([0,\ln2,\ln3,\ln4]\)，对应的标量 value 为 \([2,4,6,8]\)。指数化后是 \([1,2,3,4]\)，全部权重的和为 10，所以正确输出是：

$$y=\frac{1\times2+2\times4+3\times6+4\times8}{1+2+3+4}=6.$$

若只看第一块，它的局部输出是 \(10/3\)；第二块的局部输出是 \(50/7\)。二者等权平均得到约 5.238，已经不是 6。正确合并应给两块分别分配 \(3/10\) 和 \(7/10\) 的总概率，因为它们在全局分母中贡献了 3 和 7。

怎样不保存所有分数，也能合并结果

稳定 softmax 会先减去最大分数，避免直接计算过大的指数。对一个已经处理的块，保留三个量就够了：最大分数 \(\htmlData{symbol=maximum}{m}\)、减去该最大值后的指数和 \(\htmlData{symbol=denominator}{\ell}\)，以及同样缩放后的 value 加权和 \(\htmlData{symbol=numerator}{u}\)。

$$m=\max_i z_i,\qquad \ell=\sum_i e^{z_i-m},\qquad u=\sum_i e^{z_i-m}v_i.$$

这里 \(m\) 和 \(\ell\) 是标量，\(u\) 与 value 同维度；处理完所有块后，输出就是 \(y=u/\ell\)。要合并两个状态 \((m_1,\ell_1,u_1)\) 和 \((m_2,\ell_2,u_2)\)，先把二者换到同一个最大值 \(m=\max(m_1,m_2)\) 下，再相加：

$$\ell=e^{m_1-m}\ell_1+e^{m_2-m}\ell_2,$$ $$u=e^{m_1-m}u_1+e^{m_2-m}u_2,\qquad y=u/\ell.$$

缩放因子来自指数运算的恒等式。第一块原本保存的是“减去 \(m_1\) 后的和”，乘 \(e^{m_1-m}\) 正好把它改成“减去 \(m\) 后的和”。分子和分母同时换尺度，最终比值不变。这与 FlashAttention 的在线 softmax 使用的是同一条恒等式；分页解决存储地址，在线合并解决分块计算后的归一化。

最后一块没有填满，不能把空槽当成零分数

若请求只有 6 个有效位置、块大小为 4，第二块只有前两个槽位有效。Attention 可以按块读取，但必须根据请求的有效逻辑长度排除后两个槽。空槽的 K/V 即使碰巧都是零，点积分数 0 也会贡献 \(e^0=1\)，把真正位置的概率稀释掉。

因此，空槽的分数要被视为 \(-\infty\)，概率贡献为零。对于完全无有效位置的块，直接跳过，或使用“分母为 0”的空状态进行显式分支处理；不要机械计算 \(-\infty-(-\infty)\)，因为那会得到 NaN。这个边界比正常数据流更容易在单元测试中漏掉。

4. 用页数算容量，而不只数 token

分页后的容量预算有两层：先计算一个 token 的 KV 占多少字节，再计算实际占用了多少个物理块。设模型有 \(\htmlData{symbol=layers}{L}\) 层，每层有 \(\htmlData{symbol=kv-heads}{H_{kv}}\) 个 KV 头，每头 \(\htmlData{symbol=head-dim}{d}\) 维，每元素占 \(\htmlData{symbol=element-bytes}{e}\) 字节；K 与 V 维度相同，全部这些层都保留完整历史。

$$\htmlData{symbol=token-bytes}{m_{\mathrm{tok}}}=2\,\htmlData{symbol=layers}{L}\,\htmlData{symbol=kv-heads}{H_{kv}}\,\htmlData{symbol=head-dim}{d}\,\htmlData{symbol=element-bytes}{e},\qquad \htmlData{symbol=page-bytes}{m_{\mathrm{page}}}=\htmlData{symbol=page-size}{b}\,m_{\mathrm{tok}}.$$

\(m_{\mathrm{tok}}\) 是跨全部缓存层、每 token 的 KV 字节数；\(m_{\mathrm{page}}\) 是同样范围内一组物理块的字节数。\(b\) 仍是每块 token 数，前面的 2 来自 K、V 两份。按层分别建池的实现应对每层单独核算，再考虑各池的约束。

例如 \(L=24\)、\(H_{kv}=4\)、\(d=128\)，使用 BF16，每元素 \(e=2\) 字节。于是每 token 占 \(49{,}152\) B，也就是 48 KiB。若每块 16 token，一块就是 768 KiB。这里使用二进制单位：1 KiB = 1024 B，1 GiB = 2³⁰ B。

长度为 \(\htmlData{symbol=sequence-length}{S}\) 的请求，不共享块时要分配 \(\lceil S/b\rceil\) 块。上面的模型若当前长度为 1025，块大小为 16，就需要 65 块，实际有 1040 个槽位，其中 15 个尚未使用。它们占据 \(15\times48=720\) KiB；这份尾部浪费不会因页表而消失。

$$\text{尾部空槽}=\left\lceil\frac{\htmlData{symbol=sequence-length}{S}}{\htmlData{symbol=page-size}{b}}\right\rceil b-S,\qquad 0\le\text{尾部空槽}\le b-1.$$

对于多条独立请求，把每条请求向上取整后再相加，不能先把总 token 数相加再取整。长度为 17、32、63 的三条请求，块大小为 4 时，块数为 \(5+8+16=29\)，总共 116 个槽位，实际用了 112 个，浪费 4 个；块大小改成 16 后，块数为 \(2+2+4=8\)，128 个槽位中有 16 个未使用。

页内布局怎样配合 GPU 读取

页表决定访问哪个物理块，块内布局决定相邻线程能否读到相邻地址。QK 点积沿头维度累加，value 的加权和沿历史位置累加，这两次归约可以采用不同的存储顺序。

一种向量化布局将 K 写成 [块, KV头, d/x, b, x]，V 写成 [块, KV头, d, b]。这里 d 是每头维度，b 是每块 token 数，x 是一组连续加载的元素数。BF16 每元素 2 B，取 x=8 时，一组恰好 16 B；K 中同一 token 的连续分量便于组成点积，V 中连续的历史位置便于沿 token 维度归约。

例如 d=128、b=16，一个头的单个 K 块包含 \(128\times16\times2=4096\) B，K 和 V 合计 8 KiB。换一个页大小会同时改变尾部浪费、每块数据量和线程的工作划分。因此选择页大小时，应同时比较容量利用率和 attention kernel 耗时；同一页表算法可以对应多种高效的 GPU 布局。

块越小越好吗？

小块通常减少尾部空槽，也让共享与回收更细。但相同历史会对应更多页表项、更多块边界，kernel 的访存、工作划分和元数据处理也会变化。大块通常减少这些管理工作，却增加短请求的尾部浪费，并可能扩大一次写时复制需要复制的内容。

页大小因而是容量与执行效率的共同选择。先用真实长度分布计算尾部浪费，再比较对应 kernel 在目标 batch、上下文长度下的时间。仅凭“页表更短”或“碎片更少”，都不能直接推出整体服务更快。

还要留出权重、激活、通信缓冲、临时 workspace 和运行时占用。若把整张卡的显存都当作 KV 池，算出来的并发没有可执行意义。对于多卡服务，这份账应按每张卡实际保存的 KV 头与层计算；头复制、不同层的缓存策略，都可能让简单的“总量除以卡数”失效。

5. 共享前缀之后，谁可以写入

两条请求若有完全相同的有效前缀，并且模型、adapter、位置与 attention 配置一致，这段前缀对应的 K/V 也相同。它们可以让各自的页表指向同一组物理块。区别在于，页表属于请求，物理块可以同时被多个请求引用。

共享需要计数。一个物理块的引用计数为 2，意味着仍有两个所有者依赖它，不能因为其中一条请求完成就释放。若缓存管理器还要把这块留给后续请求复用，管理器的持有关系也必须纳入生命周期设计。图中的引用来自两个活动请求，引用归零后块被归还空闲池。

完整块里的历史不会再写入，共享比较直接；真正容易出错的是未填满的共享尾块。假设一块能装 4 个 token，现在已经存了 3 个。A、B 都指向它，A 想把自己的下一个 token 写进最后一槽。若直接写，B 随后追加自己的 token 时就会覆盖 A 的内容。B 的有效长度仍为 3 时还不会读取这个槽位，但同一个槽位无法同时保存两条分支各自的第 4 个 token。

解决办法是写时复制（copy-on-write，COW）：A 先申请一个新块，把旧尾块中有效的 3 个位置复制过去，再让自己的页表改指新块，最后追加 A 的 token。B 保持指向旧块。已经共享的完整前缀块不需要一起复制。

如果共享块恰好已经填满，情况更简单：A 的下一个 token 直接写进新申请的下一块，旧块继续共享，不需要复制旧块。这就是“逻辑追加”和“原地改写共享尾块”的区别。若引擎只复用填满的 prefix 块，也可以避免跨请求复用未满尾块的这类复杂性；但请求分叉等场景仍需要清楚地定义写入权限。

共享也不会把所有 attention 读取合为一次。两个请求的 query 可能不同，仍然各自计算 attention；共享首先减少物理存储和重复前缀计算。能否在某次 kernel 执行里进一步复用缓存读取，还取决于实际执行方式。

6. 把生命周期写进代码

分页系统至少要同时维护三份状态：请求的页表和有效长度、物理块的引用计数、空闲块集合。它们必须描述同一个事实。只更新页表却忘了减旧块引用，会泄漏；引用归零后提前回收 GPU 仍在读取的块，则可能把另一条请求的新数据当作旧历史读入。

追加一个 token 时，可以先判断尾块状态。下面把“块里有几个有效位置”也作为显式元数据；省略模型计算，只展示内存管理顺序：

if 没有尾块 or 尾块已满:
    new = allocate()          # 失败时尚未改变请求页表
    page_table.append(new)
elif refcount[尾块] > 1:
    old = 尾块
    new = allocate()          # 先确保申请成功
    copy_valid_KV(old, new)
    page_table[-1] = new
    refcount[old] -= 1
write_KV(page_table[-1], next_slot)
valid_length += 1

为什么先申请，再改旧引用？因为申请可能失败。若先把旧块引用减掉、甚至释放，再发现没有空闲块，原来的有效状态已经被破坏。CPU 实验中会专门制造这个失败：一个块被两条请求共享，池里没有空块，此时 COW 必须报告容量不足，并保持两个页表、原内容和引用计数完全不变。

GPU 上还多了一层时间关系：复制尚未完成时不能开始读取新块；读取旧块的 kernel 尚未完成时不能把它复用给别人。引用计数表达“谁拥有”，event 或其他完成协议表达“谁还在使用”。这两个条件都满足，回收才成立。它们与 跨 stream 的缓冲区生命周期 是同一个问题。

所有活动请求也可能在同一轮跨越块边界。每条请求当前看起来都能继续，下一轮却一起申请新块。调度器需要结合可用块、增长预算和抢占策略作出准入决定。保守预留上界可以避免这类同时增长耗尽容量，但会降低利用率；更积极的策略则需要可靠的等待、重算或换出路径。分页提供可管理的块，调度器据此决定准入和抢占。

7. 结果错了，先检查哪一层

不要一开始就用生成文本判断缓存是否正确。一个错位的 K 向量可能只略微改变分数，argmax 恰好没变，文本仍然看起来正常。更有效的办法是固定输入和权重，比较每一步的 attention 输出或 logits，并从最小输入开始缩小范围。

现象优先检查最小复现
只在跨块后出错页表索引、除法/取模、块 stride长度 b−1、b、b+1
只有最后一块出错有效长度与空槽 mask块大小 4、长度 5 或 6
换物理块编号后结果变了把物理顺序误当成逻辑顺序或 RoPE 位置把 [0,1] 改成 [5,1]
分叉后两请求互相影响COW、共享尾块、缓存身份共享 3/4 满的尾块，再分别追加
数值正确，运行久了却 OOM完成/取消/失败路径的引用释放反复创建、分叉、释放，核对空闲数

再加两个很实用的不变量。第一，空闲块不能同时出现在任何有效页表中；第二，每个物理块的引用数，应等于当前所有拥有者对它的引用总数。对于没有持久 prefix cache 的小实验，全部请求结束后，空闲块数量应回到初始值。实际引擎若保留 prefix cache，要把“仍被缓存持有”与“泄漏”区分开。

比较 attention 时，参考路径可以先按逻辑顺序把 K/V 拼回连续数组，显式构造 mask，再做标准 softmax。优化路径通过页表直接读取；二者只共享模型输入，尽量不共享地址转换代码。否则同一个地址错误可能同时出现在实现和“参考”里，让测试错误地通过。

外部缓存接入后，引用还要覆盖异步读者

如果冷启动的结果正常，打开外部 prefix cache、运行一段时间后才出现结果漂移，可以沿着块的生命周期检查：后台任务何时开始读取 GPU 数据，请求何时被抢占，物理块何时被重新分配。页表和哈希都正确时，后台任务仍可能在物理块已经改归另一条请求后，读出新请求的 K/V，再把它存到旧缓存键下。

解决这类竞争需要把在途搬运纳入所有权。提交异步读取时持有块，等待完成事件后释放；或者先把有效数据复制到具有独立寿命的 staging buffer。请求取消、抢占和正常完成都要经过这套释放协议。调试时给块分配增加 generation 编号，同时记录任务提交、完成、归还、重新分配四类事件；这样一次错误命中能追溯到具体的复用时刻。

缓存池频繁满：把抢占次数和尾延迟一起看

当空闲块反复降到零，服务仍能输出，但长请求的尾延迟突然上升，检查抢占与重算计数。重算会重新执行已处理的前缀，占用计算与调度预算。先固定请求长度分布，降低活动请求上限，观察抢占次数和 P99 延迟是否同步下降；再根据剩余显存调整 KV 池预算。比较配置时一起记录有效吞吐、等待队列和峰值占用，才能判断容量增加带来的实际收益。

8. 练习：从计算走到排错

下面继续使用同一套记号：\(b\) 是每块 token 数，\(L\) 是层数，\(H_{kv}\) 是 KV 头数，\(d\) 是每头维度；BF16 每元素为 2 字节。每道题都可以先写出单位，再代入数字。

练习 1：8 GiB 的 KV 池能装多少请求？

模型有 24 层、4 个 KV 头，每头 128 维，使用 BF16；每块 16 token。已有一份专门划给 KV 的 8 GiB 池，不共享块。每条请求当前长度都是 1025。求每 token 与每块的字节数、池中完整块数、最多能放多少条请求，以及最后剩多少空间。

展开参考解答

每 token 为 \(2\times24\times4\times128\times2=49{,}152\) B，即 48 KiB；每块 16 token，所以每块为 768 KiB。

池能容纳 \(\lfloor8\times2^{20}/768\rfloor=10{,}922\) 个完整块，还余下不足一块的 512 KiB。每条请求需要 \(\lceil1025/16\rceil=65\) 块，因此最多为 \(\lfloor10922/65\rfloor=168\) 条，剩 2 个完整块；加上不足一块的 512 KiB，共剩 2 MiB。

这 168 条请求各自还有 15 个尾部空槽。它们已经属于请求占用的块，不能与池中“剩 2 块”混为一谈。请求继续增长时，这个当前长度下的并发还需要重新做增长预算。

练习 2：共享尾块之后，谁该归还哪一块？

每块 4 token。A、B 共享一个已有 3 token 的块 P2，引用为 2，当前空闲块数为 5。A 追加一个 token，随后 A 完成，最后 B 完成。不保留 prefix cache。逐步写出引用与空闲块数。

展开参考解答

A 不能直接写共享尾块，先申请 P3 并复制三个有效位置：P2 的引用变为 1，P3 的引用为 1，空闲块数变为 4。A 的页表改指 P3，再把新 token 写进它的槽位 3。

A 完成时只归还自己持有的 P3，空闲数回到 5；P2 仍由 B 持有。B 完成时 P2 的引用从 1 变成 0，空闲数变为 6。

最后比最初多一块，是因为最初 P2 仍被请求占用。若 A 完成时直接释放共享的 P2，就会破坏 B 的后续读取。

练习 3：页表没错，attention 为什么还是错？

长度为 6，每块 4 token，页表为 [5,1]。一个 kernel 把第二块的 4 个槽位全部送进 softmax；另一个 kernel 正确屏蔽空槽，但把每块独立 softmax 的输出等权平均。两个错误分别怎样修？

展开参考解答

第一个错误与地址无关：第二块只有逻辑位置 4、5 有效。逻辑位置大于等于 6 的分数必须屏蔽为 −∞，不能依靠空槽碰巧为零。若整块没有有效元素，跳过它或显式处理空状态。

第二个错误与归一化有关：不同块的指数和不同，局部输出不能等权平均。用全局 softmax，或按正文的最大值、指数和、加权和三个状态合并。

验证时先固定逻辑 K/V，随机打乱物理块编号，再与连续布局参考比较。覆盖长度 1、b−1、b、b+1；长度 0 则验证 API 的拒绝或空结果约定。

练习 4：手算一次在线合并

块 A 的分数为 [0, ln 2]，value 为 [2,4]；块 B 的分数为 [ln 3, ln 4]，value 为 [6,8]。分别求两个局部状态，再合并。为什么第一块的分子和分母都要乘 1/2？

展开参考解答

A 以 ln 2 为最大值，缩放后的指数为 [1/2,1]，所以状态是 \((\ln2,1.5,5)\)。B 以 ln 4 为最大值，指数为 [3/4,1]，状态是 \((\ln4,1.75,12.5)\)。

共同最大值是 ln 4。A 的尺度要乘 \(e^{\ln2-\ln4}=1/2\)，得到指数和 0.75、加权和 2.5。合并后分母为 2.5，分子为 15，输出为 6。

只缩放分子会改变 A 的局部平均值；只缩放分母也会改变输出。两者一起缩放，才能只改变表示方式，同时保留原来的概率关系。

9. 用一个小实验检查页表与生命周期

下载 lab.py

实验只需要 Python 3，不依赖 GPU。它把每个 token 的 KV 简化为一个可检查的编号，重点验证分页后的逻辑读取、分叉隔离、引用计数、释放和 COW 失败时的状态完整性。编号模型不执行真正的 attention；正文的 softmax 算例用于单独检查归一化。

python3 lab.py
python3 lab.py --block-size 16 --lengths 17,32,63

默认块大小为 4，第一条命令应输出：

block_size=4 blocks=29 slots=116
useful=112 tail_waste=4
PASS: dense oracle, COW isolation, refcounts, release, transactional OOM, address=110 B

第二条命令会把块数改为 8、槽位改为 128、尾部浪费改为 16。先预测这些变化，再运行。接着修改 self_test() 的分叉位置：让尾块分别处于未满和恰好填满状态，检查什么时候必须复制，什么时候只需追加新块。最后故意去掉 COW，看最早失败的检查是否确实指出两个分支相互影响。

把这份管理逻辑接入 最小推理引擎 后，就可以继续验证真实 logits：更换物理布局或页大小，输出应在数值容差内保持一致；调整请求到达与完成顺序，页池仍应正确回收。这时，地址、数学和调度三个层面的检查才真正连起来。
