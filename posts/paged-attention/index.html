PagedAttention：让 KV cache 按需生长

token 要按顺序读，显存不必连成一整片。

按 → 推进 · 动画可播放、拖动和倒回

2026-10-20 · 图中的容量、时长与 token 均为教学示意

01 · 问题

答案有多长，开始时并不知道

生成一个 token，就要把它的 K、V 留下来，供后续 token 读取。

如果每个请求一开始都预留最大长度，短答案也会占着一大片空地。

这里两条请求实际只用了 8 个位置，却预留了 24 个。空位挡住了其他请求。

每个方格代表一个 token 在各层的 KV；图中容量仅用于演示。

02 · 分页

顺序留在表里，数据放进空闲块

先把序列切成小块：每块放 4 个 token 的 KV。最后一块可以暂时没装满。

block table 记录“逻辑第几块，对应物理哪一块”：这里是 [P5, P1, P7]。

物理块可以散落在显存里。请求看到的 token 顺序仍然是 0、1、2……

教学块大小 B = 4；实际引擎按模型与 kernel 选择块大小。

03 · 寻址

读 token 6，先查表，再找偏移

attention 仍然按逻辑序列读历史。分页改变的是地址计算。

token 6 落在逻辑块 1。查表得到 P1，再取 P1 里偏移为 2 的 K、V。

PagedAttention kernel 一边按表定位，一边计算 attention。无需先把整个历史复制成连续数组。

token 编号从 0 开始，token 6 是第 7 个；图中只画一层、一个 KV head 的寻址。

04 · 生长

写满一块，再拿下一块

P5 已装满 4 个 token。下一次 decode 会为 token 4 生成新的 K、V。

从空闲池取出 P2，把新 token 的 KV 写进去。原来的 P5 不需要搬家。

block table 追加一项。以后继续填 P2，直到它也装满。

一般只有尾块会留下未用槽位；不同模型的分层存储细节由引擎处理。

05 · 回收

请求结束，块就能交给下一位

一个请求结束后，它独占的 KV 不再需要。这里先看不保留 prefix cache 的情况。

移除 A 的 block table，P5、P2 回到空闲池。无需把其他请求挪到一起。

B 可以立刻拿走空闲块。分页让“结束、释放、再使用”变成小块之间的交接。

启用 prefix caching 时，引用计数归零的满块可以先保留内容，等有新需求再驱逐。

06 · 共享

只读时共用，要写入时再分开

同一提示词生成两种续写时，两条分支可共享已算好的 KV。这里共享的尾块还剩一个空位。

A、B 要写入不同 token，不能同时改同一尾块。给 B 分配 P8，复制已有的 a、b、c。

A 在 P3 写 X，B 在 P8 写 Y。更早的完整只读块仍可继续共享，这就是写时复制。

这是分支采样的写时复制示意；满块 prefix cache 命中通常直接共享，不必复制。

07 · 容量

把浪费限制在尾块里

所需块数 = ceil(序列长度 / 块大小)

长度 10，块大小 4

分配 3 块，共 12 个位置。前两块装满，尾块空 2 个。

每条序列的尾部空位 < 1 块

固定大小块可以互换使用，避免为了连续地址留下大段碎片。

这里计算的是 KV 的 token 槽位，不含 block table、模型权重和临时工作区；共享还会进一步减少实际块数。

08 · 合起来看

调度决定谁上场，分页决定住哪里

请求到来 → 调度本轮 token → 分配 / 查找 KV 块 → GPU 计算

分页让长度不同的请求更容易共存；调度器才能不断让新请求填进空位。
