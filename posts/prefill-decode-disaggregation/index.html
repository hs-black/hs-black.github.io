Prefill / Decode 分离：把计算与缓存交接清楚

交互2026-10-20更新于 2026-10-22

一个正在逐字输出的对话突然停住，几十毫秒后又恢复。此时 GPU 可能正在处理另一条很长的 prompt：prefill 的大矩阵计算占用了本轮时间，原有请求的 decode 一起等待。把 prefill 和 decode 放到不同的 worker，可以分别调度两种工作；代价是把 prefill 产生的 KV cache 交给 decode 一侧。

这次交接同时涉及时间、显存和正确性。要判断拆分是否合适，需要知道传多少字节、谁先排队、缓存对应哪个前缀，以及复制到一半时谁还拥有源页。

1. 交接的是已经完成的模型状态

Prefill 一次处理已知 prompt，在每层写入这些位置的 K/V。Decode 用一个新的输入 token 查询历史，产生下一轮的分布。将两阶段拆开后，P worker 负责 prompt 的前向，D worker 接收对应缓存并继续生成。两端各自保存执行模型需要的权重。

一个完整的交接对象至少包括：请求标识、token 序列与有效长度、位置、每层 KV 的布局与数据、模型/adapter 身份，以及生成过程下一步要消费的 token。如果 P 在末尾 logits 上完成第一次采样，那么这枚采样 token 还要由 D 跑一次前向，它的 K/V 才会进入缓存。协议需要明确第一枚输出由哪一端产生，路由器据此发送 token 并启动后续步骤。

TTFT 的观测边界也随之确定。若 P 的第一枚输出立即发给客户端，KV 交接等待可能出现在第一段 ITL 中；若服务把交接后的 D 输出作为首 token，交接就进入 TTFT。压测时保存真实的 token 时间戳，才能定位等待落在哪一段。

2. 用层、头和位置算出传输体积

普通 GQA 中，每层、每个历史位置保存一组 K 和一组 V。设 \(\htmlData{symbol=layers}{L}\) 是层数，\(H_{kv}\) 是每层 KV 头数，\(d\) 是每头维度，\(\htmlData{symbol=length}{S}\) 是待交接位置数，\(b_e\) 是每元素字节数，则

$$V_{KV}=2LH_{kv}dSb_e.$$

32 层、8 个 KV 头、每头 128 维、BF16 每元素 2 B，得到每 token 128 KiB。1024 token 占 128 MiB；8192 token 占 1 GiB。量化缓存还要传输相应 scale，MLA 则按压缩隐向量和位置分量的实际布局重新计数。

有效带宽记为 \(\htmlData{symbol=bandwidth}{\beta}\)，单位 B/s。一次交接的时间可以拆成

$$T_{handoff}=T_{queue}+T_{setup}+V_{KV}/\beta+T_{convert}+T_{ready}.$$

排队等待、连接/注册开销、布局转换和完成发布都能在 trace 中找到对应区间。若 1 GiB 数据以 8 GiB/s 复制，纯复制需要 125 ms；再加 4 ms setup，得到 129 ms。跨机传输可能占据与一次完整 prefill 相当的时间，因此长 prompt 的传输预算应尽早计算。

3. 同样两张卡，怎样公平比较容量

先比较两个共置 P+D 副本与一个 P 加一个 D。设每请求在 P 上占用 \(s_P\) 秒，在 D 上占用 \(s_D\) 秒；每个 worker 一次执行一个完整阶段。两个共置副本的容量为 \(2/(s_P+s_D)\)。拆分以后，P、网络和 D 是三个依次相连的服务站，长期速率受最慢的一站限制：

$$\mu_{PD}\le\min\left(\frac{n_P}{s_P},\frac{n_D}{s_D},\frac{\beta}{\mathbb E[V_{KV}]}\right).$$

这里 \(n_P,n_D\) 是两侧 worker 数量；\(\mu_{PD}\) 单位为请求/s。取 \(s_P=60\) ms、\(s_D=140\) ms，两个共置副本上限为 10 req/s；1P+1D 的 P 能做 16.67 req/s，D 只能做 7.14 req/s。两端隔离之后，P 的闲置时间无法替 D 完成计算。

在这个阶段独占模型里，均衡分配满足 \(n_P:n_D\approx s_P:s_D=3:7\)。真实引擎通过 batching 同时服务多个请求，服务需求随上下文和 batch 改变。部署时测量两侧在目标 SLO 下的服务曲线，再选择副本比例、TP/PP 和调度预算。

两条请求可以在不同阶段重叠：P 为第二条请求计算时，网络和 D 处理第一条。第二份 KV 在 140 ms 已经到达，但 D 要到 220 ms 才空闲。这 80 ms 等待会占据目标侧缓存；同样的等待也可能发生在源端的发送队列里。

4. 给计算、缓存和网络一起做准入

若路由器只观察 P 的空闲程度，会不断产生已经算好、却暂时交不出去的 KV。根据 Little 定律，平均额外驻留量近似等于“完成 prefill 的速率 × 交接等待 × 每请求 KV 字节”。10 req/s、等待 0.5 s、每份 128 MiB，平均就多驻留 640 MiB；突发和长 prompt 会进一步提高峰值。

因此，准入至少同时检查 D 的空闲 KV blocks、后续生成增长预算、网络在途字节和 P 的执行预算。先预留目标资源，再开始一项预计很大的 prefill，能够减少计算完成后无处安放的情况。交接期间同一份逻辑缓存同时存在于两端，要分别计入各自显存。

例如 D 剩余 24 GiB，留出 4 GiB 给 workspace 和后续增长，每请求当前占 1 GiB，那么当前最多接收 20 份。长输出增加 KV 时，需要继续申请页；将剩余显存全部用作初始准入，会在后续 decode 遇到增长压力。与 分页缓存结合时，应按完整块数和保留页预算计算。

5. 数据相同，要同时满足内容和布局契约

一份 K/V 是某一层对某段历史、使用某套权重计算的结果。两端必须对齐权重 revision、adapter、token IDs、位置、RoPE 配置与 attention 可见范围。缓存键或交接描述符应携带这些身份信息，使接收侧能在调度前判断复用是否有效。

布局契约决定字节怎么解释：KV dtype、量化 scale、block size、层顺序、头维度和分片方案都要一致或经过显式转换。P 的物理块地址只在 P 的地址空间中有意义；D 用自己的物理页表保存逻辑位置映射。

假设模型有 8 个 KV heads，P 使用 TP=2，每个 rank 持有 4 头；D 使用 TP=4，每 rank 需要 2 头。P0 的 heads 0–3 要分给 D0 的 0–1 与 D1 的 2–3，P1 类似分给 D2、D3。选择 connector 前，检查其支持的 attention backend、dtype、并行度组合与 layout 转换路径。头复制和不同页大小会改变实际传输量。

6. 异步复制怎样安全地转移所有权

源页在异步复制真正结束之前保持有效。一个清楚的流程是：D 预留目标页；P 给源页增加传输引用；提交复制；接收方验证身份与完整范围；完成写入同步后发布 ready；随后确认并释放源传输引用。Prefix cache 或其他请求仍可继续持有源页。

target = reserve_decode_slots(request, kv_shape)
source = prefill(tokens, cache_identity)
lease = pin_source_blocks(source, expiry)
transfer_id = copy_async(source, target)
await completion(transfer_id)
verify(identity, valid_token_range, all_required_blocks)
publish_ready(target)
ack_and_release_transfer_reference(lease)
schedule_decode(target, pending_token)

在每次 kernel 发起前，所有将被读取的层和 token 范围都要已经发布。按层流水交接可以让早期层先执行，但 ready 状态必须细化到相应层和范围。若先写页表、后完成数据复制，attention 可能读到尚未填完的目标块。

租约为等待和回收设置期限。例如某协议从源页预留时开始计时，要求 500 ms 内收到 ACK，网络等待 300 ms、复制 150 ms、确认 80 ms，共 530 ms，按该规则就需要续租或走失败路径。已经验证的目标副本有独立的有效性；协议应通过完成记录和 generation 明确接管时刻，防止重试引用已被复用的旧地址。

取消和超时也要沿引用关系清理。停止后续计算后，还需等相关异步复制不再访问源地址，才归还对应引用。目标进程重启则创建新的连接与地址 generation；重复的 transfer ID 应得到幂等处理。回退到 D 重算可以恢复结果，但会重新占用 D 的 prefill 资源，需要记录额外 token、TTFT 和失败率。

7. 多轮对话会让缓存来回移动

第一轮 P 处理 prompt，D 生成回答。第二轮如果包含上一轮回答，新增回答的 KV 位于 D；P 可以从 D 接回，或对相应前缀重新计算。选择取决于回传等待、传输量和重算时间：

$$T_{queue}+T_{setup}+V_{new}/\beta+T_{convert}\quad\hbox{与}\quad T_{recompute}.$$

新增 512 token，沿用每 token 128 KiB，需要 64 MiB。8 GiB/s 下复制约 7.8125 ms，加 4 ms setup 为 11.8125 ms；如果重算需要 40 ms，空闲链路下回传更快。若发送队列额外等待 80 ms，回传则需要约 91.8 ms。

能复用的范围是两次实际 token 序列的最长一致前缀。Chat template 删除 thinking、截断早期历史、插入工具消息或者更换 adapter，都会改变首次不一致位置之后的计算状态。即使某段 answer 文本相同，也要根据它当前的可见前缀和位置决定从哪里重算。

路由也应比较预计完成时间。P1 命中很长前缀但排队 400 ms，P2 没命中却能在 250 ms 内完成整段 prefill，此时 P2 更早完成。把前缀命中收益、队列、网络与 D 等待一起估计，可以避免热点缓存把大量请求聚集在同一实例。

8. 从分段证据找慢在哪

一次 128 MiB 交接耗时 200 ms，可以进一步拆为提交前等待 100 ms、复制 80 ms、接收方调度 20 ms。第一段检查 credit、在途字节和目标页准入；第二段检查实际链路、host staging、每个 rank 的分片量和有效带宽；最后一段对齐完成事件、ready 发布与 D 的首个 kernel。

搭建部署时，先固定一条请求，比较共置与拆分的 token 序列或 logits；然后逐步增加 prompt 长度、到达率和 decode 并发。记录 model revision、connector 版本、两端 TP/PP、KV dtype、block size 和网络拓扑。对主动取消、复制超时、目标重启进行恢复测试，检查结束后空闲块数与在途引用能否回到预期。

性能对照使用相同 GPU/NIC 数量、同一 trace 和 SLO。共置基线先调好 chunked prefill；P/D 侧同时查看两端队列和 KV 峰值。假设固定四卡比较，测得共置吞吐 8.5 req/s、goodput 5.1；拆分吞吐 8.2、goodput 7.6。若目标为 TTFT≤1 s、TPOT≤50 ms，拆分改善了合格速率。修改 SLO 后，要重新逐请求判断通过条件。

9. 练习与可运行的交接实验

练习 1：8k prompt 的交接

32 层、8 KV heads、head_dim=128、BF16、8192 token，8 GiB/s 有效带宽，setup 4 ms。求 KV 体积与无排队的复制加 setup 时间。

展开解答

每 token \(2\times32\times8\times128\times2=131072\) B，即 128 KiB；总共 1 GiB，复制 125 ms，加 setup 得 129 ms。布局转换、确认与排队可继续作为独立项加入。

练习 2：两张卡怎样分配

P 阶段每请求独占 60 ms，D 阶段独占 140 ms，网络无限快。比较两个共置副本和 1P+1D 的容量上界；十个相同 worker 如何均衡？

展开解答

共置容量 \(2/0.2=10\) req/s；拆分容量 \(\min(1/0.06,1/0.14)=7.14\) req/s。十个 worker 的均衡起点是 3P+7D，两侧各 50 req/s。

练习 3：复制完成与协议完成

协议要求 ACK 在 500 ms 前到达；数据在 450 ms 完成，ACK 在 530 ms 到达。应如何处理？怎样设计续租和重试的身份检查？

展开解答

按给定期限应走交接超时路径。可以在到期前续租，或用明确的持久完成记录接管已验证目标。续租与重试携带 owner、transfer ID 和页 generation；源页回收要等待访问它的复制结束。

练习 4：删掉 thinking 后复用到哪里

旧 token 序列为 [system,user,thinking,answer]，新序列为 [system,user,answer,new_user]。哪一段缓存仍可直接复用？

展开解答

复用最长一致前缀 [system,user]。从首次不同的 token 开始重新计算，新的 answer 位置和可见历史已经改变。再核对权重、adapter 与位置配置，确定前缀身份一致。

下载 lab.py。实验使用 Python 3 标准库，20 个请求以 8 req/s 到达，P=60 ms、D=140 ms，独立模拟共享网络队列和缓存租约：

python3 lab.py
# KV=128.000 MiB; transfer=19.625 ms
# capacity bounds: colocated=10.000 req/s; PD=7.143 req/s
# colocated: throughput=7.767 req/s mean_TTFT=80.000 ms
# PD: throughput=6.945 req/s mean_TTFT=242.125 ms
python3 lab.py --bandwidth-gib 0.125
# transfer=1004.000 ms; PD capacity bound=0.996 req/s
python3 lab.py --prefill-ms 80 --decode-ms 80 --rate 12

先预测瓶颈在 P、网络还是 D，再比较吞吐与等待。这个模型的每个 worker 一次服务一个阶段，D 首步之后发出第一枚 token；所有时间是显式输入。修改 prompt 长度时，KV 字节随之变化，还应给 prefill 设置相应的服务时间。进一步加入续租、重算或网络 credit，并记录恢复工作量。
