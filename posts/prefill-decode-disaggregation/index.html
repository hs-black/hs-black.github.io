一段长 prompt，为什么让别人也停了？

一张卡正在为很多请求 decode。一个长 prompt 进入同一轮计算后，这轮 GPU 工作变长，已有请求要等它结束才能继续输出。

要改善的指标

控制长 ITL 的尾部，并分别调整 prefill 与 decode 的资源配置。

新增的成本

KV 传输、两边排队、缓存一致性和故障恢复。拆分后必须重新计算 TTFT 与容量。

先修：KV cache、分布式推理、推理压测与 SLO。

Prefill 与 decode 的计算形状不同

阶段本次输入主要权衡
Prefill[B, T, D]，T 通常较长GEMM 利用率、attention、首响应时间
Decode每个活跃请求通常 1 个新 token读权重与 KV、batch、单步延迟
不同请求之间形状与长度各不相同资源利用与尾延迟的折中

“Prefill 算力受限、decode 带宽受限”是常见起点。实际瓶颈还取决于 batch、长度、模型结构与硬件，应结合 Roofline 和 trace 判断。

推理工程 · 服务与测量

搬运的是所有相关层的缓存

K、V：各 [L, T, Hkv, d]；总字节 = 2 × L × T × Hkv × d × b

L 为层数，T 为 prompt token 数，Hkv 为 KV 头数，d 为每头维度，b 为每元素字节。这里计算普通 GQA 的逻辑 KV；不含 metadata 与分配对齐。

只传最后一层不够：decode 经过每一层时，都需要这一层历史 token 的 K/V。MLA、滑窗或压缩 attention 要按各自缓存布局重新记账。

一个 1,024-token prompt 搬多少？

2 × 32 × 1024 × 8 × 128 × 2 = 134,217,728 B = 128 MiB

每 token

128 KiB/token。8,192-token prompt 为 1 GiB；长度翻倍，逻辑 KV 也翻倍。

链路单位

8 GiB/s = 8 × 2³⁰ B/s；128 MiB / 8 GiB/s = 15.625 ms。不要把 Gb/s 当 GB/s。

这是整模型逻辑体积。TP 后每条链路搬多少，还要看 KV 头如何分片、复制以及两端拓扑。

链路时间有固定项，也有随字节增长的项

Ttransfer ≈ Tsetup + Bytes / BWeffective

上例为 4 + 15.625 = 19.625 ms。假如有效带宽降到 0.125 GiB/s，则是 4 + 1,000 = 1,004 ms；prompt 计算再快也无法消掉这段关键路径。

有效带宽

通过真实连接器、页大小、分片与并发测到的持续速度。

额外开销

注册、打包、host staging、轮询、排队或布局转换会使端到端时间更长。

带宽预算也必须乘上到达率

平均链路需求 = λ × E[KV bytes/request]　[bytes/s]

20 req/s，每个请求 128 MiB：平均需要 2.5 GiB/s。若 5% 请求长达 8,192 token，平均 KV = 0.95×128 + 0.05×1024 = 172.8 MiB。

20 × 172.8 MiB/s = 3.375 GiB/s

这只是均值。多个长请求同时完成 prefill 时，链路突发会产生队列；还要给同链路集合通信留余量。

先说清楚：首 token 在哪里发给用户？

先交接，再返回输出

TTFT = P 排队 + P 计算 + 传输排队/复制 + D 排队 + 首步 + 输出处理。实验采用这个约定。

Prefill 先返回首 token

TTFT 可提前结束，但第一段 ITL 仍可能包含交接与等待。单看 TTFT 会把成本藏进下一个间隔。

首 token 常由 prefill 的最后位置 logits 采样得到；下一轮是否还需消费它、其 KV 是否已写入，必须和缓存长度协议一致。

公平的对照应包括 chunked prefill

先用阶段服务需求算一个容量上界

共置：μC = nC / (sP + sD) 拆分：μPD ≤ min(nP/sP, nD/sD, BW/E[KV])

sP、sD 是每请求占用对应 worker 的时间。本页假设一次只服务一个完整阶段、无 batching，用于看资源分配是否失衡。

2 卡共置，sP=60 ms、sD=140 ms：μC=10 req/s。拆成 1P+1D：P 为 16.67 req/s，D 为 7.14 req/s，decode 先饱和。

推理工程 · 服务与测量

P 多一张还是 D 多一张，要看服务需求

均衡条件：nP / sP ≈ nD / sD → nP : nD ≈ sP : sD

若 sP:sD = 60:140 = 3:7，10 个同类 worker 的起点是 3P+7D。2 个 worker 没法精确分成这个比例，拆分容易留下资源空闲。

真实 batching 下 sP 与 sD 随 batch、prompt 和上下文长度变化。先测两侧服务曲线，再按 workload 分布与 SLO 分配，不直接照搬这个比例。

推理工程 · 服务与测量

只看 P 空不空，会把缓存堆在交接处

如果 router 不断把新请求送入空闲 P，但 D 已经满载，完成的 KV 会等待复制或等待 admission，占用 P 或 D 的显存。

额外驻留 KV ≈ 完成 prefill 的速率 × 等待时间 × 每请求 KV 字节

例如 10 req/s、交接平均等 0.5 s、每请求 128 MiB：平均多驻留 5 份，即 640 MiB。突发与长 prompt 可能远高于这个均值。

Admission 同时考虑 P 计算、D token budget、KV 空间与网络在途字节。

推理工程 · 服务与测量

两端 TP 不同时，要重排谁拥有的 KV

示例：8 个 KV heads。P 使用 TP=2，每 rank 拥有 4 头；D 使用 TP=4，每 rank 需要 2 头。每个 P rank 的数据要分给两个 D ranks。

P0: heads 0–3 → D0: 0–1 + D1: 2–3 P1: heads 4–7 → D2: 4–5 + D3: 6–7

头数整除是这个例子的条件。若 KV 复制、不同 block size 或不同 attention backend，需要转换与额外流量；先确认连接器支持矩阵，再选择拓扑。

推理工程 · 服务与测量

拆分没有让模型权重自动少一份

P 显存 = 权重 + prefill activation + 待交接 KV + 工作区 D 显存 = 权重 + 活跃 KV + 接收 buffer + 工作区

两端分别有执行模型所需的权重。交接期间，同一份逻辑 KV 可能同时存在源与目标；提前预分配目标空间会形成短时双份驻留。

教学预算：D 剩余 24 GiB，留 4 GiB 给增长与工作区，若每请求 KV=1 GiB，20 个只是静态容量上限，不能继续无限增长输出。

推理工程 · 服务与测量

复制完成前，源 block 不能被别人重用

P 暂时持有源页，D 分配目标页；完成确认后，P 才能结束传输占用并回收对应引用。

教学状态机。源缓存可能仍因 prefix cache 或其他引用而保留，释放传输引用不等于立刻销毁物理页。

推理工程 · 服务与测量

租约保护页的生命周期，也限制等待时间

设协议要求在 READY 后 500 ms 内完成 ACK。网络排队 300 ms、复制 150 ms、确认 80 ms，总共 530 ms；若没有续租，这次交接错过了协议期限。

需要覆盖：交接排队 + 复制 + 确认 + 调度抖动

已完成且验证过的目标副本不因源租约到期自动失效。协议需要明确何时转移所有权；本实验采用 ACK 必须早于期限的保守规则。续租与回收还须校验 owner 和版本号。

“已经收到了大部分”还不能开始正确推理

完整性

所有将被 attention 读取的层与 token 范围必须就绪。部分页到达不代表缓存可读。

发布顺序

先完成数据写入与必要同步，再把 block 标为 ready；读者只能看到已发布的范围。

支持按层或按块流水时，可以缩小就绪单位，但每次 kernel 发起前仍必须检查它将访问的精确范围。

推理工程 · 服务与测量

下一轮对话，新增的 KV 在谁那里？

第一轮 P 处理 prompt，D 生成回答。第二轮 prompt 若包含上一轮回答，P 可能没有这些回答 token 的 KV，需要回传或重算。

回传条件

复用前缀必须与新 prompt 的 token IDs 和位置严格一致，包含相同 chat template 与保留的历史。

失效条件

历史被裁剪、工具结果替换、thinking 被删除或 adapter 改变时，从首次不一致的位置重新计算。

缓存 identity 对齐后，再比较回传耗时与增量重算耗时。字符串相同也要检查 tokenizer 与特殊 token。

推理工程 · 服务与测量

回传还是重算，可以先列一个不等式

当 Tsetup + Bytes/BW + 传输等待 < T重算 + P排队 时，回传在该路径上更省时。

教学例子：新增回答 512 token，占 64 MiB；8 GiB/s 传输 7.8125 ms，加 setup 4 ms 为 11.8125 ms。若重算为 40 ms，且两边都无排队，回传节约约 28.2 ms。

若链路排队 80 ms，同样的回传变成 91.8 ms，空闲 P 上的 40 ms 重算反而更快。显存驻留与网络费用也需纳入选择。

练习 1 · 先算再展开

8k prompt 的交接下限是多少？

32 层、8 KV heads、head_dim 128、BF16 K/V。prompt 长 8,192 token。有效带宽 8 GiB/s，setup 4 ms，无排队。求 KV 体积与传输时间。
展开参考解答

每 token = 2×32×8×128×2 = 131,072 B = 128 KiB。8,192 token 共 1 GiB。

复制时间 = 1/8 s = 125 ms；加 setup 得 129 ms。这未计布局转换、协议确认或两端等待；若网络给的是 Gb/s，先除以 8 并统一二进制/十进制单位。

练习 2 · 先算再展开

为什么 1P+1D 可能比两个共置副本更慢？

两张相同 GPU。每请求独占 P 60 ms、D 140 ms，网络无限快且无 batching。比较两个共置副本与 1P+1D 的长期容量上界。
展开参考解答

共置：每副本 1/(0.06+0.14)=5 req/s，两副本共 10 req/s。拆分：P 16.67、D 7.14 req/s，流水吞吐由 D 限制为 7.14 req/s。

P 的剩余容量无法自动变成 D 的容量。更大资源池可按 3:7 比例分配；实际系统再用 batch 服务曲线与 SLO 复核。

练习 3 · 先算再展开

复制完成了，为何仍不能读这份缓存？

协议要求 ACK 在 500 ms 前完成。复制在 450 ms 完成，但确认在 530 ms 到达，未做续租。按这个规则能直接发布目标缓存吗？若目标数据已验证，源租约到期必然使它失效吗？
展开参考解答

按给定协议应判交接失败，因为 ACK 超期。但源租约到期不会自动改变已经复制且验证过的目标数据；这是协议接受规则，不是字节突然失效。

可在到期前续租，或设计明确的完成记录与所有权转移规则。重新使用源地址时必须校验 generation，避免把新一代物理页当成旧缓存。

练习 4 · 先算再展开

第二轮回答少了一段，能整块复用吗？

D 保留上一轮 [system, user, thinking, answer] 的 KV。下一轮模板只保留 [system, user, answer, new_user]。即使 answer 文本不变，可以直接复用 answer 的旧 KV 吗？
展开参考解答

不能。answer 的位置与可见前缀已变，中间层 hidden state 和 K/V 一般都会改变。只能复用两条 token 序列的最长一致前缀对应的有效缓存。

在首次不同 token 后重新计算；同时核对模型、adapter、RoPE 与 attention mask。KV 内容取决于完整历史，不能按段落文字拼接。
