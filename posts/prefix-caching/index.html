Prefix caching：相同的开头，只算一次

交互2026-10-20更新于 2026-10-22

一个客服系统的每条请求都带着同一段系统提示词、工具定义和产品手册。第一条请求已经为这些位置算过每一层的 K/V；下一条请求沿着相同前缀继续，便可以直接使用这些缓存，把计算从第一个不同的位置接上。这就是 prefix caching。

复用的对象是一次模型计算的中间结果。要让它正确、稳定且真正降低首 token 延迟，需要同时解决三个问题：怎样证明前缀相同，缓存块的生命周期怎样管理，以及省下的计算能抵消多少查找和读取成本。

相同前缀怎样产生相同 KV

在因果 Transformer 中，第 \(j\) 个位置的状态只由位置 \(0\ldots j\) 的输入以及模型配置决定。固定模型权重、adapter、位置编码、attention 配置和输入后，这个位置每层的 K/V 就被确定了。因此，两条请求的共同 token 前缀可以共享同一段 KV。

这里的“输入”从 tokenizer 之后开始核对。相同的可见句子可能因为 chat template、空白、特殊 token 或工具顺序而变成不同的 token ID。多模态模型还需要把图像、音频等特征纳入身份；LoRA 请求需要带上 adapter 标识及版本。租户隔离可以通过命名空间或 cache salt 实现，使不同隔离域具有不同的缓存键。

一个实用的缓存身份可以写为 \(I=(M,A,P,X,S)\)：\(M\) 是模型版本，\(A\) 是 adapter 版本，\(P\) 是位置配置，\(X\) 是额外输入特征，\(S\) 是隔离命名空间。模型进程中恒定的项目可以绑定在整个缓存池上；会随请求变化的项目应进入每个请求的键。完整身份让同一个 token 序列对应唯一的计算上下文。

用哈希链描述每一个完整前缀

设每个缓存块容纳 \(\htmlData{symbol=b}{b}\) 个 token。第 \(j\) 块的键 \(h_j\) 可以由上一块的键、本块 token ID 和额外身份组成：

$$h_j=\operatorname{Hash}\big(h_{j-1},\;x_{jb:(j+1)b},\;I_j\big).$$

上一块的哈希把全部更早历史接进来。若只对当前块的 token 求哈希，两个完全不同的上下文恰好以同样几个词结束，就会错误共享这一块。哈希链把每块与它之前的完整前缀绑定，后缀的键会随着前面任意 token 的改变而变化。

图中位置 5 属于第二块，第一块仍可复用 4 个 token。第二块内容发生变化，其键改变；第三块即使自己的 token 没变，父哈希已经变化，因此也需要重新计算。查询沿前缀向后进行，找到首个缺口后，剩下的输入就由前向计算接续。

序列化本身也属于协议。将整数数组、模型版本和额外键用确定的顺序、类型和编码序列化，再求哈希；字符串拼接容易把不同字段组合映射成相同文本。需要跨语言、跨进程交换缓存键时，还应固定序列化格式与哈希算法版本。

命中长度怎样对齐到块边界

设 prompt 长为 \(\htmlData{symbol=n}{N}\)，已匹配的完整前缀长度为 \(H\)。如果接口只保存 K/V，生成首个输出还需要某个输入位置经过输出层得到 logits。对只复用整块的实现，可用命中长度满足

$$\htmlData{symbol=h}{H_{\mathrm{use}}}\le b\left\lfloor\frac{N-1}{b}\right\rfloor.$$

这个边界来自“至少留一个输入位置继续算 logits”和“以完整块命中”两个要求。prompt 为 13 token、块大小为 4 时，最多复用 12 个位置；prompt 恰为 12 token 时，整块粒度的实现会复用前 8 个，再计算最后 4 个。若系统还缓存最终 logits，或支持更细的复用边界，应按那套接口重新计算。

这也是排查“相同 prompt 为何没有 100% 命中”的第一步：查看返回的 cached token 数，确认它与块大小、最后 logits 的生成方式一致，再检查缓存身份或驱逐。完整块发布前必须已经完成 K/V 写入；异步计算中应在结果完成后更新“可命中”状态。

命中以后，后缀还要做多少工作

命中前 \(H\) 个位置后，投影和 MLP 只需处理剩余 \(N-H\) 个输入。后缀的 query 仍要读取前面的 K/V。若按完整 causal attention 的 query-key 配对数计量，原始工作为 \(N(N+1)/2\)，复用前缀省去 \(H(H+1)/2\)：

$$A_{\mathrm{remain}}=\frac{N(N+1)-H(H+1)}{2}.$$

当 \(N=4096\)、\(H=3072\) 时，输入位置减少 75%，attention 配对从 8,390,656 降到 3,670,528，省约 56.25%。原因可以沿每个后缀 query 追踪：它自身没有缓存输出，必须重新与允许读取的历史 key 计算分数，再对 value 加权。

一个简化首 token 预算是 \(T_{\mathrm{cold}}=Q+F+cN\)、\(T_{\mathrm{hot}}=Q+F+c(N-H)+T_{\mathrm{lookup}}\)。其中 \(Q\) 是排队时间，\(F\) 是固定成本，\(c\) 是每个待处理位置的平均成本，查找成本由 \(T_{\mathrm{lookup}}\) 表示。排队占比高时，节省的 prefill 计算可能主要体现为服务器容量增加；单请求 TTFT 的变化还取决于到达负载。

共享块什么时候可以回收

缓存块有两个不同的使用状态：活动请求正在引用它，或当前无人引用但保留着可供未来命中的内容。请求完成时减少引用计数；引用归零后，块可以进入可驱逐队列。分配压力出现时，再移除哈希索引并将物理块交给新请求。

完整前缀块适合只读共享。请求各自追加到私有尾部，页表保持自己的逻辑顺序。若实现允许共享未满尾块，写入前需要 copy-on-write：取得新块、复制有效位置、更新写入请求的页表，然后追加新内容。

活动请求与保留前缀共同使用有限的物理块池。设总容量为 1000 块，活动请求独占或共享引用了 700 个不同物理块，另有 250 个无人引用的缓存块。新一轮需要 120 块时，可以使用 50 个空闲块，再驱逐 70 个缓存块。分配以后仍能保留 180 个缓存块。一个前缀被 20 条请求共享时，容量账本只计算它占据的物理块数，引用计数则记录 20 个使用者。

因此，缓存命中与并发容量之间存在直接联系。共享热点前缀能同时节省 prefill 和活动请求的 KV 空间；保留无人使用的长尾前缀则消耗未来可分配容量。准入时应统计不同物理块、活动引用和可驱逐块，驱逐策略可结合近期复用频率、前缀长度与重算成本。更新或回滚请求输入时，从首个变化块开始重建哈希链，让每个键始终对应当前的 token 前缀。

从命中异常定位到具体层次

重复发送相同请求，命中一直很短。先保存实际 token ID，求两次输入的最长公共前缀；再按块边界向下取整。时间戳、随机 request 标记、工具序列化顺序和模板差异，都可能让前部过早分叉。把长期稳定的内容放在可共享的前部，可变内容放在后面，并对规范化后的输入做回归检查。

首次与再次请求输出发生明显变化。使用同一权重、确定性解码和固定输入，分别禁用与启用 prefix cache，比较首个差异位置的 logits。重点核对图片特征、adapter、绝对位置、token 截断后的哈希重建和“已写入”状态。对于浮点误差，记录最大误差与 top 候选间距；对于错误身份，直接检查缓存键对应的输入记录。

命中率高，TTFT 仍然变慢。把请求时间拆成排队、查找、KV 搬运、后缀计算和响应。远程缓存可能需要跨机搬运；长前缀的多次哈希查询也会占用 CPU。用同一请求比较冷缓存、热本地缓存和热远程缓存，查看到底是哪一项在增长，再决定缓存的驻留位置与驱逐策略。

度量命中时同时保留请求数和 token 数。128-token 与 10000-token 请求若都命中前 96 个位置，省下的输入行数相同，命中比例分别为 75% 与 0.96%，剩余后缀也有很大差别。按请求统计时，两者都会计为一次命中。将命中 token 数、复用字节、被驱逐块数与实际 prefill 时间联系起来，才能解释业务上的收益。

练习：边界、身份与收益

1. 从哪一块开始重算？

prompt 长 65，块大小 16。两条请求的第 35 个零基位置首次不同。已有原请求的所有完整块。求可复用 token 数与待重算数。

参考解答

位置 35 位于第三块 [32,47]，前两块共 32 个 token 可复用，剩余 33 个重算。后续块的父哈希发生变化，因此查询在第三块处停止。

2. 估计首 token 收益

prompt 4000 token，命中 3072；固定时间 55 ms，每个未复用位置 0.05 ms，忽略查找时间。计算冷热 TTFT 与加速比。

参考解答

冷请求为 55+4000×0.05=255 ms；热请求为 55+928×0.05=101.4 ms；加速比约 2.515。节省 153.6 ms 的输入计算，固定成本保留。

3. 共享与驱逐怎样进入容量账本？

池中共有 256 块。三条活动请求共享 32 块前缀，各有 40 块私有历史；另外保留 80 个无人引用的缓存块。新请求需要 48 个额外块。最少驱逐多少块？其中一条活动请求完成后，可释放多少活动容量？

参考解答

活动物理块为 32+3×40=152，空闲块为 256−152−80=24，所以最少驱逐 24 个缓存块。一个活动请求完成后，它的 40 个私有块失去活动引用；共享前缀还有两条请求引用，继续保留。这 40 块可以作为缓存驻留，也可在下次分配时回收。

用哈希链实验检查复用边界

下载 lab.py，运行：

python3 lab.py
python3 lab.py --block-size 4 --change-position 8

默认修改位置 5，输出 reused=4 recompute=9；位置改成 8 后，可复用 8 个 token。实验还检查模型与租户身份隔离、完整块边界、缺失前块时的终止，以及 4096-token attention 的配对账本。

给命名空间加入 adapter 版本，模拟同一 token 序列切换 adapter；再给块池增加容量上限，记录长前缀被驱逐后下一次请求的命中变化。正确性实验与命中统计组合起来，才构成一份可解释的缓存实现。
