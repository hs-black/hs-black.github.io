01 · 重复工作

开头一样，为什么每次都从头算？

很多请求带着相同的系统提示词、工具说明或文档开头。普通 prefill 会把它们反复算一遍。

第一次请求先正常计算这段前缀，留下各层的 K、V。

后续请求找到同一段已计算前缀后，可以直接接上它的 KV，只处理后面的新内容。

图中文字只表示提示词片段；匹配发生在分词后的 token 和模型执行上下文上。

02 · 精确前缀

中间改了一个 token，后面也会跟着变

这里先逐 token 看匹配。缓存是 A B C D E F，新请求是 A B X D E F。

从开头连续匹配，A、B 一样，走到第三个 token 就停。

D、E、F 虽然字面相同，它们看到的历史已从 C 变成 X，对应的 KV 也会改变。

标准因果 attention 中，某个 token 的表示依赖它之前的整个前缀；这里的逐 token 匹配用于解释原理。

03 · 查找

用一条哈希链，记住“这个块之前是什么”

实际缓存常按满块管理。每块的键不仅包括本块 token，还包括它前面的前缀。

第一块从起点算出 h0。第二块用 h0 和 EFGH 算出 h1，把此前的历史接进来。

这样，相同的 EFGH 只要前文不同，缓存键就不同。其他执行条件也必须一致，才能共享结果。

H 表示哈希；vLLM 还把 LoRA、图像内容标识、cache salt 等必要条件纳入键。模型实例定义复用边界。

04 · 命中

直接接上 KV，只计算没见过的后缀

块大小为 4，缓存中已有前 8 个 token 的计算结果。新请求总共 10 个 token。

前两块命中：新请求的 block table 直接引用 P5、P2，不需要再跑这 8 个 token 的 prefill。

GPU 计算最后 2 个 token，同时读取已有前缀的 KV。省的是前缀计算，后缀依然需要理解整个历史。

满块缓存示意；为了得到首个输出的 logits，提示词全命中时，引擎仍可能保留最后一个 token 做计算。

05 · 共享

两条请求，读同一份 KV

A 正在使用 P5，引用计数是 1。已计算的前缀只读，可以安全地被多条请求共用。

B 命中 P5，让自己的 block table 也指向它。引用计数变成 2，显存中的 KV 仍只有一份。

A 结束后计数减回 1。因为 B 还在用，P5 必须保留。

请求生成的不同后缀各用自己的块；共享前缀保持只读。

06 · 生命周期

没人使用，可以先留着，也可以被替换

当所有请求都结束，P5 的引用计数归零。它已经可以回收，但缓存内容还可以暂时留在显存中。

如果另一个请求及时命中，就重新使用它；如果新请求需要空闲块，分配器可以选中这个闲置块。

驱逐时先移除旧缓存键，再覆盖 P5。旧前缀下次到来会 miss，重新 prefill 后再建立缓存。

vLLM 通过空闲队列管理可回收块；仍被活跃请求引用的块不能被直接覆盖。

07 · 实际提示词

稳定的内容放前面，可变的内容放后面

系统提示词 → 固定工具 / 文档 → 用户问题

相同 token 的前缀越长，能复用的计算越多。把时间戳、随机标识放在开头，会让后面的公共内容也失去匹配。

典型命中

重复系统提示词；同一长文档上的多轮提问。

典型 miss

前缀 token 改变；内容已被驱逐；模型或其他必要上下文不同。

08 · 省在哪里

更快开始回答，后面的生成仍要继续

省 prefill

跳过已计算前缀，减少到首个输出 token 的等待。共享块还可省重复的 KV 空间。

仍然需要 decode

每个新 token 仍要做模型计算、读历史 KV。缓存前缀不等于缓存整段答案。

Continuous batching 管“这一轮算谁”
PagedAttention 管“KV 放在哪里” · Prefix caching 管“哪段已经算过”
