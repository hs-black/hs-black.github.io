预训练数据怎样筛选：去重、质量与多样性

交互2026-10-22

假设手里有 1T tokens 的原始网页，但预训练预算只有 100B tokens。直接均匀抽样，模型会把大量算力花在转载文章、站点导航和搜索结果页上；反过来，如果只挑打分最高的 100B，又很容易把代码、论坛问答和小语种一并挤出去。

所以数据筛选从来不是单一开关，而是去重、质量过滤和采样配比三件事纠缠在一起：去重决定同一份内容留几份，质量过滤改变各类文本的存活率，采样再把剩下的池子折算成模型实际看到的 token 分布。只有把这三步分开算账，才能搞清楚一次清洗到底动了什么、收益又从哪来。

过滤就是一次分布变换

很多人把质量过滤当成“筛掉垃圾文档”，但它对训练分布的真实影响远不止于此。把语料按来源或能力拆成若干个域（比如通用网页、代码、数学，或者不同语种），设域 \(i\) 原本占全部 token 的比例是 \(p_i\)，经过滤器后留下的比例是 \(r_i\)。如果之后直接从保留池里均匀抽样，域 \(i\) 的新占比就变成了：

$$\htmlData{symbol=retained-share}{p'_i}=\frac{p_i r_i}{\sum_j p_j r_j}.$$

分母就是全库的总保留率。拿组具体数字算一下：假设网页、代码、数学原本各占 60%、30%、10%，过滤器对它们的保留率分别是 20%、80%、90%。算下来全库只剩 45% 的 token，但三者的新占比已经悄悄翻成了 26.7%、53.3% 和 20%——哪怕你根本没打算调配比，同一个过滤器已经在暗地里做了一次剧烈的重加权。

算这笔账时有个常见坑：千万别拿文档数当 token 数看。一篇十万 token 的系统日志和一篇一千 token 的教程，按文档算都是 1 篇，吃掉的训练预算却差了一百倍。所以统计保留率必须直接用训练时的 tokenizer，并且以截断、packing 和有效 loss mask 之后真正参与算梯度的 token 为准，数据报表才能和训练输入对上账。

真实语料里经常撞上这种副作用：质量分类器天然偏爱行文工整、解释详尽的长文章，全库一刀切地拉高门槛，简短问答、论坛对话和精炼的代码片段往往成片遭殃。因此上线过滤前，一般要按域分别看分数分布和保留量，决定是设分域门槛，还是先留下来再显式重做配比——显式配比的做法见数据配比怎样学出来。

从重复字串到 MinHash

网页里的重复分好几个层次：有时整篇文章原样转载，有时只是复制了一段回答，有时则是同个站点每个页面都挂着一模一样的页眉页脚。针对不同粒度，手段也不一样——整篇哈希只能拦住完全相同的文档，Lee 等人把去重进一步拆成 ExactSubstr 和 NearDup：前者用 suffix array 扫出跨文档反复出现的长子串，专门压低模型逐字背诵和复现的概率；后者用 MinHash 揪出大段重叠的近似文档，避免大量换汤不换药的页面白白吃掉训练预算。

做近似去重的第一步，是把每篇文档拆成词级连续 \(n\)-gram 的集合（例如“the cat sat on the mat”就有 4 个 3-gram）。记两篇文档的集合为 \(A,B\)，它们之间的 Jaccard 相似度就是交并比：

$$\htmlData{symbol=jaccard}{s}=J(A,B)=\frac{|A\cap B|}{|A\cup B|}.$$

注意这是集合定义：同一篇文档里反复出现的 \(n\)-gram 只算一次，段落对调后大部分短 \(n\)-gram 也依然重合。反过来，如果网页里导航栏、免责声明这类模板占了一大半，两篇正文毫无关系的同站页面也会算出很高的 Jaccard——所以跑近似去重前先抽正文，这一步省不得。

直接拿完整集合算交并比太费内存，MinHash 用一个极巧妙的概率性质把集合压成短签名：想象给全宇宙所有可能的 \(n\)-gram 做一次均匀随机排列，然后每篇文档只记下自己集合里排名最靠前的那一个元素。两个集合的最小值撞车，当且仅当并集 \(A\cup B\) 里排第一的那个元素恰好落在交集 \(A\cap B\) 里。由于排列均匀随机，这件事发生的概率正好就是 \(|A\cap B|/|A\cup B|=s\)。工程上没法真的保存随机排列，就用一族独立的哈希函数去近似；重复做几十上百次，两篇文档签名相同的比例就是 Jaccard 相似度 \(s\) 的无偏估计。

签名把文档变短了，但面对上亿篇文档，依然不可能两两比对。LSH（局部敏感哈希）把每篇文档的签名切成 \(b\) 个 band，每个 band 包含 \(r\) 个哈希值，只要两篇文档在任意一个 band 内全部 \(r\) 个值都相等，就把它们塞进同一个桶里作为候选对。在独立哈希假设下，单个 band 全部命中的概率是 \(s^r\)，所有 \(b\) 个 band 全部落空的概率是 \((1-s^r)^b\)，所以至少命中一个 band 的候选概率是：

$$\htmlData{symbol=candidate}{P_{\mathrm{cand}}(s)}=1-(1-s^r)^b.$$

这里 \(r\) 控制单个 band 的严苛程度，\(b\) 决定给多少次“中奖机会”。比如 FineWeb 用的是 5-gram、\(b=14\)、\(r=8\)，每篇文档存 112 个哈希值：当 \(s=0.75\) 时，候选命中率约 77.2%；降到 \(s=0.5\) 时，命中率就跌到了约 5.3%。也就是说，LSH 并不是一刀切的硬阈值，而是一条把高相似度往 1 推、把低相似度往 0 压的 S 形概率曲线。

找到候选对之后，怎么“成簇”和“留谁”同样会改写最终语料。因为相似度不满足传递性：A 和 B 很像、B 和 C 很像，A 和 C 却可能差得很远。如果把所有相似边直接求连通分量、每簇只留一篇代表，C 就会顺带被一锅端；换作按顺序只跟“已经留下的代表”比对，A 和 C 反而都能活下来。至于同一簇里究竟留哪一篇，是按正文更长、质量分更高还是抓取时间更新来挑，也会悄悄左右数据质量。

语义去重把问题移到表示空间

“如何释放 CUDA 显存”和“怎样清理 GPU 上不用的张量”，词面几乎没有重叠，讲的却是同一件事。词面去重拦不住这种改写，SemDeDup 的思路是把文档喂给预训练模型编码成单位向量，让语义相近的内容在表示空间里聚在一起——对单位长度的向量 \(z_a,z_b\)，余弦相似度就是内积 \(z_a^\top z_b\)，越接近 1 说明方向越一致。

面对上亿条向量，直接两两算内积显然跑不动，所以 SemDeDup 先做 \(k\)-means 聚类，只在簇内找相似对（它的文本实验用的是 OPT-125M 最后一个 token 的顶层表示）。这里有个很容易被忽略的前提：你选的编码模型、截断长度和池化方式，本身就定义了什么是“语义重复”。阈值一旦收得太狠，一篇讲解概念的教程和配套习题明明提供不同角度的监督信号，却可能因为向量挨得太近被删掉一半。

在每个簇内部，SemDeDup 默认按离簇中心从远到近排序（优先保留边缘处更有特点的样本），第一个向量无条件留下，排在第 \(j\) 位的向量则计算它与所有更早向量的最大相似度：

$$m_j=\max_{i\lt j}z_i^\top z_j,\qquad \text{当 }m_j\le 1-\epsilon\text{ 时保留 }j.$$

这里 \(\epsilon\) 是允许删掉的语义距离门槛，\(\epsilon\) 越大，删得越狠。留意一个反直觉的细节：公式里比对的是所有更早的向量（\(i\lt j\)），包括那些自己已经被删掉的样本。换句话说，哪怕 B 已经被 A 干掉了，排在后面的 C 依然可能因为撞上 B 而被顺手删掉。如果改成“只和已保留代表比较”，拿到的就是另一份语料——后面的第 3 题和实验脚本会用三点反例把这件事摊开验证。

再算一笔计算账：如果把 \(N\) 篇文档均匀分成 \(K\) 个簇，簇内两两比对次数会降到大约 \(N^2/(2K)\)。但现实里的聚类很少均匀，真正决定开销的是 \(\sum_c n_c(n_c-1)/2\)（\(n_c\) 是第 \(c\) 簇的大小），只要冒出一个异常巨大的超级簇，就能拖垮整台机器的算力和峰值内存。工程上通常不会把整张 \(n_c\times n_c\) 矩阵摊进显存或内存，而是分块算点积、逐列刷新最大值；代价是落在簇边界两侧的近邻会被硬生生切开漏检，必要时只能靠抽样跨簇检索来摸底召回。

为什么跨快照去重会改变质量

网页抓取自带时间维度。一篇扎实的技术教程往往连续十个月稳稳挂在网上，每个月的 Common Crawl 快照里都能抓到它；而随机生成的垃圾 SEO 页面，可能下个月就 404 了，只在单个快照里出现一次。如果跨快照做全局去重，教程的十次出场机会会被压成一次；如果只在每个快照内部单独去重，它跨时间存活的频次就被保留了下来。

FineWeb 在 96 个 Common Crawl 快照上直接对比了这两种做法：按从新到旧做全局去重时，较早的快照里有多达约 90% 的内容被删掉，而旧快照里幸存下来的“独有页面”质量反而明显偏低，最终训练效果反而不如“逐快照独立去重后再随机混合”。原因其实很直白：网页跨时间反复出现，同时混着冗余和长期存活的优质信号两层含义，一刀切全局去重把后者也顺手抹平了。

想把这个机制拆明白，可以对照三种干净的分布设计：第一种是全局每簇留一篇；第二种是每个快照内每簇留一篇；第三种则是把存储和采样解耦——硬盘上仍旧全局只存一份，训练采样时再按跨快照出现次数 \(m\) 乘上一个温和的权重，比如 \(w(m)=\sqrt{m}\)。如果温和加权能把性能拉回来，说明全局去重的掉点主要是丢了频次信号；如果加了权重还是拉不回来，问题就大概率出在代表挑得不好，或者独有低质内容的占比被抬高了。

质量分数怎样定义

所谓质量分类器，本质上只是在学正负样本之间的边界：拿教程当正例，它就偏爱条理清晰的长文；拿代码仓库当正例，它就偏爱语法工整、带注释的代码。DCLM 把语料池、训练预算和评测协议全锁死，横向对比了一批过滤方案，其中很能打的一套做法反倒非常朴素——训练一个 fastText 二元分类器，用 OpenHermes 2.5 和 ELI5 当正例、随机抽取的 RefinedWeb 当负例，然后按打分只留前 10%。可见正例怎么挑、门槛卡在哪，直接决定了模型的胃口。

FineWeb-Edu 走的则是另一条路：直接把“教育价值”作为显式目标，先让大模型给样本打分，再蒸馏出轻量分类器筛出高教育价值子集。这种定向筛选往往能让知识与推理类评测猛涨，但代价也很直观——它不会替你盯着代码补全、口语对话或最新事件是不是被误杀了。把“质量”粗暴压成一个总分，很容易掩盖这类偏科；按目标能力和来源覆盖分开看账，取舍才清楚。

更现实的约束来自语料总量。设域 \(i\) 过滤后剩下 \(U_i\) 个唯一 token，总训练预算是 \(D\)，分给该域的比例是 \(\alpha_i\)，那么这个域里的每份数据平均会被模型读上几轮？算式很简单：

$$\htmlData{symbol=exposure}{E_i}=\frac{D\alpha_i}{U_i}.$$

举个例子：数学语料筛完只剩 2B tokens，如果在 100B 的训练里给它排 10% 的配比，平均就要反复读 5 轮。问题就在这里——把质量门槛再往上拧，单条样本确实更干净了，但 \(U_i\) 会跟着缩水、曝光轮数 \(E_i\) 随之飙升；一旦重复过头，过拟合的代价就会吃掉质量提升的收益。所以评测过滤器时，离开唯一 token 量 \(U_i\) 和曝光轮数 \(E_i\) 单看分数，很容易得出误判。

在十亿文档上实现与评估

真正把 MinHash 推到亿级规模，最先撞上的墙是签名存储与排序。一亿篇文档、每篇 112 个 64-bit 哈希值，光原始签名就要吃掉 \(10^8\times112\times8=89.6\) GB，还没算文档 ID、桶索引和排序缓冲。所以像 Datatrove 这样的工程管线不会试图把所有文档对塞进内存，而是拆成签名生成、分桶写盘与排序归并、聚类、按删除清单重读过滤这几个独立阶段。

一旦流水线拆成多阶段落盘，可复现性就是头号暗坑：同一篇文档的稳定 ID、输入顺序、哈希种子以及同簇内的代表优先级，必须彻底确定。尤其是用“分片号 + 片内序号”定位文档时，最后重读过滤必须严丝合缝地复现前面的分片和枚举规则。一个特别管用的排查招数，是把同一份小语料分别切成 1、2、4 个 shard 跑一遍，核对最终留下来的文档 ID 集合是否完全一致——只要对不上，十有八九是跨分片匹配或 tie-break 规则写漏了，根本用不着去怀疑训练随机性。

语义去重的账单还要再加一笔编码与存储开销：十亿条 768 维 FP16 向量本身就占 1.536 TB，真要按簇加载相似度矩阵，还会叠加上平方级的峰值内存。落地时通常先落盘缓存向量，拉出簇大小分布（尤其是最大簇的规模），再决定算力和工程精力该砸在编码吞吐、向量索引还是分块点积上。另外，只要换了 embedding 模型，原来的余弦距离门槛就不能直接照搬——表示空间的几何结构已经变了，必须重新抽样核对相似对。

评测集污染也得单拉一条线来处理。很多人以为跑完文档级去重就安全了，但网页里经常嵌着零散的考题、答案，甚至是轻微改写过的题干，整篇完全匹配根本拦不住。靠谱的做法是在固定验证集后，拿着题干、答案和长重叠片段去训练池里扫，并沿着来源、时间和近似簇顺藤摸瓜；同时把命中的原文证据记下来，人工抽检有没有因为常见短句误伤正常语料，再对照去污前后的评测指标。

最后，想判断一套清洗方案到底值不值，唯一的硬标准是在固定训练预算下做对照：锁死模型架构、tokenizer、上下文长度、packing 规则、总训练 token 数、学习率计划和随机种子，把原始抽样、词面去重、语义去重、质量过滤及它们的组合拉到同一起跑线上，再把验证集拆到各个能力域里看账。只要某个过滤器拉高了总均分却悄悄拖垮了代码或小语种，下一步怎么改就一目了然：换分类器正例、分域卡门槛，或者在保留池上重新学一遍采样比例。

计算与实验设计

1. 签名预算与漏检

一亿篇文档，14 个 band，每个 band 有 8 个 64-bit 哈希值。光存签名要占多少 GB？Jaccard 为 0.75 的文档对，至少命中一个 band 的概率是多少？如果把 band 数翻倍，这两项分别怎么变？

展开解答

按十进制算，签名体积是 \(10^8\times14\times8\times8=89.6\) GB；候选命中率为 \(1-(1-0.75^8)^{14}\approx0.772\)。把 band 翻倍到 28 后，签名直接涨到 179.2 GB，命中率抬升到约 0.948。代价不只是存储翻倍：低相似度文档对误入候选桶的比例也会跟着变高，后面的桶匹配和去重开销都会跟着涨。

2. 算清过滤后的分布

三个域原本占全库（1T tokens）的比例是 [0.6, 0.3, 0.1]，过滤后的保留率分别是 [0.2, 0.8, 0.9]。求各域的剩余量与新占比。如果接下来要训 300B tokens，并给三个域各分 1/3 预算，哪个域平均读得最多轮？

展开解答

各域剩余量分别是 [120B, 240B, 90B]，总共 450B，新占比变成 [26.67%, 53.33%, 20%]。如果显式按 1/3 均分 300B 预算，每个域各消费 100B，平均曝光轮数依次为 [0.833, 0.417, 1.111]，第三域最多，已经超过一轮。同样是这 450B 剩余数据，按自然份额均匀读和强制按域均分，不仅配比不同，各域的重复轮数也完全不一样。

3. 相似关系为什么会删掉第三篇

三个单位向量 A、B、C 依次相隔 20°，相似度门槛设在 0.9，处理顺序为 A、B、C。按 SemDeDup 的“与所有更早向量比较”和“只与已保留向量比较”两种规则，最后分别留下谁？

展开解答

相邻两篇的相似度是 \(\cos20°\approx0.940\)，超过门槛；A 和 C 之间则是 \(\cos40°\approx0.766\)，低于门槛。按“所有更早向量”规则，A 留下，B 因为撞上 A 被删，C 依然要和 B 比，于是也被顺带删掉，最后只剩 [A]。换成“只比已保留向量”时，B 被删后 C 只需要和 A 比，因此留下 [A, C]。这个三点反例正好适合写进保留逻辑的单元测试里。

4. 全局去重后验证损失变差，怎样定位

两次训练的总 token 数完全一致，但跨快照全局去重的效果不如逐快照去重。设计三个能把根因拆开的对照实验，并说明各自能证明什么。

展开解答

在相同训练配置下做三组对照：第一，锁死全局去重后的代表集合，按原始跨快照出现频次重新加权——如果性能恢复，说明掉点主要来自丢掉了频次采样信号。第二，固定每簇的总曝光量，分别把簇代表换成最新、最高质量和随机挑选——如果三者拉开差距，问题出在代表选择策略。第三，固定各域份额和曝光轮数，单独对比全局独有页面与重复簇代表的分域验证表现，确认是不是全局去重把低质量独有页面的比例给抬高了。

可复现的小语料实验

下载实验 lab.py，运行 python3 lab.py --seed 7 --trials 30000。脚本只依赖 NumPy，把全文几个核心结论拆成独立校验：用真实短句构造 \(n\)-gram 集合并验证精确去重与 Jaccard，拿随机排列实测 MinHash 碰撞概率，模拟 \(14\times8\) 的 LSH 命中率，重现上面的三向量相似链，再顺手核对过滤后的域份额与签名体积。

默认跑完后，你会看到 MinHash 经验碰撞率紧贴精确 Jaccard（0.6），LSH 模拟命中率落在 77.2% 附近，两种语义保留规则分别返回 ['A'] 和 ['A', 'C']，最后所有断言通过。把语义门槛调高到 --semantic-threshold 0.95，三个向量都会留下来；也可以在脚本里把 shingles 的 n 从 3 改成 5，直观看看改一个词对短文本 Jaccard 的冲击有多大。
