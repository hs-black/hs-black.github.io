同一组参数多算几遍：共享深度与递归推理

交互2026-10-22

一个只有 8 层独立参数的网络，可以跑出超过 100 层的计算深度。做法很直接：前后各留 2 层负责进出，把中间 4 层打包成一个循环模块反复调用 32 轮，展开深度就是 \(2+4\times32+2=132\)。权重体积没涨，模型却把算力花在了多轮状态更新上。

这种循环是沿着深度转的。像状态空间模型那样的序列递归，每读一个新 token 更新一次记忆；深度循环则是盯着同一份输入，把内部表示反复打磨好多遍——Universal Transformer、ALBERT 以及近期的 recurrent-depth 语言模型走的都是这条路。两者并不冲突，也能叠进同一个网络，但深度循环带来的是一套很不一样的账本：参数省下来了，算力、梯度和 KV cache 却各有各的开销。

1. 参数共享以后，哪些成本还在

普通 Transformer 每层都有自己独立的一套参数 \(\theta_l\)；共享深度则反过来，反复调用同一个变换 \(F_\theta\)（或者由几个不同层组成的小模块）。拆开看，这件事里其实藏着三个可以自由组合的旋钮：参数共享（比如 ALBERT 用跨层共享压小模型体积）、增加执行轮次（多算几轮换推理质量），以及动态停止（比如 Universal Transformer 给循环加上轮次编码，再让不同位置的 token 自己决定算到哪一轮停）。

先算一笔最基础的账。假设非循环的前后层一共 \(L_0\) 层，中间循环模块包含 \(K\) 层，执行 \(R\) 轮，每层参数量大约都是 \(P_{\mathrm{layer}}\)，那么独立存储的参数量和实际展开的执行深度分别是：

$$P_{\mathrm{unique}}\approx(L_0+K)P_{\mathrm{layer}},\qquad \htmlData{symbol=depth}{L_{\mathrm{exec}}}=L_0+K\htmlData{symbol=rounds}{R}.$$

这两个数很容易让人产生错觉。把轮数 \(R\) 翻倍，权重和优化器状态确实一点没涨，但核心前向计算量却实打实地跟着翻倍；训练时的激活显存、反向计算量，还有推理时的 KV cache，也通通按实际执行轮数走，而不是按 \(P_{\mathrm{unique}}\) 走。换句话说，参数共享省下来的是静态权重开销，不是算力——单看独立参数量去比循环模型和普通模型，几乎一定会把真实成本算错。

算力之外，参数共享还给网络本身套上了一道硬约束。普通网络里浅层只管提取低级特征、深层只管做高层抽象，各司其职；共享权重之后，同一套参数既要接得住第 1 轮刚进来的原始表示，又要能精修第 30 轮的高层语义。常见的工程解法也都绕着这个矛盾转：喂入轮次编码让它知道“现在是第几轮”，每轮持续重新注入输入防止跑偏，或者把头尾几层单独拆出来不共享，专门负责输入编码和输出解码。

2. 把多层网络写成一次次迭代

把共享深度写成一个迭代系统，很多性质会立刻变清楚。给定长度为 \(T\)、隐藏维度为 \(d\) 的输入序列 \(x\)，前置模块先把它编成 \(E(x)\in\mathbb R^{T\times d}\)，随后从初始状态 \(Z^{(0)}=Z_{\mathrm{init}}\) 出发，反复调用同一个循环块 \(F_\theta\) 更新状态 \(Z^{(r)}\in\mathbb R^{T\times d}\)，跑完 \(R\) 轮后再交给后置头 \(G_\psi\) 投影到词表：

$$Z^{(0)}=Z_{\mathrm{init}},\qquad \htmlData{symbol=state}{Z^{(r+1)}}=F_\theta\!\left(Z^{(r)},E(x),r\right),\qquad p_R=\operatorname{softmax}\!\left(G_\psi(Z^{(R)})\right).$$

具体实现里，\(F_\theta\) 通常就是几层 causal attention 加 MLP，\(G_\psi\) 是后置模块和词表投影。注意 \(E(x)\) 被显式塞进了每一轮的输入里：如果只在第 0 轮看一眼输入，跑上几十轮后状态很容易把原始问题忘光；每轮持续注入 \(E(x)\)，相当于给迭代拴了一根锚绳。至于轮次 \(r\) 要不要做成步数编码喂进去，则取决于具体模型的设计。

为什么把同一个变换多跑几遍有可能越算越准？先拿一个最简标量模型看清迭代的脾气：\(z^{(r+1)}=az^{(r)}+e\)，从 \(z^{(0)}=0\) 出发，其中 \(e\) 是每轮注入的输入，\(a\) 是共享参数。只要 \(|a|\lt1\)，跑完 \(R\) 轮的状态就是一个等比数列求和：

$$z^{(R)}=e\sum_{j=0}^{R-1}a^j=\frac{e(1-a^R)}{1-a}.$$

当 \(R\to\infty\) 时，它会收敛到固定点 \(z^*\)，而第 \(R\) 轮剩下的误差按 \(a^R\) 指数衰减：

$$z^*=\frac{e}{1-a},\qquad z^*-z^{(R)}=a^Rz^*.$$

代个数感受一下：取 \(a=0.5,e=1\)，前四轮状态依次是 1、1.5、1.75、1.875，每多算一轮就把离固定点 2 的差距砍掉一半。不过要注意，这个玩具模型之所以越算越准，是因为 \(|a|\lt1\) 天然保证了收缩迭代；换成真实神经网络，没有任何定理白送你收敛性——它必须靠训练学会“多算一轮能把表示修得更好”，否则推理时硬把轮数拉高，状态幅度可能直接漂移甚至发散。

想让模型在推理时按需调节轮数，训练时就不能把 \(R\) 写死，而是每次从某个分布 \(\pi\) 里随机抽一个轮数算 loss：

$$\mathcal L(\theta,\psi)=\mathbb E_{x}\mathbb E_{R\sim\pi}\left[\ell\bigl(p_R(x),y\bigr)\right].$$

其中 \(y\) 是目标 token。因为同一个样本在训练中可能被要求跑几轮就交卷，也可能被要求跑上几十轮，模型被迫学会在不同预算下都能给出合理输出。Recurrent Depth 的大规模预训练正是这个套路：前向随机采样轮数、每轮持续注入输入，反向则只对最后几轮反传梯度来压住激活显存。这马上引出下一个问题：同一个 \(\theta\) 在前向里被调了 \(R\) 次，反向梯度到底怎么算？截断反传又丢掉了什么？

3. 同一参数怎样接收多轮梯度

参数 \(\theta\) 在计算图里被调用了 \(R\) 次，反向传播就会把这 \(R\) 次调用产生的梯度全部加起来。假设最终损失只挂在末轮状态 \(Z^{(R)}\) 上，记第 \(r\) 轮对上一轮状态的 Jacobian 为 \(J_r=\partial Z^{(r+1)}/\partial Z^{(r)}\)，对参数的直接 Jacobian 为 \(U_r=\partial Z^{(r+1)}/\partial\theta\)，链式法则展开就是：

$$\frac{\partial Z^{(R)}}{\partial\theta} =\sum_{r=0}^{R-1}\left(J_{R-1}\cdots J_{r+1}\right)U_r.$$

最末一项 \(r=R-1\) 前面的连乘为空，按恒等矩阵算。这和 RNN 里的随时间反向传播（BPTT）在数学上完全同构，只是把时间轴换成了深度轴：每一轮既通过 \(U_r\) 直接贡献梯度，又靠 \(J_r\) 把前面轮次的梯度往后传。一旦连乘矩阵在某些方向上迅速放大或衰减，深度拉长后就会梯度爆炸或消失，所以循环块里的归一化、初始化和每轮输入注入，本质上都在帮这串 Jacobian 连乘稳住尺度。

工程上更直接的压力来自显存：跑 32 轮就得为完整反传攒下 32 轮中间激活，哪怕全开重计算也很费时间。常见做法是截断反传（truncated backprop）——前 \(R-k\) 轮包在 no_grad() 里只往前推状态，在边界做一次 detach()，最后只对末尾 \(k\) 轮建立计算图：

state = initial_state
with no_grad():
    for r in range(R - k):
        state = core(state, encoded_input, r)
state = state.detach()
for r in range(R - k, R):
    state = core(state, encoded_input, r)
loss = prediction_loss(head(state), target)

别把截断反传和激活重计算（activation checkpointing）混为一谈：重计算是拿算力换显存，算出来的梯度和完整反传分毫不差；截断反传则是直接剪断前 \(R-k\) 轮的反向路径，改变的是梯度本身。实际训练里两者常叠着用——外层截断到最后 \(k\) 轮，这 \(k\) 轮内部再做重计算。顺带一提，只要前面说的输入表示 \(E(x)\) 还在最后 \(k\) 轮继续注入，前置编码器依然能从最后 \(k\) 轮拿到梯度，不会被一起“断奶”。

拿前面的标量例子 \(z^{(r+1)}=az^{(r)}+1\)（\(a=0.5,R=3\)）手算一遍，差距一眼就能看清。三轮展开是 \(z^{(3)}=a^2+a+1=1.75\)，完整导数为 \(dz^{(3)}/da=2a+1=2\)；如果把第 2 轮状态 \(z^{(2)}=a+1=1.5\) detach 掉、只反传最后一轮，导数就只剩边界值 \(z^{(2)}=1.5\)，丢掉的 0.5 正是 \(a\) 通过改写前两轮状态间接产生的那部分贡献。写代码时拿这个精确差值做单测，很快就能查出 detach() 有没有放错位置。

4. 让每个 token 选择计算量

前面默认整条序列一起跑满 \(R\) 轮，但真实文本里每个 token 的难度差得远——功能词和套话一两轮就能猜个八九不离十，推理的关键一步才值得多转几圈。早期的 Universal Transformer 用 ACT 给每个位置学一个停止信号，停下来的位置把状态直接透传到最后；近期的 MoR（Mixture-of-Recursions）则干脆把深度分配写成类似 MoE 的路由问题。记 token \(t\) 实际跑了 \(R_t\) 轮，第 \(r\) 轮还在继续算的活跃集合是 \(\mathcal A_r=\{t:R_t\ge r\}\)，那么整条序列的总计算预算按人头加是 \(\sum_t R_t\)，按轮次加就是 \(\sum_r |\mathcal A_r|\)。

路由怎么选人，主要有两条路：expert-choice 每轮固定挑出指定数量的 token 继续算，张量形状规整、对硬件友好；token-choice 让每个 token 自己决定要跑几轮，语义上最自然，但每轮活下来多少人完全随输入波动。这里藏着一个极易踩的因果陷阱：expert-choice 如果直接对着整条序列做全局 top-\(k\)，那第 10 个 token 能不能进下一轮，实际上取决于后面第 100 个 token 打了多少分——训练时看着一切正常，到了自回归解码根本看不到未来 token，路由行为立刻错位。所以凡是要做 causal 解码的动态深度，训练时的选择机制必须严格对齐推理时拿得到的信息。验证方法很干脆，做一次前缀一致性测试：锁死同一段前缀、换几组完全不同的后缀，检查前缀每个位置的路由决定是不是纹丝不动。

另一个容易混淆的地方是“算稳了”不等于“算对了”。工程里常用相邻两轮的 logit KL 散度当停止条件，KL 掉到阈值以下就早停；但这只能说明预测不再摇摆，不能保证答案本身是对的——模型完全可能在第二轮就非常自信地锁定一个错误结果。想看清动态深度到底有没有把预算花在刀刃上，光看平均轮数远远不够，得把简单和困难样本拆开看质量–算力曲线，顺手抽查提前停下来的样本：再多给它算两轮，正确率还会不会接着涨？如果不会，早停才算真的赚到了。

5. 每轮 KV 的身份与缓存协议

权重共享最容易让人踩坑的误区之一，是以为“权重只存一份，KV cache 也能跟着省成一份”。其实不行：虽然 \(W_Q,W_K,W_V\) 是同一套矩阵，但每一轮送进去的隐藏状态 \(z^{(r-1)}\) 都在变，算出来的 K 和 V 自然也各不相同。对单头 attention 写出第 \(r\) 轮、位置 \(t\) 的 query 和历史位置 \(s\) 的 key/value：

$$q_t^{(r)}=W_Qz_t^{(r-1)},\qquad \htmlData{symbol=key}{k_s^{(r)}}=W_Kz_s^{(r-1)},\qquad v_s^{(r)}=W_Vz_s^{(r-1)}.$$

所以按最直白的逐轮缓存来存，每个 \((r,s)\) 对都得各占一份空间。假设循环模块里有 \(K\) 个 attention 层，每层 \(H_{kv}\) 个 KV head、每头宽度 \(d_h\)，每个元素占 \(u\) 字节（BF16 就是 2 字节）。固定执行 \(R\) 轮、batch 为 \(B\)、历史长度为 \(T\) 时，光是循环部分的 KV cache 就要吃掉：

$$M_{KV}=2BTRK H_{kv}d_hu.$$

最前面的 2 对应 K 和 V 各一份。权重体积没随 \(R\) 涨，KV cache 却结结实实多出了一条轮次轴。一旦再叠上动态深度，还会撞上一个更棘手的协议问题：如果早期 token \(s\) 在第 1 轮就退出了，后面某个 token 在第 3 轮做注意力时，到底还能不能看到它？看到的又是哪一轮的状态？

MoR 给出了两种写进训练里的缓存协议，取舍截然不同：

  • Recursion-wise caching（按轮缓存活跃 token）：第 \(r\) 轮只缓存本轮还在场的活跃 token，本轮注意力只能看到 \(\{s\le t:s\in\mathcal A_r\}\)。省下的显存直接看每轮活下来多少人，但早退的 token 对后续深层轮次来说就“隐身”了。
  • Recursive KV sharing（跨轮共享第一轮 KV）：所有 token 只存第 1 轮算出来的 \(k_s^{(1)},v_s^{(1)}\)，后续轮次的 query 始终回头读这一份。历史上下文一个不落，但深层轮次读到的永远是第一轮的浅层表示。

代一组常见尺寸算笔账：\(B=1,T=8192,R=8,K=4,H_{kv}=8,d_h=128\)，用 BF16 存。逐轮全存要占整整 1 GiB；改用第一轮共享后，循环部分立刻降到 128 MiB，省了 8 倍容量。但这里有个常被漏算的细节：显存容量省了 8 倍，不等于访存带宽也省了 8 倍——第 2 到第 8 轮的 query 依然要扫一遍全部历史 KV，读流量并没有按比例消失。反过来，按轮缓存活跃 token 能同时压低容量和读流量，代价则是缩小了深层轮次的可见上下文。

这也引出一条很硬的工程纪律：KV 缓存协议不是纯推理侧的内存优化，而是模型数学定义的一部分。同一个“共享”开关，改的不只是内存布局，还改了网络实际计算的函数——拿逐轮缓存训出来的权重，推理时切到第一轮共享，输出本来就不会一致。给加速内核做等价性测试时，必须先钉死同一种协议，把缓存键精确索引到（请求、循环层、轮次），再拿整段前向、不同 chunk 的 prefill 和逐 token 解码互相对齐。

6. 把动态深度放到 GPU 上

纸面上省掉一半 FLOPs，搬到 GPU 上未必能快出一半。假设一个 batch 里有 4 个 token，分别需要 1、2、3、6 轮，有效计算只有 12 个 token-round。如果直接把所有人补齐（pad）到 6 轮，总共会开出 \(4\times6=24\) 个槽位，一半算力都在空转。反过来，每轮把提前退出的 token 踢掉、把活跃集合压紧（pack）再算，虽然消灭了空算，代价却是每轮都要做索引重排和数据搬运；等跑到第 5、6 轮只剩寥寥几个 token 时，矩阵瘦得根本喂不饱 Tensor Core，kernel 启动和访存延迟反而成了大头，实测耗时未必比直接补齐更快。

好在权重共享本身送了调度器一张好牌：跨轮次批处理。既然每一轮用的都是同一套参数模块，正在跑第 5 轮的 token A 和刚进第 1 轮的 token B 完全可以拼进同一次矩阵乘里一起算。当然，同一个 token 自己的第 \(r+1\) 轮还是得等第 \(r\) 轮算完，能合并的只是不同请求或不同位置上已经就绪的活儿；调度器需要一边跟踪每个 token 的状态、轮次编码和可读 KV 集合，一边尽量把就绪任务凑成足够胖的 batch 喂给 GPU。

放到多卡训练里，动态深度还会惹出两个分布式的麻烦。第一是步调不齐：数据并行时如果各卡独立随机采样轮数，抽到 4 轮的卡算完只能在 AllReduce 前干等抽到 32 轮的卡，所以通常得跨卡对齐轮数或者按轮数分桶。第二是框架 hook 重入：同一个循环块在一次 step 里要反复进出 \(R\) 次，参数分片（FSDP/ZeRO）的拉取、梯度归约钩子和梯度累加很容易在重入时互相打架。最稳的排错习惯是先在小模型上写一份完全展开的参考实现，和共享版本逐项核对输出与梯度，确认分毫不差后，再一次只打开一个开关——依次叠上 checkpoint、混合精度和参数分片。

最后怎么公平地评估循环模型？三种对比口径回答的是三个不同的问题：固定参数量看的是“靠多算几遍能把小模型压榨到多强”，固定训练 FLOPs看的是“同样的训练预算，把钱花在多加层参数还是多转几圈更划算”，固定推理延迟才决定它上线后值不值得用。和 HC 的多路残差、AttnRes 的历史聚合不同，深度循环并不是在层间多搭几条线，而是给同一套变换更多次出手机会；至于多跑出来的轮次到底有没有真的推进表示，还是只是在原地打转，可以接着看有效深度的测量与干预。

练习 1：参数量与执行深度

前后共 4 个非循环层，中间模块有 4 层，每层 100M 参数，忽略 embedding。执行 8、32 轮时，独立参数量与展开深度分别是多少？一个完全不共享、深度相同的网络又有多少参数？

展开解答

独立参数始终是 \((4+4)\times100\mathrm M=800\mathrm M\)。执行 8 轮和 32 轮时，展开深度分别为 \(4+4\times8=36\) 和 \(4+4\times32=132\)，完全不共享的话分别对应 3.6B 和 13.2B 参数。但算前向和反向 FLOPs 时，依然要按 36 层和 132 层调用来算，不能按 800M 参数估算。

练习 2：截断改变了哪一项？

迭代 \(z^{(r+1)}=az^{(r)}+1\)，\(z^{(0)}=0,a=0.5,R=3\)。目标为 2，损失 \(\ell=\tfrac12(z^{(3)}-2)^2\)。求完整梯度与只反传最后一轮的梯度。checkpoint 全部轮次时应得到哪个？

展开解答

最终状态 \(z^{(3)}=1+a+a^2=1.75\)，损失对最终状态的导数是 \(z^{(3)}-2=-0.25\)。完整反传下 \(dz^{(3)}/da=1+2a=2\)，乘起来得到完整梯度 \(-0.25\times2=-0.5\)。只反传最后一轮时，边界状态 \(z^{(2)}=1.5\) 被当成常数，只剩最后一次乘法的导数 1.5，梯度变成 \(-0.25\times1.5=-0.375\)。activation checkpointing 只是在反向时重算中间状态，计算图依赖一根没断，所以结果仍然是完整的 −0.5。

练习 3：权重共享后 KV 有多大？

循环模块 3 层，每条序列长度 4096，batch 为 2，执行 6 轮，每层 4 个 KV head、每头 64 维，缓存为 BF16。分别计算逐轮全部缓存和只存第一轮的容量。

展开解答$$M=2\times2\times4096\times6\times3\times4\times64\times2=150994944\ \mathrm B=144\ \mathrm{MiB}.$$

只存第一轮时，轮次轴从 6 缩成 1，循环部分的 KV cache 直接降到 24 MiB（前后非循环层的 KV 另算），代价是后面 5 轮的 query 读到的全都是第一轮的历史表示。

练习 4：动态停止能节省多少调用？

一个 batch 的执行轮数为 \((1,2,3,6)\)。计算补齐执行的槽位利用率；写出每轮活跃 token 数。若每轮只缓存活跃 token，每个 token-round 一份 KV，共有多少份？如何判断路由有没有偷看未来？

展开解答

有效调用一共 \(1+2+3+6=12\) 次，补齐到 6 轮要开 \(4\times6=24\) 个槽位，利用率正好 50%。六轮的活跃 token 数依次为 \((4,3,2,1,1,1)\)，加起来同样是 12，也就是要存 12 份 KV。排查路由有没有偷看未来，做一次前缀一致性测试就行：固定前缀、换几组不同后缀，看前缀位置每轮的路由决定有没有变动；一旦变了，多半是全序列 top-\(k\)、跨位置归一化或辅助路由器里漏进了后缀信息。
