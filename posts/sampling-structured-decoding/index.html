采样器与结构化解码

交互2026-10-20更新于 2026-10-22

模型输出一行 logits 后，生成循环还差一个决定：下一步选哪个 token。这个决定会改变文本的多样性，也会影响是否能按指定格式输出。一个可靠的采样器需要明确概率变换的顺序、随机数的归属，以及每条请求当前允许生成什么。

假设词表只有 A、B、C，当前概率是 [0.5,0.3,0.2]。温度、top-k、top-p 和语法约束都在改变这行分布。把每一步写成可核对的数组，就能解释为什么相同模型、相同 seed，在两个服务框架里仍可能得到不同结果。

从 logits 得到稳定的概率

设 token \(i\) 的 logit 为 \(z_i\)，温度为 \(\htmlData{symbol=t}{T}>0\)。采样概率为 \(p_i=\exp(z_i/T)/\sum_j\exp(z_j/T)\)。直接求指数可能溢出，所以先减去允许位置中的最大 logit \(m\)：

$$p_i=\frac{\exp((z_i-m)/T)}{\sum_j\exp((z_j-m)/T)}.$$

减去同一个数保持概率比值，而所有指数的输入都不大于 0。温度低于 1 时，大 logit 的优势更明显；高于 1 时，分布更平缓。若已有基础概率 \(p_i\)，相同变换也可以写成 \(\widetilde p_i\propto p_i^{1/T}\)。

对 [0.5,0.3,0.2] 取 \(T=0.5\)，先平方得到 [0.25,0.09,0.04]，总和 0.38，归一化后约为 [0.6579,0.2368,0.1053]。温度为 0 时走单独的 greedy 分支：在允许位置中选择最大 logit，打平规则也应固定。

Top-k 与 top-p 怎样保留候选

Top-k 按分数保留最高的 \(k\) 个 token；top-p 则按概率降序累加，保留累计概率第一次达到阈值的最短前缀。两者都要对保留的概率重新归一化。

基础概率 [0.5,0.3,0.2] 在 top-p=0.75 时，第一项累计 0.5，第二项累计 0.8。因此 A、B 都被保留，最终为 [0.625,0.375,0]。跨过阈值的 B 是边界 token，应进入候选集合。若只保留累计值小于阈值的项，就会在这个例子中错误地只留下 A。

处理顺序属于采样策略的一部分。这里采用“语法 mask → temperature → top-k → top-p → 归一化”。例如原概率 [0.7,0.2,0.1]，A 被语法禁止、top-k=1 时，应该从合法位置 B、C 中选最高的 B。先只保留 A 再应用语法 mask，会得到空候选集合。

实现时将 NaN、正无穷、非法参数和全 mask 状态作为可定位的错误处理。全 mask 往往指向 tokenizer、matcher 状态、停止条件或过滤顺序的冲突。保留请求 ID、当前文本尾部、grammar 状态和过滤前后候选数，能把失败复现到单独的一行 logits。

有了最终概率，最简单的抽样办法是取均匀随机数 \(u\in[0,1)\)，寻找第一个累计概率超过 u 的 token。对 [0.625,0.375,0]，区间 [0,0.625) 对应 A，剩余区间对应 B。将这一步与 logits 变换分开，就能独立测试分布和随机抽样。

有限精度也会影响边界。候选排序需要固定打平规则，累计和应使用足够精度；计算 top-p 时保留跨阈值项，归一化后检查总和。测试中可以用固定 u 逐个穿过边界，再做大量随机抽样检查频率。真实服务还需要让随机数与请求的采样步对应，方便比较不同调度顺序。

结构化解码把语法变成每一步的 mask

要生成 JSON，可以用一个状态机或带栈的语法匹配器跟踪当前前缀。读到 [ 后，接下来允许一个值或结束空数组；读完一个值后，接下来允许逗号或 ]。嵌套数组需要栈记录每一层的状态。

在状态 \(s\) 下，定义 \(\htmlData{symbol=m}{M_s(i)}\) 为 token \(i\) 是否可继续生成。合法 token 的 logit 保留，其他位置置为 \(-\infty\)。采样以后，将选中 token 提交给匹配器，再进入下一轮。

$$z_i'=\begin{cases}z_i,&M_s(i)=1,\\-\infty,&M_s(i)=0.\end{cases}$$

关键单位是完整 token。一个 token 可能对应 ,1] 三个字符，跨过“逗号、值、闭括号”三个语法状态；也可能包含 UTF-8 字节片段。判定时必须让该 token 的全部内容沿 grammar 前进，整段有效才提交。候选测试使用临时状态；一个候选后半段失败时，主状态保持原样。

图里 token [0 一次打开数组并写入一个值；,1] 再一次完成三个状态转换，得到 [0,1]。回滚一个 token 时，需要恢复到 [0 对应的快照，之后可以直接用 ] 结束为 [0]。回滚的单位与模型输出的 token ID 一致。

EOS、结束状态与应用层校验

匹配器的“语法已完整”和生成循环的“请求已结束”是相连的两个状态。完整值已经出现后，可以允许 EOS；接受 EOS 后停止继续采样。若在字符串、数组或对象内部提前达到输出长度上限，最终文本只是一个有效前缀，应用应按截断结果处理。

JSON Schema 约束提供字段结构、类型与部分取值范围。业务要求还需要自己的验证，例如订单号是否存在、两个日期的先后关系、生成代码是否通过测试。一个合适的服务接口同时返回内容、结束原因和校验结果，让调用方决定接受、重试还是提示用户补充信息。

语法可接受的路径也可能非常长。JSON 允许某些位置出现空白，字符串还允许连续空格。如果模型在这些合法分支上概率很高，就可能持续生成空白。排查时先区分字符串内部与结构间空白，再检查 tokenizer 配置、prompt 与 schema 的匹配；需要紧凑输出时使用后端支持的空白限制，并保留输出长度上限。

接上投机解码时，需要一起回滚哪些状态

投机验证可能一次产生多个候选。第一个候选的 mask 来自当前已接受前缀；第二个候选的 mask 来自假设第一个已被接受的状态。每个请求因此需要自己的可回滚 matcher，和它的 KV 长度、已接受输出及随机数状态对应起来。

若前三个候选被接受、第四个被拒绝，就恢复到前三个候选之后的 grammar 状态，再处理纠正 token。最终 p/q 接受检验应使用经过同样约束和采样变换的实际分布。语法状态偏移一个 token，会把正确词拒绝，也可能让应被禁止的候选进入结果。

批处理还要保存请求到输出行的映射。某条请求结束以后，剩下的请求会被压紧到新的 batch 行；matcher 必须随请求 ID 移动。把 grammar 对象固定绑在第 0、1、2 行，会在请求退出或新请求插入后串状态。

现象要检查的状态最小复现方法
同 seed 的输出不同tokenizer、变换顺序、随机流、batch 形状固定一行 logits，逐阶段保存概率与随机数

建立自己的采样单测时，除了验证输出频率，还应检查精确分布。用 [0.5,0.3,0.2] 这类可手算的概率覆盖温度、nucleus 边界、打平和极值；再用独立 JSON parser 检查生成的完整文本。精确数组可以定位算法错误，采样频率可以定位随机抽样实现错误。

练习：从概率数组到状态栈

1. 手算低温采样

原概率 [0.5,0.3,0.2]，温度 0.5。求最终概率。

参考解答

平方得到 [0.25,0.09,0.04]，除以 0.38，约为 [0.657895,0.236842,0.105263]。

2. 跨过 top-p 阈值的 token 要保留吗？

概率 [0.45,0.3,0.15,0.1]，top-p=0.8。写出候选集合和归一化概率。

参考解答

前两项累计 0.75，加入第三项达到 0.9，所以保留前三个。最终为 [0.5,1/3,1/6,0]。第三个是跨阈值项。

3. 回滚一个 token 会退几个字符？

依次接受 [0 和 ,1] 后得到 [0,1]。回滚一个 token 后，文本、栈状态和 EOS 的可用性分别是什么？

参考解答

文本回到 [0，数组栈顶是“逗号或结束”；EOS 此时不可用。回滚撤销的是第二个 token 的全部三个字符以及对应的语法转换。

4. 为什么先 top-k 会得到空集合？

logits 对应概率 [0.7,0.2,0.1]，只允许 B、C，top-k=1。比较两种顺序。

参考解答

先语法过滤，B 的分数最高，得到 B 概率 1。先 top-k 保留 A、再过滤 A，则集合为空。框架应固定并测试自己的处理顺序。

运行概率与 JSON 栈实验

下载 lab.py，安装 NumPy 后运行：

python3 -m pip install numpy
python3 lab.py --samples 100000 --seed 7

实验检查 temperature、top-p、grammar-before-top-k、全 mask 和数值极值；采样频率应接近 [0.625,0.375,0]。随后构造允许 0、1 和嵌套数组的小语法，检查多字符 token 原子提交、回滚与 EOS，再用 json.loads 独立解析 100 个完成结果。

加入一个含多个括号的 token，先预测哪些状态允许它，再补上回滚测试。然后将同一 matcher 放进最小推理引擎，验证请求重排后状态仍跟随请求 ID。
