LLM 工程 · 原理与实现

forward 结束后，还有一条决定输出的计算链

hidden → vocabulary logits → 约束与截断 → 概率 → 采样 → 状态更新

词表大小 V 时，每个请求拿到 V 个 logits。采样器既要实现指定的概率分布，也要保持 token、KV cache 与语法状态一致。

数值问题

稳定 softmax、温度、top-k、top-p、随机数。

状态问题

合法候选、token 字节、请求隔离、停止条件、回滚。

先修：KV cache；后续：投机解码。

LLM 工程 · 原理与实现

logits 不是概率，先做稳定归一化

pᵢ = exp(zᵢ − m) / Σⱼ exp(zⱼ − m)，m = maxⱼ zⱼ

给所有 logits 减去同一个数不改变概率，却能避免 exp(1000) 溢出。被禁止的 token 用 −∞ 表示。

logits减最大值得到的概率
[ln 5, ln 3, ln 2][0, ln(3/5), ln(2/5)][0.5, 0.3, 0.2]

如果全部是 −∞，分母没有有效质量；应报告约束冲突，而不是把 NaN 送进随机采样。

温度改变概率差距，不改变排序

pᵢ(T) = softmax(z/T)ᵢ ∝ pᵢ(1)^(1/T)，T > 0
输入 p = [0.5,0.3,0.2]归一化前归一化后
T = 0.5[0.25,0.09,0.04][0.6579,0.2368,0.1053]
T = 1[0.5,0.3,0.2][0.5,0.3,0.2]
T = 2[√0.5,√0.3,√0.2]约 [0.4154,0.3218,0.2628]

低温使分布集中；高温使分布平缓。温度不是“事实正确率”的直接旋钮。

同一排 logits，概率柱怎样变化

温度从 2 降到 0.5。每一帧都重新归一化，不是把概率直接乘一个倍数。

T = 0 用单独的 greedy 分支

next_token = argmax(合法 logits)

不要真的计算 logits / 0。若接口规定 temperature=0 表示 greedy，就走确定性的最大值选择。

并列最大值

约定 tie-break，例如 token id 较小者优先；测试时保持一致。

可复现

固定 seed 约束随机数流；batch 调度和 kernel 数值误差仍可能改变具体路径。

需要跨调度复现时，为每个请求管理独立 RNG 状态，并记录采样策略与模型版本。

Top-k 给候选数量设上限

p = [0.50, 0.30, 0.15, 0.05]；k = 2
保留 [0.50,0.30] → 归一化为 [0.625,0.375,0,0]

top-k 的 k 固定，保留下来的概率质量却不固定。面对接近平分的候选和一个特别确定的候选，k=2 都会留下两枚 token。

无效 token 不应占用 k 个名额；先应用硬性合法性 mask，再选择候选。

Top-p 给累计质量设目标

排序后 p = [0.50, 0.30, 0.15, 0.05]；阈值 τ = 0.75
累计质量 [0.50, 0.80, 0.95, 1.00] → 保留 A、B

保留达到或超过 τ 的最短前缀：跨过阈值的 B 也要留下。再归一化为 [0.625,0.375,0,0]。

τ 是 top-p 阈值；不要把它与 temperature 的 T 混为一谈。

跨过 0.75 的那一枚也留下

按 A、B、C、D 的概率降序扫描；图块宽度就是它的概率质量。

先看 A，再加 B；达到阈值以后，后面的候选不再进入集合。

LLM 工程 · 原理与实现

约束和截断的顺序会改变结果

原始概率 A=0.7、B=0.2、C=0.1；语法禁止 A，使用 top-k=1。

执行顺序候选集合结果
先 top-k，再 grammar先只剩 A，再禁用 A空集合，无法采样
先 grammar，再 top-k先剩 B、C，再保留 B输出 B

本课实验固定策略：grammar → temperature → top-k → top-p → 归一化。引擎需要明确公开并测试自己的策略。

LLM 工程 · 原理与实现

一次输出看不出采样器是否正确

同一分布独立抽样 N 次，比较经验频率与理论概率。误差通常按 1/√N 缩小，而不是必须完全相等。

单个 token 的频率标准差 ≈ √(p(1−p)/N)

p=0.625，N=100000 时标准差约 0.001531；出现 0.62415 属于正常采样波动。

同时做确定性边界测试：top-p 跨阈值 token、并列 logits、全 mask、只剩一项、EOS、T=0。

要生成 JSON，合法性应该进入采样分布

当输出已经是 {"ok": 时，接下来可以是 true 或 false；一个任意单词会让结构失效。

p合法(i) = p(i) / Σⱼ∈合法 p(j)，i ∈ 合法；其余为 0

模型负责在合法续写中分配偏好；matcher 根据已生成前缀产生下一步允许的 token 集合。

结构合法只说明符合语法与已支持的 schema 约束；字段内容是否符合事实仍需任务判断。

LLM 工程 · 原理与实现

一枚 token 可能横跨多个语法状态

词表 token 不是字符。一个 token 可能包含 ,1]，一次完成逗号、值、闭括号三个动作。

候选 token 合法 ⇔ 它的全部字节可从当前 matcher 状态继续匹配

逐字符检查 token 内部，但提交与回滚按 token 边界进行。若最后一个字节失败，前面已经走过的状态也必须撤销。

真实 tokenizer 还要处理 byte fallback、特殊 token、UTF-8 与解码规则。实验用小型 ASCII 词表隔离状态逻辑。

一个 token，走过三个状态

当前前缀为 [0，候选 token 的字节串是 ,1]。只有全部消费成功，才接受这枚 token。

一次 token 接受必须是原子操作：全部成功，或恢复原状态。

共享编译结果，每个请求独立持有状态

每个模型 / schema

tokenizer 信息、编译后的 grammar、可复用的匹配数据。相同 grammar 可以共享编译产物。

把 matcher 接进 decode 的三个时刻

mask = matcher.allowed_next_tokens()
logits = model_step(request)
logits[~mask] = -inf
token = sample(logits, request.sampling_policy, request.rng)
assert matcher.accept_token(token)
request.output.append(token)
# 这枚 token 的 KV 通常在下一次 model_step 中计算

mask 只依赖已提交前缀，可与 GPU forward 重叠。采样前必须等对应 mask 就绪并应用到正确请求行。

LLM 工程 · 原理与实现

把词表合法性压成 bitmask

V = 128000；int32 bitmask 需要 ceil(V/32) = 4000 个字
每请求 4000×4 = 16000 bytes ≈ 15.625 KiB

同样的 bool 数组若每项 1 byte，需要 128000 bytes。bitmask 让传输量缩小 8 倍，但仍要考虑生成、复制与应用 mask 的成本。

本例是存储格式计算；实际延迟需要按 batch、grammar 和设备路径测量。

投机验证时，每个候选位置都有自己的 mask

draft 生成 d₁、d₂、d₃；验证第 2 枚时，grammar 状态应已经临时接受 d₁。用同一个初始 mask 套全部位置会漏掉状态变化。

state₀ → d₁ → state₁ → d₂ → state₂ → d₃ → state₃

先保存前缀状态，沿 draft 临时推进；target 验证后，只提交接受的前缀，并回滚拒绝的后缀。

分布一致性推导见 投机解码；树状 draft 要维护对应分支的状态。

只接受第一枚，后面的状态全部撤销

先从 [ 临时接受 draft [0, 逗号, 1]；target 接受 0，在逗号处拒绝并选择 ]。

最终输出为 [0]。回滚按 token 数进行，不能简单减去相同数量的字符。

LLM 工程 · 原理与实现

接受率公式用的是处理后的分布

接受 draft d 的概率：min(1, p(d)/q(d))

这里 p、q 必须是实际 target / draft 采样分布：包括各自使用的 grammar mask、温度与截断。直接拿原始 softmax 代入，会验证另一套分布。

被拒绝时，修正分布正比于 max(p−q,0)。若合法候选只有一个，分布会集中到它，仍应推进 matcher 与 KV 状态。

draft 可以采用不同策略，但必须保留其真实提案概率 q，并以正确的目标 p 做校正。

top-p 的跨阈值项不能漏

排序概率为 [0.45,0.30,0.15,0.10]，top-p=0.70。保留哪些 token？最终概率与原分布有什么区别？

累计为 [0.45,0.75,0.90,1]，保留前两项，包含跨过 0.70 的第二项。除以保留质量 0.75 后得到 [0.6,0.4,0,0]。保留质量可以大于阈值，最终概率总和仍为 1。

练习 3 · 计算与排错

一枚 token 失败，状态应该停在哪里？

当前前缀为 [0，候选 token 是 ,1]X。前 3 个字符能完成数组，最后的 X 非法。若 accept_token 返回 false，matcher 应处于什么状态？
展开参考解答

应完全回到接受 token 之前的 [0 状态，等待逗号或 ]；不能停在已完成的 [0,1]。可以先在副本上试走，或记录快照，在任意字符失败时整体恢复。否则后续 mask 会基于从未提交的前缀。

练习 4 · 计算与排错

投机后缀退回多少个状态？

已有前缀 [，draft 的三枚 token 是 0、逗号、1。target 只接受 0，再给出修正 token ]。需要回滚多少枚？修正 token 的 KV 已存在吗？
