Transformer 推理的数学

交互2026-10-19更新于 2026-10-22
分布式推理图解：把权重、KV cache 和中间结果放进每张 GPU，看清计算与通信发生在哪里。

训练时我们只关心一件事：每秒每张卡处理多少 token。推理多了一个维度——延迟。用户在等第一个字出来，在等后面的字一个个往外冒。好在推理可以拆成能算的东西：每一步要从显存里搬多少字节、做多少 FLOPs、什么时候受带宽限制、什么时候受算力限制。KV cache 压缩、张量并行、预填充/解码分离、continuous batching、PagedAttention、前缀缓存、投机解码和量化，解决的都是这本账里的某一项。

算例主要用 TPU v5e：它的规格简单、每美元算力高，数字也好算；需要时同时给出 H100 的对应数字。算术强度、硬件强度这两个概念来自 Roofline。

1. 自回归生成与 KV cache

语言模型做的事情是：给定前缀 \(x_{\lt t}\)，输出下一个 token 的分布 \(p(x_t \mid x_{\lt t})\)。生成就是循环：从分布里采一个 token，拼到序列末尾，再把整个序列送回模型。

最朴素的实现每一步都把完整前缀重新跑一遍前向。生成 \(n\) 个 token，第 \(t\) 步要处理 \(t\) 个 token：MLP 部分总共 \(\sum_t t = O(n^2)\) 的工作量，注意力部分每步是 \(O(t^2)\)，合起来 \(O(n^3)\)。这显然浪费——第 \(t\) 步重新算的前 \(t-1\) 个位置的结果和上一步完全一样，因为因果注意力里位置 \(j\) 只看得到 \(\le j\) 的位置，后面追加的 token 不会改变它。

真正被后续 token 需要的，只有每一层里每个历史位置的 key 和 value 向量：新 token 的 query 要和所有历史 key 做内积、再对所有历史 value 加权求和。把它们存下来，就是 KV cache。有了它，第 \(t\) 步只需要把一个新 token 跑过网络：线性层只算这一个位置，注意力用新 query 去读缓存。总代价降到 MLP \(O(n)\)、注意力 \(O(n^2)\)。

于是推理自然分成两个阶段：

  • 预填充（prefill）：把整个 prompt 一次性跑一遍前向（和训练的前向一样，所有位置并行），把每层每个位置的 K、V 写进缓存，同时得到最后一个位置的 logits。
  • 解码（decode / generation）：从 logits 采一个 token，把这一个 token 送进模型，读 KV cache 做注意力，把它自己的 K、V 追加进缓存，得到下一组 logits。重复直到遇到结束符或长度上限。

两个阶段的性质截然不同：较长 prompt 的预填充一次处理成百上千个 token，权重能被很多位置复用；解码每条序列每步只有一个 token，而且步与步之间有串行依赖，没法在时间维度上并行，只能靠把很多条请求拼成一个 batch来摊薄读权重的成本。

2. 推理在优化什么

先定几个量：

  • TTFT（time to first token）：从请求到达到第一个输出 token 的时间，主要由排队和预填充决定。
  • ITL（inter-token latency）：相邻两个输出 token 的时间间隔。一个请求会产生多个 ITL；其平均值称为 TPOT（time per output token）。二者的平均值可以相同，尾部分位数却不能混用。稳定解码时，ITL 约等于一次 step 的时间，生成速度约为它的倒数。
  • 吞吐：整个系统每秒生成多少 token；除以芯片数就是每芯片吞吐，直接决定每 token 的成本。

不同场景要的东西不一样：离线批量推理（跑评测、合成数据）只看总成本，单条延迟无所谓；聊天要在成本可控的前提下让 TTFT 短、生成速度高于人的阅读速度；端侧推理（笔记本上跑 llama.cpp）只服务一个用户，追求最低延迟。提高硬件利用率通常有助于训练吞吐，推理里它往往要拿延迟去换。

3. 线性层：解码为什么受带宽限制

这里的 \(\htmlData{symbol=batch}{B}\) 是本次矩阵乘的 token 行数：解码时每条请求贡献一行，所以它等于活动请求数；prefill 时一条请求也会贡献多行。\(\htmlData{symbol=width}{D}\) 是输入宽度，\(\htmlData{symbol=ffn}{F}\) 是输出宽度；\(\htmlData{symbol=compute}{C}\) 是每卡算力（FLOP/s），\(\htmlData{symbol=bandwidth}{\mathcal{B}}\) 是每卡 HBM 带宽（B/s），权重矩阵记为 \(\mathbf{W}\)。

回顾：roofline 与临界 batch

一次运算要花的时间至少是两样东西的较大者（假设二者能完全重叠）：算 FLOPs 的时间 \(\htmlData{symbol=math-time}{T_\text{math}}=\text{FLOPs}/\htmlData{symbol=compute}{C}\)，以及把数据从 HBM 搬进计算单元的时间 \(\htmlData{symbol=memory-time}{T_\text{mem}}=\text{Bytes}/\htmlData{symbol=bandwidth}{\mathcal{B}}\)。其中 \(\htmlData{symbol=compute}{C}\) 是芯片的峰值算力（FLOPs/s），\(\htmlData{symbol=bandwidth}{\mathcal{B}}\) 是 HBM 带宽（Bytes/s）。算术强度 = FLOPs / Bytes；当它超过硬件强度 \(\htmlData{symbol=compute}{C}/\htmlData{symbol=bandwidth}{\mathcal{B}}\) 时，算子受算力限制（compute-bound），否则受带宽限制（memory-bound）。

看一个线性层：bf16 激活 \(X[\htmlData{symbol=batch}{B}, \htmlData{symbol=width}{D}]\) 乘 bf16 权重 \(\mathbf{W}[\htmlData{symbol=width}{D}, \htmlData{symbol=ffn}{F}]\)。\(\htmlData{symbol=batch}{B}\) 是这一步里送进来的 token 数。

$$\htmlData{symbol=math-time}{T_\text{math}}=\frac{2\htmlData{symbol=batch}{B}\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}}{\htmlData{symbol=compute}{C}},\qquad \htmlData{symbol=memory-time}{T_\text{mem}}=\frac{2\htmlData{symbol=batch}{B}\htmlData{symbol=width}{D}+2\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}+2\htmlData{symbol=batch}{B}\htmlData{symbol=ffn}{F}}{\htmlData{symbol=bandwidth}{\mathcal{B}}}$$

（每个乘加算 2 FLOPs；bf16 每个数 2 字节，分别是读 \(X\)、读权重、写输出。）推理时 \(\htmlData{symbol=batch}{B}\) 通常最多几百，而 \(\htmlData{symbol=width}{D}, \htmlData{symbol=ffn}{F}\) 上万，所以分母里 \(2\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}\)（读权重）占绝对主导：

$$\frac{2\htmlData{symbol=batch}{B}\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}}{2\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}}=\htmlData{symbol=batch}{B} \;\ge\; \frac{\htmlData{symbol=compute}{C}}{\htmlData{symbol=bandwidth}{\mathcal{B}}}\quad\Longrightarrow\quad \htmlData{symbol=batch}{B} \ge \htmlData{symbol=critical-batch}{B_\text{crit}}=\frac{\htmlData{symbol=compute}{C}}{\htmlData{symbol=bandwidth}{\mathcal{B}}}$$

TPU v5e 的 bf16 算力是 \(1.97\times10^{14}\) FLOPs/s，HBM 带宽 \(8.2\times10^{11}\) B/s，\(\htmlData{symbol=critical-batch}{B_\text{crit}}\approx 240\)。H100 SXM 的 bf16 稠密算力是 989 TFLOPs、HBM 带宽 3.35 TB/s，\(\htmlData{symbol=critical-batch}{B_\text{crit}}\approx 295\)。两者都是几百。

结论：在读权重占主导的近似下，一个矩阵乘的 token 数需要超过 \(\htmlData{symbol=critical-batch}{B_\text{crit}}\)（几百）时才受算力限制。预填充时一个 prompt 就有几百上千个 token，天然满足；解码时每条序列只贡献 1 个 token，必须同时有几百条请求在解码才有机会越过理想 Roofline 的拐点；实际利用率还受矩阵形状和 kernel 效率影响。这在大多数在线服务里很难做到——240 条并发请求意味着 240 份独立的 KV cache。

精度如何改变临界 batch

如果权重用 int8/fp8 存（每参数 1 字节），读权重的字节数减半，而计算仍用 bf16，那么条件变成 \(2\htmlData{symbol=batch}{B}\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}/\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}=2\htmlData{symbol=batch}{B}\ge \htmlData{symbol=compute}{C}/\htmlData{symbol=bandwidth}{\mathcal{B}}\)，即 \(\htmlData{symbol=critical-batch}{B_\text{crit}}\) 减半到 120。如果连计算也用 int8（v5e 的 int8 算力是 \(3.94\times10^{14}\)，翻倍），\(\htmlData{symbol=compute}{C}\) 翻倍，\(\htmlData{symbol=critical-batch}{B_\text{crit}}\) 又回到 240。一般地：

$$\htmlData{symbol=critical-batch}{B_\text{crit}}=\frac{\text{每参数字节数}}{2}\cdot\frac{\htmlData{symbol=compute}{C}_\text{所用精度}}{\htmlData{symbol=bandwidth}{\mathcal{B}}}$$

直觉是：每个参数从 HBM 读进来要花 \(\htmlData{symbol=weight-bytes}{b_w}/\htmlData{symbol=bandwidth}{\mathcal{B}}\) 秒，在这段时间里芯片能做 \(\htmlData{symbol=compute}{C}\cdot \htmlData{symbol=weight-bytes}{b_w}/\htmlData{symbol=bandwidth}{\mathcal{B}}\) 次 FLOPs；每个 token 对每个参数只做 2 次 FLOPs，所以要攒够 \(\htmlData{symbol=weight-bytes}{b_w}\htmlData{symbol=compute}{C}/(2\htmlData{symbol=bandwidth}{\mathcal{B}})\) 个 token 才能把读参数的时间"填满"。

4. 解码注意力为什么难以摆脱带宽限制

这一节只计算一个头：\(\htmlData{symbol=batch}{B}\) 是请求数，\(\htmlData{symbol=queries}{T}\) 是本次 query 的位置数，\(\htmlData{symbol=history}{S}\) 是可见 key/value 的位置数，\(\htmlData{symbol=head-dim}{d_h}\) 是每头维度。下面的字节账本使用 BF16，每个元素 2 B，忽略 softmax 与中间工作区。

线性层的权重是所有序列共享的，batch 越大、每字节权重被复用的次数越多。注意力不一样：每条序列有自己的 KV cache。看一个头的标准多头注意力（用 FlashAttention 融合，不把注意力矩阵写回 HBM），query 长度 \(\htmlData{symbol=queries}{T}\)，key/value 长度 \(\htmlData{symbol=history}{S}\)：

  • 读 \(Q\)：\(\text{bf16}[\htmlData{symbol=batch}{B},\htmlData{symbol=queries}{T},\htmlData{symbol=head-dim}{d_h}]\)；读 \(K, V\)：两个 \(\text{bf16}[\htmlData{symbol=batch}{B},\htmlData{symbol=history}{S},\htmlData{symbol=head-dim}{d_h}]\)；写输出 \(\text{bf16}[\htmlData{symbol=batch}{B},\htmlData{symbol=queries}{T},\htmlData{symbol=head-dim}{d_h}]\)。
  • \(QK^\top\) 做 \(2\htmlData{symbol=batch}{B}\htmlData{symbol=history}{S}\htmlData{symbol=queries}{T}\htmlData{symbol=head-dim}{d_h}\) FLOPs，乘 \(V\) 再做 \(2\htmlData{symbol=batch}{B}\htmlData{symbol=history}{S}\htmlData{symbol=queries}{T}\htmlData{symbol=head-dim}{d_h}\)。
$$\text{强度}=\frac{4\htmlData{symbol=batch}{B}\htmlData{symbol=history}{S}\htmlData{symbol=queries}{T}\htmlData{symbol=head-dim}{d_h}}{4\htmlData{symbol=batch}{B}\htmlData{symbol=history}{S}\htmlData{symbol=head-dim}{d_h}+4\htmlData{symbol=batch}{B}\htmlData{symbol=queries}{T}\htmlData{symbol=head-dim}{d_h}}=\frac{\htmlData{symbol=history}{S}\htmlData{symbol=queries}{T}}{\htmlData{symbol=history}{S}+\htmlData{symbol=queries}{T}}$$

预填充时 \(\htmlData{symbol=history}{S}=\htmlData{symbol=queries}{T}\)，强度 \(=\htmlData{symbol=queries}{T}/2\)，序列长到几百就受算力限制。解码时 \(\htmlData{symbol=queries}{T}=1\)、\(\htmlData{symbol=history}{S}\gg1\)，强度 \(\approx 1\)——而且 \(\htmlData{symbol=batch}{B}\) 和 \(\htmlData{symbol=head-dim}{d_h}\) 都约掉了，增大 batch 不会提高这份理想化字节账本中的算术强度，因为 batch 每多一条，要读的 KV 也多一份。

GQA 会把它稍微抬高。设 \(\htmlData{symbol=hq}{H_q}\) 个 query 头共享 \(\htmlData{symbol=hkv}{H_{kv}}\) 个 KV 头，组大小 \(\htmlData{symbol=group}{G}=\htmlData{symbol=hq}{H_q}/\htmlData{symbol=hkv}{H_{kv}}\)。同一个 KV 头被 \(\htmlData{symbol=group}{G}\) 个 query 头读，解码时强度变成

$$\frac{\htmlData{symbol=history}{S}\htmlData{symbol=group}{G}}{\htmlData{symbol=history}{S}+\htmlData{symbol=group}{G}}\;\xrightarrow{\htmlData{symbol=history}{S}\gg \htmlData{symbol=group}{G}}\;\htmlData{symbol=group}{G}$$

LLaMA-3 的 \(\htmlData{symbol=group}{G}=8\)，离 240 差得远。所以这类长上下文 GQA 的解码注意力通常受带宽限制，它的耗时就是"读一遍 KV cache"的时间。这也说明了一个关键的不对称：batch 增大时，权重读取被摊薄，KV 读取不会。当一条序列的 KV cache 字节数和参数字节数可比时，增大 batch 带来的吞吐收益会迅速递减。

5. KV cache 有多大：MHA、MQA、GQA、MLA

容量从一条序列开始算：\(\htmlData{symbol=layers}{L}\) 是层数，\(\htmlData{symbol=hkv}{H_{kv}}\) 是每层 KV 头数，\(\htmlData{symbol=head-dim}{d_h}\) 是每头维度，\(\htmlData{symbol=history}{S}\) 是缓存长度，\(\htmlData{symbol=kv-bytes}{b_{kv}}\) 是元素字节数。\(\htmlData{symbol=hq}{H_q}\) 表示 query 头数；\(\htmlData{symbol=batch}{B}\) 条同长度序列的总容量再乘 \(\htmlData{symbol=batch}{B}\)。

基本公式

每层、每个 token 要存一个 key 和一个 value，各是 \(\htmlData{symbol=hkv}{H_{kv}}\) 个头 × 每头 \(\htmlData{symbol=head-dim}{d_h}\) 维。于是

$$\text{KV 字节数}=2\cdot \htmlData{symbol=layers}{L}\cdot \htmlData{symbol=hkv}{H_{kv}}\cdot \htmlData{symbol=head-dim}{d_h}\cdot \htmlData{symbol=history}{S}\cdot \htmlData{symbol=kv-bytes}{b_{kv}}$$

2 对应 key 和 value 两份，\(\htmlData{symbol=layers}{L}\) 是层数，\(\htmlData{symbol=history}{S}\) 是每条序列已经缓存的 token 数，\(\htmlData{symbol=kv-bytes}{b_{kv}}\) 是每个 KV 元素的字节数。几种注意力变体的区别只在 \(\htmlData{symbol=hkv}{H_{kv}}\)：

  • MHA（多头注意力）：\(\htmlData{symbol=hkv}{H_{kv}}=\htmlData{symbol=hq}{H_q}\)，每个 query 头有自己的 KV 头。
  • MQA（多查询注意力，Shazeer 2019）：\(\htmlData{symbol=hkv}{H_{kv}}=1\)，所有 query 头共享一个 KV 头，缓存缩小 \(\htmlData{symbol=hq}{H_q}\) 倍，但质量会掉一些。
  • GQA（分组查询注意力，Ainslie et al. 2023）：\(1\lt \htmlData{symbol=hkv}{H_{kv}}\lt \htmlData{symbol=hq}{H_q}\)，每 \(\htmlData{symbol=group}{G}=\htmlData{symbol=hq}{H_q}/\htmlData{symbol=hkv}{H_{kv}}\) 个 query 头共享一组 KV。实践中质量接近 MHA、速度接近 MQA，已经是开源模型的默认选择。

几个具体数字（bf16）：LLaMA-2-13B 是 MHA，\(\htmlData{symbol=layers}{L}=40, \htmlData{symbol=hkv}{H_{kv}}=40, \htmlData{symbol=head-dim}{d_h}=128\)，每 token \(2\cdot2\cdot40\cdot40\cdot128=819{,}200\) 字节 ≈ 0.82 MB，一条 8192 长的序列就是 6.7 GB，四条就超过了 26 GB 的参数。LLaMA-3-70B 用 GQA，\(\htmlData{symbol=layers}{L}=80, \htmlData{symbol=hkv}{H_{kv}}=8, \htmlData{symbol=head-dim}{d_h}=128\)，每 token 327,680 字节 = 320 KiB；如果按 MHA（\(\htmlData{symbol=hkv}{H_{kv}}=64\)）就是 8 倍。

MLA：存一个低秩隐向量

下标 \(t,j\) 表示序列位置，\(i\) 表示注意力头。\(h_t\) 是这一层的输入，\(c_t^{KV}\) 是压缩后的 KV 隐向量；上标 C/R 分别表示内容部分与 RoPE 部分。\(\htmlData{symbol=latent}{d_c}\) 是隐向量维度，\(\htmlData{symbol=rope-dim}{d_h^R}\) 是旋转部分的维度；矩阵 \(W\) 的上标区分各次投影，\(\top\) 表示转置。

DeepSeek-V2 提出的多头隐注意力（Multi-head Latent Attention）换了一个思路：不减少头数，而是把 K、V 联合压缩成一个低维向量再缓存。记第 \(t\) 个位置的隐状态为 \(h_t\in\mathbb{R}^{D}\)，\(\htmlData{symbol=hq}{H_q}\) 个头、每头 \(\htmlData{symbol=head-dim}{d_h}\) 维：

$$c_t^{KV}=W^{DKV}h_t\in\mathbb{R}^{\htmlData{symbol=latent}{d_c}},\qquad k_{t,i}^{C}=W^{UK}_i\,c_t^{KV},\qquad v_{t,i}^{C}=W^{UV}_i\,c_t^{KV}$$

\(W^{DKV}\) 是下投影，\(W^{UK}, W^{UV}\) 是把隐向量上投影回每个头的 key/value。推理时只缓存 \(c_t^{KV}\)。妙处在于根本不需要把 key、value 显式算出来：第 \(i\) 个头的注意力分数是

$$q_{t,i}^\top k_{j,i}^C=q_{t,i}^\top W_i^{UK}c_j^{KV}=\big((W_i^{UK})^{\top}q_{t,i}\big)^\top c_j^{KV}$$

所以可以把 \(W^{UK}\) "吸收"进 query 一侧：先把每个头的 query 映射到 \(\htmlData{symbol=latent}{d_c}\) 维隐空间，再直接和缓存里的 \(c_j\) 做内积。value 同理，\(W^{UV}\) 可以吸收进输出投影 \(W^O\)。

麻烦出在 RoPE 上。RoPE 在 query 和 key 上各乘一个依赖位置的旋转矩阵，分数变成 \(q_{t,i}^\top R_t^\top R_j W_i^{UK}c_j\)，中间夹着依赖 \(j-t\) 的 \(R_{j-t}\)，无法预先合并成一个固定矩阵，吸收就失效了。DeepSeek 的做法是解耦 RoPE：额外算一个很小的、所有头共享的带位置 key \(k_t^R=\text{RoPE}(W^{KR}h_t)\in\mathbb{R}^{\htmlData{symbol=rope-dim}{d_h^R}}\)，每个头的 query 也拆出一段带 RoPE 的 \(q_{t,i}^R\)，分数是两部分之和：

$$\text{score}_{t,j,i}=q_{t,i}^{C\top}k_{j,i}^{C}+q_{t,i}^{R\top}k_j^{R}$$

缓存里每层每 token 存 \(c^{KV}_t\)（\(\htmlData{symbol=latent}{d_c}\) 维）和 \(k_t^R\)（\(\htmlData{symbol=rope-dim}{d_h^R}\) 维）。DeepSeek-V2 和 V3 的配置相同：\(\htmlData{symbol=latent}{d_c}=512\)，\(\htmlData{symbol=rope-dim}{d_h^R}=64\)，\(\htmlData{symbol=hq}{H_q}=128\)，\(\htmlData{symbol=head-dim}{d_h}=128\)（对应 config.json 里的 kv_lora_rank、qk_rope_head_dim、num_attention_heads、v_head_dim）。于是每层每 token 是 \(512+64=576\) 个元素。换个角度看：\(\htmlData{symbol=latent}{d_c}=4\htmlData{symbol=head-dim}{d_h}\)、\(\htmlData{symbol=rope-dim}{d_h^R}=\htmlData{symbol=head-dim}{d_h}/2\)，缓存量相当于只有 \(2.25\) 组的 GQA（\(2\cdot2.25\cdot128=576\)）。

以 DeepSeek-V3（61 层）为例，bf16 下每 token 的缓存是 \(61\times576\times2=70{,}272\) 字节 ≈ 69 KiB，比 LLaMA-3-70B 的 320 KiB 还小得多，而它有 128 个注意力头。如果同样的头配置用 MHA（key 是 128+64=192 维，value 128 维），每层每 token 要存 \(128\times320=40{,}960\) 个元素，是 MLA 的 71 倍。DeepSeek-V2 相对 DeepSeek 67B 把 KV cache 减少了 93.3%，最大生成吞吐提高到 5.76 倍。

MLA 还有一个常被忽略的好处：吸收之后，解码时 128 个头都在读同一份 576 维的缓存，相当于 \(\htmlData{symbol=group}{G}=\htmlData{symbol=hq}{H_q}\) 的 MQA，注意力的算术强度随头数增长。代价是每个头的 query 要先做一次到 512 维的投影，注意力里的 FLOPs 变多。

其他减小 KV 的办法

  • 局部（滑动窗口）注意力：一部分层只看最近 \(w\) 个 token，这些层的缓存上限是 \(w\)，与上下文长度无关。和少量全局层交错使用，长上下文时总缓存能大幅缩小。
  • 跨层共享 KV：相邻几层共用一份 KV。缓存变小，batch 能开更大；但如果共享的缓存要被不同层各读一次，读取字节数不一定减少，单步时间未必变快。
  • 量化 KV（见第 11 节）和分页/只读有效部分（见第 9 节）是运行时手段，与架构无关。

6. 延迟下界与吞吐上界

以下估算针对稠密模型的单个副本。\(\htmlData{symbol=batch}{B}\) 条活动请求各生成一个 token，历史长度都取 \(\htmlData{symbol=history}{S}\)；\(\htmlData{symbol=devices}{N_{dev}}\) 是这个副本使用的卡数。\(\htmlData{symbol=kv-token}{k_{KV}}\) 是一条序列、一个历史位置在全部层占用的 KV 字节数。假设权重和 KV 均匀分片，并使用每卡带宽 \(\htmlData{symbol=bandwidth}{\mathcal{B}}\)。

推理时显存里都有什么

训练要存参数、梯度、优化器状态和用于反向的激活 checkpoint；推理只存一份参数，没有梯度和优化器状态，激活也很小（不需要为反向保留；8k token 的预填充一份激活只有 \(8192\times5120\times2\) 字节 ≈ 80 MB 量级，长的预填充还可以切块做）。剩下的大头就是 KV cache，它的总量是 batch × 上下文 × 每 token 大小，上限只取决于你允许多长的上下文、多大的 batch。

一步解码要多久

把前两节合起来。设参数量 \(\htmlData{symbol=params}{P}\)、每参数字节 \(\htmlData{symbol=weight-bytes}{b_w}\)，每 token 的 KV 字节 \(\htmlData{symbol=kv-token}{k_{KV}}\)，batch \(\htmlData{symbol=batch}{B}\)、上下文 \(\htmlData{symbol=history}{S}\)，\(\htmlData{symbol=devices}{N_{dev}}\) 张芯片完全分片（每张卡读 \(1/\htmlData{symbol=devices}{N_{dev}}\) 的权重和缓存）。一步解码：

  • 注意力：在长上下文、常见 GQA 的带宽受限近似下，读全部 KV：\(\htmlData{symbol=kv-time}{T_\text{KV}}=\dfrac{\htmlData{symbol=batch}{B}\cdot \htmlData{symbol=history}{S}\cdot \htmlData{symbol=kv-token}{k_{KV}}}{\htmlData{symbol=devices}{N_{dev}} \htmlData{symbol=bandwidth}{\mathcal{B}}}\)。
  • 线性层：读一遍权重，或者算 \(2\htmlData{symbol=batch}{B}\htmlData{symbol=params}{P}\) FLOPs，取较大者：\(\max\!\Big(\dfrac{\htmlData{symbol=params}{P} \htmlData{symbol=weight-bytes}{b_w}}{\htmlData{symbol=devices}{N_{dev}}\htmlData{symbol=bandwidth}{\mathcal{B}}},\ \dfrac{2\htmlData{symbol=batch}{B}\htmlData{symbol=params}{P}}{\htmlData{symbol=devices}{N_{dev}}\htmlData{symbol=compute}{C}}\Big)\)。
$$\htmlData{symbol=step-time}{T_\text{step}}\approx\underbrace{\frac{\htmlData{symbol=batch}{B} \htmlData{symbol=history}{S} \htmlData{symbol=kv-token}{k_{KV}}}{\htmlData{symbol=devices}{N_{dev}}\htmlData{symbol=bandwidth}{\mathcal{B}}}}_{\text{KV 读取}}+\max\!\Big(\underbrace{\frac{\htmlData{symbol=params}{P} \htmlData{symbol=weight-bytes}{b_w}}{\htmlData{symbol=devices}{N_{dev}}\htmlData{symbol=bandwidth}{\mathcal{B}}}}_{\text{权重读取}},\ \underbrace{\frac{2\htmlData{symbol=batch}{B}\htmlData{symbol=params}{P}}{\htmlData{symbol=devices}{N_{dev}}\htmlData{symbol=compute}{C}}}_{\text{矩阵 FLOPs}}\Big)$$

推理性能的账，基本都在这个式子里。小 batch 时 max 取权重读取，得到理论最小步时：

$$\htmlData{symbol=min-time}{T_\text{min}}=\frac{\htmlData{symbol=batch}{B}\cdot\text{KV 大小}+\text{参数大小}}{\text{总 HBM 带宽}},\qquad \text{吞吐上界}=\frac{\htmlData{symbol=batch}{B}}{\htmlData{symbol=min-time}{T_\text{min}}}$$

这个估计保留权重读取、KV 读取与线性层计算三项主要成本，并假设线性层读写和计算充分重叠。测量时还需要加入 attention 计算、非矩阵算子、通信、调度与工作区的成本。

举个例子：30B 稠密模型，int8 权重、bf16 计算，16 张 v5e，上下文 8192，每 token KV 100 kB。batch 4 时 \((4\times819\text{MB}+30\text{GB})/(16\times8.2\times10^{11})\approx2.5\) ms；batch 256 时 MLP 已经受算力限制，\(256\times819\text{MB}/(16\times8.2\times10^{11})+2\times256\times30\times10^9/(16\times1.97\times10^{14})\approx16+4.9\approx21\) ms。batch 扩大 64 倍，步时只涨 8 倍左右——这就是吞吐和延迟的交换。

什么时候解码才受算力限制

只看线性层：\(2\htmlData{symbol=batch}{B}\htmlData{symbol=params}{P}/(\htmlData{symbol=devices}{N_{dev}}\htmlData{symbol=compute}{C})\ge \htmlData{symbol=params}{P}\htmlData{symbol=weight-bytes}{b_w}/(\htmlData{symbol=devices}{N_{dev}}\htmlData{symbol=bandwidth}{\mathcal{B}})\iff \htmlData{symbol=batch}{B}\ge \htmlData{symbol=weight-bytes}{b_w} \htmlData{symbol=compute}{C}/(2\htmlData{symbol=bandwidth}{\mathcal{B}})\)，正是第 3 节的 \(\htmlData{symbol=critical-batch}{B_\text{crit}}\)，这里的 batch 指一个模型副本共同处理的请求数；芯片数在两边约掉，因此临界 batch 保持不变。但注意 KV 那一项永远在：即使线性层进了算力区，步时里还有一块纯带宽的时间，所以整体 MFU 达不到 100%，上下文越长、KV 那块越大，MFU 天花板越低。

8. 推理的分片：权重、缓存与服务副本

这里比较的是一个模型副本内部的分片。\(\htmlData{symbol=batch}{B}\) 仍是每轮的活动请求数，\(\htmlData{symbol=width}{D},\htmlData{symbol=ffn}{F}\) 是矩阵的两个维度；\(\htmlData{symbol=shards}{Y}\) 是这次矩阵乘的分片路数。\(\htmlData{symbol=bandwidth}{\mathcal{B}}\) 表示 HBM 带宽，\(\htmlData{symbol=net-bandwidth}{\mathcal{B}_{\rm net}}\) 表示互联有效带宽，单位都是 B/s。

预填充：和训练几乎一样

预填充是受算力限制的大矩阵乘，训练里能用的分片几乎都能用：先做张量（模型）并行，直到通信成为瓶颈（在 TPU 上，单个 mesh 轴的界约为 \(\htmlData{symbol=ffn}{F}/2200\) 路，一般是 4–8 路，推导见张量并行一篇）；再往上做序列并行（沿序列维切，注意力部分用 ring attention 之类的方式交换 KV），长上下文时它的额外通信相对较小。增加芯片换来更低的 TTFT，代价是通信开销、每卡吞吐略降。

解码：先区分单请求延迟与总服务容量

小 batch 解码频繁读取权重，因此常让权重常驻各卡，只交换较小的激活。几种并行方式解决的目标不同：

  • 张量并行把一个矩阵或若干头分给多张卡，减少单卡读取与计算，同时引入每层通信。MLP 常按中间维度 \(\htmlData{symbol=ffn}{F}\) 切；attention 的 \(W_Q,W_O\) 可按头切。
  • 服务副本（数据并行）复制模型，让不同副本处理不同请求，提高总容量与故障隔离能力；它不会直接缩短同一个请求的一步。
  • 流水线并行把层分到不同卡，帮助放下大模型，并让不同请求或 micro-batch 交错执行。单请求仍需依次通过所有阶段。
  • 缓存的上下文分片沿历史 KV 的序列维切分；当前 query 虽然只有一个位置，历史仍有很多位置。各卡算局部 attention，再合并。

逐层 all-gather 完整权重的 FSDP 路径需要反复经过互联，通常不适合追求低延迟的解码。KV 头少于并行卡数时，也可能在部分卡上复制 KV；要把这部分复制量计入容量和带宽。

为了延迟，可以切得比训练更多

训练里张量并行的上限来自"通信时间不能超过计算时间"。解码时我们本来就不受算力限制，受的是权重读取。所以要比较的是：每张卡读自己那份权重的时间 vs 每层的激活通信时间。对一个 \([\htmlData{symbol=width}{D},\htmlData{symbol=ffn}{F}]\) 的 BF16 矩阵，切 \(\htmlData{symbol=shards}{Y}\) 路。下面忽略集合通信的启动延迟与拓扑系数，激活也按每元素 2 B 计算：

$$\htmlData{symbol=hbm-time}{T_\text{HBM}}=\frac{2\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}}{\htmlData{symbol=shards}{Y}\,\htmlData{symbol=bandwidth}{\mathcal{B}}},\qquad \htmlData{symbol=network-time}{T_\text{ICI}}\approx\frac{2\htmlData{symbol=batch}{B}\htmlData{symbol=width}{D}}{\htmlData{symbol=net-bandwidth}{\mathcal{B}_{\rm net}}}$$

令 \(\htmlData{symbol=network-time}{T_\text{ICI}}\gt \htmlData{symbol=hbm-time}{T_\text{HBM}}\)：\(\dfrac{2\htmlData{symbol=batch}{B}\htmlData{symbol=width}{D}}{\htmlData{symbol=net-bandwidth}{\mathcal{B}_{\rm net}}}\gt\dfrac{2\htmlData{symbol=width}{D}\htmlData{symbol=ffn}{F}}{\htmlData{symbol=shards}{Y}\,\htmlData{symbol=bandwidth}{\mathcal{B}}}\iff \htmlData{symbol=shards}{Y}\gt\dfrac{\htmlData{symbol=ffn}{F}}{\htmlData{symbol=batch}{B}}\cdot\dfrac{\htmlData{symbol=net-bandwidth}{\mathcal{B}_{\rm net}}}{\htmlData{symbol=bandwidth}{\mathcal{B}}}=\dfrac{\htmlData{symbol=ffn}{F}}{\htmlData{symbol=batch}{B}\htmlData{symbol=ratio}{\rho}}\)，其中 \(\htmlData{symbol=ratio}{\rho}=\htmlData{symbol=bandwidth}{\mathcal{B}}/\htmlData{symbol=net-bandwidth}{\mathcal{B}_{\rm net}}\)，在 v5e/v6e 上约为 8。例如 \(\htmlData{symbol=ffn}{F}=16384\)、\(\htmlData{symbol=batch}{B}=32\)，按这个带宽近似可切到 \(16384/(32\cdot8)=64\) 路；实际还要检查小消息启动延迟与集合通信实现。batch 越小，能切得越多——小 batch 的低延迟服务可以靠堆卡继续降延迟。

KV cache 也要分片

长上下文时，KV 读取常占主要成本，理想情况是把缓存均匀分片。先按 KV 头切（Megatron 风格），但最多只能切 \(\htmlData{symbol=hkv}{H_{kv}}\) 路（LLaMA-3 只有 8 个 KV 头，MQA 只有 1 个）；再多的卡就沿 batch 维切：用下标 Z、Y 标记 batch 轴与头轴上的局部分片，缓存形状记为 \(\text{KV}[2, \htmlData{symbol=local-batch}{B_Z}, \htmlData{symbol=history}{S}, \htmlData{symbol=local-heads}{H_{kv,Y}}, \htmlData{symbol=head-dim}{d_h}]\)，完全分布。代价是每层注意力前后各一次 AllToAll：把按头切的 query 转成按 batch 切，算完注意力再转回来。这些通信作用在小小的激活上，换来的是不用搬巨大的、原地不动的 KV。上下文特别长、batch 又小时，还可以沿序列维切 KV：先 AllGather query，各卡算局部注意力，再像 FlashAttention 那样用 log-sum-exp 合并。

两个细节

  • 延迟受限的集合通信：小 batch 时激活非常小，一次集合通信的耗时被每跳的固定开销（TPU 上约 1 μs 量级）主导。例如在 v5e 上做 8 路张量并行时，缓冲区小于约 360 kB 就进入这个区，而 batch 16、\(\htmlData{symbol=width}{D}=8192\) 的 int8 激活只有 131 kB。
  • 2D 权重驻留分片（来自 Efficiently Scaling Transformer Inference）：权重同时沿 \(\htmlData{symbol=width}{D}\) 和 \(\htmlData{symbol=ffn}{F}\) 切成接近方形的块，通信量随总芯片数 \(\sqrt{\htmlData{symbol=devices}{N_{dev}}}\) 下降。在 \(\htmlData{symbol=ffn}{F}=4\htmlData{symbol=width}{D}\) 时，芯片数超过约 72 它就优于 1D 张量并行。

MoE 顺带一提：记 \(\htmlData{symbol=experts}{E}\) 为总 expert 数、\(\htmlData{symbol=active-experts}{r}\) 为每 token 选中的 expert 数。每个 token 只激活 \(\htmlData{symbol=active-experts}{r}\) 个 expert，但要读的是被任何 token 选中的 expert 权重。以 \(\htmlData{symbol=experts}{E}=16, \htmlData{symbol=active-experts}{r}=2\) 为例，若 batch 足够大、几乎全部 expert 都会被选中，相比单 expert 层，要读的 expert 权重多了 \(\htmlData{symbol=experts}{E}\) 倍、FLOPs 多了 \(\htmlData{symbol=active-experts}{r}\) 倍，所以受算力限制所需的 batch 要乘 \(\htmlData{symbol=experts}{E}/\htmlData{symbol=active-experts}{r}\)：v5e 上约 \(240\times8=1920\) 个 token。MoE 的解码比稠密模型更难吃满算力。

9. 推理引擎：分离、continuous batching、分页与前缀缓存

单次预填充和单步解码各自做快之后，真实服务还要把源源不断、长短不一的请求喂给这两个函数，在延迟-吞吐曲线上停在我们想要的位置。

从最朴素的方案说起

攒一批请求，一起做预填充，然后一起解码到全部结束，再处理下一批。问题很多：TTFT 被整批预填充拖慢；短的生成要等长的生成，batch 里越来越多空槽；预填充要 pad 到最长的 prompt，浪费算力；预填充和解码被迫用同一种分片（解码想要更多张量并行，预填充不需要）。

改进一步是交错（interleaved）：预填充一条一条做（单条就已经受算力限制），解码则把很多请求拼成 batch，一有空槽就插入新请求的预填充。这对离线批量生成很好，但在线服务有个问题：做某个用户的预填充时，所有正在解码的用户都要停下来等，生成速度变得一顿一顿的。

预填充 / 解码分离（disaggregation）

把两个阶段放到两组不同的芯片上：预填充服务器算出 KV cache，经网络发给解码服务器，后者把它插进自己的解码 batch。好处：

  • 一个用户的请求不会被另一个用户的预填充阻塞；两组服务器的数量可以按负载各自扩缩。
  • 两边可以用各自最优的分片和拓扑；预填充服务器除了正在处理的那条，不用常驻 KV，空出的显存可以拿来做前缀缓存。

代价是 KV cache 要过网络——又一个让 KV 变小的理由。DistServe、Splitwise 等系统在 GPU 上做了同样的事。

continuous batching

解决"短请求等长请求"的办法是以解码步为调度粒度（也叫 iteration-level scheduling，最早由 Orca 提出）。引擎编译两个函数：一个能处理变长 prompt、把结果插入 KV 缓冲区某个槽位的预填充；一个对当前所有活跃槽位各走一步的解码。调度器维护请求队列：每步之后，结束的序列立刻释放槽位，排队的请求立刻被预填充并插入。这样 batch 可以及时补入新请求，不用等最慢的那条。

和"交错"的问题相关，还有一种折中叫 chunked prefill（SARATHI）：把长 prompt 的预填充切成小块，每个解码步里顺带算一块，把预填充的算力"捎带"在受带宽限制的解码步上，同时避免长时间阻塞解码。它和分离是同一个问题的两种答案。

PagedAttention：像操作系统一样管理 KV

如果给每个槽位预留"最大上下文"长度的连续 KV 缓冲区，大部分请求根本用不到那么长，显存被大量浪费，batch 开不大；读取时如果也按最大长度读，还浪费带宽。第一步改进是"不规则读取"：注意力 kernel只读每条序列有效的那段。PagedAttention（vLLM）更进一步：把 KV 切成固定大小的块（比如每块 16 个 token），像虚拟内存的页一样按需分配，每条序列有一张块表把逻辑块映射到物理块。

这样每条序列只占用它实际需要的显存（浪费最多是最后一块没填满的部分），而且多条序列可以共享物理块（引用计数 + 写时复制），并行采样多个回答时共享 prompt 的 KV 不用复制。vLLM 在相同延迟下的在原论文的测试负载上比 FasterTransformer、Orca 等基线高 2–4 倍。代价是实现复杂度：kernel 要按块表做间接寻址。它是纯运行时的优化，与模型架构无关。

前缀缓存

预填充受算力限制、很贵，最好的优化是少做。在相同模型/adapter、位置配置和可见性下，两个 prompt 的相同 token 前缀会得到相同 KV（因果注意力，前面的位置看不到后面）。于是：

  • 多轮对话：每一轮都是在上一轮后面追加。保存上一轮的 KV，新一轮只需预填充新增的 token。
  • 系统提示 / few-shot 示例：大量请求共用同一段开头，算一次、反复用。

实现上，缓存的 KV 很自然地组织成一棵按 token 序列索引的前缀树（trie），共享前缀共享节点，按 LRU 淘汰。难点在容量：KV 动辄几 GB，要等到下一轮请求到来才有用。常见做法是用预填充服务器上空闲的 HBM，再加上主机内存（例如一台 8 卡 v5e 服务器有 128 GiB HBM，主机 DRAM 却有约 450 GiB）——主机内存对解码来说太慢，但对"读回一份缓存"足够。另外 KV 只存在处理过初始请求的那组卡上，所以需要亲和路由把同一会话的后续请求送回同一副本，这会和负载均衡冲突。KV 越小，能缓存的会话越多、读回越快——又是那个主题。

一个具体的实现是 Google 开源的 JetStream：一组"预填充引擎"和"解码引擎"（通常在不同的 TPU 切片上）由一个控制器编排；预填充线程、解码线程和负责把 KV 从预填充切片复制到解码切片的传输线程各司其职。引擎接口只有三个方法：prefill（输入 token，产出 KV cache）、insert（把一份 KV 插入解码 batch）、generate（对 batch 里每条序列各生成一个 token 并追加其 KV）。

10. 投机解码

投机解码另有一组局部符号：\(\htmlData{symbol=draft}{k}\) 是一轮草稿长度，\(\htmlData{symbol=produced}{N}\) 是这一轮最终输出的 token 数，\(\htmlData{symbol=accepted}{\alpha}\) 是简化模型中每一步的条件接受率，\(\htmlData{symbol=cost-ratio}{c}\) 是一次草稿前向与普通目标模型解码一步的耗时比。

解码受带宽限制，意味着在小 batch 时芯片的算力大量闲置：把 1 个 token 和把 5 个 token 送过模型，要读的权重相同；若新增计算仍藏在读权重的时间里，两者耗时就可能接近。投机解码就利用这一点：用一个便宜的草稿模型先猜 \(\htmlData{symbol=draft}{k}\) 个 token，再让大模型（目标模型）一次前向同时验证这 \(\htmlData{symbol=draft}{k}\) 个位置。

贪心版本

  1. 草稿模型贪心生成 \(\htmlData{symbol=draft}{k}\) 个 token \(\tilde x_1,\dots,\tilde x_{\htmlData{symbol=draft}{k}}\)。
  2. 目标模型处理上轮尚未写入 KV 的最后一个 token，加上这 \(\htmlData{symbol=draft}{k}\) 个草稿 token，一次得到 \(\htmlData{symbol=draft}{k}+1\) 组 logits。若最后一个前缀位置的 logits 已保存，也可以直接复用它。
  3. 从左往右检查：第 \(i\) 个草稿 token 是不是目标模型在该位置的 argmax。找到第一个不一致的位置，前面都接受，这个位置换成目标模型的 argmax；如果全部一致，再用最后一个位置的 logits 免费多出一个 token。

输出和直接用目标模型贪心解码完全一样，只是一次验证可能前进多个 token。

采样版本：修正的拒绝采样

固定当前已接受的前缀后，p(x) 是目标模型给 token x 的概率，q(x) 是草稿模型的概率。两者必须对应同一个前缀。β 是这个位置的总接受概率，α 才是后面简化长度模型使用的平均接受率。

非贪心时要保证输出分布严格等于目标模型的分布 \(p\)。设草稿模型在该位置的分布是 \(q\)，草稿 token \(x\sim q\)。Leviathan et al. 和 Chen et al. 同时给出了做法：

  • 以概率 \(\min\!\big(1, p(x)/q(x)\big)\) 接受 \(x\)；
  • 否则拒绝，并从修正分布 \(p'(x)=\dfrac{\max(0,\,p(x)-q(x))}{\sum_y \max(0,\,p(y)-q(y))}\) 重新采一个。

证明只需一行。接受的总概率 \(\htmlData{symbol=accept-prob}{\beta}=\sum_x q(x)\min(1,p(x)/q(x))=\sum_x\min(p(x),q(x))\)，拒绝概率 \(1-\htmlData{symbol=accept-prob}{\beta}=\sum_x\big(p(x)-\min(p,q)\big)=\sum_x\max(0,p(x)-q(x))\)。于是输出 \(x\) 的概率是

$$\underbrace{\min(p(x),q(x))}_{\text{直接接受}}+\underbrace{(1-\htmlData{symbol=accept-prob}{\beta})\cdot\frac{\max(0,p(x)-q(x))}{1-\htmlData{symbol=accept-prob}{\beta}}}_{\text{拒绝后重采}}=\min(p,q)+\max(0,p-q)=p(x).$$

所以平均接受率 \(\htmlData{symbol=accepted}{\alpha}=\mathbb{E}[\htmlData{symbol=accept-prob}{\beta}]=1-\mathbb{E}[\text{TV}(p,q)]\) 衡量草稿与目标分布的接近程度；TV 是总变差距离。贪心路径按 argmax 一致性判断，不直接把普通 softmax 的接受率套进去。

每次验证期望前进几个 token

做一个简化假设：每个草稿 token 被接受的概率都是 \(\htmlData{symbol=accepted}{\alpha}\)，彼此独立。一次验证产生的 token 数 \(\htmlData{symbol=produced}{N}\)：若第一个被拒的是第 \(i\) 个（\(1\le i\le \htmlData{symbol=draft}{k}\)），产生 \(i\) 个（\(i-1\) 个接受 + 1 个修正）；若全部接受，产生 \(\htmlData{symbol=draft}{k}+1\) 个。所以 \(\Pr(\htmlData{symbol=produced}{N}\ge n)=\htmlData{symbol=accepted}{\alpha}^{n-1}\)（前 \(n-1\) 个都被接受），\(n=1,\dots,\htmlData{symbol=draft}{k}+1\)。用 \(\mathbb{E}[\htmlData{symbol=produced}{N}]=\sum_{n\ge1}\Pr(\htmlData{symbol=produced}{N}\ge n)\)：

$$\mathbb{E}[\htmlData{symbol=produced}{N}]=\sum_{n=1}^{\htmlData{symbol=draft}{k}+1}\htmlData{symbol=accepted}{\alpha}^{n-1}=\frac{1-\htmlData{symbol=accepted}{\alpha}^{\htmlData{symbol=draft}{k}+1}}{1-\htmlData{symbol=accepted}{\alpha}}$$

当 \(\htmlData{symbol=accepted}{\alpha}=1\) 时，每轮输出 \(\htmlData{symbol=draft}{k}+1\) 个 token，应直接取这个极限，不能代入分母为零的式子。接受概率随位置变化时，\(\Pr(\htmlData{symbol=produced}{N}\ge n)\) 要用前 \(n-1\) 步条件接受率的乘积。这里暂不计 EOS 或输出长度上限的提前终止。

这是一个截断几何分布，\(\htmlData{symbol=draft}{k}\to\infty\) 时趋于 \(1/(1-\htmlData{symbol=accepted}{\alpha})\)。例如 \(\htmlData{symbol=accepted}{\alpha}=0.8\)、\(\htmlData{symbol=draft}{k}=4\) 时 \(\mathbb{E}[\htmlData{symbol=produced}{N}]=(1-0.8^5)/0.2\approx3.36\)。

时间上，每次验证要跑 \(\htmlData{symbol=draft}{k}\) 次草稿模型和 1 次目标模型。记草稿一次前向与目标一次前向的耗时比为 \(\htmlData{symbol=cost-ratio}{c}\)，并假设目标模型验证 \(\htmlData{symbol=draft}{k}+1\) 个 token 的耗时约等于普通解码一步（需要用当前 batch、草稿长度和上下文长度的测量来检查），则期望加速比为

$$\text{加速比}=\frac{1-\htmlData{symbol=accepted}{\alpha}^{\htmlData{symbol=draft}{k}+1}}{(1-\htmlData{symbol=accepted}{\alpha})(\htmlData{symbol=draft}{k}\htmlData{symbol=cost-ratio}{c}+1)}$$

它在 \(\htmlData{symbol=draft}{k}\) 上有一个最优值：\(\htmlData{symbol=draft}{k}\) 太小浪费了验证的并行度，太大时后面的草稿 token 几乎总被拒，草稿的成本白付。代价是总 FLOPs 增加——每次验证目标模型都算了 \(\htmlData{symbol=draft}{k}+1\) 个位置，平均只留下 \(\mathbb{E}[\htmlData{symbol=produced}{N}]\) 个。

什么时候划算：投机解码用多余的算力换延迟。小 batch、受带宽限制时，验证多几个 token 的增量成本可能很低；收益还要扣除草稿和调度开销；batch 已经大到线性层受算力限制时，多验证的 token 要实打实地花 FLOPs，收益就消失甚至为负。另外它在长上下文时还能省 KV 读取：一次读 KV 服务多个 token。在 Chinchilla 70B 配 4B 草稿模型的实验里（Chen et al.），自然语言摘要（XSum）上最优的草稿长度是 3–4 个 token；代码（HumanEval）更可预测，可以猜得更激进。

草稿从哪里来：可以是同系列的小模型（最好蒸馏过），也可以是 n-gram 或从上下文里查找匹配；也可以把草稿器做进主模型里，例如在主模型后几层加几个额外的预测头（Medusa、EAGLE 一类），它们共享大部分参数，跑得快、分布也更接近。

11. 量化：权重与 KV

重新看字节账本：\(\htmlData{symbol=params}{P}\) 是参数个数，\(\htmlData{symbol=weight-bytes}{b_w}\) 是每个权重的存储字节，\(\htmlData{symbol=kv-bytes}{b_{kv}}\) 是每个 KV 元素的字节；\(\htmlData{symbol=compute}{C}\) 必须取实际计算精度对应的算力，\(\htmlData{symbol=bandwidth}{\mathcal{B}}\) 是每卡 HBM 带宽。位宽降低时，还需另外计入 scale 等元数据。

推理对参数和 KV 的精度通常没有训练那么敏感，而且量化可以在训练后直接做。按第 6 节的公式，它影响三件事：

  1. 权重量化（int8 / fp8 / int4）：参数字节数 \(\htmlData{symbol=params}{P}\htmlData{symbol=weight-bytes}{b_w}\) 减半或减到四分之一。小 batch 时步时几乎就是权重读取时间，权重读取这一项按比例下降；参数占的显存变少，KV 可用的空间变多，batch 能开更大；同时 \(\htmlData{symbol=critical-batch}{B_\text{crit}}=\htmlData{symbol=weight-bytes}{b_w}\htmlData{symbol=compute}{C}/(2\htmlData{symbol=bandwidth}{\mathcal{B}})\) 下降，更小的 batch 就能进入算力区。PaLM 的推理测量（Pope et al.）显示：int8 权重带来更好的延迟-吞吐前沿，但并不提高最大吞吐——在算力区，速度由 FLOPs 决定，和权重存成什么无关。
  2. 低精度计算（W8A8：权重和激活都是 int8 / fp8，用 8-bit 张量核心）：\(\htmlData{symbol=compute}{C}\) 翻倍（v5e int8 394 TOPS，H100 fp8 约 1979 TFLOPs 稠密），提高的是算力区的速度，也就是最大吞吐和预填充速度；\(\htmlData{symbol=critical-batch}{B_\text{crit}}\) 随之回升。权重 int8 + bf16 计算是更常见的组合，因为只量化权重时，激活可以继续使用较高精度；精度损失仍需用任务评估检查。
  3. KV 量化（int8 / fp8）：\(\htmlData{symbol=kv-time}{T_\text{KV}}\) 减半，同样显存能放两倍的序列。长上下文时 KV 才是大头，这一项往往比权重量化更值。

实现上，量化就是 \(x\approx s\cdot\text{round}(x/s)\)，关键在缩放因子 \(s\) 的粒度：权重常按输出通道或按每 64/128 个元素一组取 \(s\)（int4 必须分组，否则离群值会吃掉精度）；KV 常按头、按 token 取 \(s\)。反量化通常与矩阵乘融合，但 scale、元数据和转换也有成本；最终收益要看实际 kernel 与负载。int4 这类激进量化一般需要 GPTQ、AWQ 之类利用校准数据的方法来控制误差。在上面的计算器里切换"权重 / KV / 矩阵计算"三个精度，就能看到这三种效果分别作用在哪条线上。

12. 实例：在 TPU v5e 上服务 LLaMA-3-70B

这一节用 \(\htmlData{symbol=layers}{L}\) 表示层数、\(\htmlData{symbol=width}{D}\) 表示模型宽度、\(\htmlData{symbol=ffn}{F}\) 表示 MLP 中间维度；\(\htmlData{symbol=hq}{H_q},\htmlData{symbol=hkv}{H_{kv}}\) 分别是 query/KV 头数，\(\htmlData{symbol=head-dim}{d_h}\) 是头维度，\(\htmlData{symbol=vocab}{V}\) 是词表大小。卡数始终写作 \(\htmlData{symbol=devices}{N_{dev}}\)，避免与头数混淆。GB/TB 都按十进制估算。

LLaMA-3-70B：\(\htmlData{symbol=layers}{L}=80\)、\(\htmlData{symbol=width}{D}=8192\)、\(\htmlData{symbol=ffn}{F}=28672\)、\(\htmlData{symbol=hq}{H_q}=64\)、\(\htmlData{symbol=hkv}{H_{kv}}=8\)、\(\htmlData{symbol=head-dim}{d_h}=128\)、\(\htmlData{symbol=vocab}{V}=128256\)。硬件选 TPU v5e，理由是每美元的 FLOPs 最多：按 2025 年 2 月的 Google Cloud 价格，H100 约 \(3.3\times10^{17}\)、v5p 约 \(3.9\times10^{17}\)、v5e 约 \(5.8\times10^{17}\) FLOPs/美元。代价是每张 v5e 只有 16 GB HBM，必须切得很碎。

KV 有多大

int8 下每 token \(2\cdot \htmlData{symbol=hkv}{H_{kv}}\cdot \htmlData{symbol=head-dim}{d_h}\cdot \htmlData{symbol=layers}{L}=2\cdot8\cdot128\cdot80=163{,}840\) 字节，约 164 kB。一条 32k 的序列约 5.4 GB；batch 240 就是 1.3 TB，比 70 GB 的参数大得多，光装下这些就要约 \((70\text{GB}+1.3\text{TB})/16\text{GB}\approx85\) 张 v5e。

batch 32、上下文 8k、int8 权重与 KV

KV 总量 \(164\text{kB}\times8192\times32\approx43\) GB，加上 70 GB 参数共约 113 GB。至少要 8 张卡（4×2，共 128 GB），非常紧，算上其他开销实际上得用 4×4。

步时：int8 权重 + bf16 计算，\(\htmlData{symbol=critical-batch}{B_\text{crit}}\approx120\)，batch 32 远在带宽区，步时就是把这 113 GB 读一遍。4×2 上 \(\htmlData{symbol=step-time}{T_\text{step}}\approx113\text{GB}/(8\times8.2\times10^{11})\approx17\) ms，吞吐 \(32/0.017\approx1860\) token/s，即每芯片约 230 token/s。还要检查张量并行有没有撞上通信界：用两个轴做模型并行，界约为 \(2\htmlData{symbol=ffn}{F}/2200\approx26\) 路，8 路没问题。换成 4×4：通信仍在这个带宽下界之内，步时减半到约 8.6 ms，每芯片吞吐不变。

分片能切多宽

bf16 在 4×8 上能不能纯张量并行？按受算力限制的界 \(\htmlData{symbol=shards}{Y}\gt \htmlData{symbol=ffn}{F}\cdot \htmlData{symbol=mesh-axes}{M_Y}/2200\)（\(\htmlData{symbol=mesh-axes}{M_Y}\) 是用于模型并行的轴数），两轴约 26 路，所以 4×4 可以、4×8 不行。但解码受带宽限制时，按第 8 节的条件可以放宽到 \(\htmlData{symbol=shards}{Y}\approx \htmlData{symbol=ffn}{F}/(8\htmlData{symbol=batch}{B})\)：batch 64 时约 56 路。具体算一下单个矩阵乘在 4×8 上的三个时间：\(\htmlData{symbol=network-time}{T_\text{ICI}}=2\cdot64\cdot8192/(9\times10^{10})\approx12\) μs，\(\htmlData{symbol=hbm-time}{T_\text{HBM}}=2\cdot8192\cdot28672/(32\cdot8.2\times10^{11})\approx18\) μs，\(\htmlData{symbol=math-time}{T_\text{math}}=2\cdot64\cdot8192\cdot28672/(32\cdot1.97\times10^{14})\approx5\) μs——仍然受 HBM 带宽限制，可以用 4×8 换更低的延迟。如果只压缩权重，HBM 读取时间缩短，通信反而可能更早显露出来；是否能继续扩大 batch，要同时检查激活通信精度与容量。

预填充与两池配比

配比使用平均负载：\(\htmlData{symbol=input-length}{I}\) 是平均 prompt 长度，\(\htmlData{symbol=output-length}{O}\) 是平均输出长度；\(\htmlData{symbol=prefill-pools}{P_\text{srv}},\htmlData{symbol=decode-pools}{G_\text{srv}}\) 分别是预填充池和解码池的副本数。后面的 0.91 s 是一个预填充副本处理一条输入的用时，0.019 s 是这里假设的解码步时。

8192 token 的预填充在 16 张 v5e 上、40% MFU：\(2\cdot70\times10^9\cdot8192/(16\cdot1.97\times10^{14}\cdot0.4)\approx0.91\) s。比起十几毫秒的解码步，这相当可观。

假设平均 prompt 为 8192、平均生成长度为 4096、batch 32 时，平均每步有 \(32/4096\) 条序列结束，每步被淘汰的 KV 约 \(\htmlData{symbol=batch}{B}(\htmlData{symbol=input-length}{I}+\htmlData{symbol=output-length}{O})/\htmlData{symbol=output-length}{O}=32\times12288/4096=96\) 个 token。

分离式部署时，预填充池的产出速率是 \(\htmlData{symbol=prefill-pools}{P_\text{srv}}/0.91\) 条/秒，解码池的消耗速率是 \(\htmlData{symbol=batch}{B}\cdot \htmlData{symbol=decode-pools}{G_\text{srv}}/(0.019\times512)\)。取 batch 32、生成长度 512，令两者相等得 \(\htmlData{symbol=prefill-pools}{P_\text{srv}}\approx3\htmlData{symbol=decode-pools}{G_\text{srv}}\)：长 prompt、短回答的负载需要三倍于解码的预填充服务器。

延迟-吞吐前沿

把 int8 权重、16 路张量并行（4×4）的配置沿 batch 扫一遍，就得到它的前沿：每 token 延迟从小 batch 的约 5.5 ms 到大 batch 的约 20 ms，延迟增加数倍时，每 token 成本可显著下降；具体倍数由上下文与 batch 决定。2k 上下文时吞吐在 batch 120 附近饱和于约 1 token/ms/芯片；上下文更长时 batch 装不下，永远到不了饱和点。在所有超过 2048 的上下文长度下，KV 读取时间都超过 FLOPs 时间。上面的计算器可以画出这条前沿：选 LLaMA-3-70B、TPU v5e、16 卡、8-bit 权重，拖动上下文看右侧曲线。

13. 小结

回看公式时：\(\htmlData{symbol=batch}{B}\) 是活动请求数，\(\htmlData{symbol=weight-bytes}{b_w}\) 是每参数字节数，\(\htmlData{symbol=compute}{C}\) 是每卡算力，\(\htmlData{symbol=bandwidth}{\mathcal{B}}\) 是每卡 HBM 带宽。下方投机解码公式中的 \(\htmlData{symbol=draft}{k}\) 是草稿长度，\(\htmlData{symbol=accepted}{\alpha}\) 是恒定条件接受率。

  • 推理 = 预填充（长 prompt 更容易受算力限制，关注 MFU 和 TTFT）+ 解码（小 batch 通常受带宽限制，关注每步字节数与 ITL）。
  • 解码一步的下界：\(\big(\htmlData{symbol=batch}{B}\cdot\text{KV}+\text{参数}\big)/\text{总带宽}\)；线性层要 batch 超过 \(\htmlData{symbol=critical-batch}{B_\text{crit}}=\htmlData{symbol=weight-bytes}{b_w}\htmlData{symbol=compute}{C}/(2\htmlData{symbol=bandwidth}{\mathcal{B}})\)（v5e bf16 为 240）才进入算力区，常见 GQA 解码注意力的强度仍远低于同一硬件拐点。
  • batch 是吞吐和延迟之间的旋钮；在固定 batch 的带宽区，增加芯片可以降低延迟，单卡吞吐近似保持不变；受 KV 容量限制时，加卡也能换来更大 batch 和更高单卡吞吐。
  • KV cache 是推理特有的主角：GQA / MQA / MLA / 局部注意力缩小它，量化压缩它，PagedAttention 不浪费它，前缀缓存复用它，分离式部署要传输它。
  • 张量并行与 KV 分片可以降低单步成本；服务副本提高总容量，流水线并行帮助容纳大模型。不同方案要一起计算通信和排队。
  • 投机解码用闲置算力换延迟，每次验证期望前进 \((1-\htmlData{symbol=accepted}{\alpha}^{\htmlData{symbol=draft}{k}+1})/(1-\htmlData{symbol=accepted}{\alpha})\) 个 token，在小 batch 时划算。
