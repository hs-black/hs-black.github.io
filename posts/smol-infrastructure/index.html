基础设施：GPU 集群、通信与存储

交互2026-10-19

做模型的人大多很在意架构和数据，却很少了解基础设施：租几张 GPU、装好 PyTorch，似乎就完事了。可 SmolLM3 在 384 张 H100 上训了将近一个月、11T token，一路上遇到的节点故障、存储问题和重启（见训练马拉松），几乎都是基础设施问题。基础设施要回答的其实只有一件事：瓶颈在哪里，怎么修掉。

要找瓶颈，就得知道数据路径上每一级到底有多快：GPU 内部的计算和显存、CPU、节点内的其他 GPU、其他节点、存储。理论值和实测值常常差得不少，这里的实测数字都来自 AWS p5 集群（每节点 8 张 H100），用 nvbandwidth、nccl-tests、gdsio 等工具量出。

1. GPU 内部：SM、Tensor Core 与 FLOPs

GPU 是为吞吐而不是延迟优化的大规模并行处理器。CPU 擅长快速执行少数复杂的指令流；GPU 靠同时执行成千上万个简单操作取胜。最高层面上它只做两件事：搬运和存储数据（存储系统），以及用数据做有用的计算（计算流水线）。性能取决于两者的配合：理论算力再高，数据喂不进来也是白搭。

FLOPs（floating-point operations per second）衡量计算速度，一次 FLOP 就是一次像 \(a+b\) 这样的浮点运算。GPU 的基本计算单元是流式多处理器（SM），每个 SM 里有两类核：处理普通浮点运算的 CUDA core，和专门做矩阵乘法的 Tensor Core。H100 SXM5 有 132 个 SM。每个 SM 以 32 个线程为一组（称为 warp）同步执行同一条指令（SIMT，单指令多线程）；warp 调度器在一个 warp 等数据时切换到另一个 warp，以此隐藏延迟。上百个 SM、每个同时跑多个 warp，一张卡上能同时有数万个线程。

FLOPs 和精度强相关：Tensor Core 支持 FP64、FP32、FP16/BF16、FP8、FP4 等格式，精度越低，每次搬的数据越少、同样硅面积能塞下的运算越多，吞吐可以差几个数量级。各代 GPU 的理论峰值（TFLOPs，稠密，不含 2:4 结构化稀疏；B200 按 HGX B200 的单卡规格）：

精度A100H100 SXMH200B200
FP649.7343437
FP3219.5676775
TF32（Tensor Core）1564954951,125
FP16/BF163129909902,250
FP8–1,9791,9794,500
FP4–––9,000

NVIDIA 规格表上 Tensor Core 那几行默认写的是 2:4 稀疏下的数字，正好是稠密的两倍：比如 H100 的 FP8 写作 3,958、BF16 写作 1,979。训练用的是稠密矩阵乘，算利用率时要用上表的稠密值。

实测：理论峰值能拿到多少

他们用 SemiAnalysis 的 GEMM 基准，在 Llama 70B 训练中真实出现的矩阵形状上测 H100：

  • BF16：714–758 TFLOPs，约为理论 990 的 72–77%。对真实负载来说是很好的利用率。
  • TF32（PyTorch 在 Tensor Core 上处理 FP32 张量的默认格式）：356–396 TFLOPs，约为稠密峰值（~495）的 72–80%。NVIDIA 规格表常写的 989 是 2:4 稀疏下的数字。
  • FP64：49–56 TFLOPs。
  • FP8：torch._scaled_mm（e4m3）1,210–1,457 TFLOPs；Transformer Engine 的 TE.Linear 只有 547–1,121。前者约为稠密峰值 1,979 的 61–74%，比 BF16 的利用率低：FP8 把算力翻了一倍，但同样形状下更容易撞上内存带宽的限制。而且同一硬件、同一精度，换个 kernel API 能差 2–3 倍。

MFU（model FLOPs utilization）是端到端训练效率：模型有用计算量 / 硬件理论峰值。kernel 层面的 72–77% 是上限，端到端还要扣掉非矩阵乘的算子、通信等开销。参考值：Meta 训练 Llama 3 405B 时 MFU 38–41%；DeepSeek-V3 约 20–30%（MoE 带来更紧的通信瓶颈）；SmolLM3 约 30%。相对可达的 77% 来说，这些端到端数字大约是「可达 matmul 性能」的 50–55%，差距主要来自节点间通信。

Compute capability（CC）是 NVIDIA 对硬件代际的版本号，决定能用哪些指令和特性。H100 是 9.0（内核名里会出现 sm90）。他们遇到过 PyTorch 在 H100 上选了 sm_75（Turing 代）的内核，导致莫名其妙的变慢——同一块硬件上 720 和 500 TFLOPs 的区别。用预编译库或自定义内核时，确认它是为目标 CC 编译的；nvidia-smi --query-gpu=compute_cap 可以查。

2. 显存层级与 roofline

GPU 存储是一个层级：越靠近计算单元越快、越小。H100 上各级的大致情况：

层级容量带宽说明
寄存器（RMEM）每 SM 256 KB，每线程私有最快，比 SMEM 再高一个量级紧挨计算单元
L1 / 共享内存（SMEM）每 SM 256 KB（两者共用）每 SM 每时钟 128 字节，全卡合计约 30 TB/s共享内存由程序员管理
L2 缓存50 MB数 TB/s，约为 HBM 的两倍全卡共享的 SRAM
HBM3（全局显存）80 GB理论 3.35 TB/sDRAM，最大也最慢

层级的成因是物理：SRAM 快但面积大、贵；DRAM 密度高、便宜但慢。所以快的存储只能少量地放在计算旁边。现代 AI 负载经常是受内存限制（memory-bound）的：瓶颈在搬数据，不在算。Horace He 举过一个例子：「读内存 → 自乘两次 → 写回」和「读内存 → 自乘一次 → 写回」耗时几乎一样，计算相对访存是「免费」的。

这就是算子融合有效的原因：把多个操作合进一个 kernel，中间结果留在 SRAM 里，不写回 HBM。FlashAttention 是典型：标准注意力要把 \(N\times N\) 的分数矩阵写进 HBM、softmax 时再读出来写回、乘 V 时再读一次；FlashAttention 把 Q、K、V 切成能放进 SRAM 的块，分块计算并在线更新 softmax，中间分数从不离开片上存储，只把最终输出写回 HBM。HBM 访问量从 \(O(N^2)\) 降到 \(O(N)\)，实际加速通常是 2–4 倍。

实测 HBM 带宽。用 NVIDIA 的 nvbandwidth 跑 device_local_copy：小于 1 MB 的消息受延迟限制，达不到峰值；1 MB 以上稳定在约 1,519 GB/s。这是一次拷贝（读和写同时发生），读 + 写合起来约 3 TB/s，接近 3.35 TB/s 的规格。

Roofline

判断一个 kernel 是计算受限还是内存受限，决定了哪种优化有用。算术强度 \(I\) = FLOPs / 访存字节数。kernel 能达到的性能上限是

$$P = \min\bigl(P_{\text{peak}},\ I \times B_{\text{mem}}\bigr).$$

两条边界交于脊点 \(I^* = P_{\text{peak}}/B_{\text{mem}}\)。用 H100 的 BF16 数字：\(990\times10^{12} / 3.35\times10^{12} \approx 296\) FLOPs/byte。算术强度低于它的 kernel 受内存限制，提高算力没用，要减少访存（融合、更好的访问模式）；高于它的受计算限制，优化访存没用，要更好的算法或用上 Tensor Core。举个例子：BF16 矩阵乘 \((M\times K)\cdot(K\times N)\) 做 \(2MNK\) 次 FLOP，至少读写 \(2(MK+KN+MN)\) 字节；\(M=N=K=8192\) 时 \(I = 2\cdot8192^3 / (2\cdot3\cdot8192^2) \approx 2731\)，远在脊点右边，是计算受限的；而逐元素的 GELU 每个元素 1 次读 1 次写（4 字节）只做个位数 FLOP，\(I\) 远小于 1，完全受内存限制。Nsight Compute 能直接画出某个 kernel 在 roofline 图上的位置，离边界越远，优化空间越大。（roofline 的完整推导见本站规模化训练系列。）

3. CPU ↔ GPU：PCIe、延迟与 NUMA

GPU 不是孤立工作的：数据要先进显存，CPU 要调度 kernel，分布式训练里 GPU 之间还要不停交换激活、梯度和权重。GPU 对外的连接可以分成四条：CPU–GPU、节点内 GPU–GPU、节点间 GPU–GPU、GPU–存储。实验机器是 AWS p5 实例（8 张 H100 80GB HBM3）。

CPU 是编排者：启动 kernel、管理显存分配、协调数据传输。它和 GPU 之间走 PCIe。用 lstopo 看 p5 的拓扑：

  • 两个 NUMA 节点（每个 CPU 插槽一个内存域），CPU 是 AMD EPYC 7R13，2 路、每路 48 核；
  • 每个 CPU 插槽通过 PCIe Gen4 x8（15.75 GB/s）连 4 个 PCIe 交换机；
  • 每个 PCIe 交换机通过 PCIe Gen5 x16（63.02 GB/s）连 1 张 H100；同一个交换机下还挂着 4 张 EFA 网卡和 1 块 NVMe 盘。

PCIe 每代单通道速率翻倍：Gen3 8 GT/s（x1 约 0.985 GB/s）、Gen4 16 GT/s（1.969 GB/s）、Gen5 32 GT/s（3.938 GB/s）、Gen6 64 GT/s。GT/s 是原始信号速率，GB/s 扣除了编码开销。所以 Gen4 x8 ≈ 8 × 1.969 = 15.75 GB/s，Gen5 x16 ≈ 16 × 3.938 = 63 GB/s。

CPU 到 GPU 要过两跳：CPU → 交换机（Gen4 x8，15.75 GB/s），交换机 → GPU（Gen5 x16，63 GB/s）。瓶颈是第一跳。nvbandwidth 的 host_to_device_memcpy_ce 实测大消息约 14.2 GB/s，是理论值的约 90%。往返延迟（host_device_latency_sm，用指针追逐 kernel 访问主机内存）约 1.4 μs，这解释了 ML 负载里常见的几微秒 kernel 启动开销。

  • CUDA Graphs：把一串操作捕获下来作为一个整体重放，省掉每个 kernel 启动的 CPU–GPU 往返。对大量小 kernel 或频繁同步的负载特别有用。
  • MoE 与 CPU–GPU 同步：有些 MoE 实现每次迭代都要 CPU–GPU 同步来调度选中的专家。MakoGenerate 优化 DeepSeek MoE kernel 的例子里，参考实现每次前向派发 1,043 个 kernel、67 个同步点；重构路由后变成 533 个 kernel、3 个同步点，同步开销减少 97%，端到端延迟减少 44%。现代实现通常把路由完全留在 GPU 上。
  • Grace Hopper：1:1 的 GPU:CPU 比例（x86+Hopper 是 4:1），每张 GPU 的 CPU 内存带宽高 3.5 倍；NVLink-C2C 取代 PCIe，CPU–GPU 带宽 900 GB/s 对 128 GB/s。

NUMA 亲和性。GPU 进程如果跑在另一个插槽的 CPU 核上，访问就要穿过 CPU 互联（AMD Infinity Fabric）。numactl --hardware 显示的节点距离是本地 10、跨插槽 32，访存延迟相差约 3.2 倍。每张 GPU 应该绑定到同一 NUMA 节点上的 CPU 核。

4. 节点内 GPU ↔ GPU：三条路与 NVLink

同一节点里的两张 GPU 有三种通信方式，用错环境变量会让带宽差两个数量级。

  1. 经过 CPU（SHM）：GPU1 → PCIe 交换机 → CPU → 主机内存 → CPU → PCIe 交换机 → GPU2。多次内存拷贝，挤占 PCIe 和 CPU 内存总线，四张 GPU 共享同一组 CPU 内存总线时更糟。设置 NCCL_P2P_DISABLE=1 和 FI_PROVIDER=tcp 可以强制走这条路，NCCL_DEBUG=INFO 会打印 via SHM/direct/direct。受 Gen4 x8 限制。
  2. 经 EFA 网卡的 GPUDirect RDMA：GPUDirect RDMA 让网卡直接读写 GPU 显存，不经过 CPU 和系统内存的缓冲区。p5 上每张 GPU 能用 4 张 EFA（AWS 自研、基于以太网的高性能网卡，传输协议是 SRD），每张 100 Gbps = 12.5 GB/s，所以每张 GPU 50 GB/s，每节点 \(100\times4\times8 = 3{,}200\) Gbps = 400 GB/s。设 FI_PROVIDER=efa、NCCL_P2P_DISABLE=1 时日志显示 via NET/Libfabric/0/GDRDMA。
  3. NVLink：NVIDIA 的 GPU 直连互联。H100 用 NVLink 4.0：18 条链路、每条 50 GB/s 双向，合计 900 GB/s 双向（单向 450）。前几代：Volta 300 GB/s，Ampere 600 GB/s；Blackwell 的 NVLink 5.0 是 1.8 TB/s。DGX H100 里 4 个 NVSwitch 连接 8 张 GPU，每张 GPU 分别以 5+4+4+5 条链路连到 4 个交换机，任意两张卡之间都只隔一个 NVSwitch，全网 3.6 TB/s 双向带宽。NCCL 默认优先用 NVLink（日志 via P2P/CUMEM，CUMEM 表示用 cuMem API 的显存句柄）；没有 NVLink 时退回到 PCIe 上的 GPUDirect P2P 或 SHM。

实测（NCCL SendRecv，单节点两卡）：NVLink 364.93 GB/s，EFA 38.16 GB/s，经 CPU 3.24 GB/s。NVLink 比 EFA 快 9 倍、比经 CPU 快 112.6 倍。nvbandwidth 的双向拷贝测试在所有 GPU 对之间都是约 786 GB/s，是理论 900 的 85%。

集合通信：algbw 与 busbw

nccl-tests 报两个带宽。algbw = 数据量 \(S\) / 耗时 \(t\)，直观但不能跨卡数比较。busbw 换算成「每张卡链路上实际走的流量速率」，可以直接和硬件链路带宽比。以 all-reduce 为例：\(n\) 张卡的 ring all-reduce 里，每张卡要发送（和接收）\(2(n-1)/n\cdot S\) 字节（reduce-scatter 和 all-gather 各 \((n-1)/n\cdot S\)），所以

$$\text{busbw}_{\text{all-reduce}} = \text{algbw}\times\frac{2(n-1)}{n},\qquad \text{busbw}_{\text{all-gather / reduce-scatter / all-to-all}} = \text{algbw}\times\frac{n-1}{n}.$$

单节点 all-reduce 实测 busbw 达到 480 GB/s，超过了 NVLink 4.0 单向的理论 450 GB/s。原因是 NVLink SHARP（NVLS）：NVSwitch 本身能做规约运算（硬件加速集合通信），数据不必在 GPU 之间来回传，单节点 H100 上给 all-reduce 带来约 1.3 倍加速。all-to-all 用不上 NVLS，实测 340 GB/s，只依赖 NVLink 的基础带宽。想精细控制 NVLink/NVLS 操作，可以关注 PyTorch 的 SymmetricMemory API；ThunderKittens 这类内核会专门分配一些 warp 发起 NVLink 传输，其余 warp 继续计算，在 SM 级别重叠通信和计算。

5. 节点间 GPU ↔ GPU：EFA / InfiniBand / RoCE

跨节点要走网络。三类主要技术：

以太网（25–100 Gbps）以太网（200–400 Gbps）RoCEInfiniBand
厂商多家多家多家NVIDIA/Mellanox
单向带宽（Gbps）25–100200–400100400
端到端延迟（μs）10–30N/A~1<1
RDMA否否是是

RoCE（RDMA over Converged Ethernet）在以太网上提供 RDMA，用显式拥塞通知（ECN）而不是 TCP 机制做拥塞控制；InfiniBand 是 NVIDIA 的交换网络，有 RDMA，配合 GPUDirect RDMA 可以绕过主机 CPU 直接读写对端 GPU 显存。p5 用的是 EFA。GPU 和它的网卡挂在同一个 PCIe 交换机下，GPUDirect RDMA 只需经过这个交换机，不碰其他交换机和 CPU 内存总线。理论上 8 个交换机 × 4 张 EFA × 100 Gbps = 3,200 Gbps = 400 GB/s 每节点。

实测带宽（nccl-tests，配置参照 aws-samples/awsome-distributed-training）：

  • SendRecv：2–4 节点约 42–43 GB/s（理论每卡 50 GB/s）；5 个节点以上掉到约 21 GB/s。原因是超过 4 个节点时 NCCL 自动把每个对端的点对点通道数从 2 减到 1。设 NCCL_NCHANNELS_PER_NET_PEER=2 能恢复，但可能伤害 all-to-all（见 NCCL issue #1272），要小心。
  • All-reduce：单节点 480 GB/s，2 节点 479 GB/s，3–16 节点稳定在 320–350 GB/s。跨出节点时因为从 NVLink 换到网络有一次下降，之后基本不随节点数变化。这正是数据并行能扩展到成百上千张卡的原因；这种行为是「8-rail 优化的胖树（fat tree）」网络的典型特征：每个节点的 8 张 GPU 各接一个独立的交换机「轨道」，最大化对分带宽。
  • All-to-all：单节点 344 GB/s，2 节点骤降到 81 GB/s，更多节点约 45–58 GB/s。每张卡都要和所有其他卡交换数据，网络拥塞严重得多——这对需要大量 all-to-all 的 MoE 专家并行是坏消息。

实测延迟：SendRecv 在多节点下 40–53 μs，基本由网络往返时间决定；all-reduce 单节点 12.9 μs，2 节点 55.5 μs，之后几乎线性增长，16 节点 235 μs；all-to-all 单节点 7.6 μs，2 节点 60 μs，16 节点 621 μs，超线性增长。

对 MoE 这类 all-to-all 密集的负载，NVSHMEM 越来越重要：它把多张 GPU 的显存组成一个分区全局地址空间（PGAS），由 GPU 自己发起异步的单边通信（借助 GPUDirect Async），不需要 CPU 编排，小消息（<1 KiB）吞吐最高可高 9.5 倍。支持 InfiniBand/RoCE（Mellanox CX-4 及以上）、Slingshot-11 和 Amazon EFA。

6. 互联排障清单

带宽低于预期时，按这个顺序查：

  1. 库版本：NCCL、EFA、CUDA 太旧可能缺少优化或修复；重要实验要记录版本。
  2. CPU 亲和性：错误的绑核会造成跨 NUMA 流量。NCCL issue #1017 里，NCCL_IGNORE_CPU_AFFINITY=1 加 --cpu-bind none 显著降低了容器内的延迟。
  3. 网络拓扑与放置：云上的 placement group 不保证最少跳数；胖树里挂在不同顶层交换机下的实例延迟更高、带宽可能更低。AWS 的 Instance Topology API 能看到每台实例挂在哪个网络节点下；小规模消融时尽量让实例在同一个交换机下。
  4. 环境变量：网卡相关的 NCCL 标志（自适应路由、GPU 发起传输、缓冲区大小等）缺失或错误会严重限制带宽，按 AWS EFA cheatsheet 等官方推荐配置。
  5. 容器：Docker 默认共享内存和锁页内存很小，要加 --shm-size=1g --ulimit memlock=-1；Docker 默认禁用 NUMA 支持，会让 cuMem 主机分配失败，加 --cap-add SYS_NICE；正确挂载 /sys，让 NCCL 能发现 GPU 和网卡的真实 PCI 拓扑。

7. GPU ↔ 存储

训练期间 GPU 要不断读数据、定期写 checkpoint，I/O 也会成为瓶颈。p5 上每张 GPU 对应一块 NVMe SSD，同样挂在那个 PCIe 交换机下。GPUDirect Storage（GDS）让存储控制器附近的 DMA 引擎直接把数据搬进/出 GPU 显存，不经过 CPU 的中转缓冲区，降低 CPU 开销和延迟。gdscheck.py -p 可以查配置；他们的集群里 GDS 只对 NVMe 配置了，实际并未启用。

节点上可用的存储（lsblk、df -h）：

  • /：291 GB 的 Amazon EBS 根文件系统（EBS 是 AWS 的块存储服务）；
  • /scratch：8 块 3.5 TB 的本地 NVMe 实例盘组成 RAID 0（条带化，不冗余），XFS，共约 28 TB；
  • /fsx：393 TB 的 WekaFS（名字是从 FSx 迁移过来时沿用的），面向 AI 的高性能并行文件系统；
  • /admin：4.5 TB 的 FSx for Lustre。Lustre 把元数据和数据服务分开以并行访问，大文件好，但元数据密集、小文件多的 AI 负载容易吃力。

用 gdsio 在不同线程数和 I/O 大小下测吞吐和 IOPS（每秒完成的 I/O 操作数，衡量处理大量小而分散的访问的能力），并比较三种传输方式：GPU_DIRECT（直接进显存）、CPU_GPU（先进主机内存再拷到 GPU）、CPUONLY（不涉及 GPU 的基线）。结果：

9. 韧性：节点健康、checkpoint 与自动评测

硬件快只是底线。训练跑几周到几个月，要的是能扛住必然发生的故障、不用人盯、出事能灵活调整的系统。

节点健康监控与替换

开训前他们跑了两套诊断：内部工具 GPU Fryer（压测降频、显存错误和性能异常），以及 NVIDIA 的 DCGM Diagnostics（覆盖计算、PCIe 连通性、显存完整性、温度稳定性）。DCGM 有四个级别：r1（几秒，PCIe/NVLink、显存、显存带宽）、r2（2 分钟内，加诊断和定向压力测试）、r3（30 分钟内，加定向功耗、NVBandwidth、显存压力）、r4（1–2 小时，全部测试）。这些测试找出了两张有问题的 GPU。在他们的 dcgmi diag -r 2 输出里能看到 GPU 到主机 14.26 GB/s、主机到 GPU 8.66 GB/s 等 PCIe 读数。

训练期间，固定的 48 节点 Slurm 预留让他们能长期跟踪同一批节点；用 Prometheus 采集所有 GPU 的 DCGM 指标、Grafana 可视化，Slack 机器人在节点行为异常时报警，在它拖垮整个训练之前主动换掉。

降频。规格假设散热完美，实际 GPU 过热会自动降低时钟。他们监控 DCGM 的 DCGM_FI_DEV_CLOCK_THROTTLE_REASONS 指标，非零就说明在降频。降频不只伤害那一张卡：压测时 all-reduce 带宽在超过 14 个节点后从 350 GB/s 骤降到 100 GB/s（预期应保持在 300 以上），原因是一个节点上一张降频的 GPU，所有其他节点在梯度同步时都要等它。分布式训练的速度由最慢的那个节点决定。开训前压测、持续监控温度、确认 GPU 时钟设在最高性能档。

Checkpoint 管理

Checkpoint 的用途：故障恢复、评测追踪进度、给社区分享中间模型。恢复最重要：如果每 4 小时存一次，立即恢复的话最多损失 4 小时（平均是一半）。两个细节：保存要在后台进行，不影响吞吐；注意存储——24 天、每 4 小时一次就是约 144 个 checkpoint，带上优化器状态体积很大。Nanotron 训练时他们每 2 小时在本地存一次，立刻上传 S3，确认备份成功后删掉本地那份；恢复时如果本地没有最新的就从 S3 拉。Slurm 上用 #SBATCH --requeue 自动从最新 checkpoint 重启。

一个惨痛教训：第一次大规模训练（StarCoder-15B）一路重启都没事，最后一天却发现整个 checkpoint 目录被删了——脚本末尾留着一条早年测吞吐时的 rm -rf $CHECKPOINT_PATH，只有 Slurm 任务真正结束时才会执行，之前的重启都没触发。幸好前一天的 checkpoint 另有备份，只损失了一天。教训：生产脚本里不要留破坏性命令；保存后立即自动备份。

多久存一次？有一个经典近似（Young, 1974）：设写一次 checkpoint 的开销为 \(C\)（训练被阻塞的时间），平均无故障时间为 \(M\)。间隔为 \(\tau\) 时，单位时间的损失约为 \(C/\tau + \tau/(2M)\)（存储开销 + 故障时平均重算半个间隔），对 \(\tau\) 求导得最优间隔

$$\tau^* \approx \sqrt{2CM}.$$

例如阻塞式保存要 \(C = 2\) 分钟、整个集群平均每 \(M = 24\) 小时出一次故障，\(\tau^* \approx \sqrt{2\times 2\times 1440} \approx 76\) 分钟。后台异步保存让 \(C\) 接近 0，就可以存得更频繁，此时主要约束变成存储空间和上传带宽。

自动评测

手动跑评测很快成为瓶颈。SmolLM3 用 LightEval 评测 Nanotron 的 checkpoint，每存一个 checkpoint 就在集群上触发一个评测任务，结果直接推到 Weights & Biases 或 Trackio。如果只能自动化一件事，就自动化评测。

10. 需要多少张 GPU

该租或买多少张卡？基本的估算公式：

$$\text{GPU 数} = \frac{\text{总 FLOPs}}{\text{每卡实际吞吐} \times \text{目标训练时长}}.$$

关键是用实际吞吐（乘上 MFU），而不是规格峰值。SmolLM3：3B 参数、11T token、目标约 4 周、预期 MFU 30%（来自相近规模的实验）。总 FLOPs 用 \(6N\) 近似：

$$6 \times 3\times10^{9} \times 11\times10^{12} = 1.98\times10^{23}\ \text{FLOPs}.$$

规划时保守一点：「峰值」不取规格上的 990，而取前面实测的 BF16 matmul 可达值 720 TFLOPs，于是每卡有效吞吐是 \(720\times10^{12}\times0.30 = 216\times10^{12}\) FLOPs/s。代入：

$$\frac{1.98\times10^{23}}{216\times10^{12} \times 4 \times 604{,}800} \approx 379\ \text{张 GPU}.$$

这指向 375–400 张 H100，他们拿到了 384 张：既和并行策略对得上（\(384 = 2^7\times3\)），又给节点故障、重启留了余量。实际训练时每卡吞吐约 13,750 tokens/s，按 \(6N\) 算是 \(248\) TFLOPs/s，比规划的 216 略高，所以 11T token 用了约 24 天，而不是 4 周。

Amdahl 定律：卡不是越多越好。并行加速比受不可并行部分的限制：

$$\text{最大加速比} = \frac{1}{\text{串行比例} + \dfrac{\text{并行比例}}{\text{处理器数}}}.$$

训练里「串行」部分主要是通信：梯度、权重、激活的同步。如果通信占每步 10%，加多少卡都不会超过 10 倍加速。更糟的是卡越多通信比例往往越大：all-reduce 参与者更多、网络带宽/延迟成为瓶颈、小模型的计算量不足以掩盖通信。SmolLM3 用的是弱扩展：全局 batch 随卡数一起放大，每张卡分到的工作量保持不变（SmolLM3 的配置里是每个数据并行副本每步 12k token），让计算/通信比保持合理。

12. 为 SmolLM3 找并行配置

拿到卡之后要决定怎么切模型。可以按三步走：先让一个训练步放进显存，再达到目标全局 batch，最后最大化吞吐。（各种并行方式的细节见本站的5D 并行等文章。）

第 1 步：放进显存。用 Nanotron 的 predict_memory 工具估算参数、优化器状态、梯度和激活，3B 模型单卡峰值约 74 GB，逼近 H100 的 80 GB。所以至少需要一种降低单卡显存的并行：张量并行（TP，层内切权重矩阵）、流水线并行（PP，按层深度切）或 ZeRO（切优化器状态）。

第 2 步：达到目标全局 batch。目标全局 batch（GBS）约 2M token：

$$\text{GBS} = \text{DP}\times\text{MBS}\times\text{GRAD\_ACC}\times\text{SEQLEN} \approx 2\text{M tokens},$$

DP 是数据并行副本数，MBS 是每卡每个微批的序列数，GRAD_ACC 是梯度累积步数，SEQLEN 在第一阶段是 4,096。硬件约束是 \(\text{DP}\times\text{TP}\times\text{PP} = 384 = 2^7\times3\)。这两个方程定义了搜索空间。

第 3 步：最大化吞吐。硬件有两种互联：节点内 NVLink（900 GB/s）和节点间 EFA（约 50 GB/s 每卡），自然地至少要两种并行去匹配。模型方面：不是 MoE，不需要专家并行；第一阶段序列长 4,096，不需要上下文并行。于是只剩 DP、TP、PP 三个维度，扫描：

  • DP 搭配 ZeRO-0 / 1 / 3：1 到 384，必须是 2 和/或 3 的倍数；
  • TP ∈ {1, 2, 3, 4, 6, 8}：限制在节点内，充分利用 NVLink；
  • PP ∈ 1..48；
  • MBS ∈ {2, 3, 4, 5}；
  • 激活重计算：无 / 选择性 / 全部；
  • 内核优化：CUDA Graphs 和可用的优化内核。

组合很多，实用的办法是先逐维度单独测，砍掉明显伤吞吐的选项。他们发现 PP 表现差：3B 模型小，跨节点的流水线气泡同步开销抵消了收益，而且当时没有能消除气泡的高效调度。ZeRO 级别高于 0 时引入的 all-gather 和 reduce-scatter 对吞吐的伤害大于省下的显存。剩下的就是「数据并行 + 适度的张量并行」。每个配置跑 5 次迭代，记录每卡每秒 token 数。

结果：DP = 192（梯度同步走节点间 EFA），TP = 2（留在节点内走 NVLink），MBS = 3，ZeRO-0，PP = 1，GRAD_ACC = 1。全局 batch \(192\times3\times1\times4096 = 2{,}359{,}296 \approx 2.36\)M token。每个数据并行副本每步处理 \(3\times4096 = 12{,}288\) 个 token；一个副本由 TP=2 的两张卡组成，它们处理的是同一批数据，所以折合到每张卡是 \(2.36\text{M}/384 \approx 6.1\)k token。

这些选择受当时库的状态影响：Nanotron 还不支持 ZeRO-3，也没有能消除气泡的 PP 调度。框架演进后结论可能会变。完整配置在 SmolLM 仓库的 stage1_8T.yaml。顺带一提，这个 TP=2 就是马拉松篇里那个随机种子 bug 的来源。
