训练马拉松：吞吐、loss spike 与中途调整

交互2026-10-19

这一篇读的是 Hugging Face 的 The Smol Training Playbook 中「The Training Marathon」一章：架构、数据配比和超参都定好了以后，真正按下「开始训练」之后会发生什么。主角是 SmolLM3：一个 3B 的稠密模型，在 384 张 H100（48 个节点）上训了将近一个月，一共 11T token。

这一章没有新算法，讲的是一次真实大规模训练里的各种意外：吞吐突然塌掉、数据加载器有隐藏的扩展性问题、loss 变得更抖、一个张量并行的随机种子 bug 让模型在 1T token 时落后于预期，最后不得不重启。然后是怎么监控、遇到 loss spike 怎么办、训练中途怎么换数据配比，以及怎么把上下文从 4k 扩到 128k。我按「先把账算清 → 起跑检查 → 四个谜案 → 监控与 spike → mid-training → 长上下文」的顺序写，每一部分都尽量把背后的机制讲到能自己复现推理的程度。

1. 先把账算清：吞吐、MFU 与完成时间

长跑之前，先定义几个整篇都会用到的量。

  • 吞吐（throughput）：训练系统每秒处理多少 token。可以按整个集群算，也可以按单卡算（tokens/s/GPU）。playbook 在基础设施一章里明确说，比较并行配置时他们看的就是「每卡每秒 token 数」。
  • 训练 FLOPs：稠密 Transformer 每个训练 token 大约要 \(6N\) 次浮点运算，\(N\) 是参数量。其中前向 \(2N\)（每个参数一次乘加 = 2 FLOPs），反向约是前向的两倍 \(4N\)。这个近似忽略了注意力里与序列长度相关的那部分计算，对 4k 上下文的 3B 模型来说误差不大。
  • MFU（model FLOPs utilization）：模型「有用」计算速度占硬件理论峰值的比例： $$\text{MFU} = \frac{6N \cdot \text{tokens/s/GPU}}{\text{峰值 FLOPs/s}}.$$

把 SmolLM3 的数字代进去。playbook 说他们的配置目标是约 30% MFU，监控时预期的稳定吞吐是 13,500–14,000 tokens/s（playbook 没写这是单卡还是整体，但只有按单卡理解，下面的账才对得上）。取中间值 13,750：

$$6 \times 3\times 10^{9} \times 13{,}750 \approx 2.48\times 10^{14}\ \text{FLOPs/s} \approx 248\ \text{TFLOPs/s}.$$

H100 的 BF16 稠密峰值是 990 TFLOPs/s，所以按 \(6N\) 算出来的 MFU 约 25%；如果把注意力的 FLOPs 也算上会再高一点，和「约 30%」是一个量级。整个集群的吞吐是 \(384 \times 13{,}750 \approx 5.28\text{M}\) tokens/s，11T token 需要

$$\frac{11\times 10^{12}}{5.28\times 10^{6}} \approx 2.08\times 10^{6}\ \text{s} \approx 24\ \text{天}.$$

这和 playbook 在 checkpoint 一节里随口提到的「24 天的训练」吻合。这笔账说明了为什么吞吐是基础设施上最重要的指标：吞吐掉一半，一个月的训练就变成两个月。账上每一项都是乘法关系，任何一项塌掉都直接体现在完成日期上。

2. 起跑前检查清单

按下开始键之前，playbook 会把下面五件事从头到尾过一遍。每一条后面其实都对应着一次「以前吃过的亏」。

  1. 基础设施就绪。如果集群调度系统（Slurm）支持预留（reservation），就用。SmolLM3 整个训练期间有一个固定的 48 节点预留：不用排队、吞吐稳定，还能长期跟踪同一批节点的健康状况。开训前对 GPU 做压力测试（他们用内部工具 GPU Fryer 和 NVIDIA 的 DCGM Diagnostics），检查降频和性能退化——SmolLM3 开训前就这样找出了两张会降频的卡并换掉了。另外要防止存储膨胀：每个 checkpoint 存完后上传到 S3，下一个 checkpoint 存好就删掉本地那份，所以本地高速 SSD 上永远只有一份。
  2. 评测流水线。评测比看起来更耗时间：手动跑、记结果、画图，一次就是几个小时。尽量全自动化，并且在开训之前确认它能正常运行和记录。SmolLM3 每保存一个 checkpoint 就自动在集群上触发一个评测任务，结果写进 Wandb 和 Trackio。
  3. Checkpoint 与自动恢复。确认 checkpoint 存得对，并且训练任务能在无人干预的情况下从最新的 checkpoint 恢复。Slurm 上用 --requeue：任务失败后自动重新排队，并从最近的 checkpoint 接着跑。
  4. 指标记录。确认所有关心的指标都在记录：评测分数、吞吐（tokens/s）、训练 loss、梯度范数、节点健康（GPU 利用率、温度、显存占用），以及本次训练特有的调试指标。
  5. 配置自查。训练配置、启动脚本、Slurm 提交命令再核对一遍。

这几条看起来朴素，但后文每一个谜案的排查都依赖它们：没有节点监控就看不出吞吐下跌和磁盘读延迟相关；没有自动评测和参考 checkpoint，就发现不了 TP 的 bug；没有自动恢复，每次掉节点都要有人半夜起来重启。

3. 交互：吞吐与完成日期计算器

把第 1 节的账做成一个小工具。输入模型大小、目标 token 数、卡数和单卡吞吐，再估计一下中途会挂几次、每次损失多少时间，就能得到预计完成日期。默认值是 SmolLM3 的配置；故障次数、每次恢复耗时和 checkpoint 间隔是我编的示意值，不是 playbook 报告的数字。

每次故障损失的时间按「恢复开销 + 半个 checkpoint 间隔」估算：故障发生的时刻在两个 checkpoint 之间大致均匀分布，所以平均要重算半个间隔的训练。

吞吐 / 完成日期计算器
吞吐下跌0%
集群吞吐–
估算 MFU（6N）–
纯计算时间–
故障损失–
预计完成–

拖一下「吞吐下跌」：跌 50% 时纯计算时间直接翻倍。这就是 playbook 把吞吐当作头号红线指标的原因——下一节的前两个谜案，都是吞吐出了问题。

4. 规模化带来的四个谜案

SmolLM3 的消融做得很充分：3B 模型在 100B token 上的消融结果不错；相对 SmolLM2 的架构改动（GQA、NoPE、文档内注意力掩码、新分词器）都被验证过，要么提升要么持平；数据配比也在英文、多语言、代码和数学之间找到了平衡；整套配置在 48 个节点上调到了约 30% 的 MFU，开训前还专门在 48 节点上验证过吞吐。即便如此，正式开始 11T token 的长跑之后，问题一个接一个。

谜案 1：消失的吞吐

症状。开训几个小时内，吞吐就大幅下跌，而且是反复的、陡峭的下跌。消融里从没出现过。

什么变了？排查的第一步是列出「正式训练和吞吐消融相比，到底有什么不同」。答案只有三项：

  1. 训练数据集的规模：现在用的是完整的约 24 TB 数据，消融只用了子集（数据来源相同）；
  2. 训练步数：按 11T token 设置的真实步数，而不是 100B token 的消融步数；
  3. 可能还有硬件状态：长时间满负载下，消融时正常的 GPU 可能出故障，网络连接可能退化。

其余一切——节点数、dataloader 配置、模型布局、并行方式——都和吞吐消融完全一样。直觉上数据集大小和步数都不该影响吞吐，所以先怀疑硬件。查看节点监控后发现：吞吐的大幅下跌和磁盘读延迟的尖峰同时出现。矛头指向数据存储。

集群的三层存储。他们的集群里训练数据可以放在三个地方：

  • FSx（实际是 Weka）：网络附加存储，采用「保热」缓存模型——常访问的文件留在本地，容量快满时把不活跃的「冷」文件逐出到 S3；
  • Scratch：每个节点上的本地 NVMe RAID（8 块 3.5 TB 的 NVMe 盘），比 FSx 快，但只有本节点能访问；
  • S3：远端对象存储，放冷数据和备份。

24 TB 的数据一开始放在 Weka 上。加上其他团队已经占用的空间，Weka 被推到了容量极限，于是它开始在训练中途逐出数据分片。被逐出的分片下次读取时要从 S3 拉回来，训练就卡住等数据——这就是吞吐断崖。

修复 1：换数据存储位置。他们找不到办法让 Weka 在整个训练期间把数据目录固定为「热」，于是换存储。直接从 S3 流式读太慢，最后决定在每个节点的本地 scratch 盘上各放一份完整数据。

这带来一个新问题：节点坏掉被替换时，新节点上没有数据。用 s5cmd 从 S3 下载 24 TB 要 3 小时；改用 fpsync 从同机房另一个健康节点复制，缩短到 1.5 小时。换算一下有效带宽：\(24\,\text{TB}/3\,\text{h}\approx 2.2\,\text{GB/s}\)，\(24\,\text{TB}/1.5\,\text{h}\approx 4.4\,\text{GB/s}\)。但每次故障还是要停 1.5 小时，而且需要有人立刻手动去复制数据。真正让它变得可以忍受的是一个朴素的办法：在 Slurm 预留里多留一个备用节点，数据预先装好。哪个节点坏了就直接换成备用节点，恢复延迟为零；备用节点闲着的时候跑评测或开发任务，不算浪费。

这解决了谜案 1……他们当时是这么以为的。

谜案 2：挥之不去的吞吐下跌

症状。数据搬到本地盘以后，个别的吞吐下跌仍然存在，而且硬件监控里看不到任何异常。和消融时的吞吐曲线对比，下跌反而变得更尖锐了。

缩小范围。仍然先怀疑硬件：384 张卡，总有一张出问题的概率不小。于是在更少的节点上测试——结果在单个节点上就能复现完全一样的下跌，无论换哪个节点。这排除了硬件。

回到三个变量：存储已经换了，硬件排除了，只剩步数。他们把步数从 3.2M 缩回 32k（其余配置不变，只改 train_steps、lr_decay_starting_step、lr_decay_steps 三个字段），下跌就变小了；步数越大，下跌越尖、越频繁。问题不在硬件，而在软件，而且几乎只可能是 dataloader：训练里其他组件对每个 batch 的处理都与总步数无关。

根因。SmolLM2 当年是用一个从 Megatron-LM 派生的 dataloader（TokenizedBytes）训练的，通过内部封装接到 Nanotron 上，吞吐一直平稳。SmolLM3 换成了 Nanotron 自带的 dataloader（nanosets），而他们从没用它做过大规模预训练。读了实现以后发现：它会天真地构建一个随训练步数增长的巨大索引。步数非常大时，这个索引占用的共享内存越来越多，引发了吞吐下跌。

修复 2：换回 TokenizedBytes。为了确认，他们用内部的 SmolLM2 框架加 TokenizedBytes、同样的数据跑了 48 个节点：没有下跌。最快的路径是把这个 dataloader 直接拷进 Nanotron。下跌消失，吞吐回到目标值。

谜案 3：变得更抖的 loss

症状。换了 dataloader 以后吞吐没问题了，但 loss 曲线比用 nanosets 时更抖。

这让他们想起几年前调过的一个 bug：文档是打乱了，但一个 batch 里的序列没有打乱，导致出现小的 loss 尖峰。检查新 dataloader，果然：它从每个文档里按顺序读取序列。对短文件没问题；但在代码这类领域，一个很长的低质量文件会被切成许多连续序列，可能填满整整一个 batch，造成 loss 尖峰。

修复 3：在序列级别打乱。两个选择：

  • 改 dataloader，支持随机访问（风险：内存占用更高）；
  • 离线把 tokenize 好的序列预先打乱。

集群预留在烧钱、时间很紧，他们选了第二个，更安全也更快：数据已经在每个节点上了，本地重新打乱很便宜（约 1 小时）。而且每个 epoch 用不同的种子各生成一份打乱顺序，避免多个 epoch 重复同样的打乱模式。

补丁还是修好？时间紧时，采用一个经过验证的现成方案或临时绕过，往往比调试自己坏掉的实现更快：谜案 2 直接搬来 TokenizedBytes 而不是修 nanosets 的索引，谜案 3 用离线预打乱而不是改 dataloader。但 playbook 也提醒，捷径走多了，系统会变成一堆难以维护和优化的补丁。

第二次起跑。到这时他们有了：稳定的吞吐（本地 scratch 存储 + 备用节点）、不再随步数下跌（TokenizedBytes）、干净的序列级打乱（每个 epoch 离线预打乱）。重新启动后，loss 平滑，吞吐稳定。

谜案 4：不达预期的效果

症状。前两天一切顺利，日志里看不出任何问题。但在约 1T token 处，评测结果出乎意料。他们手里有 SmolLM2（1.7B，配方相近）的中间 checkpoint，可以对比两个模型在同一训练阶段的表现。结果：参数更多、数据配比更好的 3B 模型，在同一训练位置反而比 1.7B 的差。loss 仍在下降、评测分数仍在上升，只是提升速度明显低于预期。

缩小范围。相对 SmolLM2 的每一处架构和数据改动都单独验证过，所以怀疑转向训练框架。两套设置之间尚未测试的差异只剩几处，最明显的是张量并行（TP）：SmolLM2 单卡放得下，训练时没开 TP；SmolLM3 需要 TP=2 才放得进显存。之前没想过专门测试它，因为 3B 消融也用了 TP，结果看起来合理。

验证。用和 SmolLM3 完全相同的设置（文档掩码、NoPE、同样的数据和超参）训练一个 1.7B 模型，一组开 TP、一组不开。差别立刻显现：开 TP 的版本 loss 一直更高、下游表现更差。确认是 TP 相关的 bug。

根因。对比 TP 和非 TP 训练的权重后发现：所有 TP rank 用的是同一个随机种子，而每个 rank 本应用不同的种子来初始化自己那一片权重。修复只有几行：

# nanotron/trainer.py（playbook 给出的 diff，略去上下文）
- set_random_seed(self.config.general.seed)
+ # 每个 TP rank 用不同的种子，保证各分片初始化不同
+ tp_rank = dist.get_rank(self.parallel_context.tp_pg)
+ set_random_seed(self.config.general.seed + tp_rank)

为什么同一个种子会出问题？回忆一下张量并行怎么切一个线性层。以 MLP 第一层为例，权重 \(W \in \mathbb{R}^{d \times 4d}\) 按列切成两半 \(W = [W_1 \mid W_2]\)，rank 0 存 \(W_1\)、rank 1 存 \(W_2\)，各自算出一半的中间激活；第二层按行切，各自算部分和再 all-reduce。每个 rank 都是「生成一个形状为 \(d\times 2d\) 的随机矩阵」——如果两个 rank 的随机数生成器状态相同，就会得到 \(W_1 = W_2\)。

下面是我自己的分析，不是 playbook 的原话：如果两片权重完全相同，而且后续每一步的更新也完全对称（同样的输入、同样的下游权重，所以同样的梯度），那这两片永远保持相同——等于把 MLP 和注意力的有效宽度砍掉了一半。实际中对称性能被打破多少，取决于实现细节（比如哪些参数并不按 TP 切分、数值误差等）。playbook 的描述是：权重初始化在分片之间相关，影响了收敛；不是灾难性的，模型照样在学、在进步，但效率损失足以解释在规模上观察到的差距。他们的原话是「我们一半的权重没有被正确初始化」。

修好种子后，他们重复了消融，确认 TP 与非 TP 的 loss 曲线和下游表现一致；又做了额外的健全性检查：分别训练 SmolLM2 风格（架构和数据）的 3B 模型和 SmolLM3 的 3B 模型，与 SmolLM2 的 checkpoint 对比。结果符合预期：1.7B 的 SmolLM2 弱于 3B 的 SmolLM2 变体，后者又被 SmolLM3-3B 超过。

值得注意的是这个 bug 被定位的速度：从发现差距到修好只用了一天。原因是其他所有组件都被消融验证过，TP 是唯一可疑的、没被单独测试过的部分。playbook 把这一点归功于前面反复强调的原则：扎实的消融不只是为了做出好模型，更是为了训练出问题时，能对每个决定有信心，迅速知道哪些部分没被充分测试。之后剩下的一个月基本平静，只有偶尔因为节点故障触发的重启。

5. 监控：只看 loss 曲线不够

TP bug 能被发现，靠的不是 loss 曲线——loss 看起来一切正常——而是下游评测落后于预期。而 SmolLM2 的中间 checkpoint 评测结果是关键的参照物：它让团队很早就意识到 3B 模型没走在正轨上。由此得到两条建议：

  • 训练大模型时，尽早开始跑下游评测，不要等训练结束；
  • 如果要和某个开源模型对比，问问作者能否提供中间 checkpoint，它们作为参照点非常有价值。

基础设施这边，最重要的指标是吞吐。SmolLM3 预期整个训练期间吞吐稳定在 13,500–14,000 tokens/s，任何持续偏离都是红灯。但只看吞吐不够，还需要持续的硬件健康监控来预判和发现硬件故障：GPU 温度、显存占用、计算利用率等。他们把这些指标接进 Grafana 仪表盘，并为硬件异常设置了实时 Slack 告警（细节见本系列的基础设施篇）。

把这些合在一起，监控其实分三层，每一层抓不同的问题：

层看什么本次能抓到的问题
系统吞吐、磁盘读延迟、GPU 温度/降频/显存、节点存活谜案 1（读延迟尖峰）、谜案 2（吞吐下跌）、降频 GPU、坏节点
优化训练 loss、梯度范数谜案 3（loss 变抖）、loss spike、发散
能力中间 checkpoint 的下游评测，与参考模型同阶段对比谜案 4（TP 种子 bug：loss 正常但学得慢）

6. Loss spike：分类、成因、预防与急救

SmolLM3 在 1T token 处重启了。那么，训练出问题时是不是总得重启？取决于问题的严重程度和根因。最常见的「中途问题」是 loss spike：训练 loss 突然跳高，可能只是小插曲，也可能是发散的前兆。playbook 引用了 Stas Bekman 在《Machine Learning Engineering Open Book》里的比喻：训练 loss 曲线像心电图，有好的、坏的、和「你该担心了」的。

两大类

  • 可恢复的 spike：要么很快恢复（spike 之后立刻回到原来的轨迹），要么慢慢恢复（要再训一段才回到 spike 前的轨迹）。通常可以直接训过去。如果恢复非常慢，可以回滚到之前的 checkpoint 并跳过出问题的 batch。
  • 不可恢复的 spike：模型要么发散，要么停在比 spike 之前更差的平台上。这需要比「回滚」更大的干预。

常见成因

我们并不完全理解训练不稳定，但知道规模越大越常见。在架构和优化器都比较保守的前提下，常见的罪魁祸首有：

  • 学习率过高：在训练早期引起不稳定，降学习率即可。
  • 坏数据：通常是可恢复 spike 的主因，但恢复可能很慢。问题可能在训练很深入时才出现，也就是模型遇到低质量数据的时候。谜案 3 里长代码文件填满 batch 就是例子。
  • 数据与参数状态的交互：PaLM（Chowdhery et al., 2022）观察到 spike 往往来自「特定数据 batch」和「特定参数状态」的组合，而不仅仅是「坏数据」：从另一个 checkpoint 出发、在同样的问题 batch 上训练，并不能复现 spike。
  • 初始化不佳：OLMo 2 的工作发现，把 scaled initialization 换成简单的正态分布（均值 0、标准差 0.02）提升了稳定性。
  • 精度问题：现在已经没人用 FP16 训练了，但 BLOOM 当年发现 FP16 比 BF16 不稳定得多。原因是 FP16 只有 5 位指数，最大值约 65504，容易溢出；BF16 有 8 位指数，动态范围与 FP32 相同。

预防：在 spike 发生之前把稳定性做进去

小模型、保守的学习率、好的数据，很少出 spike；更大的模型需要主动的稳定性措施：

  • 数据过滤与打乱。确保数据干净且充分打乱。例如 OLMo 2 发现，去掉含有大量重复 n-gram 的文档（1 到 13 个 token 的片段重复 32 次以上）能显著降低 spike 频率。
  • Z-loss。在 loss 里加一项，防止输出 logits 变得过大。记 softmax 的配分函数为 \(Z = \sum_{i} e^{z_i}\)（\(z_i\) 是词表上的 logits），则 $$\mathcal{L}_{\text{z-loss}} = \lambda \cdot \log^2 Z.$$ 它把 \(\log Z\) 往 0 拉，也就是让 logits 的整体尺度不要漂移；交叉熵对 logits 整体平移不敏感，所以这一项基本不影响模型本身要学的东西。playbook 的 1B 消融里加 z-loss 不影响 loss 和下游表现；SmolLM3 最后没用，因为他们的实现有额外开销，开训前没来得及优化。
  • Embedding 不做权重衰减。OLMo 2 发现这能提升稳定性。原因是 weight decay 会让 embedding 的范数逐渐变小，而 LayerNorm 的雅可比与输入范数成反比，范数小会让前几层梯度变大。
  • QK-norm。在算注意力之前对 query 和 key 做归一化，防止注意力 logits 过大。OLMo 2 等团队发现它有助于稳定；有意思的是，Marin 团队发现它甚至可以在训练中途加进去，用来修复发散。不过 playbook 在架构一章也提到，有工作发现 QK-norm 损害长上下文检索，所以 SmolLM3 没用（3B 模型本来也不太容易不稳定）。

急救：spike 还是发生了

  • 跳过问题 batch：回滚到 spike 之前的 checkpoint，跳过出问题的 batch。这是最常见的处理。Falcon 团队为解决 spike 跳过了 1B token；PaLM 团队发现跳过 spike 附近的 200–500 个 batch 能防止复发。结合上面「数据与参数状态交互」的观察，这个做法之所以有效，是因为它同时改变了「在哪个参数状态上看到哪批数据」。
  • 临时收紧梯度裁剪：把梯度范数阈值调低一段时间。梯度裁剪的公式是 $$g \leftarrow g \cdot \min\!\left(1, \frac{c}{\lVert g \rVert_2}\right),$$ \(c\) 越小，单步更新的最大幅度越小，异常 batch 能造成的破坏就越有限。
  • 架构修补：如上所述，QK-norm 可能有效。

8. 重启还是在线修复

回到开头的问题：SmolLM3 为什么选择在 1T token 处重启，而不是在线修？playbook 的理由是：TP 种子 bug 意味着「起跑就站错了脚」，一半的权重没有被正确初始化。当时模型的表现和 SmolLM2 相近，并且在相似的位置趋于平缓——也就是说继续训下去，大概率得到一个和 SmolLM2 差不多、但训练成本几乎翻倍的模型。这时重启才划算。

把它抽象一下，判断的依据大致是：

  • 问题是否已经「写进」了参数状态，而且后续训练无法纠正？初始化错误属于这一类，坏 batch 造成的可恢复 spike 不属于。
  • 修好以后，继续训练的终点能否达到目标？如果只能得到一个与旧模型相当的结果，已花的算力是沉没成本。
  • 修复的代价：回滚几个小时、跳过一些 batch，通常远比从头再来便宜。很多问题可以在线修正，避免浪费算力——这正是 loss spike 的处理方式。

9. Mid-training：多阶段数据配比

现代 LLM 的预训练通常分多个阶段，每个阶段数据配比不同，最后往往还有一个扩展上下文的阶段。例如 Qwen3 用了三阶段：先在 30T token、4k 上下文上做通用训练；再用 5T 更高质量、偏 STEM 和代码的 token 做推理阶段；最后在几千亿 token、32k 上下文上做长上下文阶段。SmolLM3 的思路类似：既有计划内的干预（引入更高质量的数据集、扩展上下文），也有根据监控做的反应式调整。

  • 计划内：SmolLM3 从一开始就打算在第 2 阶段引入更高质量的 FineMath4+ 和 Stack-Edu，在最后的学习率衰减阶段加入精选的问答和推理数据。
  • 反应式：在 SmolLM2 时，他们发现数学和代码表现落后于目标，就专门做了全新的数据集（FineMath 和 Stack-Edu），在训练中途引入。

SmolLM3 的三个阶段（各阶段配置和精确权重在 SmolLM 的 GitHub 仓库里）：

  • 阶段 1，基础训练（8T token，4k 上下文）：核心预训练配比——网页数据（FineWeb-Edu、DCLM、FineWeb2、FineWeb2-HQ）、代码（The Stack v2、StarCoder2）、数学（FineMath3+、InfiWebMath3+）。
  • 阶段 2，注入高质量数据（2T token，4k 上下文）：引入更严格过滤的数据——代码用 Stack-Edu，数学用 FineMath4+、InfiWebMath4+，以及面向高级数学推理的 MegaMath（加入其中的 Qwen 问答数据、合成改写和文本-代码交错块）。
  • 阶段 3，学习率衰减 + 推理与问答数据（1.1T token，4k 上下文）：进一步上采样高质量代码和数学，并引入 OpenMathReasoning、OpenCodeReasoning、OpenMathInstruct 等指令和推理数据。问答样本只是简单地拼接、用换行分隔。

为什么配比能在训练中途换、而且换在衰减阶段特别有效？架构一章里 playbook 用的是 WSD（warmup–stable–decay）调度：大部分时间学习率恒定，最后一段快速衰减。衰减阶段模型「定型」，这时看到的数据对最终能力影响最大，所以把最高质量、最稀缺的数据留到这时上采样，单位 token 的收益最高。这一点在系列的上一篇分词器、优化器、超参与数据配比里有更多讨论。

10. 长上下文扩展：4k → 64k 训练，YaRN 到 128k

上下文长度决定模型一次能处理多少文本：分析长文档、维持多轮对话的连贯、处理整个代码库都需要它。SmolLM3 以 4k 开训，但实际应用需要 128k。

为什么放在训练后段扩展

从一开始就用长上下文训练很贵：注意力的计算量随序列长度平方增长。而且研究表明（Gao et al., 2025，《How to Train Long-Context Language Models (Effectively)》），在训练末尾或继续预训练时，用几十到一百 B token 做上下文扩展，就足以得到不错的长上下文能力。

逐级扩展：4k → 32k → 64k

他们没有一步跳到 128k，而是分两个阶段逐步扩展，给模型时间适应每一个长度：先 4k → 32k，再 32k → 64k；128k 的能力来自推理时的外推，不是训练出来的。一个具体发现：每个阶段重新开一个学习率调度、训练 50B token，比在主衰减阶段的最后 100B token 里扩展上下文效果更好。每个阶段都通过消融选择长上下文数据配比和 RoPE θ，并用 RULER 评测。

基座模型上的长上下文评测。消融时他们发现，HELMET 在基座模型上噪声很大：同样的训练换个种子，结果差异明显。Gao et al. 建议在上面先做 SFT 来降低方差；SmolLM3 团队选择改用 RULER，在基座模型层面信号更可靠。

数据：上采样长文档没带来提升。这个阶段常见的做法是上采样长文档，比如长网页和书。他们试了上采样书籍、文章，甚至仿照 Qwen2.5-1M 的方法，用 FineWeb-Edu 和 Python-Edu 合成检索、填空（fill-in-the-middle）类任务的文档。出乎意料，这些都不比直接沿用阶段 3 的配比好——后者在 RULER 上已经能和 Llama 3.2 3B、Qwen2.5-3B 竞争。他们的猜测：基线配比里本来就有来自网页和代码的长文档（估计约占 10% 的 token），而且 NoPE 帮了忙。（这里的 NoPE 指 RNoPE：每四层里有一层不用位置编码，其余层用 RoPE，见系列的架构篇。）

扩展阶段他们还顺手进一步上采样了数学、代码和推理问答数据，并加入了几十万条 ChatML 格式的样本。另外试过在 4k → 32k 扩展时用滑动窗口注意力（窗口 4k、8k、16k），RULER 上都不如全注意力。

RoPE 回顾：为什么要调 θ

RoPE 把 query/key 向量的维度两两配对，每一对看作平面上的一个点，按位置 \(m\) 旋转角度 \(m\,\theta_k\)。第 \(k\) 对（\(k=0,\dots,d/2-1\)，\(d\) 是每个头的维度）的角频率是

$$\theta_k = b^{-2k/d},$$

\(b\) 就是常说的「RoPE theta / base」，原始值是 10,000。两个 token 在位置 \(m, n\) 的点积只依赖相对位置 \(m-n\)。第 \(k\) 对转满一圈所需的位置数（波长）是

$$\lambda_k = \frac{2\pi}{\theta_k} = 2\pi\, b^{2k/d}.$$

\(k\) 小的维度对转得快（波长短，分辨局部顺序），\(k\) 大的转得慢（波长长，编码远距离信息）。问题在于：如果训练时上下文只有 4k，那些波长远大于 4k 的低频维度，在训练中只见过「转了一小段弧」的情形；推理时把上下文拉长到 32k，这些维度会出现训练中没见过的角度，注意力行为就不可预期。同时，随着距离增大，旋转造成的点积衰减也会让远处 token 的注意力分数衰减过快（Xiong et al., 2023；Rozière et al., 2024）。

RoPE ABF（Adjusted Base Frequency，Xiong et al., 2023） 的做法就是把 \(b\) 调大：所有维度的旋转都变慢，同样的角度对应更远的距离，远处 token 的注意力不会衰减得那么快。可以一次调大，也可以随着上下文逐级调大。

SmolLM3 的取值：4k → 32k 时 θ 调到 2M，32k → 64k 时调到 5M。（同一团队的 SmolLM3 发布博客写的第一阶段是 1.5M，与 playbook 的 2M 不一致，这里以 playbook 为准并注明。）他们发现更大的值如 10M 能让 RULER 略好一点，但会伤害一些短上下文任务（比如 GSM8k），所以停在 5M——这个值不影响那些任务。作为对比，Qwen3 在把上下文从 4k 扩到 32k 时把 θ 从 10k 调到了 1M，然后用 YaRN 做 4 倍外推到 131k。

YaRN：推理时外推到 128k

他们希望 SmolLM3 推理时能处理 128k，但在 128k 序列上训练太贵，于是用 YaRN（Yet another RoPE extensioN，Peng et al., 2023）让模型外推到训练长度之外。和 ABF「所有维度一起调慢」不同，YaRN 对不同频率的维度区别对待。设原训练长度为 \(L\)、扩展倍数为 \(s = L'/L\)，对第 \(d\) 对维度计算「训练长度内转了几圈」：

$$r(d) = \frac{L}{\lambda_d}.$$

然后用一个斜坡函数 \(\gamma\) 决定这一对维度要不要插值（论文对 Llama 推荐 \(\alpha=1,\ \beta=32\)）：

$$\gamma(r) = \begin{cases} 0, & r \lt \alpha \\ 1, & r \gt \beta \\ \dfrac{r-\alpha}{\beta-\alpha}, & \text{其他} \end{cases} \qquad \theta_d' = \bigl(1-\gamma(r(d))\bigr)\frac{\theta_d}{s} + \gamma(r(d))\,\theta_d .$$

含义是：在训练长度内转了很多圈的高频维度（\(r\gt\beta\)）已经见过所有角度，不需要动；连一圈都没转满的低频维度（\(r\lt\alpha\)）按 \(1/s\) 做位置插值，把新长度压回训练见过的角度范围；中间的线性过渡。此外 YaRN 还给注意力 logits 加一个温度：\(\text{softmax}\bigl(q^\top k / (t\sqrt{d})\bigr)\)，其中 \(\sqrt{1/t} = 0.1\ln s + 1\)，用来补偿插值后注意力分布变「平」的问题。

playbook 写道，理论上 YaRN 允许把序列长度扩大四倍。实践中他们发现：用 64k 的 checkpoint 外推到 128k，比用 32k 的 checkpoint 效果更好，说明训练长度越接近目标推理长度越好；但推到 256k（64k 的 4 倍）时 RULER 表现下降，所以他们建议只用到 128k。

12. 小结

playbook 对整个预训练的总结很朴素：规划确定哪些东西值得测，消融验证每个决定，监控尽早发现问题，出问题时，系统性的去风险告诉你去哪里找。SmolLM3 最终得到了一个 11T token 训练的 3B 模型，在数学、代码、多语言和长上下文上有竞争力，位于 Qwen3 系列模型的帕累托前沿上。把这一章的经验按我自己的理解压缩成几条：

  1. 排查从「什么变了」开始。谜案 1、2 都是先列出正式训练与消融的全部差异，再逐个排除：硬件（换节点、缩到单节点复现）、存储、步数。
  2. 能在小规模复现就在小规模复现。谜案 2 在单节点复现，谜案 4 在 1.7B 上复现，调试成本从「几百张卡」降到「几张卡」。
  3. 没用过的组件就是风险。nanosets 和 TP 都是「以前没在这个规模用过」的东西，问题就出在它们身上。
  4. loss 正常不代表一切正常。要有下游评测和参照模型的同阶段 checkpoint。
  5. 多数 spike 可以在线处理：回滚、跳 batch、收紧裁剪；只有问题写进了参数、且继续训练无法达到目标时，才值得重启。
  6. 长上下文放在后段逐级扩，每级单独调 RoPE θ 和数据、单独开学习率调度，最后用 YaRN 外推，但别外推太远。

基座模型训完以后还要做后训练才能变成一个助手，这是下一篇的内容；而这一篇里反复出现的存储、网络、降频、checkpoint，在基础设施篇里有完整的测量数据。
