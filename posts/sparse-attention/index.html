Sparse attention：只看需要的历史

交互2026-10-20更新于 2026-10-22

上下文增长到十万 token 时，一次 decode 会为每个新 query 扫描很长的 K/V 历史。许多任务只依赖其中一小部分：最近的句子、文档开头的规则，或者与当前问题相关的几个片段。Sparse attention 为每个 query 指定一个读取集合，把计算和访存集中在这些位置。

真正需要设计的是三个环节：怎样确定集合，怎样保持集合内计算正确，以及怎样让 GPU 实际跳过其余数据。集合选得准确、索引组织得高效，才会同时带来质量和速度收益。

选定集合以后，重新计算概率

对第 \(i\) 个 query，允许读取的 key 集合记作 \(\htmlData{symbol=selected}{\mathcal S_i}\)。集合必须满足因果约束，并包含至少一个有效位置。缩放点积、softmax 和输出分别为：

$$s_{ij}=\frac{q_i^\top k_j}{\sqrt d},\qquad a_{ij}=\frac{e^{s_{ij}}}{\sum_{k\in\mathcal S_i}e^{s_{ik}}},\qquad y_i=\sum_{j\in\mathcal S_i}a_{ij}v_j.$$

这里 \(d\) 是 query/key 的向量维度。分母只包含选中位置，所以改变集合也会改变每个保留位置的权重。这个定义直接给出正确性参考：用相同集合构造 dense mask，再比较 sparse gather 的输出。

完整集合给出权重 [1/6,2/6,3/6]，输出 \(17/3\approx5.667\)。保留位置 0、2 后，指数和由 6 变成 4，权重变为 [1/4,3/4]，输出为 6.5。若在完整 softmax 后只清掉中间权重，会得到 4.333；再除以保留权重之和 2/3，才能恢复 6.5。

固定窗口的成本可以精确计算

包含当前 token 的因果窗口宽度记作 \(\htmlData{symbol=window}{w}\)。位置 \(i\) 读取从 \(\max(0,i-w+1)\) 到 \(i\) 的 key。前几行逐渐填满窗口，之后每行只读取 \(w\) 个位置。长度 \(n\ge w\) 时，总 query-key 配对数为：

$$\sum_{i=1}^{n}\min(i,w)=nw-\frac{w(w-1)}2.$$

当 \(n=4096,w=256\)，配对数为 1,015,936；完整因果 attention 为 \(4096\times4097/2=8,390,656\)，约减少 8.26 倍。每个配对要做 QK 点积和对 V 的加权累积，常见同维度情形约需 \(4d\) FLOPs，因此可以把配对数进一步换成计算量。

多层窗口让信息逐层向后传播。若每层的窗口均为 \(w\)，堆叠 \(L\) 层后，一个位置最多间接受到前方 \(L(w-1)\) 个位置的影响。这条路径经过层间变换；需要直接提取远处原始细节的任务，可以额外保留全局位置或采用内容选择。

动态选择怎样保持因果性

内容选择器用轻量分数从历史中选出 top-k 位置，主 attention 再读取这些位置的完整 K/V。选择器可以使用低维索引、分块摘要或者已训练的相关性打分。它处理的表示越小，越有机会把选择开销控制在节省的读取时间之内。

valid = key_positions <= query_position
scores = where(valid, index_scores, -inf)
chosen = topk(scores, k=min(k, valid.sum()))
chosen = sorted(unique(chosen + local_positions))
output = attention(q, K[chosen], V[chosen])

先执行因果过滤，才能让 top-k 的名额全部用于有效历史。局部窗口与远程位置合并后需要去重：重复索引会让同一个 value 在 softmax 中获得多份指数质量。带 padding 的 batch 还要把无效 key 排除在选择器和最终 attention 之外。

选择质量可以用“保留了多少完整 attention 的概率质量”辅助分析。若目标权重为 [0.80,0.15,0.05]，保留前两项得到质量 0.95；保留后两项只得到 0.20。遗漏位置的 value 与已保留位置相差越大，输出变化通常越明显。训练选择器时，可以让索引分数学习主 attention 的重要位置，同时保留局部访问作为稳定的基础路径。

从保留质量推导一个误差尺度

设完整 attention 对被保留集合的总概率为 \(p\)，保留位置按自己的概率重新归一化后的输出为 \(y_{keep}\)，其余位置的条件加权平均为 \(y_{drop}\)。完整输出可以拆成 \(y=p\,y_{keep}+(1-p)y_{drop}\)。因此稀疏输出的偏差为 \((1-p)(y_{keep}-y_{drop})\)。

若所有 value 的范数都不超过 \(V_{max}\)，两份条件平均的距离最多为 \(2V_{max}\)，于是有 \(\|y-y_{keep}\|\le2(1-p)V_{max}\)。这条界解释了为何“保留几个位置”不足以描述质量：保留的概率质量越多、被丢弃内容与保留内容越接近，偏差越小。它也为选择器训练提供了比纯粹命中率更接近输出的观察量。

具体例子中，完整权重 [0.8,0.15,0.05] 配 values [1,1,100]，前两个位置已经保留 95% 的概率质量。完整输出仍为 5.95，稀疏输出为 1，差距 4.95，来自最后一个 value 的大幅度。评估选择器时，把概率质量与 value 范围一起记录，能解释这类少量遗漏却有显著输出影响的情况。

稀疏索引怎样变成高效访存

GPU 以成块数据执行矩阵运算。假设每块 4 个 token，选中的位置是 1、5、9，它们落在三个不同块中，kernel 可能要读取 12 个位置，块内利用率只有 \(3/12=25\%\)。把选择预算写成 token 数之后，还要统计实际访问块数与边界块数量。

对每个 query tile，可以记录块数和块编号数组。完整可见块直接执行整块计算；跨过窗口、因果或文档边界的部分块，在块内应用精确 mask。先把每块的可见性正确分类，才能安全地省去完整块上的逐元素判断。

在 FlexAttention 中，score_mod 适合修改分数，mask_mod 描述可见性，再由 create_block_mask 构造块稀疏结构。固定窗口的 block mask 可以缓存；文档边界每个 batch 才变化时，可在该 batch 开始处构造一次，供各层复用。缓存键需要包含形状、设备、窗口和文档边界等决定 mask 的条件。

稀疏之后更慢，怎样拆开问题

先把一次调用分成 mask/索引构造、选择与 gather、attention kernel 三段，分别记录时间。一个示例是：完整 attention 用时 2.0 ms，稀疏选择 0.35 ms、gather 0.25 ms、计算 0.50 ms，总计 1.10 ms。若其余网络层还需 6 ms，端到端从 8.0 ms 降到 7.1 ms，加速约为 1.13 倍。

如果稳定运行的 kernel 很快而总调用很慢，检查是否每层都重建 block mask、每轮触发编译，或为短序列支付固定选择开销。用预先准备好的 mask 单独计时，再把构建成本加回端到端路径。随后固定真实长度与稀疏模式比较 tile 配置，关注实际处理的完整块、部分块和有效 token 比例。

当输出只在边界出错，构造长度略大于块大小的测试，例如 17 个位置配 16 大小的块。改变被遮蔽位置的 K/V 为很大的随机数，有效输出应保持一致。再加入非方形 query/key 长度、短请求 padding、多个文档和重复选择索引。这样的测试能直接区分索引错误、因果泄漏和归一化错误。

读取稀疏与缓存回收需要分别设计：当前 query 未选中的历史，未来 query 仍可能需要。若要释放 KV，必须有明确的窗口淘汰、合并或压缩规则。可以将本篇的访问集合与 KV cache 压缩的存储预算结合，分别记录每步读取字节和常驻字节。

批量请求还会带来负载不均。一个 query 选择 2 个块，另一个选择 20 个块，若它们被绑定在相同工作组里，较长路径可能决定完成时间。按实际块数分桶、拆分过长行或采用合适的 kernel 调度，都在解决这个问题；它们也可能增加索引整理与启动成本。测量时保留“每行访问块数”的分布，比只报告平均稀疏率更容易解释尾部延迟。

最后区分两种成本随长度的增长：低维索引器若扫描全部历史，它的工作仍按历史长度增长；主 attention 则按选中块数增长。当历史继续变长，瓶颈可能从大向量读取转到索引评分或 top-k。逐段画出延迟随长度变化的曲线，能看清这次稀疏设计在哪个阶段兑现了节省。

计算与排错练习

1. 窗口节省多少配对

长度 8，包含自己的窗口宽 3。求 sparse 与 full causal 配对数。

展开解答

Sparse 为 8×3−3×2/2=21，full 为 8×9/2=36，减少 15 对，约 41.7%。每行读取数依次为 1、2、3、3、3、3、3、3。

2. 理论选择数与物理读取

1024 个历史 token，每块 16 个，选择 32 个 token，恰好落在 24 个不同块中。实际覆盖多少 token？相比全读节省多少？

展开解答

读取覆盖 24×16=384 个位置，块内有效比例为 32/384≈8.33%。读取量约降为全历史的 37.5%，节省 62.5%。这些数字还需要加上索引和边界计算成本。

3. 未来候选怎样挤掉历史

Query 在位置 2，索引分数 [1,2,3,100]，top-k=2。先取 top-k 再删未来位置有什么结果？正确集合是什么？

展开解答

先选得到 {3,2}，过滤后只剩 {2}，浪费了一个名额。先遮住位置 3，再 top-k 得到 {2,1}，两项都属于有效历史。

用 dense mask 校验 sparse gather

下载实验后运行 python3 lab.py --seed 7（依赖 NumPy）。实验比较稀疏 gather 与相同 mask 的 dense 计算，并验证窗口配对数、块利用率和稀疏 softmax 数值例子。把窗口和块大小改成不能整除序列长度的数，检查最后一块；再加入重复索引，先预测它会怎样改变权重。
