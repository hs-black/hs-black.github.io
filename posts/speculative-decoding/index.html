01 · 时间从哪里来

大模型每次只前进一步，等待就串起来了

生成一个 token，需要经过大模型的所有层。草稿先给出一段候选，大模型就能把多个位置放进同一次前向。

图中文字只是示意 token；真正的分词未必按汉字划分。

02 · 一轮流程

小模型提出建议，大模型给每个位置打分

draft 给出候选及其概率 q。target 读入这些候选，算出每个位置的分布 p；最后再决定哪些 token 可以写进正式答案。

03 · 并行验证

候选已经写好，因果依赖就变成了一张掩码

同一轮可以计算所有行，每行仍然只看左侧前缀。如果 E 被拒绝，后面的分布基于错误前缀，后面的候选也就不能沿用。

04 · 先理解贪心

连续接受 E、F，遇到 G 就停

贪心解码时，候选与 target 的 argmax 一致就接受。第三个位置要 X：改成 X，丢掉 G、H。如果整段都接受，还能从下一位置分布得到一个额外 token。

假设 argmax 与并列值处理规则相同；图中为玩具词表。

05 · 随机采样

采样不能只检查“是不是最大概率”

候选 x 从 q 中抽出，再以 min(1, p(x)/q(x)) 接受。q 给 B 分配得太多，就只留下其中 60%；q 给 A 分配得少，抽到的 A 全部留下。

示意分布；p、q 必须对应同一已接受前缀，并包含实际使用的 temperature / top-p 等采样变换。

06 · 拒绝之后

把被删掉的概率，补到 target 更想要的地方

拒绝时从 normalize(max(p − q, 0)) 重采样，而不是直接从 p 重抽。于是每个 token 的总质量是 min(p,q) + max(p−q,0) = p。

同一位置先接受或拒绝；发生拒绝后结束这一轮，丢弃其后的草稿。

07 · 显存也跟着回滚

接受的是前缀，保留下来的 KV 也是前缀

验证可以提前算出候选的 KV。E、F 被接受就保留；G、H 的位置被回收。纠正的 X 在后续前向中补出 KV，成为下一轮的起点。

08 · 速度账本

省下的串行等待，要大于多做的草拟与验证

示意：普通生成 3 个 token 用 30 ms，投机一轮用 14 ms。实际收益由接受长度、草拟开销、验证 batch 和系统负载一起决定。

示例数字不是测量结果。平均输出数包含拒绝位置的纠正 token，或全部接受后的额外 token。

09 · 为什么要调长度

更长的草稿，不一定更快

前缀越长，活到末尾越难

假设每个位置条件接受率都是 0.8。

a₁ = 0.8
a₂ = 0.64
a₄ = 0.4096

第 4 个 token 只有约 41% 的机会用得上。

验证预算要花在有效位置

GPU 空闲时，多检查几个位置可能很便宜。

很多用户同时生成时，被拒绝的后缀也占用 batch 容量。

让 draft 更准，再按置信度与负载决定送验长度。

0.8 为示意；真实条件接受率会随位置、上下文和任务变化。
