投机解码

交互2026-10-20更新于 2026-10-22

普通自回归解码每次前向只确定一个新 token。若 GPU 正在用大量时间读取模型权重，能否让这次读取顺便验证几个未来位置？投机解码让一个较便宜的 draft 先提出候选，再由目标模型 target 并行检查。检查通过的连续前缀一次提交，第一次失败的位置由 target 纠正。

这项优化有两份账：概率账决定结果是否仍遵循 target 分布，时间账决定每次验证多得到的输出是否抵得上草拟成本。两份账都要成立，才值得把它接进服务引擎。

为什么多个候选可以一起验证

假设已经确定的文本是 A、B，draft 提出 C、D、E。target 用因果 mask 处理这段已知候选，就能同时计算“在 AB 后预测 C”“在 ABC 后预测 D”“在 ABCD 后预测 E”的分布。虽然这些前缀中含有猜测，验证时它们已经是确定的输入，因此矩阵计算可以并行。

提交仍然沿着顺序进行。如果 C 通过、D 失败，E 对应的分布就建立在错误的 D 上，当前轮应停在 D 的位置，输出一个纠正 token。若全部候选通过，最后一行还能给出一个 bonus token。因此一轮产生“连续接受的候选数 + 1”个输出，遇到 EOS 或输出长度上限时再按停止条件截断。

greedy 解码可以按 target 的 argmax 逐位置比较。随机采样需要更精确的接受规则，因为低概率词也必须以正确频率出现。

接受规则怎样守住概率质量

固定当前前缀，记 target 的实际采样分布为 \(\htmlData{symbol=p}{p}\)，draft 分布为 \(\htmlData{symbol=q}{q}\)。先从 \(q\) 抽取候选 \(x\)，然后以概率

$$a(x)=\min\left(1,\frac{p(x)}{q(x)}\right)$$

接受它。词 \(x\) 通过这条路径被输出的概率是 \(q(x)a(x)=\min(p(x),q(x))\)。draft 提供太多概率质量的位置被削减到 target 的要求；draft 提供不足的位置，还需要第二条路径补足。

总接受概率为 \(\htmlData{symbol=beta}{\beta}=\sum_x\min(p(x),q(x))\)。拒绝发生时，按剩余质量构造分布：

$$r(x)=\frac{[p(x)-q(x)]_+}{\sum_y[p(y)-q(y)]_+},\qquad [v]_+=\max(v,0).$$

分母等于 \(1-\beta\)。于是两条输出路径合起来：

$$\Pr(\text{输出 }x)=\min(p(x),q(x))+(1-\beta)r(x)=p(x).$$

若 \(p=q\)，所有候选都会通过，程序直接走接受分支。若某个词的 draft 概率为 0，它不会被 draft 抽到，目标为它保留的质量会通过残差分布产生。实现时应在实际抽到的候选上计算比值，并在拒绝分支才归一化残差。

这个例子的直接接受质量是 [0.2,0.3,0.2]，合计 0.7；拒绝质量为 0.3，残差分布为 [0,2/3,1/3]。乘回拒绝概率后补入 [0,0.2,0.1]，最终正好成为 [0.2,0.5,0.3]。随机实验应检查输出频率是否收敛到这行 target 概率。

p 和 q 必须对应实际抽样过程

temperature、top-k、top-p、重复惩罚和 grammar mask 都会改变分布。接受公式中的 \(q\) 必须与产生这个候选的分布相同；\(p\) 则对应用户要求的 target 采样策略。若候选使用了温度缩放，检验却读取未缩放的 logits，前面的概率守恒式就无法成立。

两个模型还要对齐 token 身份。普通实现要求相同的词表语义和 tokenizer；token ID 42 必须指向同一个事件。使用不同 tokenizer 时，需要专门的映射与验证算法，把候选转换到 target 空间，并按该算法重新处理接受概率。

调试时为每个位置保存前缀长度、候选 ID、q(x)、p(x)、随机数和接受结果。先在短词表上精确计算，再比较单请求的经验频率。最后加入不同长度的批处理，才能把采样错误与 batch 索引错误分开定位。

接受率怎样换成每轮输出数

设草稿长度为 \(\htmlData{symbol=k}{k}\)，每个位置在前面都通过的条件下，以固定概率 \(\htmlData{symbol=alpha}{\alpha}\) 通过。第 \(j\) 个候选真正贡献输出，需要前 \(j\) 个都通过，因此概率为 \(\alpha^j\)。每轮还会输出一个纠正或 bonus token，期望输出数为

$$\mathbb E[N]=1+\sum_{j=1}^{k}\alpha^j=\frac{1-\alpha^{k+1}}{1-\alpha}.$$

当 \(\alpha=1\) 时直接得到 \(k+1\)；当 \(\alpha=0\) 时为 1。以 \(\alpha=0.8,k=4\) 为例，期望输出是 \(1+0.8+0.64+0.512+0.4096=3.3616\)。不同位置的条件接受率若为 \(a_1,a_2,\ldots\)，则把 \(\alpha^j\) 换成 \(\prod_{i=1}^j a_i\)。

记普通解码一次耗时 \(T_1\)，草拟耗时 \(T_d(k)\)，target 验证耗时 \(T_v(k)\)，调度与同步开销 \(T_o(k)\)。每个输出的平均成本和预计加速比为

$$T_{\mathrm{token}}=\frac{T_d+T_v+T_o}{\mathbb E[N]},\qquad S=\frac{T_1\mathbb E[N]}{T_d+T_v+T_o}.$$

图中 k=4 时一轮用 14 ms，平均每 token 为约 4.1647 ms，加速约 2.4011 倍。更长草稿继续消耗验证位置，边际收益却按存活概率下降。高并发时 target 已被大量普通请求填满，验证候选还会挤占其他请求的工作，因此需要在目标负载下选择草稿长度。

验证完成后，KV 应保留到哪里

使用一个明确约定：原缓存含 P 个已处理位置，另有一个已采样、待消费的 anchor。target 输入为 [anchor,d₁,…,dₖ]，第 0 行 logits 验证 d₁，第 1 行验证 d₂，最后一行用于 bonus。假设连续接受 m 个候选，保留的缓存长度为 \(P+1+m\)：旧缓存、anchor、接受的候选都已经经过前向。

纠正 token 或 bonus 刚被采样出来，成为下一轮待消费的 anchor。把它加入正式输出后，缓存长度通常比已确定的完整文本少一个位置。下一轮先消费它，才产生它各层的 K/V。

例如旧缓存为 [A,B]、anchor=C，草稿为 [D,E,F]。target 一次写入 C,D,E,F，验证接受 D、E，拒绝 F，并采样 X。提交后缓存为 [A,B,C,D,E]，正式文本为 [A,B,C,D,E,X]。F 的 KV、draft 的分叉状态以及相应 grammar 状态需要回滚，X 留作下一轮输入。

高接受率却没有变快，怎样查

先同时测两件事：每轮实际输出数和整轮耗时。接受率只影响前者；draft 前向、target 验证、采样、同步和 host 调度都会影响后者。验证 batch 的 query 行数增加后，矩阵可能获得更好的利用率，也可能跨进另一个 kernel 或图捕获形状桶。用相同请求集比较开启前后的 GPU 时间线，分别标出草拟、验证和提交阶段，才能确定新增耗时出现在哪里。

再按 prompt 长度、输出类型、并发数拆分结果。平均接受率会掩盖长上下文或某类任务上的低收益。逐位置接受统计也很有用：若第一位就经常拒绝，应检查 draft 与 target 的词表、模板、位置和分布变换；若前几位很好而后面快速衰减，缩短草稿常常可以减少浪费。

正确性检查应分为概率测试与缓存测试。单位置用固定 p、q 枚举最终质量；多位置固定拒绝位置，检查留下的 KV、下一轮输入和输出序列。再覆盖全部接受、首个拒绝、EOS、最大输出边界和 batch 中部分请求结束。浮点并行路径可能改变近似 logits 的低位，测试应同时保存误差大小与输出概率。

缓存预算也会变化。target 在验证时暂时为 anchor 和候选写入 K/V，draft 还持有自己的状态；较长候选可能提前跨过物理页边界。调度器应在启动验证前预留整段需要的空间，提交后回收拒绝后缀。测量时记录权重、两套 KV、候选 logits 和临时 workspace 的峰值，避免在固定显存下用更长草稿换来更低的请求并发。

练习：概率、长度与回滚

1. 计算接受与残差

p=[0.2,0.5,0.3]，q=[0.5,0.3,0.2]，分别求每个候选的接受率、总接受率和残差分布。

参考解答

逐候选接受率为 [0.4,1,1]；总接受率为 0.5×0.4+0.3+0.2=0.7；残差质量为 [0,0.2,0.1]，归一化得到 [0,2/3,1/3]。

2. 草稿平均能贡献多少？

k=3，各位置条件接受率为 [0.9,0.8,0.5]。求期望输出数。

参考解答

累计存活率为 [0.9,0.72,0.36]，所以期望输出为 1+0.9+0.72+0.36=2.98。每个后续位置都需要前面的候选先通过。

3. 什么时候值得开启？

普通解码 8 ms/token，投机一轮 15 ms、期望输出 2.5。计算加速比；若并发增加使整轮变为 22 ms，会怎样？

参考解答

第一种为 8×2.5/15=1.333 倍；第二种为 20/22≈0.909 倍，每输出成本升到 8.8 ms，应在该负载下调整草稿长度或关闭投机。

4. 纠正 token 的 KV 是否已写好？

原缓存长度 P=100，待消费 anchor 一枚，草稿长 4，连续接受 2 个后采样纠正 token。求保留的 target KV 长度与新完整文本长度。

参考解答

缓存保留 100+1+2=103 个位置；加上新采样的纠正 token，文本有 104 个位置。下一轮消费纠正 token，才能将缓存推进到 104。

验证概率守恒与缓存边界

下载 lab.py，运行：

python3 lab.py --alpha 0.8 --length 4
python3 lab.py --alpha 1 --length 4
python3 lab.py --alpha 0 --length 4

脚本先用精确质量等式检查输出分布 [0.2,0.5,0.3]，再做十万次采样。默认期望输出为 3.3616，每轮 14 ms；边界接受率 1、0 分别得到 5、1 个输出。缓存实验检查拒绝后裁剪与下一轮 anchor 的提交。

把各位置接受率改成不同数值，用“首个拒绝位置枚举”和“累计存活概率求和”两种方法比较期望输出；再将实际 profile 的轮时带入，寻找适合目标负载的草稿长度。DSpark会进一步用每条请求的置信度分配验证预算。
