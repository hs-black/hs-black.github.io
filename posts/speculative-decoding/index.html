02 · 一轮流程

小模型提出建议，大模型给每个位置打分

draft 给出候选及其概率 q。target 读入这些候选，算出每个位置的分布 p；最后再决定哪些 token 可以写进正式答案。

03 · 并行验证

候选已经写好，因果依赖就变成了一张掩码

同一轮可以计算所有行，每行仍然只看左侧前缀。如果 E 被拒绝，后面的分布基于错误前缀，后面的候选也就不能沿用。

logits 的第 i 行，预测的是第 i+1 个 token

target 输入 该位置的输出分布 用途
前缀末尾 anchor D p(E | …,D) 检查候选 E
候选 E p(F | …,D,E) 检查候选 F
候选 F p(G | …,D,E,F) 检查候选 G
最后候选 H p(next | …,D,E,F,G,H) 全部接受后采样 bonus

如果 D 的 KV 已缓存，可复用之前保存的首行 logits；如果 D 刚采样出来，要把 D 和候选一起送入前向。两种缓存约定都可以，行号必须一致。

04 · 先理解贪心

连续接受 E、F，遇到 G 就停

贪心解码时，候选与 target 的 argmax 一致就接受。第三个位置要 X：改成 X，丢掉 G、H。如果整段都接受，还能从下一位置分布得到一个额外 token。

05 · 随机采样

采样不能只检查“是不是最大概率”

候选 x 从 q 中抽出，再以 min(1, p(x)/q(x)) 接受。q 给 B 分配得太多，就只留下其中 60%；q 给 A 分配得少，抽到的 A 全部留下。

示意分布；p、q 必须对应同一已接受前缀，并包含实际使用的 temperature / top-p 等采样变换。

工程 · 算清楚，再实现

为什么接受概率恰好是 min(1, p/q)？

候选 x 先以 q(x) 被抽到，再以 α(x) 被接受；两件事一起发生的概率是 q(x)α(x)。

q(x) · min(1, p(x)/q(x)) = min(p(x), q(x))

这个“重叠部分”已经放进输出。剩下缺的概率质量只有 p(x)−q(x) 为正的部分。

Z = 1 − Σₓ min(p(x),q(x))
r(x) = max(p(x)−q(x),0) / Z

最终概率 = min(p,q) + Zr = p。若 Z=0，p=q，拒绝不发生，也无需计算残差。

工程 · 算清楚，再实现

逐格补回概率，总量就回到 p

例子：p=(0.2,0.5,0.3)，q=(0.5,0.3,0.2)。接受总概率为 0.7，拒绝概率 Z=0.3。

拒绝后 r=(0, 2/3, 1/3)；蓝色加橙色，得到最终 (0.2,0.5,0.3)。

工程 · 算清楚，再实现

接受率衡量的是两份分布有多重合

a = Σₓ min(p(x),q(x))
= 1 − ½ Σₓ |p(x)−q(x)| = 1 − TV(p,q)

为什么成立？

min(p,q)=(p+q−|p−q|)/2。对词表求和，p 和 q 各自的总和都是 1。

数值例子

|p−q|=(0.3,0.2,0.1)，L1 距离为 0.6；TV=0.3，因此接受率 a=0.7。

top-1 猜对率只看最大的一项；随机采样接受率看整个分布。评估 draft 时要匹配实际温度与采样策略。

06 · 拒绝之后

把被删掉的概率，补到 target 更想要的地方

拒绝时从 normalize(max(p − q, 0)) 重采样，而不是直接从 p 重抽。于是每个 token 的总质量是 min(p,q) + max(p−q,0) = p。

同一位置先接受或拒绝；发生拒绝后结束这一轮，丢弃其后的草稿。

工程 · 算清楚，再实现

一轮采样：第一次拒绝就结束

for k in range(gamma):
    x = candidates[k]          # x ~ q[k]
    if uniform() < min(1, p[k][x] / q[k][x]):
        accepted.append(x)
    else:
        r = maximum(p[k] - q[k], 0)
        correction = sample(r / sum(r))
        return accepted + [correction]
return accepted + [sample(p[gamma])]  # bonus

q[k] 是真正产生 candidates[k] 的概率。若 p(x)=0，候选必拒绝；q(x)=0 的 token 不会从 q 被采到。

工程 · 算清楚，再实现

温度、top-p、logits processor 都属于分布定义

正确对齐

先让 target 的 logits 经过温度、重复惩罚、top-p 等配置，归一化为 p。q 也必须对应 draft 实际使用的采样分布。

常见错误

用截断前的 q 计算 p/q，却从 top-p 后的 q 抽样；或者验证时忘记更新 repetition penalty 的候选前缀。

temperature: pᵢ = exp(zᵢ/T) / Σⱼ exp(zⱼ/T)

数学上的分布保持以这些实际分布为准。贪心解码另用逐位置 argmax 一致的规则；随机种子相同也不保证逐 token 轨迹相同。

07 · 显存也跟着回滚

接受的是前缀，保留下来的 KV 也是前缀

验证可以提前算出候选的 KV。E、F 被接受就保留；G、H 的位置被回收。纠正的 X 在后续前向中补出 KV，成为下一轮的起点。

输出长度，比 target KV 长一格是正常状态

时刻 已确认输出 target 已有 KV
开始 A B D A B；D 是待处理 anchor
验证 D E F G H 后 A B D A B D E F G H（含临时候选）
接受 E F，拒绝 G A B D E F X A B D E F
下一轮消费 X A B D E F X A B D E F X

提交长度 = 原 KV 长度 + anchor 数 + 已接受候选数。X 是新采样的结果，还没有经过 forward，不能把 G 的 KV 改名为 X。

工程 · 算清楚，再实现

EOS、输出上限和双份缓存也要守住边界

截断正式输出

一轮可能产出 γ+1 个 token。先按第一个 EOS 或剩余 max_new_tokens 截断；丢弃其后的结果与缓存，不继续展示后缀。

同步 draft 与 target

两个模型都要回滚到共同接受的前缀。草稿缓存也不能保留被拒绝的后缀；新纠正 token 要先消费再续写。

建议记录每轮 prefix_len、accepted_len、target_kv_len、draft_kv_len。用 γ=0、首位拒绝、全接受、首位 EOS 四种小例子检查状态机。

08 · 速度账本

省下的串行等待，要大于多做的草拟与验证

示意：普通生成 3 个 token 用 30 ms，投机一轮用 14 ms。实际收益由接受长度、草拟开销、验证 batch 和系统负载一起决定。

示例数字不是测量结果。平均输出数包含拒绝位置的纠正 token，或全部接受后的额外 token。

工程 · 算清楚，再实现

平均接受长度，用“活到这一格”的概率来算

令 A 是连续接受的候选数。A 至少为 j，当且仅当前 j 个候选全部通过。

E[A] = Σⱼ₌₁ᵞ P(A ≥ j)
E[输出数] = 1 + Σⱼ₌₁ᵞ P(A ≥ j)

若每步给定前缀的条件接受率都相同为 a，前 j 格全通过的概率为 aʲ。

E[输出数] = 1 + a + a² + … + aᵞ

一般情况下应按条件概率计算前缀存活率，不能直接相乘不同样本的边际平均值。这里忽略 EOS 与输出上限截断。

4 个候选，不等于一轮输出 4 个 token

1+0.8+0.64+0.512+0.4096 = 3.3616 token。后面的候选收益越来越小，却仍消耗草拟与验证资源。

把每轮账本换成用户等一个 token 的时间

教学设定 数值 计算

在真实硬件上扫 γ、batch、上下文长度，并同时看吞吐和 p95 延迟；不要拿低负载最优值直接覆盖高负载。

09 · 为什么要调长度

更长的草稿，不一定更快

前缀越长，活到末尾越难

假设每个位置条件接受率都是 0.8。

a₁ = 0.8
a₂ = 0.64
a₄ = 0.4096

第 4 个 token 只有约 41% 的机会用得上。

验证预算要花在有效位置

GPU 空闲时，多检查几个位置可能很便宜。

很多用户同时生成时，被拒绝的后缀也占用 batch 容量。

让 draft 更准，再按置信度与负载决定送验长度。

0.8 为示意；真实条件接受率会随位置、上下文和任务变化。

练习 2 · 计算与分析

什么时候 3 个候选能带来加速？

条件接受率 a=0.5，γ=3。普通 decode 每 token 8 ms，投机一轮 13 ms。求平均输出、加速比，以及盈亏平衡轮耗时。
展开参考解答

E[N]=1+0.5+0.25+0.125=1.875。投机成本 13/1.875≈6.9333 ms/token；加速比 8/6.9333≈1.154。盈亏平衡轮耗时 8×1.875=15 ms，超过它就更慢。
