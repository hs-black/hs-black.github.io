torch.compile：从 Python 到 GPU kernel

读懂计算图、guards 与重编译，让快起来的原因可解释。

2026-10-20 · → 推进 / ← 回放 / 拖动时间轴

工程原理

三行逐元素计算，为什么值得一起看？

a = torch.sin(x)
b = a + 2.0
y = b.square()

eager 通常分别调度这些算子。a 和 b 若落到全局显存，就各经历一次写入、一次读取。

先修：张量布局、CPU overhead；GPU 上的数据移动和调用开销，往往和公式本身一样重要。

工程原理

先固定讨论的张量与计算

x ∈ ℝᴮˣᴰ；yᵢⱼ = (sin(xᵢⱼ) + 2)²

B 是样本或 token 数，D 是每行宽度。每个输出只依赖一个输入元素，彼此独立；没有归约和跨元素通信。

可以合并

读 x → 在寄存器里完成三个步骤 → 写 y。

保留的语义

形状、dtype、broadcast、别名和可观察的副作用都必须正确。

逐步演算

中间结果留在寄存器，就少跑两趟显存

比较三段 kernel 与一个融合 kernel。每份数组有 N 个 FP32 元素。

上方读写 x、a、b、y；下方只把 x 读进来、把 y 写出去。

只统计理想张量读写字节，忽略 cache、指令和实际访存事务；融合是否发生要看生成代码。

工程原理

N = 2²⁰，省下的字节可以直接算

方案元素读写次数FP32 字节
三个 kernel读 x、写 a、读 a、写 b、读 b、写 y = 6N24N = 24 MiB
一个融合 kernel读 x、写 y = 2N8N = 8 MiB
差值4N16 MiB

理想流量减少 3 倍，不代表速度一定提高 3 倍。sin 的计算、launch 开销与缓存命中都影响时间。

逐步演算

Python 表达式怎样变成设备上的工作

Dynamo 捕获可编译区域；图经过后端变换，再生成或调用可执行 kernel。

每一层表示都保留依赖，但关注的问题不同。

图示是常见 Inductor 路径的简化；后端可能调用库算子，GPU 并非所有操作都变成 Triton。

工程原理

Dynamo 捕获的是一次执行路径

Dynamo 分析 Python 字节码，把遇到的 PyTorch 运算组织为 FX 图；Python 的部分逻辑在追踪时被执行或专门化。

def f(x):
    if x.shape[0] <= 128:
        return x.sin() + 2
    return x.cos() + 2

第一次看到长度 64，可以选择短分支，但必须留下能证明这个选择仍成立的条件。这个条件就是 guard。

工程原理

Guard：复用这个版本之前，要满足的条件

可能被检查的条件为什么会影响复用
shape / stride循环范围与访问地址
dtype / device指令、类型与设备后端
Python 常量、对象状态追踪时可能已经专门化
shape 分支条件保证仍走正确的计算路径

不是每个版本都逐项使用相同 guards；实际条件以日志为准。guard 通过才复用缓存版本。

逐步演算

长度变了：先查 guard，再决定是否编译

输入长度依次为 64、96、128、96、64、192。静态方案按精确长度；符号方案按 ≤128 / >128 两个分支。

一个新输入先尝试已有版本；所有 guards 失败才需要新的版本。

教学缓存模型：静态 4 个版本，符号分支 2 个版本；真实编译器还检查 dtype、stride 等条件。

工程原理

Graph break 与 recompilation，各问一个问题

Graph break

这次追踪在哪里中断？一个 Python 函数可能切成多个编译区域，中间执行 eager Python。

Recompilation

已有版本为什么不能复用？guards 全部不满足时，针对新条件重新追踪和编译。

同样的 graph break 可以每次都发生，却没有新增版本；一个完整图，也可能因输入变化反复重编译。

工程原理

dynamic 的三个选择，解决不同的预期

参数形状处理意图
dynamic=False以静态形状专门化；新形状可能生成新版本
dynamic=None（默认）先静态；观察到形状变化时尝试自动动态化
dynamic=True从开始就尽量使用动态形状，仍可能有专门化与 guards

动态形状通常让循环边界包含符号尺寸，而不是把所有输入 pad 到一个固定大小。

它不保证“永不编译第二次”；dtype、布局、分支边界与部分算子的约束仍可能改变图。

工程原理

动态长度，也可能需要两个分支版本

if x.shape[0] <= 128:
    y = (x.sin() + 2).square()
else:
    y = (x.sin() + 2).square() / 2
短版本 guard：B ≤ 128；长版本 guard：B > 128

B=64、96、128 可以共享同一符号短版本；B=129 改变运算，不能直接套用短版本。

边界 128/129 是有价值的正确性用例；长度 0/1 也常带来额外专门化。

工程原理

输入长度没变，也可能不断重编译

def scale(x, alpha: float):
    return x * alpha
# alpha 依次是 1.0、1.1、1.2……

Python 浮点数可能按值专门化。若 alpha 应当是每步变化的数据，可考虑让它成为适当设备上的标量 tensor。

同样检查 contiguous / transpose 后的 stride、dtype、训练/推理状态。不要只盯着 shape。

tensor 化改变 API 与执行成本；先检查语义、图和实测。形状相关常量也不总适合改成 tensor。

工程原理

数据依赖的 Python 分支，比 shape 分支更难

if x.sum() > 0:
    return x * 2
return x / 2

shape 是张量元信息；sum(x) 是运行时计算结果。把这个值取回 Python 来选路，可能触发同步与 graph break。

可考虑 tensor 运算改写，或满足限制条件时使用 torch.cond 表达控制流。改写必须保持副作用、数值与计算量的预期。

工程原理

fullgraph=True 用来暴露边界

compiled = torch.compile(fn, fullgraph=True)
y = compiled(x)

要求被捕获的函数成为一个完整图；遇到无法捕获的部分会报错。适合先把热路径收窄、发现不支持的 Python 操作。

一个 FX 图可以降低成多个 kernel。fullgraph 约束图捕获的完整性，并不承诺“一图一 kernel”。

把日志、文件 I/O、调度控制留在热 tensor 函数外，通常更容易维持稳定边界。

工程原理

后端决定怎样把图排成 kernel

Inductor 的工作

分解与变换算子、安排计算和存储、融合可合并操作、生成代码或选择库调用。

不能只数源码行

一行矩阵乘法可能调用高性能库；多行 pointwise 可能合成一个 kernel。归约、依赖和布局会限制融合。

GPU 上常见 Triton kernel 与库调用；CPU 路径可生成 C++ 等代码。具体降低结果依版本和算子而定。

工程原理

训练时，还要把反向计算一起考虑

常见训练编译路径会借助 AOTAutograd/AOTDispatcher 追踪和整理前向、反向图，再交给后端编译。

正确性

不仅比输出，还要比 loss、参数梯度、优化器更新和随机数相关行为。

显存

哪些中间结果保存、哪些重新计算，会影响 forward/backward 的时间与峰值内存。

结合 gradient checkpointing；推理的纯前向结果不能代替训练验证。

工程原理

缓存里版本越多，也有维护成本

每次调用要找到 guards 成立的版本。新版本消耗编译时间、代码缓存和可能的设备资源；超过配置限制时还可能回退。

先定位变化源

把日志中的 guard 失败条件映射回输入、Python 标量和布局变化。

再管理版本数

动态维度、稳定热路径、合理分桶、复用长期存在的 compiled callable。

单纯调大重编译上限，可能只把问题推迟。磁盘编译缓存与当前进程的 guard 版本缓存也不是同一层。

工程原理

分桶用额外工作量，换较少的形状

真实长度64961289664192
pad 后长度128128128128128256
真实元素行数：640；分桶后：896；增加 40%

在这个逐元素示例中，算完裁回真实长度即可。静态版本从 4 种长度减成 2 个桶；代价是多处理 256 行。

分桶是应用层选择；dynamic=True 则让编译器处理符号尺寸，两者可以按工作负载搭配。

工程原理

Padding 的值，还必须从语义里消失

逐元素函数可以裁剪输出；mean、softmax、attention 等跨元素操作会让填充值影响真实位置。

[1, 2, 3] 的 mean = 2
pad 成 [1, 2, 3, 0]，mean = 1.5

归约需要有效长度或 mask。attention 还要正确处理 causal mask、位置编号与 KV cache；只裁剪最终输出可能已经太晚。

先对比未 pad 的独立参考，覆盖桶边界、短长度和极端值。

逐步演算

第一次变慢，要靠多少次调用赚回来？

教学成本：一次编译 C=600 ms；eager 每次 8 ms；编译后每次 5 ms。

累计时间随调用次数变化：观察两条线在第 200 次相交。

只有一个可复用版本，忽略额外 guards 成本；这些时间为计算题输入，不是 PyTorch 性能实测。

工程原理

把冷启动放回总成本

Teager(N) = 8N
Tcompiled(N) = 600 + 5N

要严格更快：600 + 5N < 8N ⇒ N > 200。200 次持平，201 次才首次领先。

如果有 K 个新版本且每个都编译 600 ms，总额外成本为 600K；版本出现的频率决定长期收益。

当编译后的每次耗时不低于 eager，重复调用也不能靠摊销消除差距。

工程原理

先用 default，再按瓶颈选择 mode

mode常见目标要记录的代价
default平衡编译成本与执行效率冷启动、稳态、版本数
reduce-overhead在适用条件下减少 Python/launch 开销CUDA Graph 相关条件、显存
max-autotune尝试更多候选实现额外调优时间、部署成本

这些是优化策略，不是性能保证。用自己的 shape、精度与硬件比较结果；mode 可能组合多项后端选项。

工程原理

编译和 CUDA Graph，可以接在一起

torch.compile

分析 tensor 计算，把算子降低为更合适的执行代码，可能减少 kernel 和中间显存流量。

CUDA Graph

重放已捕获的设备工作，减少重复提交。它本身不负责理解并融合任意 Python 表达式。

先降低计算，再捕获可重放区域，是一种组合方式。动态内存地址与形状等条件仍需满足。

继续看 CUDA Graph 与 streams / events 的同步与寿命要求。

工程原理

冷启动、已知输入、新输入，分开测

测量组回答的问题
新进程第一次调用部署或扩容要等待多久？已有磁盘缓存吗？
已见过的输入反复调用稳定执行路径能省多少？
按真实分布送入变化输入新 guards/版本带来多大尾延迟？

GPU 计时要等待工作完成；同时记录输入长度、stride、dtype、版本、编译日志和峰值内存。

调用 torch.compile(fn) 常只创建 wrapper；首次执行输入才触发主要编译工作。

工程原理

先打开能指出原因的日志

TORCH_LOGS="graph_breaks,recompiles,guards" \
  python3 torch_example.py --dynamic auto

TORCH_LOGS="dynamic" \
  python3 torch_example.py --dynamic true

先看失败的是哪个 guard，再追溯到源码和输入。需要更完整的追踪时，用 TORCH_TRACE 记录并用 tlparse 浏览。

日志可能很多；缩小到可重复触发的输入序列，比一次性阅读整台服务日志更有效。

工程原理

长度 64 很快，96 突然卡住：先验证这个假设

教学观测：64 首次 605 ms，之后 5 ms；96 首次也接近 605 ms；回到 64 又是 5 ms。

优先假设

新长度让静态 shape guard 失败，触发新版本；旧版本仍在缓存。

验证与处理

查 recompiles 日志。再比较自动动态化、显式动态和分桶，保留正确性与冷启动统计。

仅凭耗时不能证明重编译；内存分配、调优和数据准备也会造成首次调用尖峰。

工程原理

融合后结果不同，先量化误差

算子融合、计算顺序和浮点舍入可能改变数值。为每种 dtype 选择有意义的绝对与相对误差，而不是只看字符串完全相同。

reference = eager(x)
actual = compiled(x)
torch.testing.assert_close(actual, reference,
                           rtol=1e-5, atol=1e-5)

覆盖动态维度边界、非连续输入、极端值、训练梯度。误差超过任务允许范围时，再缩小到具体算子或后端。

工程原理

真实实验：把同一序列交给三个 dynamic 策略

python3 torch_example.py --dynamic false
python3 torch_example.py --dynamic auto
python3 torch_example.py --dynamic true --device cuda

程序送入 64、96、128、96、64、192、129，逐次与 eager 对齐；输出调用 wall time 和最后已见长度的稳态均值。

练习 1

融合节省多少张量流量？

x 有 2²⁰ 个 FP16 元素。sin、加常量、square 各自独立读写，或融合为一次读入与写出。按理想张量字节计算。
展开参考解答

独立：6N 次元素访问 × 2 B = 12 MiB。融合：2N × 2 B = 4 MiB。节省 8 MiB。

流量比为 3，不足以单独推出加速比；还需考虑 sin 计算、缓存、融合后的资源占用和 launch。

练习 2

编译多出一个版本，要再跑多少次？

两个版本各编译 600 ms。eager 为 8 ms / 次，编译后为 5 ms / 次；忽略其他成本。求总调用次数的严格获益门槛。
展开参考解答

总成本：1200 + 5N < 8N ⇒ N > 400。

400 次持平，401 次严格获益。本题假设每次执行都省 3 ms；若两个版本收益不同，需要按各版本的调用次数分别求和。

练习 3

dynamic=True，为什么 B=129 还会有新版本？

函数在 B≤128 时输出 f(x)，在 B>128 时输出 f(x)/2。已有动态短分支版本，现在输入 B=129。
展开参考解答

长度可以是符号值，但原版本仍须满足 B≤128 的分支 guard。129 改变了应执行的计算。

需要能覆盖长分支的版本或显式控制流表示。测试 B=128 和 129 的数值；不要为减少版本而去掉改变语义的 guard。

练习 4

一个看起来合理的桶，为什么算错了？

把长度 3 的 [1,2,3] pad 到 4，然后直接求 mean。输出为 1.5；未 pad 时应为 2。应在哪里修？
展开参考解答

归约已经把填充位置纳入分母与求和；裁剪最终标量无法恢复正确结果。

使用有效位置 mask：sum(x×mask) / sum(mask) = 6/3 = 2；或把真实长度传入计算。仍需检查空输入与全 mask 情况。

工程原理

把编译日志，接回实际服务的指标

编译版本的冷启动会出现在请求尾延迟里；分桶会影响有效 token 工作量；融合后的 kernel 还要回到 Roofline 与 GEMM 分析。

输入分布 → guards / 版本 → kernel 与字节
→ 单次延迟、尾延迟、峰值显存、启动成本

下一步把这些指标放进推理压测，而不只报告一个 warmed-up 输入的速度。
