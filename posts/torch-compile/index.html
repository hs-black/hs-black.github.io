torch.compile：从 Python 到 GPU kernel

交互2026-10-20更新于 2026-10-22

连续执行 sin(x)、加常数和平方，数学上每个输出元素只依赖同一个输入元素。Eager 模式往往为它们分别启动 kernel，并把中间结果写入显存。torch.compile 从一次 Python 执行中捕获张量计算，生成可以复用的设备程序；融合的收益、捕获边界和复用条件共同决定它是否能加速真实工作负载。

融合先省掉什么

考虑 FP32 表达式 \(y=(\sin x+2)^2\)，输入含 \(\htmlData{symbol=n}{N}\) 个元素。三次独立逐元素计算各读写一遍张量，流量约为 \(3\times8N=24N\) B。融合后，单个线程读取一个 x，在寄存器里计算 sin、加法和平方，然后写出 y，流量降为 \(8N\) B。

当 \(N=2^{20}\)，输入或输出各为 4 MiB，三段路径共搬 24 MiB，融合路径共搬 8 MiB。实际收益还取决于 sin 的计算成本、launch、缓存与编译器生成代码。这个字节账本给出一个可验证的假设：如果输出正确且中间张量写读消失，profiler 应看到更少的 kernel 与流量。

从 Python 路径到图

Dynamo 在 Python 执行过程中捕获可表达的张量运算，并记录使这条路径成立的条件。后端把图降低成 kernel；训练中还会通过 AOTAutograd 处理前反向图，使编译器能够优化梯度计算和中间值保存。torch.compile(fn) 返回可调用包装，真正编译通常发生在首次收到输入时。

一段 Python 代码可能含输入形状分支、普通 Python 对象、日志和设备数据依赖。捕获遇到无法继续纳入图的部分时，可以结束当前图，让这一段回到 Python，再继续捕获。这种 graph break 会让优化边界变小。一个能正常运行的已编译函数，也可能由多个编译区段和 Python 区段组成。

Guard 决定一个版本能否复用

生成的版本附带 guard，例如 shape、dtype、stride、设备和某些 Python 值。新调用满足 guard 时复用该版本，失败时可能建立新版本。Graph break 描述一次调用内部的捕获边界；recompilation 描述后来调用无法复用已有版本的情况。排查时要从相应日志找到是哪一种事件。

在这组输入中，精确长度策略产生 4 个版本。若长度是符号量，但程序仍有 length <= 128 的分支，至少需要覆盖短、长两条路径。默认的动态形状策略会在观察到形状变化后尝试泛化；dynamic=True 更积极使用动态形状；dynamic=False 更偏向静态特化。能否泛化还由算子约束、分支和布局共同决定。

输入长度始终相同也可能重编译：学习率等 Python 浮点数改变，tensor 换了 stride 或 dtype，模块属性发生变化，都可能让 guard 失败。读 recompiles 日志，先找具体失败条件，再决定将数值变成 tensor 输入、固定调用约定，还是保留少量特化版本。

Shape 动态与数据动态

if x.shape[0] > 128 使用输入元数据，编译器可以建立形状条件。if x.sum().item() > 0 则要先计算设备上的数值，再决定 Python 控制流；它可能引入同步和捕获边界。可以把合适的控制流改成 torch.cond，或把动态调度留在编译区外，让区内维持稳定的张量计算。

输出长度依赖数据的算子，例如 nonzero，还会产生无法从输入 shape 直接确定的维度。遇到 GuardOnDataDependentSymNode 一类错误，要沿日志找到该符号的来源，确认程序是在要求一个数据相关大小，还是仅做合法性检查。对应的动态算子支持、检查表达与编译选项需要按所用 PyTorch 版本核对。

分桶把复用条件变成服务策略

把长度 96 补到 128，可以复用 128 桶的 kernel 或 CUDA Graph，同时多执行 32 个位置。设实际长度为 \(l\)，选中的桶容量为 \(b(l)\)，这次调用的填充比例为 \((b(l)-l)/b(l)\)。评估桶集合时应按请求分布统计总填充位置，并将编译次数、持久内存和延迟一起比较。

逐元素运算通常可以计算后裁掉 padding；归约和 attention 需要让 padding 从数学语义中消失。把 [1,2,3] 补为 [1,2,3,0] 后直接求均值，会从 2 变成 1.5。正确归约保留有效元素计数；attention 使用相应 mask；位置和 KV 有效长度也要保持实际序列的语义。

稳定接口让缓存策略可控

为服务的编译入口固定 tensor 的设备、dtype 和布局，可以减少与业务无关的 guard 变化。将每轮改变的数值保留在稳定形状的 tensor 中，适合那些本来就能由设备表达的计算；Python 对象和数据结构则可以在入口前整理。这个边界把“选择怎样执行”的调度与“执行什么张量运算”的计算分开。

尺寸桶也需要按真实语义设计。若函数根据原始长度选择分支，仅把 tensor 补到大桶后再执行，会让分支看到桶长度。应传入实际长度，或者按分支区域分别划桶。Attention 的 padding mask、归约分母和最终输出裁剪也要对应原始长度，才能在复用编译版本的同时保持数值一致。

冷启动怎样摊销

设编译总额外成本为 \(\htmlData{symbol=c}{C}\)，eager 每次耗时为 \(t_e\)，编译后为 \(t_c\)，运行 n 次后要求

$$C+nt_c\lt nt_e\quad\Longleftrightarrow\quad n>\frac{C}{t_e-t_c}.$$

若 C=600 ms、eager=8 ms、compiled=5 ms，200 次恰好持平，第 201 次开始总时间更少。出现新形状、新 guard 版本时，又会支付一笔编译成本。因此服务评估至少分为首次调用、已见输入的稳态调用、未见输入触发的新版本三类。

先用默认 mode 建立正确性和稳定收益，再根据瓶颈评估 reduce-overhead 或 autotune。前者可能利用 CUDA Graph 降低 host 提交开销，后者需要更多预处理来选择 kernel。训练场景还要确认前向、反向、梯度累积和更新步骤都进入预期的测量范围。

把日志变成排查步骤

TORCH_LOGS="graph_breaks,recompiles,guards" python3 torch_example.py --dynamic auto
# 在可复现的小函数上让捕获边界直接报错
compiled = torch.compile(function, fullgraph=True)

若长度 64 很快而第一次 96 卡住，先从 recompiles 日志查 shape guard，第二次 96 再测是否命中。若每次 64 都慢，检查 Python 标量、layout 和版本上限。若没有重编译但总体慢，检查 graph break 是否把本应融合的逐元素链切开，以及 kernel 的资源和访存是否改善。

输出差异应先缩小到一个函数，并固定输入与精度策略。逐个比较 eager 与 compiled 的中间结果，记录最大绝对误差和相对误差，再检查融合后舍入顺序和 reduction 顺序。对依赖随机数或原地更新的程序，还要确认调用间状态相同。一个只比较最后 loss 的测试，很难定位误差开始出现的位置。

定位失败发生在哪个编译阶段

一个小函数在 eager 正确、compile 失败时，可以逐步缩小问题范围：先检查 Dynamo 捕获与 fullgraph 边界，再检查前反向图，最后检查后端生成代码。PyTorch 的 backend="eager" 和 backend="aot_eager" 可用于相应的阶段隔离；这些配置主要帮助定位问题，性能比较仍回到实际使用的后端。

性能回归的最小复现应保留触发问题的 shape 序列、stride、dtype、分支与状态变化。仅截取最后一次调用，可能恰好复用了已热身的版本，从而让重编译尖峰消失。记录各次输入与 guard 日志的对应关系，可以复现“哪个新输入触发了什么工作”。

训练中还需观察第一次 backward 和首次 optimizer step。若只热身 forward，后面的测量可能把反向编译或优化器状态初始化算进稳态时间。按真实训练步骤完成热身，再分别报告首次完整 step 与稳定 step，会更容易解释最终训练吞吐。

练习与实验

1. 融合字节数

FP32 输入有 2²⁰ 个元素，三个各读写一次的逐元素 kernel 融为一个。节省多少张量流量？

展开解答

eager 为 24 MiB，融合为 8 MiB，减少 16 MiB。输入和最终输出各 4 MiB，两个中间结果的写入与重读合计 16 MiB。

2. 多一个版本

每个版本编译花 900 ms，每次稳态调用节省 3 ms。一个新版本至少被调用多少次才有净收益？

展开解答

需要 n>900/3=300，所以至少 301 次。若这个版本只服务 50 次，编译成本远高于累计节省。

3. 动态长度仍有分支

函数对 B≤128 与 B>128 使用不同表达式。B=96 已编译，随后 B=129 为什么可能新增版本？

展开解答

96 版本的路径带有 B≤128 的条件。129 跨过分支边界，需要另一条图或能够表达此控制流的编译表示。符号维度允许大小变化，路径条件仍要满足。

4. Padding 后的归约

[1,2,3] 补到 4 元素后，怎样保持均值为 2？

展开解答

用 mask 对有效元素求和，分母取有效长度 3；因此结果为 (1+2+3)/3=2。对真实长度做分支的程序，还应保留该长度作为单独元数据。

NumPy guard-cache 实验用显式 key 模拟三种缓存策略：

python3 lab.py --lengths 64,96,128,96,64,192 --compile-ms 600

默认静态策略有 4 个版本，符号分支和分桶各 2 个。实验还检查 dtype、stride、Python 标量对 key 的影响，以及 padding 对均值的反例。改变长度序列，预测每次是 hit 还是 compile，再对照输出。

真实 torch.compile 实验可在带 Inductor 工具链的 PyTorch CPU 或 CUDA 环境运行：

TORCH_LOGS="graph_breaks,recompiles,guards" python3 torch_example.py --dynamic auto
python3 torch_example.py --dynamic true --device cuda

它逐个验证长度 64、96、128、192、129 的数值，并分别报告各次调用和已见输入的稳态 wall time。把 --dynamic 改为 false，比较新增版本的位置与总耗时。
